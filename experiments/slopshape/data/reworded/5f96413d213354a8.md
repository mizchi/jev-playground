# Why Forking Still Matters in the Enterprise

Teams that switch from centralized version control to Git usually adopt a familiar setup right away: a single central repository, a stable main branch, and a short-lived feature branch for each piece of work. That workflow is a good one. We rely on it heavily at Atlassian, and it's what we suggest to most teams new to DVCS.

It tends to bring an assumption with it, though, and we'd like to push back on it: the idea that forks belong to open source. On this view, forks exist so strangers on the internet can contribute to projects where they lack commit access, and inside a company, where everyone is on the same team, they only add overhead.

We disagree. Forking is one of the most useful tools an enterprise team has, and it handles problems that branches by themselves can't.

## First, What Is a Fork?

The terms get mixed up, so let's define them carefully.

A **clone** is a local copy of a repository on a developer's machine. Every Git user makes clones; it's how the work gets done.

A **fork** is a copy of a repository on the server. It sits next to the original on the Git server, with its own permissions, its own branches, and its own URL. It stays linked to the repository it was copied from, so changes can travel back upstream through pull requests and upstream changes can be synced into the fork.

The difference is important. A clone is inherently personal and private. A fork is a shared, managed object on the server that others can see, review, and work on, and its permissions are separate from the original's.

Forks are the standard model in open source. On public hosting platforms, nearly all contributions come in as pull requests from forks, since maintainers can't give write access to everyone who wants to fix a typo. Forks let anyone contribute while the project's owners keep control.

Enterprises face that same problem: letting anyone contribute while owners keep control.

## 1. Protect Core Shared Components While Inviting Contributions

Any large organization has code that many teams rely on, such as a shared UI library, an authentication service, a build toolchain, or a common data model. A particular team usually owns each of these components and has to protect it, because one careless change can break dozens of downstream products.

The obvious fix is to lock the repository so only the owning team can push. That turns the owners into a bottleneck. Other teams find bugs and need features, and if filing a ticket and waiting is the only way to get a change made, they'll either wait indefinitely or start copying the code into their own projects.

Forks resolve this neatly. Only the owning team has write access to the canonical repository. Anyone else in the company can fork it, make a change, and open a pull request, which the owners review, discuss, and merge when and how they choose. Anyone can contribute, and the owners stay in control.

That's how we run shared libraries at Atlassian. JIRA, Confluence, Stash, and other products consume our platform components, and product developers routinely send fixes and improvements back to those components through forks. Nobody has to give them broad write access to critical code.

## 2. Coordinate Departments That Maintain Their Own Variants

Some parts of an organization really do need their own version of a shared codebase. A regional division may need localization or regulatory changes. A hardware team may keep a variant tuned to a particular device. A professional services group may maintain customizations for key clients.

Branches handle this badly. Long-lived variant branches clutter the central repository, confuse everyone who doesn't work on them, and make ownership unclear. Who may push to `emea-release`? Whose job is it to keep it current?

A fork spells out the relationship. The department owns its fork entirely, including its permissions and branches. It pulls in upstream improvements when it's ready and sends general-purpose changes back through pull requests. The central team can ignore the variant's internals, and the department no longer depends on the central team's release schedule.

## 3. Keep Central Repositories Free of Branch Noise

Feature branches are great, but they pile up. An active repository with dozens of developers can easily have hundreds of branches: work in progress, abandoned experiments, spikes, half-finished refactors, and branches no one remembers making.

Every one of them sits in the central repository, and everyone has to sift through them. Branch lists become impossible to read. Automated builds run on code that was never meant to be shared. Cleanup turns into a political negotiation.

Forks let experimental and in-progress work stay in the developer's or team's own fork. The central repository holds only the branches everyone cares about, such as `master`, release branches, and features actively moving toward integration. Finished work comes in as a pull request, so the canonical repository stays clean and its history stays meaningful.

## 4. Control Contractor Access

Most enterprises rely on contractors, agencies, and outsourced development partners. These collaborators have to contribute code, but giving them write access to core repositories carries real risk. Even with good intentions, a force-push to the wrong branch can cause serious damage.

Forks draw a clear boundary. Contractors can read the upstream repository and have full control of their own fork. They do their work in the fork, and every change they want to deliver arrives as a pull request that your developers review before merging. The result is a clear audit trail, a required review step, and no chance of outside parties pushing straight to production branches.

Once the engagement is over, you revoke their access to the fork, and there are no stray branches in your central repository to clean up.

## 5. Give Developers Private Personal Forks

The last case is the simplest, and in some respects the most valuable. Developers need somewhere to back up their work, show a half-formed idea to a colleague, or experiment privately.

A local clone falls short: it isn't backed up, and no one else can see it. Pushing a branch to the central repository exposes unfinished work to everyone. A personal fork fits between the two. It's on the server, so it's safe and shareable, but it belongs to you, and you control who sees it and when.

Many Atlassian developers keep personal forks of the repositories they work in most. They push whenever they like, try risky ideas, and ask a teammate to look things over before anything reaches the main repository. That encourages the experimentation we want without creating a mess.

## Forks and Branches Are Complementary

We're not telling you to drop feature branches. The workflow of a central repository with a branch per feature remains an excellent default. Forks work alongside it, adding ownership and permission boundaries that branches were never built to provide.

Branches organize work. Forks organize people, teams, and trust.
