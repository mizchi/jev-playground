# What's New in Git 1.8.4: The Highlights You'll Actually Use

I'll admit it: I read release notes for fun. Whenever a new git version comes out, I'm the person scrolling the changelog over coffee and saying "oh, nice" to my screen. Git 1.8.4 is out, and it has a lot worth getting excited about. Instead of going through the changelog line by line, I'll give you my opinionated tour of the changes that will improve your daily work.

## First, Upgrade!

Getting the new version takes a minute:

- **Homebrew (OS X):** `brew update && brew upgrade git`
- **Ubuntu:** The default repositories usually trail behind, so use the Git maintainers' PPA: `sudo add-apt-repository ppa:git-core/ppa`, then `sudo apt-get update && sudo apt-get install git`
- **Windows:** Download the latest installer from the msysgit project page once the 1.8.4 build is available.

Run `git --version` to confirm, and then we can start.

## Submodules Get a Little Less Painful

Submodules have a bad reputation, and they partly earned it. Still, 1.8.4 fixes some of the annoyances. You can now run `git submodule update` and related commands from a subdirectory of your project instead of first going back to the top level with `cd`. It's a small change that makes daily use noticeably nicer.

Better still, `git mv` now understands submodules. When you move a submodule directory, git updates the `.gitmodules` file and the submodule's internal pointers for you, so you no longer hand-edit config files and hope you got them right. Likewise, `git submodule deinit` cleanly unregisters a submodule, instead of making you delete things in three different places.

## Rebase Grows Up: Autostash and Better Options

This is the part of the release I like most. You try to rebase, and git tells you your working tree is dirty. So you sigh, stash, rebase, and pop. Every. Single. Time.

Now `rebase.autostash` exists. Turn it on with:

```
git config --global rebase.autostash true
```

Git will stash your local changes before the rebase and reapply them afterward. Once you have it, it's hard to imagine working without it.

Rebase also handles options better. Interactive and non-interactive rebases now accept a more consistent set of flags, and `git rebase` makes it easier to pass merge-strategy options. You'll ask "wait, does this flag work here?" less often.

## Status, Log, and Diff Get New Tricks

Several configuration and ordering options arrived for the everyday commands:

- **`status.branch` and `status.short`**: If you always type `git status -sb` (I do), you can now make it the default. Set `status.short` and `status.branch` to `true`, and the compact view is permanent.
- **`log --author-date-order`**: You can now order history by when work was authored instead of when it was committed, and parents still appear before children.
- **`diff.orderfile`** and `-O`: You can set the order in which files appear in diffs, putting the interesting files, like your source, ahead of the noise, like generated files or lockfiles. This helps a lot when reviewing larger changes.

## Color by Default (Finally!)

Here's a welcome one: as of 1.8.4, `color.ui` defaults to `auto`, so your terminal shows colored output with no configuration. If you have been setting this on every new machine for years, you can delete that line from your setup scripts. New users also get a friendlier first impression.

## The Grab Bag

Some smaller additions worth mentioning:

- **`git config --get-urlmatch`** lets you set configuration per URL pattern, which helps when HTTP settings differ between hosts.
- **`git check-mailmap`** shows how a name and email would be mapped through your `.mailmap` file.
- **`@` as a shortcut for `HEAD`**: Type `git log @~3` instead of `git log HEAD~3`. Lazy? Yes. Delightful? Also yes.
- **`git fetch` and `git push`** have better messages and behavior for tag handling and refspecs.
- **`git commit --fixup`** workflows work even better with `rebase --autosquash`.

On that subject: if your team uses fixup and autosquash workflows, an Atlassian Stash add-on helps you spot and manage fixup commits inside your pull requests, so reviewers see what will be squashed before it lands. It works well alongside this release's improved rebase behavior.
