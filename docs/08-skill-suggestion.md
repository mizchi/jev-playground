# 08. skill suggestion cookbook の追試(mizchi/skills で)

[docs.typesafe.ai/cookbooks/skill_suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion) の再現。
cookbook は Nous Research の Hermes(182 スキル)で「そのターンにどのスキルを 1 つ読み込むか」を
Jev に決めさせるが、ここでは [mizchi/skills](https://github.com/mizchi/skills)(68 スキル)で同じことをする。

再現:

```bash
cd experiments/skill-suggestion && npm install
npx tsx src/roster.ts --skills-dir /home/user/mizchi/skills   # roster を作る
npx tsx src/dataset.ts --resume                                # 評価用リクエストを生成
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --limit 90 --concurrency 5
```

---

## 1. 何をするものか

エージェントのスキル一覧は**説明が 60 文字に切り詰めて**渡される。cookbook が測った Hermes では
その結果、関連するリクエストで **16.8%** 誤ったスキルを読み込み、どれも要らないリクエストで
**9.8%** 無駄に読み込んでいた。

対策は、エージェントが決める**前に** Jev を 2 段通す:

| 段 | リクエスト | 内容 |
| --- | --- | --- |
| 1 | 1 回 | 全スキルの `choice`(エージェントと**同じ切り詰め説明**)+ noul 3 問のゲート |
| 2 | 1 回 | 上位 3 件だけ、**full description + `SKILL.md` 先頭 700 文字**で `choice` + 候補ごとの fit noul |

ゲートの 3 問(cookbook の文言そのまま):

1. 「ユーザーのファイル・アカウント・端末・オンラインサービスに**作用する**ことを求められているか(説明や助言だけではなく)」
2. 「慎重な専門家なら、一般的な理解ではなく**特定の手順書やコマンド列**を参照するか」
3. 「知識のあるジェネラリストが、ツールもアクセスも無しに**文章だけで**満たせるか」

3 問目はスキルが**不要**な方向の証拠なので、反転して平均する。平均 < 0.30 なら何も提案しない。
段 2 では候補ごとの fit noul の最大値が < 0.30 なら何も提案しない。

提案はシステムプロンプトの roster 直後に 1 行入る:

```
<skill_relevance>
Relevant to the current request: <name>. Ignore this if it does not fit what the user actually asked for.
</skill_relevance>
```

## 2. 設計で目を引いた点

**段 1 の `choice` に「どれでもない」選択肢が無い。** 必ず 1 つを名指しする。
それを止めているのが**別立ての noul ゲート**で、これは
[00 の closed-world 問題](00-api-notes.md#closed-world)に対して私が
「Fix B: スコープ判定を fan-out で同じリクエストに混ぜる」と書いたものと同じ形。
独立に同じ設計に着いている。

**roster 全体が 1 問に収まる。** 182 も 68 も
[255 選択肢の上限](00-api-notes.md#name-only)の内側。
上限を超える roster では事前フィルタが必要になる。

**段 1 の criteria はエージェントと同じ切り詰め説明を使う。** ここが設計として綺麗なところで、
「Jev には情報を余分に渡しているから当たる」のではない。段 1 は**同じ情報で順位付けだけ**して、
情報を足すのは上位 3 件に絞った段 2 だけ。

## 3. cookbook との条件差

| | cookbook | この追試 |
| --- | --- | --- |
| roster | Hermes 182 | mizchi/skills **68** |
| 評価件数 | 488(315 covered / 173 none) | **90**(68 / 22) |
| 評価セット | 既存 | **生成**(リークの risk) |
| Jev | `jev-1.12` | `jev-latest`(応答 `jev-1.13.0`) |
| エージェント | `claude-haiku-4-5-20251001` | 同じ |
| 切り詰めによる衝突 | 密集(問題の核) | **先頭 30 文字の衝突は 0** |

最後の行が結果の読み方に効く。cookbook の前提は「182 個を 60 文字に切ると似たものが
区別できなくなる」だが、`mizchi/skills` は 68 個で説明の頭が被っていない
(`roster.ts` が数える衝突グループは 0)。つまり**課題としては cookbook より易しい**。
エージェント単独の誤読み込み率が 16.8% より低く出たら、それは Jev の性能ではなく roster の性質。

## 4. 結果

### 4.1 wrong load は再現した。needless load は測れなかった

| アーム | wrong loads | needless loads |
| --- | --- | --- |
| agent 単独 | **13.2%** (9/68) | 0.0% (0/22) |
| + suggestion(cookbook のまま) | **5.9%** (4/68) | 0.0% (0/22) |
| + suggestion(ゲート改良、4.3 節) | **4.4%** (3/68) | 0.0% (0/22) |
| oracle(正解を渡す上限) | 1.5% (1/68) | 0.0% (0/22) |

cookbook は 16.8% → 7.3% で **2.3x**。こちらは 13.2% → 5.9% で **2.2x**。
**wrong load 方向はよく再現した。**

**needless load は全アーム 0% で、この軸は測れていない。** haiku は 22 件の
「どのスキルも要らない」リクエストで一度もスキルを読み込まなかった。
生成した `none` が明白すぎて(「mutex と semaphore の違い」「変数名を変えて」)
ベースラインに伸びしろが無い。cookbook の 9.8% → 4.0% に対応する結果は**無い**。

コストは Jev 154 リクエスト・**$0.0138**・237 ms/リクエスト。
エージェントのターンが 9.7 秒なので、**2 段分 0.5 秒はターンの 5%** 程度。

### 4.2 提案は「決定」ではなく「助言」として効いている

面白いのは、**提案そのものより agent + 提案のほうが正確**なこと:

| | wrong loads |
| --- | --- |
| 提案そのもの(何を提案したか) | 10.3% (7/68) |
| agent が提案を見て決めた結果 | **5.9%** (4/68) |

**agent が悪い提案を捨てている。** cookbook が提案文に
「Ignore this if it does not fit what the user actually asked for」と書いているのは
飾りではなく、ここが効いている。

ただし逆向きの代償もある。agent が外した 9 件のうち提案が救ったのは 5 件で、
残り 4 件のうち **2 件は提案が正解だったのに agent が無視した**
(`formal-methods-reconciler` と `react-expert`)。助言として渡す設計は、
悪い助言を捨てられる代わりに良い助言も捨てられる。

なお**提案が agent の正解を壊した件数は 0**(cookbook は 7 件壊している)。

### 4.3 cookbook のゲートは、このロスターでは純損失だった

ここが一番の発見。ゲートは 3 問の noul の平均だが、**`needs_procedure` 1 問のほうが
両軸で優れている**。ゲートは stage 2 を走らせるかを決めるので、ゲートが止めた件には
stage 2 の答えが残らない。`src/gatecheck.ts` で全 90 件に stage 2 を後追いで埋め、
同じ答えの上でゲートだけを差し替えて測った:

| ゲート | wrong | needless |
| --- | --- | --- |
| cookbook(3 問平均 ≥ 0.30) | 10.3% (7/68) | 13.6% (3/22) |
| **`needs_procedure` 単独 ≥ 0.30** | **7.4%** (5/68) | **0.0%** (0/22) |
| `acts_on_world` 単独 ≥ 0.30 | 39.7% (27/68) | 13.6% (3/22) |
| **ゲート無し**(fits チェックのみ) | **1.5%** (1/68) | 13.6% (3/22) |
| 平均 ≥ 0.15(緩め) | 1.5% (1/68) | 13.6% (3/22) |

covered / uncovered の分離度を見ると理由が分かる:

| ゲートの問い | covered 平均 | uncovered 平均 | 分離 |
| --- | --- | --- | --- |
| `needs_procedure` | 0.67 | 0.23 | **+0.44** |
| `acts_on_world` | 0.43 | 0.18 | +0.25 |
| `generalist_suffices` | 0.31 | 0.62 | -0.31 |
| 3 問の平均 | 0.60 | 0.26 | +0.34 |

**平均が、信号を持っている 1 問を薄めている。** 単独の最良閾値での分離精度も
`procedure` が 81/90 で、平均の 79/90 より良い。

さらに強い結果として、**ゲート無しが wrong 1.5% で最良**、needless は cookbook ゲートと同じ。
つまり **stage 2 の fits チェックだけで uncovered 22 件中 19 件を既に弾いていて**、
ゲートが上乗せしている遮断は無いのに、covered を 6 件落としている。

### 4.4 なぜ外したか — ゲートは「スキル = 手順書」を前提にしている

ゲートが誤って止めた covered 6 件:

```
mean=0.16 acts=0.07 gen=0.80  「subagent を supervisor 付きで並列に動かすべき?」
mean=0.27 acts=0.04 gen=0.87  「ECS の blue/green で CodeDeploy か自前か迷ってる」
mean=0.24 acts=0.24 gen=0.65  「zenn 記事のドラフト、自分の文体っぽく読める?」
mean=0.16 acts=0.04 gen=0.87  「checkout service を instrument する前に方針を決めたい」
mean=0.22 acts=0.07 gen=0.55  「Zustand store が膨らんで半分が派生状態」
mean=0.25 acts=0.05 gen=0.67  「Stripe 連携のスキルってもう誰か作ってる?」
```

全部**助言を求めるリクエスト**で、`acts_on_world` が 0.05 前後、
`generalist_suffices` が 0.8 前後になる。ゲートは正しく
「これは行動ではなく助言の依頼だ」と読んでいる。

問題はラベル側で、**`mizchi/skills` には行動の手順書ではないスキルが多い** —
`react-expert` / `frontend-review-state` / `mizchi-blog-style` /
`multi-agent-orchestration` はどれも**意見・観点・レビュー基準**であって、
「ファイルに作用するか」で測るものではない。
`generalist_suffices`(文章だけで満たせるか)も、これらには**素朴に言えば yes** なのに、
著者固有の意見が入っているからスキルが役に立つ。

> **ゲートの 3 問は「スキルとは何か」の定義を埋め込んでいる。**
> Hermes(汎用アシスタントの操作手順)と `mizchi/skills`(専門家の観点)では
> その定義が違うので、**ゲートは移植先ごとに書き直す必要がある。**
> パイプラインの形(2 段・閾値・提案文)はそのまま使えるのに、
> ゲートだけはロスターの性質に依存する。

### 4.5 stage 1 の順位付けは強い

| | |
| --- | --- |
| 正解スキルが 1 位 | 58/68(85%) |
| 正解スキルが上位 3 件に入る | 61/68(90%) |

上位 3 件に入らなければ stage 2 は救えないので、**90% が stage 2 の上限**。
stage 2 はその中でほぼ外さない(ゲートを通った 62 件中 61 件で正解を選んだ)。

つまりこのパイプラインの誤りは、ほぼ全部**ゲートが止めすぎ**に由来していた。

## 5. 正直な限界

- **評価セットがスキル説明から生成されている。** 「説明の言い回しを写さない・スキル名を出さない・
  状況だけ書く」と指示してはいるが(`src/dataset.ts`)、リークは減らせても消せない。
  **絶対値は楽観的**で、意味があるのはアーム間の比較。両アームは同じリクエストを見ている。
- 90 件(cookbook は 488 件)。1 件の増減が 1 ポイント以上動く。
- `none` 側 22 件は「どのスキルも要らないリクエスト」を生成させたもので、
  実際のユーザー分布ではない。
- スキルを「読み込んだ後に成績が上がるか」は測っていない。cookbook と同じく、
  **読み込み判断の正しさ**だけを測っている。
- 4.3 のゲート比較は**同じ 90 件の上で閾値を動かしている**ので、選んだ変種は
  この 90 件に対して有利に出ている。`needs_procedure` が他のロスターでも勝つ保証はない
  ([04](04-agent-built-prompts.md#2-原因は設計ではなく閾値だった)の閾値フィットと同じ罠)。

## 6. この追試で確定したこと

1. **wrong load の 2.2x 削減は再現した**(13.2% → 5.9%)。cookbook の 2.3x とほぼ同じ。
   ゲートを直すと 4.4% まで下がり **3.0x** になる。
2. **提案は「決定」ではなく「助言」として渡すのが効いている**(4.2 節)。
   提案そのもの 10.3% に対し、agent が見て決めた結果は 5.9%。悪い助言は捨てられている。
   代償として良い助言も 2 件捨てられた。
3. **パイプラインの形は移植できるが、ゲートは移植できない**(4.4 節)。
   ゲートの 3 問は「スキルとは行動の手順書である」という定義を埋め込んでいて、
   観点・意見の集合であるロスターでは誤って止める。
4. **stage 1 の choice は全 roster を 1 問で扱えて、85% が 1 位・90% が上位 3 件**(4.5 節)。
   [255 選択肢の上限](00-api-notes.md#name-only)の内側なら事前フィルタは要らない。
5. **「どれでもない」を choice の外(別の noul)に置く設計は正しい**が、
   その noul が何を聞いているかはロスター依存
   ([00 の closed-world 対策](00-api-notes.md#closed-world)の実例)。

## 7. 次に試すこと

- **needless load 側をまともに測る。** 生成した `none` が易しすぎた。
  スキルの隣接領域を狙った紛らわしいリクエスト(「playwright のテストが落ちる」に対し
  `playwright-test` と `playwright-cli` と `frontend-review-ci` のどれでもない場合など)が要る。
- **ゲートをロスターから書く。** `mizchi/skills` なら
  「この依頼は、この作者の個別の意見や基準を参照する価値があるか」のほうが
  「世界に作用するか」より合う。[04](04-agent-built-prompts.md) の分業どおり、
  質問はエージェントに書かせ、閾値はこの 90 件で合わせるのが筋。
- **提案を 1 件ではなく上位 2 件出す。** stage 1 の上位 3 件に 90% 入っているので、
  2 件出せば agent 側の取りこぼし(4.2 節の 2 件)が減るかもしれない。
