# 27. otel の異常検知のトリアージ — 検知はコード、トリアージは Jev

観測データの監視は**検知**と**トリアージ**に割れます。前者は閾値と EWMA が
20 年やっていて判断の余地がない([23 §5](23-task-filter.md#5-グラフはプロンプトではなくコードに置く) の
「規則で解ける部分は判断に混ぜない」)。後者は runbook が苦手な部分 ——
**これは何の問題で、どこにあって、人を起こす価値があるか**。

6 サービスの Web アプリを 16 通りに壊して OTLP 形式のスパンとログを出し、
検知は決定的なコードでやり、トリアージを Jev に投げました。

再現:

```bash
cd experiments/otel-triage && npm install
npm test                       # 16 件、API 不要(ラベルが state に漏れていないかの検査つき)
npm run demo                   # 記録から下の表を全部出す、API 不要
npx tsx src/run.ts --arm aggregate --repeat 3   # 聞き直す(16 窓 x 3 回で $0.004)
```

state の作り方が 7 通りあり、**質問は全部同じ**なので、動くのは「何を見せたか」だけです。

---

## 結論(先に)

**1. severity は規則が勝つ。それも完勝。**
「人を起こすか」は測れる量(ユーザー向けリクエストのうち 5xx か SLO 超過の割合)の算術なので、
1 行の規則が **16/16・誤ページ 0・見逃し 0**。Jev は同じ窓で誤ページ 6〜27 件。
**順序のある答えが測れる量の関数なら、聞くのではなく計算する。**

**2. cause は判断が勝つ。ただし「ログの文面が原因を名乗っていないとき」だけ。**

| | ログ本文あり | ログ本文なし |
| --- | --- | --- |
| runbook(正規表現) | 8/10 | **4/10** |
| Jev(集計だけ) | 24/30 | **21/30** |

runbook は**文面そのもの**なので半分になり、Jev は 80% → 70% で済む。
**規則が落ちるところで劣化が緩やかなのが、判断層の存在理由。**

**3. state は「大きさ」ではなく「選び方」で効く。**
同じ件数の生ログを**うるさい順に選ぶと誤ページ 27 件、均等に選ぶと 6 件**。
4.5 倍の差が、見せる行の選び方だけで出ます。**サンプリング規則は質問の一部。**

**4. 「とりあえずログを全部送る」は選択肢に無い。**
16 窓すべてが state の上限に当たり、`log_flood` は **15,093 件を捨てて** 107 件だけ送られました。
そして JSON の実効レートは **1 トークン ≒ 2.4 文字**(散文の 4 ではない)。

**5. 逃げ道の noul は用意しても使われない。**
[17 §3](17-task-picker.md#3-逃げ道は選択肢ではなく別の問いにする) のとおり
「該当なし」は別の問いにしてあるのに、健全な 18 窓で発火は **0〜4 件**。
**「何も問題ない」と言わせるのは難しい。** そこは算術の仕事です。

全部で **304 判定・1.64M トークン・$0.069**、1 窓あたり中央値 **208 ms**。

## 1. 何を壊したか、ラベルはどこから来るか

`edge → api → {cache, db, thirdparty}` と、ユーザーが待たない `worker`。
1 窓 = 5 分・600 リクエスト(障害が増やすこともある)。

ラベルは 2 種類で、**種類が違うことが重要**です:

| | 出どころ |
| --- | --- |
| `cause` | **構成上**(注入した障害の種類、または none) |
| `severity` | **実測**。ユーザー向けリクエストのうち 5xx か 1s SLO 超過の割合から決める |

[23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した) の教訓
(規則で書いたラベルは規則を測る)への対処で、**シナリオ名から severity を決めていません**。
だから「怖く見えるが健全な窓」は noise になり、「静かだが本物の障害」も noise になります。

| scenario | 5xx | SLO 超過 | 実測 impact | severity | cause(注入) |
| --- | --- | --- | --- | --- | --- |
| `db_slow` | 26.2% | 22.7% | 43.5% | page | dependency_latency |
| `bad_deploy` | 20.7% | 0.0% | 20.7% | page | bad_release |
| `expired_cert` | 33.3% | 0.0% | 33.3% | page | upstream_outage |
| `retry_storm` | 9.6% | 1.1% | 10.6% | page | retry_amplification |
| `cache_stampede` | 4.7% | 6.3% | 10.5% | page | saturation |
| `cpu_throttle` | **0.2%** | **74.3%** | 74.5% | page | saturation |
| `pool_exhausted` | 4.7% | 0.3% | 4.8% | ticket | saturation |
| `thirdparty_outage` | 0.2% | 0.0% | **0.2%** | **noise** | upstream_outage |
| `auth_misconfig` | 0.3% | 0.0% | 0.3% | **noise** | config_error |
| `worker_disk_full` | 0.2% | 0.0% | 0.2% | noise | capacity |
| `traffic_spike` / `log_flood` / `batch_window` / `canary_1pct` / `cache_cold` / `quiet` | 0.2〜0.3% | 0.0% | 0.2〜0.3% | noise | **none** |

2 行は二度読む価値があります:

- **`thirdparty_outage` は本物の障害で impact 0.2%。** 決済プロバイダが 100% 落ちていて
  エラーログも出ているが、機能が劣化してバナーを出すだけなのでユーザーはほぼ無傷。
- **`auth_misconfig` は 33% のログインが 401 で落ちる。** 5xx とレイテンシで定義した SLO は
  **4xx を数えない**ので、実測ラベルは noise です。**人間は noise と言わないでしょう。**
  ラベルは「測ったもの」でしかない、という限界がここに出ています(§7)。

健全な 6 窓は全部「ダッシュボード上は何か起きている」形にしてあります ——
`log_flood` はログが 50 倍、`traffic_spike` は流量 3 倍、`canary_1pct` は 1% エラー。
[21](21-eslint-plugin-jev.md) が `nearmiss` と呼び、[26](26-repo-rules.md) が
「これがコーパスに無いと健全なコードで発火する」と測ったクラスです。

## 2. 検知(コード)は 10/10 当てて、健全な窓の 5/6 でも鳴る

EWMA 的なベースライン(`quiet` 窓)に対して、エラー率・p95・ERROR ログ数・流量を
それぞれ倍率で見る、ごく普通のアラート設定です。

```
fires on 10/10 of the injected faults and on 5/6 of the healthy windows.
```

**これがトリアージが要る理由です。** 数字は本当に異常で、規則は正しく鳴っている。
`quiet` 以外の健全な窓は全部何かを鳴らします(`log_flood` は worker のエラー率、
`traffic_spike` は流量 3 倍、`cache_cold` は db の流量 3.6 倍)。

## 3. severity — 算術が完勝する

```
error ratio only            severity 15/16  false pages 0  missed pages 1 (cpu_throttle)  cause 8/10
error ratio + SLO breaches  severity 16/16  false pages 0  missed pages 0                 cause 8/10
```

1 行目の唯一の見逃しが **`cpu_throttle`** —— エラーは 0.2% で、74% のリクエストが 1 秒を超える
「遅いだけの障害」。**規則の直し方は算術です**(SLO 超過率も見る)。それで 16/16。

Jev 側は同じ 16 窓で:

| arm | severity 一致 | 誤ページ | 見逃し | cause | root svc | 「何も問題ない」 | tokens | ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `aggregate` | 19/48 | 9 | **0** | **24/30** | 20/30 | 3/18 | 2026 | 182 |
| `noalert` | 19/48 | 6 | 0 | 20/30 | 18/30 | 0/18 | 1944 | 189 |
| `nostrings` | **24/48** | 6 | 0 | 21/30 | **22/30** | **4/18** | 1937 | 176 |
| `sample`(うるさい順) | 18/48 | **27** | 0 | 21/30 | 18/30 | 0/18 | 6615 | 198 |
| `uniform`(均等) | **24/48** | 6 | 0 | 21/30 | 18/30 | 3/18 | 6567 | 173 |
| `both` | 18/48 | 16 | 0 | 18/30 | 18/30 | 0/18 | 7441 | 242 |
| `raw`(上限まで) | 7/16 | 2 | 0 | 8/10 | 6/10 | 1/6 | 23044 | 473 |

- **見逃しは全 arm で 0。** Jev は一貫して過剰にエスカレートする側に外します。
- **誤ページは arm で 6〜27 件。** 起こされる側にとってはこれが唯一の数字です。
- severity の「完全一致」は厳しめの指標で、健全な窓に `ticket` を付けたものも
  不一致に数えています(§4 の表で個別に見えます)。運用上の数字は誤ページと見逃しの 2 列。

組み合わせると:

```
aggregate: jev alone                 severity 19/48  false pages  9  missed 0  cause 24/30
aggregate: rules severity + jev cause  severity 45/48  false pages  0  missed 3  cause 24/30
aggregate: conservative (max of both)  severity 19/48  false pages  9  missed 0  cause 24/30
```

**「severity は規則、cause は判断」が素直に一番良い組み合わせ**です
(45/48 は SLO 超過率を使わない規則での数字。使えば 48/48)。
[18](18-permission-hook.md#2-判定そのもの) の「原子信号と総合質問の保守側を採る」は
ここでは**効きません** —— `page` に `user_visible` の同意を要求しても
1 件も変わりませんでした(Jev がページするときは必ず user_visible ≥ 0.5)。

## 4. cause — ログ本文を伏せると規則が半分になる

runbook の cause 判定は**ログ本文への正規表現**です。本文を伏せると:

| | ログ本文あり | ログ本文なし |
| --- | --- | --- |
| runbook | 8/10 | **4/10** |
| Jev(`aggregate` / `nostrings`) | 24/30(80%) | **21/30(70%)** |

この実験のシミュレータはログ本文が診断的すぎます(`connection pool exhausted`・
`CERT_HAS_EXPIRED`・`ENOSPC`)。**だから本文があるときは runbook が Jev と並びます** ——
80% 対 80%。判断層に金を払う理由が出るのは本文が原因を名乗っていないときで、
そこでは **70% 対 40%** になります。

[16](16-eslint-oracle.md#3-どこまで見せるかは正解率を動かさない動くのは過検出) の
「ルール ID だけか説明文か」と同じ形の測り方で、結論も同じ向きです ——
**情報を抜いたときに何が残るかが、その層の正味の貢献**。

そして `nostrings` は severity も root service も**良くなりました**(19→24 / 20→22)。
うるさい文面を消すと判定が穏やかになる —— 次節と同じ現象です。

## 5. 同じ件数の生ログを、うるさい順に選ぶか均等に選ぶか

`sample` と `uniform` は**件数もトークン数もほぼ同じ**(6615 対 6567)で、
違いは 24 行のログと 14 スパンの**選び方だけ**です。

| | 誤ページ | 健全 6 窓での判定 |
| --- | --- | --- |
| `sample`(ERROR 優先) | **27/48** | 6 窓中 5 窓を `page` |
| `uniform`(等間隔) | **6/48** | 全部 `ticket` か `noise` |

**4.5 倍。** ログビューアで重要度フィルタをかけるのと同じことを state でやると、
判定が丸ごとアラーミストになります。

→ **サンプリング規則は配管ではなく質問の一部。**
[21 §6](21-eslint-plugin-jev.md#6-ファイルの文脈は精度を上げない下げる) の
「文脈は精度を上げず judgment を穏やかにする」の逆向きで、
**文脈の中身が偏っていれば judgment は険しくなる**。どちらの誤りを減らしたいかで選ぶ。

そして集計だけの `aggregate`(2026 トークン)が、生ログを足した `both`(7441)より
**cause で強い**(24/30 対 18/30)。[21 §6](21-eslint-plugin-jev.md#6-ファイルの文脈は精度を上げない下げる) の
「文脈を足すと精度は上がらない」がそのまま出ています。

## 6. 「全部送る」の値段 — 16 窓すべてが上限に当たる

`raw` は窓を到着順に、state の上限まで詰める arm です。

```
the raw arm hit the state ceiling on 16 of the 16 windows;
worst case log_flood dropped 15093 records
```

- **16/16 の窓が上限超過。** 5 分・600 リクエストの窓が、1 リクエストに入りません。
- `log_flood` は 15,200 件のうち **107 件だけ**が送られました。
  つまり `raw` が実際に見ているのは**窓の最初の数秒**です。
- 値段は **23,044 トークン・473 ms**(`aggregate` の 11 倍・2.6 倍)で、答えは同じか悪い。
- そして最初の実装は**全窓で 400 `max_tokens_exceeded`** を食いました。
  [00](00-api-notes.md#token-ceilings) の上限はトークンで、文字数から見積もるなら
  **JSON の telemetry は 1 トークン ≒ 2.4 文字**(散文の 4 ではない)。
  半分にして再送する経路([00](00-api-notes.md#token-ceilings) の助言)が実際に必要になりました。

## 7. 原子述語は校正された数字として読める

`user_visible` の noul をラベル(実測 impact > 0.5%)に対して
[25](25-thresholds.md) の部品で読むと:

| arm | 影響のある窓 | ない窓 | AUC | gap | verdict |
| --- | --- | --- | --- | --- | --- |
| `aggregate` | 0.966 | 0.358 | 1.00 | 0.04 | fit |
| `nostrings` | 0.959 | **0.227** | 1.00 | **0.19** | fit |
| `sample` | 0.970 | **0.823** | 1.00 | 0.03 | fit |
| `raw` | 0.939 | 0.259 | 1.00 | **0.32** | wide-gap |

**順序は完璧(AUC 1.00)なのに gap は 0.03〜0.32。**
`sample` の「影響のない窓」が 0.823 まで上がっているのが §5 の効果で、
**うるさい文面を見せると「ユーザーに見えている」と言い出す**。
[25 §3](25-thresholds.md#3-境界ではなく-gap-の真ん中に置く) の
「gap の中央に置く」を使うなら、state の作り方で gap が 10 倍動くことになります。

`deploy_related` は素直に効きました: デプロイのあった窓で 0.49〜0.61、無い窓で 0.05〜0.08。

そして **3 回の draw で「ページするか」の判定が割れた窓は全 arm で 0/16**。
[25 §7](25-thresholds.md#7-同じ-diff-を-10-回投げる23-11-の宿題) の
「揺れは決定に届いていない」がここでも成立します。

## 何が言えるか

- **検知と severity はコード、cause と root は判断。** 測れる量の算術に判断を混ぜると
  負けます(誤ページ 0 対 6〜27)。逆に、ログ本文が原因を名乗っていない場合の分類は
  規則が半分に落ち(8/10 → 4/10)、判断は 70% で残る。
- **state は選び方で決まる。** 同じトークン数・同じ質問で誤ページが 4.5 倍動いた。
  **何をサンプリングするかは質問の設計**です。
- **観測データは 1 リクエストに入らない。** 16/16 の窓が上限に当たり、
  集計のほうが生ログより**安くて強い**。
- **「何も問題ない」は出てこない。** 逃げ道を別の noul にしても健全な窓で 0〜4/18。
  異常検知の文脈では、**沈黙は算術にしか担保できない**。
- **アラート文を state に入れるかは好みではなく設計。** 入れると誤ページが 6 → 9 に増え、
  cause は 20 → 24 に良くなる。[08](08-skill-suggestion.md#42-提案は決定ではなく助言として効いている) の
  「提案は助言として渡す」がそのまま出ていて、**助言は精度を上げ、同時に判定を押し上げる**。

## 正直な限界

- **シミュレータです。** 実際の telemetry は形が汚く、ログ本文はここより診断的でありません。
  本文の診断性は runbook の成績を直接押し上げるので、**§4 の「あり」列は実物より高い**はず。
  逆に「なし」列(4/10 対 21/30)のほうが実物に近い可能性があります。
- **SLO のラベルは 4xx を数えません。** `auth_misconfig`(33% のログインが 401)は
  実測ラベルでは noise で、人間はそう呼ばないでしょう。
  Jev はこの窓を `ticket` と言い、**ラベル上は誤りで運用上は妥当**という位置にいます。
  severity の指標はこの 1 窓ぶん Jev に不利です。
- **16 窓・10 障害。** 24/30 は 30 件であって率ではありません。
  `raw` は 1 draw なので 16 判定しかありません。
- **severity の 3 段完全一致は厳しい指標。** 健全な窓への `ticket` を不一致に数えています。
  運用の数字は誤ページと見逃しで、そちらは全 arm で見逃し 0 です。
- **cause の選択肢は 7 個で、注入した障害はそこに必ずある。**
  実運用では「どれでもない」が普通に起きるので、逃げ道の noul が効かない(§7)のは
  実運用のほうが痛い。

## 次に試すこと

- **窓を時系列にする。** ここは 1 窓 1 判定ですが、実際のトリアージは
  「5 分前と比べて」の連続判断です。[02](https://github.com/mizchi/jev-playground-moba/blob/main/docs/02-moba.md) の tick と同じ形で、
  **同じ state に「前の窓の判定」を足すと何が変わるか**。
- **4xx を含む SLO でラベルを作り直す。** §7 の `auth_misconfig` のねじれは
  ラベルの定義の問題で、定義を変えれば消えます。消したときに
  **severity の成績が Jev 側に動くか**を見る。
- **アラートのグルーピング。** 実運用の痛みは「1 障害が 30 アラートになる」ことで、
  これは choice ではなく**クラスタリング**です。判断で束ねられるのか、
  それとも [23](23-task-filter.md) の閉包のようにコードでやるべきなのか。
- **runbook を書かせる。** 原因が当たったあとの「次の 3 手」は文字列生成なので
  Jev の外ですが、**選択肢として列挙すれば choice** です
  ([17](17-task-picker.md) の形がそのまま効くはず)。
