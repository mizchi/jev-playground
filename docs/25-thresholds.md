# 25. 閾値を当てはめる部品 — ホールドアウト・draw・コスト

[06 の提案 B](06-ideas.md#b-閾値フィットを-lib-の部品にする) が最優先で残っていた理由は
「手でやるのが 2 回目になった」から。[22](22-code-criteria.md) は 8 つの指標に
**清潔な側の最大値 + 0.01** で閾値を引き、[§11.4](22-code-criteria.md#114-当てはめた閾値は予告どおり壊れたそして直せた) で
**その閾値が次の 10 関数で壊れた**。[23](23-task-filter.md) は 1 本の閾値に
**「10 秒以下は無条件」という定数**を足した。[24](24-adhoc-rules.md) は
「読むのは閾値ではなく gap」を出した。

ここでやるのは 1 つだけ。**当てはめを部品にして、当てはめていない標本で採点する。**
新しい質問は投げていません(§7 の 10 draw だけが新規で 150 リクエスト・$0.0179)。
動かしたのは**採点の仕方**です。

再現:

```bash
cd experiments/threshold-fit && npm install
npm test                       # 18 件、API 不要
npm run report                 # 下の表ぜんぶを記録から再計算、API 不要(13.5 s)

# C 節のデータ(唯一の新規計測)
cd ../task-filter
npx tsx real/run.ts --repeat 10 --out scores-draws.json   # 150 リクエスト・$0.0179

# コストで決める filter(docs/23 の cli に生えた口)
npx tsx src/cli.ts --penalty 600
```

部品は [`experiments/shared/thresholds.ts`](../experiments/shared/thresholds.ts)、
判断規則は [`experiments/task-filter/src/cost.ts`](../experiments/task-filter/src/cost.ts)。
`npm run report` の A 節が下の §1〜§4、B 節が §5、C 節が §7 です。

## 結論(先に)

**1. 当てはめた閾値の「誤検出 0」には情報がない。**
[22](22-code-criteria.md) が報告した 24/36(元の 68 関数)は、78 関数では 23/36 で、
清潔な側をホールドアウトして誤検出 0 を要求すると **18/36** に落ちる。
共通閾値の 13/36 に対する**上乗せ 10 件のうち、半分は当てはめの自己申告**だった。

**2. 境界に置くのが間違いで、gap の真ん中に置く。**
同じ検出 23/36 のまま、ホールドアウトの誤検出が **24 件 → 7 件**になる。
清潔な側の縁に置くと、質問が稼いだ余白を全部捨てている。

**3. 閾値を壊すのは draw ではなくコーパス。**
同じ関数をもう一度聞いて越えるのは **3/816**、見たことのない関数は **24/1224** —— 約 5 倍。
モデルの揺れ(sd 0.009)は問題ではない。

**4. 閾値をコストの関数にすると、1 本の閾値に勝てる。**
[23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した) の実測ラベルで
検出 **18/18 を保って削減 73.5% → 81.4%**。同じ規則から Jev の判断だけ抜くと、
18/18 に届く設定では **40.9%** しか削れない。

**5. 同じ diff を 10 回投げても決定は動かない。**
閾値 1.25 をまたぐのは 240 組中 **7 組**で、**そのどれも赤くならないタスク**。
[23 §11](23-task-filter.md#11-次に試すこと) の「信頼区間の下限で切る」は**要らなかった**。

## 0. 部品が最初に返すのは閾値ではない

```ts
advise(samples, { range: 1 })
//=> { verdict: "wide-gap" | "fit" | "overlapping" | "no-signal", separation, noise, reason }
```

[24 §1](24-adhoc-rules.md#1-読むのは閾値ではなく-gap) をコードにしたのがこれです。
4 つの verdict で、**やることが違う**:

| verdict | 意味 | やること |
| --- | --- | --- |
| `no-signal` | 答えが 2 クラスを順序づけていない(AUC < 0.6) | **質問を書き直す**。校正の外 |
| `overlapping` | 清潔な答えがバグの答えより高い(gap < 0) | 健全さと完全さは同時に成立しない。**どちら側に倒すか決める** |
| `wide-gap` | gap が範囲の 20% 以上 | **閾値をいじらない**。gap の中ならどこでも同じ |
| `fit` | 分かれてはいるが狭い | ここだけが本当に「当てはめ」の仕事 |

置き方も名前で選びます(`boundary` / `quantile` / `midgap` / `youden` / `auto`)。
そして**正例が訓練側に無い置き方は当てはめを断る** —— 数を返しません。
22 の 8 指標は自クラスのバグが 1〜4 個しかないので、これが常に起きます。

## 1. 22 の 8 指標を当てはめ直す — 上乗せはどこから来ていたか

まず部品に 8 指標を読ませます(78 関数 × 3 draw、`full` rubric、[22 §11](22-code-criteria.md#11-追記--保留セットを作り直して穴の深さを測った) の記録):

| criterion | own | mean own | mean neg | max neg | draw sd | gap | AUC | verdict |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `api_default` | 12 | 0.20 | 0.10 | 0.25 | 0.006 | **-0.17** | 0.80 | overlapping |
| `unhandled_async` | 3 | 0.22 | 0.06 | 0.54 | 0.004 | **-0.35** | 0.92 | overlapping |
| `boundary` | 3 | 0.83 | 0.23 | 0.54 | 0.015 | 0.28 | 1.00 | wide-gap |
| `swallows_failure` | 3 | 0.80 | 0.12 | 0.38 | 0.012 | 0.41 | 1.00 | wide-gap |
| `name_mismatch` | 6 | 0.39 | 0.16 | 0.47 | 0.016 | **-0.38** | 0.67 | overlapping |
| `lost_update` | 3 | 0.94 | 0.08 | 0.73 | 0.012 | 0.20 | 1.00 | wide-gap |
| `unescaped_composition` | 3 | 0.94 | 0.04 | 0.24 | 0.004 | 0.70 | 1.00 | wide-gap |
| `unit_or_arithmetic` | 3 | 0.93 | 0.05 | 0.24 | 0.006 | 0.69 | 1.00 | wide-gap |

**8 問は 2 種類に割れます。** 5 問は gap 0.20〜0.70 で分離しており、3 問は重なっている。
そして 22 の「13/36 → 24/36」を verdict で割ると:

| | 自クラス | 共通 0.80 | 質問ごとに当てはめ |
| --- | --- | --- | --- |
| wide-gap 5 問 | 15 draw | 13/15 | **15/15** |
| overlapping 3 問 | 21 draw | 0/21 | **8/21** |

- **wide-gap 側の上乗せは校正ではない。** 13/15 → 15/15 の 2 件は
  `swallows_failure` が 0.80 の柵に届いていなかっただけで、
  **gap の中ならどこに置いても同じ答え**になります。
  「質問ごとの閾値が効いた」という 22 の読みは正しいが、**理由は微調整ではなく、
  共通の柵が正例より上にあったこと**です。
- **overlapping 側の 8/21 は、余白ゼロで買っている。** 清潔な答えの最大値の 0.01 上に置くと、
  自クラスの一部が拾えます。ただしその閾値は**見たことのない清潔なコードに対して無防備**です。
  次節がその値段です。

> ついでに部品の検算になりました: 同じ規則を 22 の元の **68 関数**に当てると
> **24/36** で、[22 §4](22-code-criteria.md#4-一番効いたのは指標ではなく指標ごとの閾値) の表と一致します。
> 78 関数では **23/36** —— 追加した 10 関数が閾値を 1 つ、自分のバグの上まで押し上げた。
> §11.4 が言っていた壊れ方が、1 つの数字になっています。

## 2. in-sample の「誤検出 0」は情報がない

関数を 5 分割して、**4/5 で閾値を引き、残りの 1/5 で採点**します(draw は関数ごとに束ねる:
同じ関数の 3 draw が訓練側と採点側に分かれないように)。
正例は `boundary` / `quantile` の当てはめに**一切入らない**(清潔な側だけで引く)ので、
検出の数は両側で同じです。**動くのは誤検出だけ。**

| 置き方 | 検出 | 誤検出(in sample) | 誤検出(held out) |
| --- | --- | --- | --- |
| 共通 0.80([22](22-code-criteria.md) の前) | 13/36 | 0 | **0** |
| 境界 +0.01([22](22-code-criteria.md) の後) | 23/36 | **0** | **24** |
| 境界 +0.05 | 21/36 | 0 | 16 |
| 負例の q90 +0.05 | 25/36 | 66 | 77 |
| 負例の q95 +0.05 | 24/36 | 32 | 43 |
| midgap(gap の中央) | 15/15 | 0 | 0(19 fold が当てはめ拒否) |
| youden(均衡正解率最大) | 27/36 | 27 | 72 |
| **auto +0.20** | **18/36** | **0** | **0** |

誤検出の母数は清潔 + nearmiss の 1224 関数-draw(8 問ぶんの合計)。

- **「当てはめたら誤検出 0 でした」は構造上そうなる。** 閾値を負例の最大値の上に置いたのだから、
  その負例たちは発火しません。**言えているのは何もない。**
- ホールドアウトすると **24 件**。1224 に対して 2.0% で、質問あたり 1〜6 件。
  発生元は overlapping 側に偏っていませんでした —— 一番多いのは
  `unescaped_composition` の **6 件**で、これは gap が **0.70** と最も広い問いです。
  **gap が広いのに、閾値を清潔な側の縁に置いたので余白を全部捨てていた。**
- `youden` は held-out で 72 件。**均衡正解率を最大化する置き方は、
  誤検出の値段が高い場所で使ってはいけない**(22 の指摘の形をそのまま再確認)。

## 3. 境界ではなく gap の真ん中に置く

そこで `auto`: **gap が広い問いは midgap、重なっている問いだけ margin を払う。**
`advise` と `place` を繋いだだけの規則です。

| margin | 境界 +margin:検出 / 誤検出(held out) | auto:検出 / 誤検出(held out) | margin / draw sd |
| --- | --- | --- | --- |
| 0.01 | 23/36 / **24** | 23/36 / **7** | 1.1 |
| 0.02 | 23/36 / 23 | 23/36 / 7 | 2.2 |
| 0.05 | 21/36 / 16 | 21/36 / 5 | 5.5 |
| 0.10 | 19/36 / 12 | 19/36 / 3 | 11.0 |
| 0.15 | 18/36 / 2 | 18/36 / 2 | 16.4 |
| 0.20 | 18/36 / **0** | 18/36 / **0** | 21.9 |
| 0.30 | 9/36 / 0 | 9/36 / 0 | 32.9 |

- **同じ検出で誤検出が 24 → 7。** 置き場所を変えただけで、質問も記録も同じ。
  wide-gap の問いでは正例が gap のずっと上にいるので、**中央に寄せても検出は 1 件も落ちない**。
- **正直な運用点は 2 つだけ。** 誤検出 0 を要求するなら **18/36**(margin 0.20 か auto 0.20)、
  誤検出を 7 件まで許すなら **23/36**。
  22 が報告した 24/36 は**この選択の外**にあった数字です。
- margin の単位は draw sd(0.009)の **1.1 倍から 22 倍**。
  「モデルの揺れのぶん余白を取る」では足りません —— 効いている margin は**揺れの 20 倍**です。
  つまり余白が要る理由は**モデルの不安定さではなく、次に来るコードが違うこと**。

## 4. 何が閾値を壊すのか — draw かコーパスか

同じ規則を 2 通りにずらします。

**(a) draw shift** —— 1 回目の draw で引いて、2〜3 回目で採点。**コードは同じ。**

| 置き方 | 検出 | 誤検出 | 母数 |
| --- | --- | --- | --- |
| 共通 0.80 | 9/24 | 0 | 816 |
| 境界 +0.01 | 16/24 | **3** | 816 |
| 境界 +0.05 | 14/24 | 0 | 816 |
| q90 +0.05 | 17/24 | 46 | 816 |

**(b) corpus shift** —— 22 の元の 68 関数で引いて、§11 が足した 10 関数で採点。

| 置き方 | 誤検出 | 母数 | どこで |
| --- | --- | --- | --- |
| **出荷されている手当てはめ** | **5** | 120 | `api_default` 3・`unescaped_composition` 2 |
| 共通 0.80 | 0 | 120 | |
| 境界 +0.01(再当てはめ) | 3 | 120 | `api_default` 3 |
| q90 +0.05 | 6 | 120 | `api_default` 3・`unescaped_composition` 3 |

- **同じ関数をもう一度聞いて越えるのは 3/816(0.37%)、新しい関数は 24/1224(2.0%)。**
  約 5 倍。閾値の脆さは**モデルの再現性の問題ではない**。
- 1 行目は再当てはめではなく、`judge.mjs` が**実際に出荷している数字**です。
  10 関数で 5 件発火し、うち 2 件が `unescaped_composition` ——
  [22 §11.4](22-code-criteria.md#114-当てはめた閾値は予告どおり壊れたそして直せた) が
  「テンプレートリテラル全部に発火した」と書いた事故そのもので、
  **ホールドアウトを切っていれば当てはめの時点で見えていた**。
- そして共通 0.80 は corpus shift でも誤検出 0。**校正しない選択は鈍いが壊れない。**
  これが「当てはめの上乗せ」の本当の値段です。

## 5. 閾値をコストの関数にする(23 §11 の宿題)

[23 §7](23-task-filter.md#7-安いタスクに同じ閾値を使ってはいけない) の唯一の見逃しは
**4 秒**の `fmt-check` が **1.24 対 1.25** で落ちたものでした。対策は「10 秒以下は無条件」という定数。
宿題は「その床を、実測済みの 2 つの数(タスクの秒数・赤くなる確率)から引く」。

やり方は閾値をやめることです。score を確率に直して、**集合を選ぶ**:

```
最小化   閉包の machine 秒数  +  penalty × P(どこかが赤い かつ 走らせた中に赤が無い)
```

`penalty` = 見逃し 1 件の値段(秒)。ここから**タスクごとの閾値が出てくる**:
`p_i ≥ cost_i / penalty` を score に戻した点です。

### 5.1 1 レシピでは校正できない

| goal | cost | 赤くなった diff | 赤のとき平均 score | 緑のとき | AUC |
| --- | --- | --- | --- | --- | --- |
| `moon-check` | 0.9s | 2/15 | 1.87 | 0.49 | 1.00 |
| `test-eslint-plugin` | 2.3s | 1/15 | 1.42 | 0.02 | 1.00 |
| `test-jevdsl` | 4.3s | 2/15 | 1.09 | 0.65 | 0.66 |
| `test-jevlang` | 5.3s | 1/15 | 1.04 | 0.80 | 0.64 |
| `test-lib` | 1.9s | 1/15 | 1.86 | 0.34 | 1.00 |
| `test-task-filter` | 0.5s | 1/15 | 1.89 | 0.35 | 1.00 |

16 ゴールのうち**赤くなったのは 6 つ、最多でも 2 回**。
だから [22 §4](22-code-criteria.md#4-一番効いたのは指標ではなく指標ごとの閾値) が禁じた
**プールした 1 本の校正**しか引けません —— これは選んだのではなく強制されています。
言えるのは AUC 列で、4 つは 1.00、`test-jevdsl` と `test-jevlang` が 0.64〜0.66。

プールしたロジスティック(ridge 1、3 draw の記録):

```
p(赤) = sigmoid(1.80 × score − 4.68)      score 1.00 → 0.053   1.25 → 0.081   2.00 → 0.254
720 判定中 24 件が赤、プール AUC 0.89
```

> 10 draw の記録では **a 2.30 / b −5.41** になります。**係数は記録集合ごとに動く。**
> それでも §5.3 の決定はほとんど動きません(§7)。

### 5.2 その校正が作る「床」

penalty ごとに、各レシピが走るために必要な score:

| goal | cost | penalty 60s | penalty 300s | penalty 1800s |
| --- | --- | --- | --- | --- |
| `test-hooks-policy` | 0.1s | 無条件 | 無条件 | 無条件 |
| `replay-rules` | 0.3s | 無条件 | 無条件 | 無条件 |
| `test-task-filter` | 0.5s | 無条件 | 無条件 | 無条件 |
| `moon-check` | 0.9s | 0.28 | 無条件 | 無条件 |
| `test-lib` | 1.9s | 0.70 | 無条件 | 無条件 |
| `test-eslint-plugin` | 2.3s | 0.81 | 無条件 | 無条件 |
| `conformance` | 3.9s | 1.12 | 0.19 | 無条件 |
| `test-jevdsl` | 4.3s | 1.18 | 0.25 | 無条件 |
| `test-jevlang` | 5.3s | 1.30 | 0.37 | 無条件 |

[23](23-task-filter.md) の「10 秒以下は無料」と同じ発想ですが、**全レシピ 1 個の数ではなく、
レシピ自身のコストが決める数**になっています。列を縦に読むと、
0.1 秒のレシピはどんな疑いでも走らせる価値があり、5.3 秒のレシピは 1.30 を要求される。

### 5.3 実測ラベルでの比較

正解は [23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した) と同じ
**終了コード**(15 の実編集、6 個が何かを壊す)。校正は **leave-one-diff-out** で、
ある diff を判断するモデルはその diff を見ていません。

| 規則 | 検出 | machine | 削減 | no-op な編集で |
| --- | --- | --- | --- | --- |
| 全部走らせる | 18/18 | 40.8s | 0% | 40.8s |
| static(glob + 依存伝播) | 18/18 | 14.8s | 63.8% | 13.6s |
| **glob だけ(無料)** | 18/18 | 8.1s | **80.2%** | 9.9s |
| 1 本の閾値 ≥ 1.0([23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した)) | 18/18 | 13.9s | 65.9% | 11.4s |
| 1 本の閾値 ≥ 1.25 | 18/18 | 10.8s | 73.5% | 9.9s |
| 1 本の閾値 ≥ 1.5 | **15/18** | 9.5s | 76.7% | 9.3s |
| ≥ 1.0 + 1 秒床 | 18/18 | 21.0s | 48.6% | 19.1s |
| 期待損失、penalty 15s | 3/18 | 0.7s | 98.3% | 0.4s |
| 期待損失、penalty 30s | 10/18 | 3.0s | 92.6% | 2.0s |
| **期待損失、penalty 60s** | **18/18** | **7.6s** | **81.4%** | 6.6s |
| 期待損失、penalty 120s | 18/18 | 10.8s | 73.5% | 10.9s |
| 期待損失、penalty 300s | 18/18 | 18.9s | 53.8% | 19.3s |
| 期待損失、penalty 1800s | 18/18 | 36.3s | 10.9% | 33.4s |
| 同じ規則を山登りで解く(60s) | 18/18 | 6.9s | 83.0% | 5.7s |
| **判断を抜いた対照**(p = 0.033 固定)60s | **3/18** | 5.6s | 86.3% | 5.6s |
| 判断を抜いた対照、300s | 18/18 | 24.1s | 40.9% | 24.1s |

- **閾値 1 本より良い。** 検出 18/18 のまま 73.5% → **81.4%**。
  [23 §12.3](23-task-filter.md#123-検出は-1818ただし-glob-だけの静的判定に負ける) が
  「glob だけの無料の判定に負ける」と書いた **80.2%** も、わずかに上回ります。
  ただし**わずかです** —— 判断に金を払う理由がこの 1.2 ポイントなら、払う必要はない。
- **対照が本題。** [07](07-escalation.md) の「ランダム同予算と比べろ」に従って、
  同じ損失モデル・同じグラフ・同じコスト表のまま **score だけ基準率に潰す**と、
  18/18 に届く設定は penalty 300s で削減 **40.9%**。
  **81.4% 対 40.9%** が、同じ検出でのコストです。
- **penalty は崖の上にある。** 30s だと 10/18 に落ちる。
  つまりこの規則は「何を聞くか」の校正を消した代わりに
  **「見逃しの値段」という 1 個のパラメータに引っ越した**だけで、無料ではありません。
  ただし引っ越し先は**コーパスなしで答えられる質問**です(壊れた main を見つけるのに何分かかるか)。
- **モデルを良く解いても結果は良くならなかった。** 山登り(不完全な最適化)は 83.0%、
  総当たり(最適)は 81.4%。**目的関数は真実ではない**ので、
  よく解くほど良くなるとは限りません。数字は最適な側を出荷しています。

## 6. 道具の形 — `--penalty`

[23](23-task-filter.md) の `cli.ts` に口を足しました。`needs` 列が §5.2 の床です。


## 7. 同じ diff を 10 回投げる(23 §11 の宿題)

15 diff × 16 ゴールを 10 draw(150 リクエスト・**$0.0179**)。

```
240 (diff, goal) 組、平均 sd 0.030、最悪 sd 0.134、最大の幅 0.44(0..3 の score)
```

| 閾値 | またぐ組 | うち赤くなるもの |
| --- | --- | --- |
| 0.75 | 26 / 240 | **0** |
| 1.00 | 13 / 240 | 1 |
| 1.25 | **7 / 240** | **0** |
| 1.50 | 4 / 240 | 0 |

- **不安定な組はほぼ全部「走らせなくてよいタスク」。** 閾値 1.25 で 7 組が draw 間で
  side を変えますが、そのどれも**実際には赤くなりません**。
- draw ごとの結果: **10 draw 全部で 6/6 検出**、machine 10.8〜10.9 秒(sd **0.06 秒**)。
- **1 リクエストで足りる。** 10 draw の平均で決めるのと 1 draw で決めるのを比べると、
  選ぶ集合が違うのは **150 決定のうち 16 件**、それでも検出(60/60)も machine 秒数(10.8s)も同じ。
  → [23 §11](23-task-filter.md#11-次に試すこと) の「信頼区間の下限が閾値を越えたら skip」は
  **作らなくてよい**。揺れは決定に届いていない。
- §5.3 の規則を 10 draw で回すと、1 本の閾値 1.25 が 60/60・73.5%、
  期待損失 60s が **60/60・84.5%**。3 draw での 81.4% と同じ場所です。

そして draw sd は 2 つの形で揃っています: **22 の noul(0..1)で 0.009、
23 の score(0..3)で 0.030** —— どちらも**答えの範囲の約 1%**。

集合選択を総当たりに書き直したとき、**タスク添字の配列をゴール添字で読んで**いました。

## 何が言えるか

- **当てはめた閾値は、当てはめていない標本で採点しないと数字として意味がない。**
  78 関数での 23/36 は、誤検出 0 を要求すると 18/36。
  それでも共通閾値の 13/36 には勝っています —— **質問ごとの閾値は正しい、上乗せが半分だった。**
- **置き場所には名前が要る。** 「清潔な側の最大値 +0.01」は最も自然に見えて最も脆い。
  gap があるなら**中央**、無いなら**どちら側に倒すか決める**。
- **壊すのは新しいコード。** draw を増やしても閾値は守られない(0.37% 対 2.0%)。
  margin は draw sd の 20 倍要る。
- **閾値が要らない問題もある。** コストが測れているなら、
  「どこで切るか」より「見逃しの値段」のほうが答えやすい質問で、
  タスクごとの床はそこから計算で出ます。
- **そして判断を抜いた対照を必ず引く。** 81.4% は、同じ損失モデルで
  判断だけ基準率にした 40.9% と比べて初めて意味を持ちます。

## 正直な限界

- **自クラスの正例が 1〜4 個。** `midgap` と `youden` は「正例が訓練側に無い」fold を
  当てはめ拒否するので、**検出側はホールドアウトできていません**(誤検出側だけ)。
  22 のコーパスでは原理的にここまでです。
- **18/18 は 6 個の壊れる編集 × 3 draw。** 6 件であって率ではありません。
  [23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した) の限界をそのまま引き継いでいます。
- **penalty は崖の直上を選んでいます。** 60s は 18/18 を保つ最小値で、
  2 倍にすると 73.5%(1 本の閾値と同じ)。**この選択は diff ごとにホールドアウトしていません。**
- **校正はプール 1 本。** 22 §4 が禁じた形で、レシピごとの失敗数が足りないため強制。
  AUC 0.64 の 2 レシピはこの 1 本に乗せられている疑いがあります。
- **glob だけの静的判定との差は 1.2 ポイント。** [23 §12.3](23-task-filter.md#123-検出は-1818ただし-glob-だけの静的判定に負ける) の
  「入れる前にグラフの形を見る」は変わりません。扇形の無いリポジトリでは、
  この節の勝ちは**勝ちと呼べるほどの幅ではない**。
- **部品は TypeScript だけ。** [06 の B](06-ideas.md#b-閾値フィットを-lib-の部品にする) は
  MoonBit の `lib` に置く提案でしたが、ラベル付きの記録が TS 側にしかありません。
  同じ理由で、提案の元の署名(順序つき n クラスの切れ目)は**実装していません** ——
  [01](01-shell-risk.md) の 24 コマンドは記録が残っていないので測れない。
- **新しい 2 レシピは `real/graph.json` のスナップショットに入れていません。**
  [23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した) と
  同じ 20 レシピ・16 ゴールで比べるためで、グラフを作り直すと上の表と比較できなくなります。
