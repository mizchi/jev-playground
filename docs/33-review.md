# 33. 機械的な指標を渡すと、レビューは良くなるのか

TODO の 7 番は「高速なコードレビューツールとして、機械的な指標を与えて、
安全性を確認する([similarity](https://github.com/mizchi/similarity))」でした。
このリポジトリの言い方に直すと、
[27 §3](27-otel-triage.md#3-severity--算術が完勝する) と
[23 §5](23-task-filter.md#5-グラフはプロンプトではなくコードに置く) の問いです ——
**レビューのどこが算術で、どこが判断か。**

題材は [32](32-repair.md) の裏返しです。
32 は「この編集はテストを通すか」を聞きました。
レビューが聞くのは逆で、**「この編集はテストを通したままにするか」**。
なので機構をそのまま再利用します:

1. 32 の各題材に**記録された fix を当てて緑にする**
2. その緑のファイルに対して 1 行の候補編集を全部生成する
3. **テストを走らせる** —— 緑のままなら `safe`、落ちたら違う

**261 個の diff、うち 46 個が安全(18%)。ラベルは全部 `node --test` の終了コード**で、
手で書いたものは 1 つもありません。

再現:

```bash
cd experiments/review && npm install
npm test                       # 14 件(node --test を数回走らせる)
npm run demo                   # 記録から全部の表、API 不要
npm run truth                  # 261 diff + カバレッジ + similarity を再測定(約 45 秒)
npx tsx src/dupes.ts           # similarity-ts をこのリポジトリに当てる(cargo install similarity-ts)
npx tsx src/run.ts --arm blind,diff,metrics,onlymetrics --repeat 2   # 128 リクエスト、$0.047
```

## 結論(先に)

**1. 指標を渡しても良くなりません。** ソースとテストを見せた版が 90%・AUC 0.941 で、
そこに機械的な指標を足すと **90%・AUC 0.921** ——
**同じか、わずかに悪い。トークンは 69% 増えます**(6,548 → 11,094)。

**2. なぜかは §1 が先に言っていました。** どの数値指標も
**AUC が 0.5 の上に座っています**(カバレッジ 0.477、テスト名との重なり 0.459、
ネスト 0.536、関数長 0.531、分岐カバレッジ 0.467)。
**ラベルを分けない指標は、プロンプトに入れても分けません。**
[27 §3](27-otel-triage.md#3-severity--算術が完勝する) で算術が完勝したのは
指標が答えそのものだったからで、ここは違います。

**3. 指標は読まれています。** これは重要な対照です ——
指標だけを渡した arm は「テストはこの行を通るか」という質問に
**261/261(100%)**で答えます(他の arm は 94〜97%)。
つまり §1 の「効かない」は**渡された中身の話**で、
見落とされているという話ではありません。

**4. 効いたのはソースとテストで、+5 ポイント。**
diff だけ(85%・AUC 0.862)→ ソースとテストも(90%・AUC 0.941)。
**トークンは 5% 増えるだけ**です。

**5. 唯一効く「指標」は数値ではなく diff の分類でした。**
`what the edit did`(どの規則が作った編集か)は、
タスク単位でホールドアウトして **84%・AUC 0.778**。
`strict-to-loose` は 89% 安全、`negate-return` は 1% 安全 ——
**測定ではなく名前**です。

**6. similarity-ts はこのコーパスでは何も言いません。** 21 題材すべてで 0 ペア。
関数が 2〜6 行で、既定の最小が 3 行だからです(1 行まで下げても変わらない)。
代わりに**このリポジトリの `experiments/` に当てたら 37 ペア**出ました。
そして **100% と報告された 3 ペアのどれも、機械的には「同じコード」ではありません**(§5)。

## 1. まず、指標だけで分かるのか

判断を抜いた対照です。[25](25-thresholds.md) の部品で、
タスク単位のホールドアウト。

```
feature       safe mean   unsafe mean  gap     AUC
lineHits      1.70 ±1.30  1.81 ±1.40   -7.00   0.477
testOverlap   0.50 ±0.69  0.59 ±0.66   -2.00   0.459
depth         1.02 ±0.33  0.94 ±0.41   -2.00   0.536
fnLines       4.35 ±2.09  4.19 ±1.95   -7.00   0.531
branchCov     0.91 ±0.08  0.92 ±0.08   -0.22   0.467
```

**全部 0.5 です。** 一番強いはずだったのはカバレッジ ——
テストが通らない行への編集はテストを壊せない —— ですが、
**261 件のうち未到達の行に触るのは 1 件だけ**なので、分けるものがありません。
モジュールが小さくテストが丁寧だと、カバレッジは飽和します。

効くものが 1 つありました。**数値ではありません**:

```
The rule class, as a classifier: predict safe when the training folds' rate exceeds 0.5.
rule class, held out by task: tp 16 fp 13 fn 30 tn 202, right 84%, P 55% R 35%, AUC 0.778
```

`what the edit did` —— どの変異規則が作った diff か —— の安全率:

```
strict-to-loose        9    diffs, 89% safe
tighten-bound          9    diffs, 67% safe
add-minus-one          24   diffs, 33% safe
loosen-bound           25   diffs, 28% safe
swap-args              35   diffs,  9% safe
loose-to-strict        15   diffs,  7% safe
negate-return          69   diffs,  1% safe
negate-if              14   diffs,  0% safe
```

→ **渡す価値のある「指標」は、コードの測定値ではなく diff についた名前でした。**

## 2. 4 通りのレビュー

```
arm          question right           said safe  said broken  AUC    tok/task  ms
blind        safe   223/261   85%   12         26           0.862  6232      240
             risk   221/261   85%   18         22           0.827
diff         safe   235/261   90%   14         12           0.941  6548      241
             risk   231/261   89%   19         11           0.901
metrics      safe   235/261   90%   15         11           0.921  11094     242
             risk   223/261   85%   28         10           0.884
onlymetrics  safe   222/261   85%   16         23           0.865  10778     237
             risk   215/261   82%   27         19           0.842
```

| arm | 何を見せたか |
| --- | --- |
| `blind` | diff だけ。「高速レビュー」の極端 |
| `diff` | diff + 変更対象のファイル + 横のテスト |
| `metrics` | それに加えて機械的な指標のブロック |
| `onlymetrics` | diff + 指標。**ファイルとテストを外した** |

**261 件のうち 46 件が安全なので、全部「壊れる」と答えると 82%。**
超えるべきはそこで、50% ではありません。

読めること:

- **ソースとテストは +5 ポイント**(85% → 90%)、AUC +0.08、**トークンは +5%**。
- **指標は 0 ポイント**(90% → 90%)、AUC は **−0.02**、**トークンは +69%**。
  `risk` の側では 89% → 85% と**下がります**。
- **指標だけ(コードなし)は diff だけと同じ**(85%/0.865 対 85%/0.862)で、
  トークンは 73% 多い。
- `onlymetrics` の偽陽性(安全と言った誤り)は 16 件で、
  `diff` の 14 件より多い ——
  **指標を渡すと「安全」寄りに振れます**。
  [31 §2](31-orchestration.md#2-聞くか組み立てるか) の
  「質問の枠組みが保守性のダイヤル」と同じ方向で、
  ここでは**渡した情報**がダイヤルになっています。

## 3. 指標は読まれているのか

これが無いと §2 は「指標が見落とされた」とも読めてしまいます。
`reached`(テストはこの行を通るか)は**指標ブロックが答えを持っている**質問です。

```
arm          right            dead lines found  AUC
blind        253/261    97%   0/1               0.881
diff         246/261    94%   0/1               0.946
metrics      247/261    95%   1/1               0.946
onlymetrics  261/261    100%  1/1               1.000
```

**`onlymetrics` は 261/261。** 渡された数字を読んでそのまま答えています。
→ **§2 の「効かない」は中身の話で、注意の話ではありません。**

そして `blind`(diff だけ、コードもテストも指標も無し)が 97% ——
**1 行の diff を見れば「テストが通る行か」はだいたい分かる**ということです。
未到達の行が 1 件しか無いので、この 97% は
「ほぼ全部 yes と答えれば当たる」でもあります(そこが `dead lines found 0/1`)。

## 4. どこで間違えるか

```
what the edit did      diffs  wrong        of which called safe
loose-to-strict        15     5      33%   5
add-minus-one          24     5      21%   1
add-return             5      5      100%  5
negate-return          69     2      3%    1
swap-args              35     2      6%    0
swap-operands          9      2      22%   0
add-await              6      2      33%   2
```

**`add-return` は 5/5 間違えて、5 件すべて「安全」と答えています。**
緑のファイルにある式文に `return` を足すと関数がそこで戻るので壊れますが、
diff としては「値を返すようにした」だけに見える ——
**diff が小さく見えることと安全であることは別**という、
レビューの一番古い罠にそのまま掛かっています。

`loose-to-strict`(`==` → `===`)も 5/15 間違えて全部「安全」側。
これは**普通は安全な編集**で、緑のファイルでは
`==` が意図的に効いている場所を壊します。

逆に `negate-return`(69 件、実際に安全なのは 1%)は 2 件しか間違えません ——
**明らかに壊す編集は明らかに壊す**と言えています。

カバレッジ別に割ると:

```
on the 1 diffs to a line the tests never run: 0/1 (0%)
on the 260 diffs to a covered line:            235/260 (90%)
```

唯一の未到達行の diff を**間違えています**。1 件なので何も言えませんが、
§1 が「カバレッジは分けない」と言った corpus では
ここに証拠が積めないということでもあります。

## 5. 名前のついた道具を、実物のコードに当てる

`similarity-ts` は **21 題材すべてで 0 ペア**でした。
`--min-lines 1 --min-tokens 3` まで下げても 0 です ——
2〜6 行の関数で本体が違えば、AST 的な近似重複ではない。
**指標が null だというのは corpus についての事実**で、道具の欠陥ではありません。

なので道具が何か言える場所に向けました ——
**このリポジトリの `experiments/` 以下 179 ファイル**、私が書いたコードです。

```
similarity  same code?  where
100%        different   orchestration/src/run.ts:473-512  ~  repair/src/run.ts:413-473
100%        different   eslint-oracle/src/metrics.ts:30-61  ~  eslint-plugin-jev/experiment/metrics.mjs:11-43
100%        different   eslint-oracle/src/metrics.ts:64-76  ~  eslint-plugin-jev/experiment/metrics.mjs:54-66
97%         different   eslint-oracle/src/metrics.ts:64-76  ~  shared/thresholds.ts:59-66
91%         different   skill-pick/src/run.ts:247-256  ~  skill-pick/src/run.ts:519-530
...
37 pairs; 0 identical, 0 the same up to renaming, and 3 reported at 100%.
```

`same code?` の列は**機械的な第二の検査**です ——
コメントと空白を落とし、型注釈を落とし、
**識別子を出現順の番号に置き換えて**比較する(プロパティ名は置き換えない)。

そして **37 ペアのどれも「同じコード」ではありません。100% の 3 ペアも含めて。**
→ **「100% similar」は構造についての言明**で、
コードが同じかどうかは別の、そしてこれも機械的に答えられる質問です。
指標を渡すレビューが**読み違えてはいけない一箇所**がここです。

読んだ結果、3 つの 100% ペアのうち 1 つは**本物の重複**でした:

```js
// experiments/eslint-oracle/src/metrics.ts
export function auc(pairs: Pair[]): number {
  const pos = pairs.filter((x) => x.truth).map((x) => x.p);      // <- .p
  ...
// experiments/eslint-plugin-jev/experiment/metrics.mjs
export function auc(pairs) {
  const pos = pairs.filter((x) => x.truth).map((x) => x.value);  // <- .value
```

同じ関数が **3 か所**にあります(`shared/thresholds.ts` にも)。
機械的な検査が「同じ」と言わなかったのは
**プロパティ名が違うから**で、それは正しい ——
`.p` と `.value` は違うコードです。**人が読めば同じもの**ですが。

**直していません。理由は構造的です** ——
`eslint-plugin-jev/experiment/*.mjs` は
`node experiment/rules-report.mjs` で**素の node から**走ります
([26](26-repo-rules.md) の replay がそうなっている)。
`shared/thresholds.ts` は TypeScript なので、
素の node からは import できません。
つまりこの重複は**リポジトリの半分が `tsx` で半分が `node` で走ることの帰結**で、
`auc` を 1 か所にするには replay の走らせ方を変えることになります。
**道具は本物を見つけ、機械的な検査は「同じとは言えない」と言い、
読むと「同じだが動かせない」だった** —— それが算術と判断の境目です。

## 何が言えるか

1. **指標を渡す前に、指標だけで分かるかを測る。** §1 の AUC が §2 を
   先に言っていました —— ラベルを分けない指標はプロンプトでも分けず、
   トークンだけ増えます(+69%、AUC −0.02)。
   [27 §3](27-otel-triage.md#3-severity--算術が完勝する) で算術が完勝したのは
   指標が答えだったからで、**「機械的だから渡すと良い」ではありません**。
2. **効く「指標」は測定値ではなく名前だった。** diff の分類
   (`negate-return` か `strict-to-loose` か)が 84%・AUC 0.778 で、
   数値指標は全部 0.5(§1)。
3. **ソースとテストは安い。** +5 ポイントでトークン +5%(§2)。
   **指標は高い。** 0 ポイントでトークン +69%。
4. **渡した情報は保守性のダイヤルでもある。** 指標を足すと
   「安全」と言う誤りが 14 → 16 件に増えます(§2)。
5. **「読まれているか」は別に測る。** 指標ブロックが答えを持つ質問で
   261/261 が出たので、§2 の結論は中身の話だと言えます(§3)。
   この対照が無い実験は「見落とし」と「無意味」を区別できません。
6. **類似度は構造の話。** 100% でも同じコードとは限らず、
   その区別も機械的に付けられます(§5)。

## 正直な限界

- **「安全」の定義が狭い。** ここでは**テストが通ったまま**という意味だけです。
  リファクタリングの良さ、可読性、API の互換性、性能 ——
  レビューが見る他の全部を測っていません。
  ラベルが終了コードであることの代償です。
- **corpus はカバレッジが飽和しています。** 261 件のうち未到達の行に触るのは
  **1 件**。カバレッジという指標を測るには向かない corpus で、
  §1 の「AUC 0.477」は「カバレッジは役に立たない」ではなく
  **「ここでは分けるものがない」**です。
  未到達コードのある題材を足せば別の答えになり得ます。
- **diff は全部 1 行**です。実際のレビューは複数行・複数ファイルで、
  そこでは diff サイズという指標が効き始めるはずですが、
  この corpus では定数なので測れません。
- **指標のブロックは 7 項目**で、私が選びました。
  別の指標(型チェッカの出力、AST の距離、call graph の到達性)なら
  違う答えになり得ます。測ったのは**この 7 つ**です。
- **similarity-ts は 0.5.0**、`--threshold 0.85`。閾値を下げれば
  ペアは増えます(0.4 でも題材側は 0 ですが)。
  37 ペアという数は閾値の関数です。
- **繰り返しは 2 回。** §2 の 5 ポイント差(235 対 223)は 12 件ぶんで、
  [31 §6](31-orchestration.md#6-もう一度聞くと) が測った draw のまたぎ率
  (38 件中 0〜1 件)を 261 件に外挿すると数件 —— **差は draw より大きい**が、
  「90% 対 85%」の 1 ポイント単位は信用しないほうがいい。
- **費用**: 2,088 判断 / 128 リクエスト / 1,108,904 入力トークン / **$0.0466**。
  `node --test` は truth の 261 + カバレッジ 16 + テストの数回。

## 次に試すこと

- **未到達コードのある題材で、カバレッジを測り直す。** §1 の唯一の弱点は
  corpus で、そこは足せます —— 使われていない関数を持つモジュールを作れば
  カバレッジ指標に分けるものが生まれます。
  **指標が効くかどうかは指標ではなく corpus で決まる**という
  §1 の主張自体を試す形になります。
- **複数行・複数ファイルの diff。** diff サイズが定数でなくなれば、
  「大きい diff は危ない」という一番古い機械的指標を測れます。
- **`add-return` と `loose-to-strict` を狙って増やす。** §4 で
  **小さく見えて壊す編集**に全部掛かっているので、
  そのクラスだけを 30 件ずつ作れば「小さく見えることの罠」が測れます。
