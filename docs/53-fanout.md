## 0. コーパスはディスクに在って、著者がラベルを貼っていました

公開パッケージの `scripts` の一部は**合成**です —— 自分の兄弟スクリプトを 2 つ以上呼びます。
そして**著者は、その枝を同時に走らせるか順番に走らせるかを書いています**:

```
concurrently 'yarn:build:types' 'yarn:build:es'    同時
npm run clean && npm run build                      順番
```

| クラス | 著者自身の動詞 | 異なる subject | 枝(中央値) |
| --- | --- | --- | --- |
| `parallel` | `concurrently`, `run-p` | **52** | 3 |
| `sequential` | `&&` | **47** | 2 |
| `single` | 1 コマンド | **818** | 1 |

**さらに 433 件を落としました。理由は 2 つで、どちらも読んで気づいたのではなくテストが見つけました。**
**369 件は inline 連鎖**: `tsc -p a && tsc -p b` は 2 ステップだが兄弟を呼ばないので、
描画する名前付きの枝が無く、かつ 1 コマンドでもありません ——
**最初の版はこれを `single` に入れていて、クラスの 16% に `&&` が入っていました**。
**残り 64 件は workspace runner にファンアウトを委譲**しています
(`yarn g:turbo run build -F=$npm_package_name`)—— 1 コマンド、解決する枝は無し、そして
**コーパスの中で最もファンアウト的な仕事が negative クラスに座っていた**ことになります。

**そのどれもが `single` に在り、合成クラスには 1 件もありませんでした**ので、
**難しい比較は影響を受けていません** —— 影響を受けたのは対照群です。

> **ラベルは非対称で、それが設計を決めます。**
>
> `concurrently` の集合は**独立性の証拠**です —— そのパッケージは枝を同時に走らせて出荷されているので、
> 互いに依存していません。
> **`&&` の連鎖は何の証拠でもありません** —— `npm run lint && npm run unit` は
> 独立した 2 つの仕事で、著者が並列化しなかっただけです。
>
> だから `sequential` は「**できなかった**」ではなく「**しなかった**」で、
> **だからこそ興味深いクラス**です —— **`parallel` と「合成であること」で揃っている**からです。
> `parallel` 対 `single` は主に「gate が 2 を数えられるか」を測ります。
> **`parallel` 対 `sequential` が本当の比較**で、§2 はそれを採点する代わりに読みます。

**そして gate に見せるものからは演算子を抜いてあります。**
著者のコマンドは一度も送りません。枝はそれぞれの解決済みコマンドから描画されるので、
`npm run lint && npm run unit` と `concurrently 'yarn:lint' 'yarn:unit'` は**同じ request** になります:

```
# 著者が書いたもの(送らない):
concurrently 'yarn:build:types' 'yarn:build:es' && yarn build:cjs

# gate が見るもの:
In the package @aws-sdk/client-bedrock-runtime, this piece of work has to be done.
It consists of 3 steps:
- build:types: tsc -p tsconfig.types.json
- build:es: tsc -p tsconfig.es.json
- build:cjs: node ../../scripts/compilation/inline client-bedrock-runtime
```

## 1. gate は 52/52 で分割しません

`jev-orchestrator` 自身の `plan()` を通すので、state・質問・framing(**`cost`**)・
cutoff(**0.5**、[31 §8](31-orchestration.md) が当てはめた値)は全部出荷のものです。

| クラス | n | `gate` 中央値 | p90 | 最大 | cutoff 超え | `plan()` が分割 |
| --- | --- | --- | --- | --- | --- | --- |
| `parallel` | 52 | **0.140** | 0.150 | **0.190** | 0/52 | **0/52** |
| `sequential` | 47 | **0.160** | 0.250 | 0.420 | 0/47 | **0/47** |
| `single` | 80 | **0.070** | 0.100 | 0.120 | 0/80 | **0/80** |

**人が実際に並列で走らせている仕事のうち、gate も分割したいのは 0 件です。**
これは [44 §3](44-components.md) が出せなかった数字です ——
あのコーパスにはそういう仕事が入っていなかったので、**偽陰性率がそもそも測れませんでした**。
そして**ゼロ**です。近いものすらありません(`parallel` の最大 0.190 対 cutoff 0.5)ので、
**cutoff に依存しない読み方は要りません —— gate はここで一度も発火しません。**

`parallel` 対 `sequential` は **AUC 0.327**、`advise()` は **no-signal**。
**0.5 を下回っている**ので、**順序は弱いのではなく逆**です。
`parallel` 対 `single` は AUC 0.997(これは簡単な対照 —— 1 コマンドには分けるものが無い)。

## 2. そして topology が、cutoff に依存しない鋭い所見です

`topology` が答えるのは「**もしこの仕事を分けるなら、どの形が合うか**」で、
gate の判断とは無関係に聞かれて記録されます。
著者が同時に走らせている枝なら、答えは
**`fanout`**(*独立した仕事を並列に、あとで統合*)であって
**`sequential`**(*A のあと B、各段が前段の出力を消費する*)ではありません。

| クラス | `sequential` | `fanout` | `blackboard` |
| --- | --- | --- | --- |
| **`parallel`**(答えが確定) | **52/52** | **0/52** | 0/52 |
| `sequential`(答えは不明) | 30/47 | **17/47** | 0/47 |
| `single`(分けるものが無い) | 37/80 | **43/80** | 0/80 |

**答えが確定している唯一のクラスで 0/52。**
そして**答えが確定していない 2 クラスの方が `fanout` を多く受け取ります** ——
**順序は弱いのではなく、既知の答えを持つクラスで反転しています。**

> **[31](31-orchestration.md) はこの同じ `choice` を 22/22 と測っていました。**
>
> あれは自分の 38 シナリオ上で、**私が書いたもの**です。
> 他人が書いた仕事で、答えが**その著者が出荷したことで確定**しているところでは、**0/52** です。
>
> **[49](49-scripts.md) の教訓が `choice` に届いた形**です ——
> **自分が書いたコーパスは、部品を他人のコーパスよりずっと優しく測る。**
> [49](49-scripts.md) は公開スクリプト上で gate が 20 倍うるさいことを見つけ、
> ここは同じ母集団で topology の問いが反転することを見つけました。

## 3. 曖昧なクラスは、採点せずに読む

`sequential` は仕事の性質というより**著者の習慣**なので、
gate がそこで発火しても必ずしも間違いではありません。

**47 件中 0 件で gate は分割を望みました。**
つまり**このコーパスで gate は、枝を連鎖させた著者に一度も反対していません** ——
そして**反対するのが正しかったかどうかも、このクラスからは分かりません。**

枝の数で揃えると(だから「ステップが何個か」の比較にはなりません):

| 枝 | `parallel` 中央値 | n | `sequential` 中央値 | n |
| --- | --- | --- | --- | --- |
| 2 | **0.130** | 12 | 0.150 | 26 |
| 3 | **0.140** | 35 | 0.170 | 14 |
| 4 | **0.150** | 4 | 0.165 | 2 |
| 5 | **0.190** | 1 | 0.215 | 2 |

**`parallel` が高いのは 4 つの枝数のうち 0 個**(4 つの不一致で p = 0.125)。
この n では向きでしかありませんが、
**このレポートで唯一交絡していない比較の、正直な大きさ**です。

## 4. §2.0 の前提は、自分のコーパスで生き残りませんでした

| §2.0 の主張 | 測定 |
| --- | --- |
| **gate の問題ではなくコーパスの問題** | **書かれたままでは成立しません。** 人が実際に並列で走らせた仕事で `plan()` は **52/52 で分割しない**。**欠けていたコーパスを供給しても seam は発火しませんでした** |
| **閉じ方はファンアウトが実際に選ばれた分布** | **満たした、ただし置き換えて。** 354 の公開パッケージの著者が書面で選んでいます、52 subject 分 —— **ただし著者であってエージェントではありません** |
| **一番見込みがあるのは §2.1 の候補 3** | **正しく、しかも同じファイルでした。** [49](49-scripts.md) が既に 2,706 エントリ全部を harvest 済みで、これはその読み直しです |

**だから読み方が 2 つ在って、意味がまったく違います。**
gate がこの仕事に対して**校正されていない**のか、
それとも**これは gate が問題にしているファンアウトではない**のか。
**`size` の答えがそれを決め、記録されています:**

| | `parallel` クラス |
| --- | --- |
| `size` 中央値(*大きい: 時間〜週、あるいは多数の項目*) | **0.120** |
| `size` 最大 | 0.220 |
| `stay_single` 中央値(*1 人で素直にやればよい*) | **0.810** |

> **gate は「この仕事は小さい」と言っていて、それは正しいです。**
>
> 1 つのソースツリーに対する `tsc` 3 回は**秒**の仕事です。
> **著者が `concurrently` に手を伸ばすのは、シェルでは 2 つ目のプロセスがほぼ無料だから**で、
> 2 人目のワーカーに値するからではありません。
> `cost` framing はエージェントの 2 人目が何を要求するかを明記しています ——
> トークン、レイテンシ、片方の間違いがもう片方の入力に伝播する確率 ——
> そして**そのどれも `concurrently` には当てはまりません。**
>
> **だから正直な読み方は「gate が正しく、このコーパスは §2.0 のコーパスではない」です。**
> §2.0 が求めた性質 —— **誰かが実際に選んだファンアウト** —— は持っていて、
> ファンアウトを**判断**にする性質 —— **ワーカーのコストが小さく見えるほど大きい仕事** —— を持っていません。
> **コーパスは条件の文面を満たして、その趣旨を外し得る。**

> **そしてその読み方でも無傷で生き残る所見が 1 つあります。**
>
> `size` の答えは gate が分割を断ったことを免責します。**topology は免責しません。**
> `topology` は条件付き —— *もし分けるならどの形か* —— なので、
> 「仕事が小さい」はその答えになりません。
> そして**形が実行で確定している唯一のクラスで、毎回間違った形を選びました。**
> **これはコーパスの結果ではなく部品の結果です。**

**§2.0 はどこに残るか。** [44 §3](44-components.md) の `Task` 0 件は**エージェントの選択**で、
ここではエージェントが違う選択をするところを**何も観測していません** ——
これらは、リポジトリを知っている人が `npm run` のために一度書いたスクリプトです。
**[§2.1](../TODO.md) の候補 1 がまた条件**です: **実在リポジトリでの実在のエージェントのトラフィック**。
**3 本のレポートが違う方向からそこに収束しました**([51](51-question.md) [52](52-intent.md) と本稿)——
それは 1 本が単独で到達するより価値があります。

## 5. 正直な限界

- **`sequential` のラベルは著者の習慣で、仕事についての事実ではありません。**
  `npm run lint && npm run unit` は独立した 2 つの仕事です。
  だから **`sequential` に対して計算した数は全部、gate の一致度の下限**で、
  §3 はそのクラスを採点せずに読んでいます。
- **positive 52 件・曖昧 47 件、そして positive は偏っています。**
  `@aws-sdk` と `@smithy` の一族が同じ `concurrently` 行を多数のパッケージに書いています。
  描画後の request で重複除去するとバイト単位の複製は消えますが、
  **一族の類似は消えません** —— **52 人の独立した著者ではありません。**
- **`parallel` 52 件のうち 40 件は `mixed`** です ——
  `concurrently A B && C` は「A と B を同時に、そのあと C」で、
  **枝のリストは 2 段を平らに潰しています。** `parallel` と分類したのは
  著者が並列を宣言しているからで、その判断は擁護できますが、**枝の並びは段を表現していません。**
- **枝は 1 パッケージの中に在ります。** それは狭い種類のファンアウト
  (1 つのソースツリーに対するコンパイラ 3 回)で、
  **[31](31-orchestration.md) のシナリオが記述する種類ではありません** ——
  研究のファンアウトも、討論も、レビューのパイプラインもありません。
  topology の数字は「独立したビルド 3 本にどの形が合うか」として読むべきで、
  **8 択の `choice` の検査としてではありません。**
- **演算子を抜くのは私がやっていて、荷重を持っています。**
  `concurrently` や `&&` が request に漏れたら gate はラベルを読むことになります。
  テストで固定してあり(**両クラスを描画して並列動詞が生き残らないことと、
  同じ枝集合がどちらのクラス由来でも同じ request になることを検査**)、
  **そのテストが実際にバグ 2 件を見つけました**(下記)。
- **framing は 1 つ。** `cost` の 0.5、出荷の既定値です。
  [31 §2](31-orchestration.md) は 2 つの framing を**本当に違う計器**と測っているので、
  このコーパスでの `plain` の数字は未知です。
- **`single` は 818 件在って、掃いたのは 80 件です。**
  標本は harvest 順の先頭 N —— つまりパッケージ順で、**ランダムではありません。**
  `single` はそもそも簡単な対照です。
- **このコーパスが一番欲しくて持っていない行**:
  **同じ枝集合が、あるパッケージでは `concurrently`、別のパッケージでは `&&` で現れる**ケース。
  **それなら比較から著者が完全に消えます。**
  §3 の向きを信じる前に、それを探す価値があります。
- **枝の中の `&&` は request に残ります。** 枝自身のコマンドが連鎖(`tsc && rollup`)であることは在り、
  それはその枝の仕事なので正当に見せています。
  **安全なのは 2 つの合成クラスが同じ率でそれを持つから**で、テストがその率の同等性を検査しています
  (`parallel` 60% 対 `sequential` 64%)。
- **テストが見つけたバグ 2 件は、どちらも目では見つかりませんでした。**
  1 つ目は枝の抽出が**裸の `yarn X` 形を落としていた**こと ——
  レポートが最初に印字した例がまさにそれで、
  `concurrently 'yarn:build:types' 'yarn:build:es' && yarn build:cjs` は枝が **3 本**なのに 2 本しか採れず、
  **gate は著者が書いたより少ない仕事について聞かれていました。**
  2 つ目は上の `single` クラスの汚染です。
