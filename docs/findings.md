## 00. API の実挙動

**試したこと** 公式スキーマとドキュメントに書かれていない挙動を実 API で確認。

**結果**

| | |
| --- | --- |
| 質問のバンドル(20 問) | 5227 ms / 8277 tok → **246 ms / 1000 tok** |
| 答えのズレ | 単独で聞いた場合との平均差 **0.011**(最大 0.04) |
| 1 リクエストの質問数上限 | **無い**。1220 問が通る |
| トークン上限 | リクエスト全体 **64Ki** / **state だけで 32Ki** の独立 2 枠 |
| choice の選択肢上限 | **255**(301 で 400) |
| レイテンシ | 125〜730 ms。質問を 1 → 20 に増やしても変わらない |

**わかったこと**

- **質問を削る最適化は意味がなく、往復を削る最適化だけが効く。**
  質問を足すコストはほぼ質問文のトークンだけ。迷ったら聞いておける。
- **noul の criteria をトップレベルに置くとサーバーが黙って捨てる。**
  200 が返るのでログを見ても気付けない。気付けるのは input_tokens の差(28 トークン)だけ。
  `lib` はこれで criteria が一切効いていなかった。
- **`choice` は必ずどれかを選ぶ。** 「燕の飛行速度は?」に technical **conf 0.96**、
  「asdf qwer zxcv」に **conf 0.99**。閾値 0.85 を越えて自動処理に流れる。
- **選択肢の説明は省ける。** `criteria` の値に `null` で「名前だけで解釈」。
  20 ハンドラで入力 441 トークン、conf 0.98〜1.00。
- `instructions` と criteria は文字列でなくてよい(object / array も通る)。
  ただし**易しいケースでは答えは変わらない**。

**効かなかったこと** 構造化した instructions は、素の文章で曖昧にならないケースでは無意味
(string / object / array すべて 0.98)。

## 01. シェルコマンドの危険度判定

**試したこと** エージェントが実行しようとするシェルコマンド 24 件を
allow / confirm / block に振り分ける。原子 noul 5 問 + `blast_radius`(score)+ 総合を 1 リクエスト。

**結果** **23/24**。ただし到達の過程が本題。

**わかったこと**

- **順序のある結論は `score` で聞く。これが全実験で一番効いた。**
  コード側の閾値をどう捏ねても **14/24** だったものが、`choice` → `score` の一手で
  **19/24 → 23/24**。`dd if=/dev/zero of=/dev/sda` が `choice` で block@**0.47**、
  `score` で 1.95/2 @**0.93**。0.47 は「危険か迷っている」ではなく
  「confirm と block のどちらに寄せるか迷っている」だった。
- **同じコマンドでも文脈で判断が変わる。** `rm -rf ./build` 対 `rm -rf ./data` が
  0.59 対 1.98。設定に「`./data` は本番ボリュームの bind mount」と書くだけで分かれる。
- **rubric は書いた軸しか答えない。** score のラベルを直感の「ひどさ」で作ると
  軸が混ざって単調にならない。
- **分解は銀の弾丸ではない。** 原子質問はレバーを与えるが、
  **合成規則の正しさが自分の責任になる**。列挙し忘れた脅威クラスに穴が空く。

## 02. ヘッドレス 3v3 MOBA(視界と戦場の霧)

**試したこと** LoL を圧縮した 2 レーン + ジャングル、視界と戦場の霧あり。
**チームの視界 = 1 state、判断が必要なキャラ = 3 体**という形を fan-out に当てる。

**結果** 1 リクエストが **2.6〜2.8 体分**の行動を決める。**73 ms / キャラ判断**。
489 判断で反則 0。scripted bot に 6-0。

**わかったこと**

- **共有状態 + 複数エージェントは fan-out の理想形。** 観測が 1 つで判断が N 個なら、
  N 問を 1 リクエストに入れる。無理をしていない自然な形。
- **criteria をその場の合法手にすると、不正手が表現できなくなる。** 489 判断で 0 件。
  文字列で手を生成させる方式との決定的な差。
- **confidence は判断の種類ごとに意味のある差が出る。**
  建物攻撃 0.68〜0.84、紙一重の交戦 0.27〜0.52。「迷ったら引く」に素直に繋がる。
- **コードが既に知っていることは criteria の説明文に書く。**
  「何 hop 先か」「タワーがあるか」「見えているか」を添える。

**効かなかったこと** 6-0 は**相手が弱いこと**に依存していた(→ [10](#10-jev-vs-jev-を独立プロセスで対戦)・[12](#12-間違ったドラフトを正しいアクションで取り返す) で基準を上げ直した)。

## 03. チェス — Jev vs Claude Sonnet 5

**試したこと** 同じ局面・**同じ合法手リスト**を両者に渡して指させる。
ルールは chess.js に任せ、blunder は深さ 3 の αβ 探索で判定。

**結果**

| | 結果 | Jev の反則 | Sonnet の反則 | Jev の blunder | Sonnet の blunder | 1 手 |
| --- | --- | --- | --- | --- | --- | --- |
| Jev = 白 | **1-0**(駒得 +22) | 0 | **2** | 1 | **7** | 0.3 s 対 13.7 s |
| Jev = 黒 | **Jev の勝ち(34 手で詰み)** | 0 | 0 | **0** | **5** | 0.3 s 対 24.1 s |

1 局 **$0.001 / 約 20 リクエスト**。

**わかったこと**

- **反則手が「表現できない」ことの価値が一番大きい。** 合法手を criteria にすると
  Sonnet が 2 回やった反則が**構造的に起こらない**。37 手で 0 件。
- **confidence が難しさを測っている。** 序盤の展開手 0.14〜0.31、駒の取り合い 0.81〜0.93。
  品質との相関は **ρ = -0.47**。
- **速度差が 40〜80 倍。** 対局全体で見ると「弱いが速い」ではなく「速くて強い」だった。

## 04. エージェントに質問を設計させる

**試したこと** Jev に渡す質問を人間ではなくコーディングエージェントに書かせ、
[01](#01-シェルコマンドの危険度判定) の 24 件で採点。何も教えない(blind)/ 効いたパターンを渡す(briefed)。

**結果**

| 条件 | 3 回の正解数 | 平均 |
| --- | --- | --- |
| blind | 18, **23**, 19 | 20.0 |
| briefed | 17, **10**, 22 | 16.3 |
| 手書き | **23** | — |

**わかったこと**

- **同じプロンプトで 10/24 から 23/24 まで振れる。** 1 回試して良い数字が出たらそれは運。
  **エージェントに書かせるなら評価が必須。**
- **原因は設計ではなく閾値だった。** 出てきた質問の形はどれも妥当で、
  閾値を合わせ直すだけで **10〜22 → 21〜22 に収束**した。
  → **設計より校正のほうが効く。** ラベル付きの小さなコーパスが一番効く投資。
- **設計は移せても校正は移せない。** 効いたパターンを文章で渡すと構成は再現するが、
  閾値は当てられない。`docs/` は設計の共有には効き、校正の代わりにはならない。

**効かなかったこと** briefed は平均を改善しなかった(n=3 でばらつきが大きいので
「悪化させた」とまでは言えない)。

## 05. ブラウザ探索(chaosbringer の次操作選択)

**試したこと** [chaosbringer](https://github.com/mizchi/chaosbringer) の
重み付きランダムな次操作選択を Jev に置き換える。
対象は 8 手連続で正しい選択が要るゲート付きショップ(各画面 14〜17 コントロール、罠 2 つ)。

**結果**

| | 到達状態数 | フロー深度 | 注文完了 | 無駄手 |
| --- | --- | --- | --- | --- |
| weighted-random | **8.3/14** | 1 / 5 | **0/3** | 4, 6, 9 |
| Jev | 7.0/14 | **5 / 5** | **3/3** | 1, 2, 2 |

60 リクエスト、**183 ms/手、3 ラン $0.0032**。

**わかったこと**

- **幅はランダム、深さは Jev。** 置き換えではなく**併用**が正しい。
  Jev は 8 手深いゴールに 3/3 到達するが、到達状態数はランダムに負ける。
- **効いたのは質問ではなく state だった。** 質問を一字も変えずに state を 4 回作り直して通った。
  候補の名前だけでは足りず、画面の内容とフォームの現在値が要る。
- **繰り返させたくない選択はコード側で候補から消す。** 言葉で禁止するより安く確実。
- 除外ロジックを入れるなら**効果判定を先に固める**(取りこぼしが正解を封じる)。

**副産物** chaosbringer 側のバグを 1 つ発見 —— driver ループが候補一覧を
**1 ページ 1 回しか作らない**ので、SPA では 2 手目以降が古い候補から選んでいた。

## 07. confidence でエスカレーションする二層構成

**試したこと** 「Jev が迷った入力だけ高いモデル / 探索に回す」を 2 ドメインで測る。
チェス(第二段 = 深さ 3 の αβ 探索)とシェル(第二段 = Claude Sonnet 5)。

**結果 チェスでは成立、シェルでは不成立。** そして「成立した」チェスでも
**期待した形(安いモデルが大半、高いモデルが難しい 1 割)では成立していない。**

**わかったこと**

**必要条件が 3 つあり、提案時に意識していたのは 1 つだけだった:**

| | 必要条件 | チェス | シェル |
| --- | --- | --- | --- |
| Q0 | 第二段が第一段より本当に強い | ✅ | ❌ **第二段のほうが弱い** |
| Q1 | confidence が判断の質を順序づける | ✅ ρ = **-0.47** | ❌ 無相関 |
| Q2' | confidence が**散らばっている** | ❌ 中央値 0.22 | — |

- **confidence が低い理由を見分ける必要がある。** 局面が難しいなら計算を足せば効く
  (チェス 122cp → 2cp)。**問いの定義が曖昧なら何に回しても効かない**
  (シェルの低 confidence 2 件はどちらも Jev が正解)。
  後者はモデルを変える問題ではなく方針を決める問題。
- **エスカレーションはランダム同予算と比べないと意味がない。** どう選んでも品質は上がるので、
  「効いた」証明にならない。

## 08. skill suggestion cookbook の追試

**試したこと** [公式 cookbook](https://docs.typesafe.ai/cookbooks/skill_suggestion) を
mizchi/skills(68 スキル)で再現。エージェント(haiku)が読み込むスキルを Jev が事前に提案する。

**結果**

| アーム | wrong loads |
| --- | --- |
| agent 単独 | **13.2%** (9/68) |
| + suggestion(cookbook のまま) | **5.9%** (4/68) |
| + suggestion(ゲート改良) | **4.4%** (3/68) |
| oracle(上限) | 1.5% (1/68) |

cookbook は 16.8% → 7.3% で 2.3x、こちらは 13.2% → 5.9% で **2.2x**。
Jev 154 リクエスト・**$0.0138**・237 ms。

**わかったこと**

- **提案は「決定」ではなく「助言」として渡すと効く。** 提案をそのまま採用すると 10.3%、
  エージェントに見せて決めさせると **5.9%**。
- **cookbook のゲートは、このロスターでは純損失だった。** ゲートの noul には
  「スキルとは何か」の定義が埋まっていて、ロスターが変わると意味が変わる。
- **複数の noul を平均してゲートにすると、信号を持つ 1 問が薄まる。** 単独のほうが強かった。

**効かなかったこと(測れなかった)** needless load は全アーム 0%。
haiku が 22 件の「どのスキルも要らない」で一度も読み込まず、ベースラインに伸びしろがなかった。
cookbook の 9.8% → 4.0% に対応する結果は**無い**。

## 09. LLM guardrails cookbook の追試

**試したこと** [公式 cookbook](https://docs.typesafe.ai/cookbooks/llm_guardrails) を再現。
入力/出力を 1 リクエストで screen する(noul 4 問 + severity score)。日本語も追加。

**結果** routing 再現(入力 8/10・出力 5/5)。不一致 2 件は判断差ではなく
**確率が閾値の境界に乗ったケース**。

**わかったこと**

- **閾値方式は境界で脆い。** severity や確率が境界付近だと、メッセージの些細な違いで
  決定が入れ替わる。**境界帯は人間レビューに回す設計が要る。**
- **フィクションの枠は中身で破れる。** 枠ではなく害を見ている。
- **日本語でも英語と同じく検出できた**(cookbook は英語のみ)。
- **1 リクエスト screen には構造的な穴が 2 つある。**
  (a) エンコードで抜ける入力にはデコード段が要る
  (b) 列挙し忘れたハザード(プロンプト漏洩)は noul を足さないと拾えない。
  → **「何を聞くか」の設計がカバレッジを決める。**

## 10. Jev vs Jev を独立プロセスで対戦

**試したこと** [02](#02-ヘッドレス-3v3-moba視界と戦場の霧) の MOBA を
referee + player ×2 の**独立プロセス**に分解し、Jev 同士で対戦。

**結果** 6 ゲーム **全ゲーム決着・引き分けゼロ**([02](#02-ヘッドレス-3v3-moba視界と戦場の霧) の scripted 同士は **3/3 引き分け・建物ダメージ 0**)。

**わかったこと**

- **独立させると膠着が解ける。** 対称ゲームで意味のある試合を生むのは
  モデルの強さではなく**エージェントの独立性**だった。
- **プロセス分離 = 並行 = 速度。** 1 tick が 1 リクエストのレイテンシに収まる(逐次の半分)。
- **視界の霧はプロセス境界で強制できる。** 相手の観測をワイヤーに乗せないので、
  player は構造的に相手を見られない。**規律ではなく設計で保証される。**
- **独立な per-champion choice で役割分担が自然に出る。**
  state に各自の役割を入れておけば、明示的な調停なしにレーンが割れた。

**追記で分かったこと** リトライ無しのクライアントで叩きすぎるとレート制限で全 hold し、
対称ゲームが 350-350 で膠着した。リトライは必須。

## 11. チャンピオンのシナジー

**試したこと** AD/AP・前衛(ピール・耐性)の機構を実装し、
編成 6 種の強弱をアリーナとフルゲームで測る。さらに Jev に**編成を選ばせる**。

**結果** 対称 scripted は 350–350 の引き分け(同時処理で先手有利が消えた)。
Jev のドラフトは**アリーナとほぼ一致する順位**を付け、最強編成を **conf 0.76** で引いた。

**わかったこと**

- **シナジーは「聞き方」ではなく「メカニクス」で作る。**
  前衛のピールを実装するまで、タンクはただの低火力の的で glass cannon が全勝していた。
  **フィールド上のシナジー効果は、それを成立させる機構を入れて初めて測れる。**
- **チーム戦では正しいシナジーが勝つ。ただしフルゲームでは macro が薄める。**
  「シナジーが勝つ」は戦闘の主張で、戦闘が試合を決めるかは別問題。
- **state に stat を渡せば「選ぶ」問題も解ける。** 「前衛/混合が強い」と教えていないのに
  順位を当てた。**構造化 state の一般則が、ドラフトという新しい問題形でも効いた。**

**効かなかったこと** ドラフトの良し悪しは **policy 依存**。
scripted に弱い編成が Jev には強い([12](#12-間違ったドラフトを正しいアクションで取り返す) の本題)。

## 12. 間違ったドラフトを正しいアクションで取り返す

**試したこと** 編成を固定して「どちらが上手く操作するか」だけを入れ替えた 3 セル。
さらに attack/HP を連続にスケールする handicap sweep で境界を測る。

**結果**

| 間違ったドラフト | vs scripted(弱) | vs smart(中) | vs Jev(強) |
| --- | --- | --- | --- |
| `classic`(素の均一) | **5-1** 取り返す | **0-6** 消滅 | 2-4 負け |
| `glass_ad`(前衛なし) | 5-1 取り返す | 4-2 取り返す | 6-0 取り返す |

handicap の境界: **scripted 相手 ~20〜30%、smart 相手 <20%**。

**わかったこと**

- **上流の小さなミスは下流の正しい判断で買い戻せる。** ただし**取り返しには天井がある**。
  アクションは戦略の赤字を買い戻すが、戦略を良くはしない。
- **買い戻せる赤字には上限があり、相手の強さに反比例する。**
- **「間違い」は編成ではなく操作者への判定のことがある。**
  `glass_ad` は scripted に弱く Jev に強い。
- **弱い基準で観測した「取り返し」を一般化してはいけない。**
  classic は scripted 相手 5-1 → smart 相手 **0-6** に反転した。
  [07](#07-confidence-でエスカレーションする二層構成) の
  「弱いベースラインと比べると何でも効いて見える」の別ドメインでの再確認。

## 16. ESLint の合否を、実装を伏せて当てる

**試したこと** コードと **ESLint ルールの評価基準だけ**渡し、`create()` は一切見せない。
説明文は ESLint 自身の `meta.docs.description` を実行時に読み出す(こちらでは書かない)。
「隠している」ことは**送信ペイロードの 48 文字窓検査**で担保。

**結果** **190/215(88.4%)、AUC 0.95**(多数派ベースライン 55.8%)。
素直な違反 55/60・素直な合格 60/60。

| arm | 正解 |
| --- | --- |
| ルール ID だけ | 86.5% |
| **説明文だけ** | **88.4%** |
| 両方 | 87.4% |
| + 公開されている既定オプション | 87.4% |

**わかったこと**

- **判定基準だけ渡せば、実装なしで合否が当たる。**
- **どこまで見せるかは正解率をほとんど動かさない。動くのは「何を間違えるか」。**
  ID だけだと過検出が 2〜3 倍(101 対 34)—— 暗記ではなく読解が効いている。
- **説明文は仕様ではない。逃げ道が仕様で、それは実装にしかない。**
  5 回とも外すペアは全部「説明文は禁止と言っているが、実装だけが例外を認めている」ケース。
- **逃げ道を渡せば直るのは、逃げ道が言語化できる場合だけ。**
  公開オプションで表現できる `no-cond-assign` は **10/15 → 15/15**、
  `create()` にハードコードされた `no-empty` は **15/25 のまま**。
- **そして逃げ道を渡すと逃げ道を探しに行く。** 見逃しが 0 → **11 件**に増え、

## 18. Claude Code の `PreToolUse` hook

**試したこと** [01](#01-シェルコマンドの危険度判定) の判定を**本物の hook** にする。
依存ゼロの Node スクリプト 1 枚、判定ロジックは `.jev` に外出し。

**結果** 24 コマンドに対して **68/72(94.4%)**、**median 329 ms(p90 394 ms)**、
1 コマンド **$0.000032**。フェイルセーフ 7 経路すべてが「判断なし」に落ちる。

**わかったこと**

- **精度より先に決まるのは「失敗の落とし先」。** 全失敗経路を**判断なし = 通常フロー**に落とす。
  allow に倒せば黙って承認、deny に倒せば障害で全停止。
- **ゲートは狭める方向にだけ使う。** `allow` を返すと
  **ユーザーが設定した permission ルールを上書き承認**してしまう。
- **リトライしない。** hook の予算ではリトライが予算を食い潰す。
- **原子信号と総合質問の保守側を採る。** スコア単独 90.3%・原子単独 61.1% に対し **94.4%**。
- **判定ロジックをデータ(`.jev`)に出すと、規則と理由文の 16 分岐を API なしで検証できる。**
  ただしそのファイルは**信頼された入力**(全部 defer にすればゲートは無効化される)。

**一番大きい発見** **オフラインの正解率は質問文の妥当性を保証しない。**
[01](#01-シェルコマンドの危険度判定) の `exfiltrates` の文言をそのまま写したら、
**1 発目でごく普通の `git push` が deny された**。
24 件のコーパスに「正当な外向き転送」が 1 件も入っていなかっただけ。
**実運用の形に載せることが最後のテスト**で、それ以外に文言の穴を出す方法は無い。

そして**保守側採用は誤った述語の害も増幅する** ——
スコアが allow 0.43 と言っているのを、誤った原子述語が deny に引き上げていた。

## 19. jevlang — 条件が Jev の判断である言語

**試したこと** `if noul("家に牛乳がない") { ... }` が動く小さな言語を、
**JS と MoonBit の 2 実装**で作る。同じ `.jev` の結果一致をテスト。

**結果** 動く。巻き上げ(speculative batching)で **4 → 2 リクエスト、1501 → 867 トークン**。
2 実装の一致テスト 3 本、ポリシー規則の検証 16 分岐(いずれも API 不要)。

**わかったこと**

- **設計判断は構文で強制できる。** ライブラリなら「閾値はコード側に置け」はお願いだが、
  言語なら**質問文に閾値を書く場所を作らない**で済む。
  「逃げ道は選択肢ではなく別の問い」も、`else` 腕が gate noul を生やす設計にすれば
  **混ぜる書き方が存在しなくなる**。
- **質問文が実行前に確定している judgment は巻き上げられる。**
  補間のない質問は 1 リクエストにまとめられる —— 言語レベルの fan-out。
- **確率的な判断には record/replay が必須。** 無いとテストが書けず、
  実装差とモデルのばらつきも区別できない。
- **2 実装であることが実際に効いた。** 手書きの数値パーサが `0.6` を
  **0.6000000000000001** にしていて、**これが閾値なので境界で分岐が変わる**。
  一致テストで発見した。小数部は整数で溜めて最後に 1 回割る。

**効かなかったこと(直したこと)** `match` の gate noul を subject を見ずに付けていたので、
**文字列の `match` にも「どれも当てはまらないか」を聞いていた**。
gate が要るのは `choice` が必ず何かを返すからで、普通の値に閉じた世界は無い。

## 20. jevdsl — `match` できる薄いラッパー

**試したこと** MoonBit から
`match jev.noul("家に牛乳がない") { (true, c) if c > 0.5 => ... }` と書けるようにする。

**結果** 書ける。3 種すべてが `(result, confidence)` なので `match` の形が揃う。

**わかったこと**

- **3 種を同じ形に揃えるには noul の confidence を導出するしかない。**
  API は確率 1 本しか返さない。そのまま使うと `confidence > 0.5` が
  `result == true` と同義になって **guard が無意味**になる。
  コイン投げからの距離 `|p - 0.5| * 2` にした(**これは発明した値**なので埋めずに出している)。
- **薄いラッパーでも「1 判断 1 リクエスト」を既定にすると高くつく。**
  同じ 3 判断が **3 リクエスト/1069 トークン 対 1 リクエスト/435 トークン**。
  アクセサを共通にして、束ねる形へ移る道を最初から用意する。

**限界** `match` は confidence の帯の網羅性を強制しない(`(true, _)` と `(false, _)` で型が通る)。
逃げ道もラッパーは足さない(「該当なし」は自分で別 noul として入れる)。

## 21. eslint-plugin-jev

**試したこと** **本物の ESLint プラグイン**として、関数ごとに
「レビューでどれだけ押し返すか」を score で出す。ファイル 1 個 = 1 リクエスト。
ラベルは**バグ 1 個ごとにプローブ**を付けてコード実行で証明。

**結果** 自信のある指摘 **15/15 が本物のバグ、誤検出 0**(clean+nearmiss 117 判定)。
ただし **12 バグ中 5 個**しか捕まえない。精度 100% / 再現率 42%。関数 1 個 **$0.000017**。

**わかったこと**

- **本題は精度ではなく「ルールが同期関数」だった。**

  | | 事前準備 | lint 時間(12 ファイル) |
  | --- | --- | --- |
  | 事前バッチ + 同期ルックアップ | warm pass | **31 ms**(何もしない lint が 36 ms) |
  | ルール内でブロッキング(`execFileSync`) | 不要 | 4327 ms(1 ファイル 361 ms) |

  **バッチの単位は「拡張点が全体を見られる瞬間」**で決まる(ESLint なら `Program:exit` = ファイル)。
- **state の一部分についての質問を束ねても汚染はほぼ無い。**
  4.7x 少ないリクエストで平均絶対差 0.082・ρ 0.931・判定差 3.6%。
- **confidence をゲートにすると 7〜11 ポイント損する。**
  clean も bug も 0.54〜0.57 に入るので、柵にすると正解ごと捨てる
  (score 2.42 / conf 0.42 の当たりが消えていた)。**ルーティングに使う。**
- **ファイルの文脈は精度を上げない(下げる)。** 関数単体で見せると AUC は上がるが
  **誤検出が 5 倍**になる。文脈は judgment を穏やかにするだけ。
- **質問にコードを重ねるのは払い損。** state にあるものを質問で繰り返すと
  **32% 多く払って 0.4 ポイント下がる**。
- **捕まえるのは契約の齟齬、落とすのは API の誤用。**
  捕まえた 5 個は関数の中だけ読めば辻褄が合わない。
  落とした 6 個は `.sort()` / `splice(at)` / `/g` / `await` —— **1 トークンの差**。
  → **型・ルール・テストの代わりではなく補完。**

**副産物** バッチ上限が 256 ではなかった([00](#00-api-の実挙動) の 2 枠を発見)。

## 22. 具体的な「良いコード」の指標を名前で聞く

**試したこと** [21](#21-eslint-plugin-jev) の曖昧な 1 問を、
**8 つの具体的な欠陥クラスに名前を付けた 8 問**に置き換える。
落とした 6 個は**見えなかったのか、聞かれていなかったのか**。
さらに列挙外クラスの穴を 2 通りで測る(held-out セット + **指標を 1 つ抜いて投げる**)。

**結果** 33/51 → **41/51**(誤検出は同じ)。指摘が `median matches api_default (0.35)` と**名前で返る**。

**わかったこと**

- **落とした 6 個のうち、戻ったのは 2 個だけ。**
  専用の指標を名指しで投げても、`splice(at)` は **0.12**、`/g` なしは **0.09**、
  `await` 忘れは 0.22(3 回とも)。**ちょうど正しい問いに自信をもって「いいえ」**。
  → **「rubric は書いた軸しか答えない」は真だが、軸を書けば答えが来るとは限らない。**
- **一番効いたのは指標ではなく「指標ごとの閾値」。**
  自クラスへの答えが **0.20〜0.94** に開く。共通 0.80 は AUC 0.80/0.92 の 2 指標を
  丸ごと捨てる(**13/36 → 24/36**)。検出の問題ではなく校正の問題。
- **指標が効くのは「見えにくいバグ」でだけ。**
  関数の中だけ読めば分かるバグは naming の有無にかかわらず **15/15**、
  API の挙動を知らないと見えないバグで **14% → 52%**。
  **列挙の穴は約 32 ポイントで、hard なバグにしか存在しない。**
- **8 指標は互いに重複している。** 1 つ抜いても **7 個は自クラスを失わない**
  (隣の指標か汎用 noul が拾う)。本当に失うのは広い 1 個だけ(9/12 → 4/12)。
  → **指標を増やすより、広い 1 個を正しく校正する。**
- **原子質問は汎用質問の上乗せで、代わりではない。**
  原子だけだと列挙外クラスで 11/15 に落ち、両方なら 15/15 に戻る。
- **再現率と説明可能性は同じ通貨で買っている。**
  高い閾値で発火したときの「どの指標か」は **13/13 正しい**。
  拾う数を増やすために下げると **20/26(77%)**に落ちる。
- **当てはめた閾値は次のコーパスで越える。** 10 関数足しただけで
  `unescaped_composition` が**テンプレートリテラル全部**に発火した。
  1 段上げれば自クラスは無傷で誤検出が消えたが、**上げた直後の閾値にも次の draw が乗った**。
- **質問を抜いても他の答えは動かない**(平均絶対差 0.005)。
  [00](#00-api-の実挙動) の fan-out 独立性は**引く方向にも成立する**ので、
  leave-one-out は確率的な判断でも使える測り方。
- **記録に閾値を書いておく必要がある。** 無いと閾値を直すたび
  **過去のレポートの数字が黙って書き換わる**。

**訂正したこと** 最初の held-out セット 5 個は**全部「関数の中だけ読めば分かる」易しいバグ**で、
naming の有無にかかわらず 15/15 になるセルを測っていた。
「汎用質問が穴を埋めた」という読みは間違いで、作り直して測ったのが上の 32 ポイント。
そして**コーパスを正直にしたら全体の数字は下がった**(balanced 81.3% → 73.0%)。

## 23. タスク/テストランナーの filter

**試したこと** `just` で依存グラフを先に作り、**今の diff を state に**して
**ゴールタスク 1 つにつき `score` 1 問**を 1 リクエストで投げ、閾値で切った集合を走らせる。
[17](#17-タスクランナーから正しいタスクを選ぶ) と違って**ゴール文を渡さない** ——
diff が依頼そのもの。正解は人手ラベルではなく規則で、
**run set に実際に赤くなるタスクが入っているか**で採点する。

**結果** 検出 **45/45** を保ったまま machine time を **68.6%**(閾値 1.25 で **75.8%**)削減。
1 ブランチ **0.17 秒・$0.000131**。

| 戦略 | 検出 | machine | 削減 |
| --- | --- | --- | --- |
| 全部走らせる | 15/15 | 18.5m | 0% |
| static(glob + 依存伝播) | 15/15 | 12.8m | 30.9% |
| glob だけ(伝播なし) | **14/15** | 8.6m | 53.4% |
| **Jev(t=1.0)** | **45/45** | **5.8m** | **68.6%** |

**わかったこと**

- **グラフと判断は分業できる。** ゴールだけ採点させて**前提と順序は閉包が足す**ので、
  Jev は依存関係を間違えようがない。[17](#17-タスクランナーから正しいタスクを選ぶ) の
  「1 タスクしか選べない」はグラフを外に置くと消える。
- **静的解析だけでは健全さと安さが両立しない。** 依存伝播を外すと **14/15** に落ち
  (`a11y` の入力 glob は `web/**`、変更は `packages/ui`)、
  足すと 15/15 だが **30.9% しか削れない**。
- **文脈が効くのは意図が書かれていないときだけ** ——
  [17](#17-タスクランナーから正しいタスクを選ぶ) の予想がそのまま当たった。
  ブランチ名と題名を外すと、**パスだけの arm は無害な変更の判別が 0.482(コイン投げ)**
  に落ち、hunk を渡す arm だけが 0.183 で残る。
  hunk が要るのは**パスが内容を決めないファイル**(`package.json`・lockfile)で、
  パスだけの arm はそこを「依存が増えた」と読んで `audit` を 1.86 で選ぶ。
- **同じグラフを、コードに置くと効きプロンプトに置くと逆効果。**
  前提・入力 glob・コストを各質問に載せると **68.6% → 66.3%**、トークンは 1.3 倍。
  閉包が既に解いていることに金を払っている。
- **閾値はコストで重み付けする。** 唯一の見逃しは **4 秒**の `fmt-check` が
  **1.24 対 1.25** で落ちたもの。飛ばして節約できるのは 4 秒で、失うのは
  **その変更で赤くなる唯一のチェック**。「10 秒以下は無条件」で 45/45 に戻り、代償 0.5 分。
- **逃げ道の noul は片側 0 誤りのゲートになる。** 「どれも走らせずに通る」を
  p ≥ 0.4 で読むと**無害 9/15 に発火し、壊れている 45 件には 0 件**。
  ただし無害側の平均が 0.479 なので、**閾値 0.5 は谷ではなく山の上**。

**効かなかったこと** **グラフをプロンプトに載せること**(上記)。
それと **`score` の上限を閾値にすること** —— t=2.0 は 0/45 で、
`score` が満点を返すことは実際にはほぼ無い。

**追記 — このリポジトリ自身で、正解ラベルを実測した**([23 §12](23-task-filter.md#12-追記--このリポジトリ自身で正解ラベルを実測した))

上の正解は「欠陥の種類とパス」から**規則**で決めていた(規則を書いたのもこちら)。
根に `justfile` を置いてこのリポジトリの 20 レシピを実際に走らせ、
**終了コードをラベルにして**やり直した。ベースラインは 20/20 green・40.8 秒。

- **「ありそうな編集」15 個のうち、6 個しか検出されない。**
  丸めの違い(**コメント自身が**「ここで 2 実装が食い違う」と警告している箇所)も、
  実 API に対して測った定数 `max_choices = 255` も、
  差し替え可能にしたはずの `policy.jev` の閾値も、**誰も固定していない**。
  → **フィルタの精度を測るつもりで、スイートの穴を測ることになった。**
- **規則では書き漏らすものが出た。** `report/fmt.mbt` のシグネチャを変えたら
  `test-jevdsl` と `test-jevlang` が落ちた —— 予測していなかった 2 つ。
- **検出は 18/18(見逃し 0)。ただし glob だけの無料の静的判定に負ける**
  (80.2% 対 65.9%)。合成 monorepo では glob だけが 14/15 で取りこぼしたのに、
  ここでは 6/6。差は**グラフの扇形**で、共有パッケージから伝播する形でないと
  静的解析は悲観的にならない。→ **入れる前にグラフの形を見る。**
- **効いたのは 1 行のコメント。** Jev は閉包が一番深い `conformance` を
  31/45 で選びすぎていた。doc が「何をするか」しか書いていなかったので
  「何を守るか」に書き直したら **18/45・削減 53.3% → 65.9%**(検出は 18/18 のまま)。
  [17](#17-タスクランナーから正しいタスクを選ぶ) の
  「投資先は項目名と 1 行の説明」が実在の justfile で再現した。
- **ビルドキャッシュがあると値段が順序に依存する。** 最初の計測では MoonBit の
  テストが全部 0.0 秒だった —— 先に走った `moon-build` が払っていたから。
  cold で測り直して 19 秒 → 40.1 秒。

**訂正したこと** 上の「静的解析だけでは健全さと安さが両立しない」は
**合成グラフの性質**だった。実リポジトリでは両立する(glob だけで 6/6・80.2%)。
また `p(振る舞いを変える)` は実測ラベルと噛み合わない(壊れない側 0.180 → **0.580**):
実測の「壊れない」は**無害ではなく「このスイートには見えない」**で、
タイムアウトを 2500ms から 250ms にする編集は**確かに振る舞いを変える**。
**質問をスイート基準で書いたか真実基準で書いたかを意識する必要がある。**

## 24. まだ存在しないルールを自然言語で書く

**試したこと** [21](#21-eslint-plugin-jev) と [22](#22-具体的な良いコードの指標を名前で聞く) は
**こちらが質問を決めていた**。逆に、使う側が ESLint の設定に 1 文書けばルールになる形を作る。
**コードで書くのはノードセレクタだけ**で、違反かどうかは文で聞く。
当たったノードごとに score(noul ではなく)、1 リクエストに最大 256 件。

**結果** 5 ルール・**49 ノードを 12 リクエスト・$0.0011**。
**7 件の指摘、うち 6 件がラベル付きのバグ/smell の上、自信のある 5 件は 5/5 正解。**
外した 1 件は意図的に catch している関数で、**confidence 0.31 なので「質問」として出た**。

**わかったこと**

- **読むべき数字は閾値ではなく gap(違反と残りの点数差)。**

  | | gap | 閾値をどうするか |
  | --- | --- | --- |
  | 効いている 4 ルール | 1.79〜2.16 | **何もしない**(既定 2.0 が真ん中に落ちる) |
  | 失敗した 2 ルール(1 稿目) | 0.16 / 0.28 | **閾値では直らない。文を書き直す** |

  [22](#22-具体的な良いコードの指標を名前で聞く) の「検出ではなく校正の問題」と**対**。
  22 は答えが分かれているのに共通閾値で潰していた。こちらは答えが**分かれていない**。
  **同じ「閾値を動かす」操作で、直る場合と直らない場合がある。**
- **5 ルール中 2 つは 1 稿目の文が失敗した。そして失敗の仕方が違った。**
  `no-magic-rounding` は `*100 / 100` を聞いたがコーパスにそんなコードは無く、
  **0.53 は間違った質問への正しい答え**だった(書き直して gap 0.16 → 2.16)。
  `no-swallowed-catch` は「呼び出し元が失敗を知る必要があるか」= catch 節から見えない
  判断を文に混ぜて全部真ん中に来た(0.28 → 0.77)。
  → **判断できない条件を質問文に書かない。**
- **書き直しループが安い。** 文と note だけがキャッシュキーなので、
  1 文直すとそのルールだけ再質問(18 件 / $0.0004)。
  **閾値はキーに入っていないので `at` を変えても再質問 0 件。**
  → 「1 発で正しい文を書く」必要が無い。
- **絞り込み側(セレクタ)はわざと広く書くのが正しい。** 49 → 7。
  score のレベル 0 を「このルールは当てはまらない」にしてあるので、
  **セレクタが余計なものを拾ったことをモデルが言える**。
  `reportAt` の既定 2.0 は当てはめた数字ではなく**レベル境界**
  (レベル 1 =「満たしている」を報告するのはルールの逆走)。
- **決定的な側は静かに失敗する。これだけは測れない。**
  `compareTokens`(空トークン 2 つが一致)は握り潰しだが catch が無く、
  `CatchClause` に当たらないので**どの閾値でも質問されず、レポートにも出ない**。
  [22](#22-具体的な良いコードの指標を名前で聞く) の「列挙の穴」は指標を増やせば埋まる
  可能性があったが、**こちらの穴はセレクタを読むしかない**。
- **256 は自分で決めた上限で、効いているのはファイル単位。**
  49 ノードが 12 リクエストになったのはファイルが 12 個だったから。
  実際の上限は [00](#00-api-の実挙動) のトークン 2 枠。

**副産物** テストで fail-safe の穴が 1 つ出た。**パースできないセレクタは
トラバース中に throw して lint 全体を落としていた**(`create()` が返ったあとに
解釈されるのでルールの中からは捕まえられない)。事前検証して `ruleConfig` として
報告する形にした。ただし**設定不備は沈黙させない** —— 設定が落とされて発火しない
ルールは、何も見つからなかったルールと見分けが付かない。

## 25. 閾値を当てはめる部品

**試したこと** [22](#22-具体的な良いコードの指標を名前で聞く) と [23](#23-タスクテストランナーの-filter) で
**手で 2 回引いた閾値**を部品にする([06 の提案 B](06-ideas.md#b-閾値フィットを-lib-の部品にする))。
新しい質問は投げず、記録済みの答えを**当てはめていない標本で採点し直す**
(関数の 5 分割 / draw / コーパスの 3 通り)。さらに 23 の宿題 2 つ ——
閾値をコストの関数にする・同じ diff を 10 回投げる。

**結果**

| | |
| --- | --- |
| 22 の 8 指標、当てはめ(23/36)を誤検出 0 で要求すると | **18/36**(共通閾値は 13/36) |
| 境界 +0.01 の誤検出 in-sample / held-out | **0 / 24**(1224 関数-draw 中) |
| 同じ検出で置き場所だけ変える(gap の中央) | 誤検出 **24 → 7** |
| 閾値を越える確率:同じ関数の再 draw / 新しい関数 | **0.37% 対 2.0%** |
| 23 §12 の実測ラベル、コストで決める(検出 18/18) | 削減 73.5% → **81.4%** |
| 同じ損失モデルから判断を抜くと(検出 18/18) | **40.9%** |
| 同じ diff 10 draw、閾値 1.25 をまたぐ組 | **7/240、うち赤くなるもの 0** |

**わかったこと**

- **当てはめた閾値の「誤検出 0」は構造上そうなるだけで、情報がない。**
  22 の上乗せ 10 件のうち半分は当てはめの自己申告だった。
  それでも**質問ごとに引く判断自体は正しい**(13/36 → 18/36)。
- **置き場所には名前が要る。** 「清潔な側の最大値 +0.01」は最も自然に見えて最も脆い。
  gap があるなら**中央**に置く(検出は 1 件も落ちず誤検出が 1/3)。無いなら**どちら側に倒すか決める**。
- **閾値を壊すのは draw ではなく新しいコード。** 効く margin は draw sd の **20 倍**必要で、
  「モデルの揺れのぶん余白を取る」では足りない。
- **`advise` が最初に返すのは閾値ではなく「当てはめるべきか」。**
  22 の 8 問は 5 問が wide-gap(閾値をいじる意味がない)・3 問が overlapping(どの閾値でも
  健全と完全が両立しない)で、**本当に校正が効く形は 1 問も無かった**。
- **コストが測れているなら閾値は要らない。** 「閉包の秒数 + penalty × P(見逃し)」を最小化すると、
  タスクごとの床が計算で出る(0.1 秒のレシピは無条件、5.3 秒のレシピは 1.30 を要求)。
  自由なパラメータは**「見逃し 1 件の値段」1 個**に移り、これはコーパス無しで答えられる質問。
- **ばらつきは決定に届いていない。** 10 draw で選ぶ集合が変わるのは 150 決定中 16 件だが、
  検出も machine 秒数も同じ。**1 リクエストで足りる。**

**効かなかったこと** **モデルを良く解くこと。** 集合選択を総当たり(最適)にすると 81.4%、
山登り(不完全)のほうが 83.0% で良かった。**目的関数は真実ではない。**
そして glob だけの無料の静的判定(80.2%)との差は **1.2 ポイント**しかない ——
[23 §12.3](23-task-filter.md#123-検出は-1818ただし-glob-だけの静的判定に負ける) の
「入れる前にグラフの形を見る」は変わらない。

**副産物** 集合選択を bitmask で書き直したとき、**タスク添字の配列をゴール添字で読んでいた**。
例外も型エラーも出ず目的関数だけが静かに変わる。素朴な実装との突き合わせテストで出た
(45 決定中 3 件しか一致せず → 修正後 45/45)。
[19](#19-jevlang--条件が-jev-の判断である言語) の「2 実装が丸めのバグを出した」と同じ形。

## 26. 実リポジトリで jev/rule を走らせる

**試したこと** [24](#24-まだ存在しないルールを自然言語で書く) の限界
(**641 行のラベル付きコーパスでしか走らせていない**)を埋める。
対象は**このリポジトリ自身の JS 9,315 行**。ルールは 3 系統 ——
24 の文を**逐語で** 3 本、`docs/` にしか書いていない規約を 3 本、
**すでに守れている規約**(指摘は定義上すべて誤検出)を 2 本。

**結果** 579 判定・**2.9 秒・$0.0135**。指摘 **19 件**、1 件ずつコードを読んで分類:

| | |
| --- | --- |
| 要修正だった指摘 | **2 件**(どちらも「数値の由来が書かれていない」) |
| 意図的にそうしてあるコードへの指摘 | 17 件 |
| confidence ≥ 0.5 の指摘の正解 | **0 / 5** |
| 当たった 2 件の confidence | **0.29 と 0.19**(= 「質問」として出た) |
| わざと広くした `TemplateLiteral` | 422 件中 **398 件が level 0**(誤検出 0)、ただしトークンの **74%** |
| 8 文のうち出荷したもの | **6 文**(2 文は測って retire) |

**わかったこと**

- **コーパスに無いのは「バグの種類」ではなく「わざとやっている版」。**
  `catch { return {} }` は文のとおり違反で、[18](#18-claude-code-の-pretooluse-hook) が決めた
  「判定層は失敗を判断なしに落とす」**そのもの**。
  プローブの `catch { return true }` は `true` がアサーション。
  [21](#21-eslint-plugin-jev) が `nearmiss` クラスを作ったのと同じ穴が、ad-hoc ルールにも開く。
- **confidence の向きが 24 と逆になった。** 形が自明なほど自信は高く、
  **形が自明な違反は意図的であることが多い**。だから
  「低 confidence を弱い指摘として畳む」は実リポジトリでは**当たりを畳む**。
- **gap の隣に band(答えがどのレベルに居るか)が要る。**
  狭い gap が 3 ルールで出て、2 つは「違反が無い」・1 つは「文が働いていない」だった。
  実コードでは前者が普通の状態なので、区別が無いと**働いているルールを毎回書き直す**。
- **level 0 は実コードで効く。** セレクタは広く書いてよい —— **ただし請求書は来る**
  (指摘 0 件のルール 1 本が実行の 74%)。
- **文でも subject でも直らない判断がある。** `no-swallowed-catch` を 3 draft
  (note の書き直し / subject を catch 節 → 囲む関数)測ると、ラベル付きコーパスで
  **意図的な catch が本物のバグを上回る順位が 3 通りとも変わらない**(2.43 / 2.35 / 2.31 対 1.57 / 1.76 / 1.69)。
  必要な情報(呼び出し元が失敗を判別すべきか)が**コードのどこにも書いていない**。
  [24](#24-まだ存在しないルールを自然言語で書く) に従って subject から見える範囲だけを聞くと、
  **意図を見分ける情報がまさに範囲外**になる。
- **例外を渡してもラベル付きのバグは失われなかった**(1.57 → 1.76)。
  [16](#16-eslint-の合否を実装を伏せて当てる) の「逃げ道を渡すと見逃しが 0 → 11 件」は起きていない ——
  16 が渡したのは**仕様の例外**、こちらは**証拠の形**。
- **規約同士が同じノードで矛盾する。** 18 の「沈黙に倒す」と 24 の「握り潰すな」は
  `catch { return {} }` に対して 1.08 と 2.90。**散文のままでは気付けない。**
- **指摘の中身は「バグ」ではなく「書かれていない前提」だった。**
  `TIMEOUT_MS = 2500` と `INLINE_LIMIT = 600` の由来。書いたら 2 つは黙り(2.19 → 1.41)、
  **1 つは書いても黙らなかった**(2.12 のまま)—— ルールの方が正しい。

**効かなかったこと** `measured-number-has-a-source`(実測値に出典を書く)は
**2 draft とも分離しない**(gap 0.26 / 0.39、答えが閾値をまたぐ)。
「なぜその数か」に**決定可能な版が無い** —— タイムアウトには理由が要り、
列挙型の `DENY = 2` には要らず、コードはどちらかを言わない。
一番役に立った 1 文(要修正 2 件を出したのはこれ)を、それでも retire した。

**副産物** 設定の罠 3 つ。**(1)** ESLint はルールオプションをブロック間でマージせず
**最後が勝つ**(`hooks/**` 用のブロックが他 7 ルールをそこから消していた。`--dry-run` の件数で気付いた)。
**(2)** ファイル glob は鈍い(`hooks/**` がフックの**テストハーネス**を拾った)。
**(3)** キャッシュキーはノードのテキストなので、**コメントを証拠にするルールはコメントを直しても無効化されない**。

## 27. otel の異常検知のトリアージ

**試したこと** 6 サービスの Web アプリを 16 通りに壊して OTLP のスパンとログを出し、
**検知は決定的なコード**(閾値と倍率)、**トリアージを Jev** に投げる。
state の作り方を 7 通り試し、質問は全部同じ。ラベルは 2 種類で、
`cause` は構成上・`severity` は**実測**(ユーザー向けリクエストのうち 5xx か SLO 超過の割合)。

**結果** 304 判定・**1.64M トークン・$0.069**、1 窓 **208 ms**。

| | severity 一致 | 誤ページ | 見逃し | cause |
| --- | --- | --- | --- | --- |
| 規則(エラー率だけ) | 15/16 | 0 | 1 | 8/10 |
| 規則(+ SLO 超過率) | **16/16** | **0** | **0** | 8/10 |
| Jev(集計) | 19/48 | 9 | 0 | **24/30** |
| Jev(集計・ログ本文なし) | 24/48 | 6 | 0 | 21/30 |
| Jev(生ログ・うるさい順) | 18/48 | **27** | 0 | 21/30 |
| Jev(生ログ・均等) | 24/48 | 6 | 0 | 21/30 |
| Jev(集計 + 生ログ) | 18/48 | 16 | 0 | 18/30 |

**わかったこと**

- **severity は算術が完勝する。** 「人を起こすか」は測れる量の関数なので、
  1 行の規則が 16/16・誤ページ 0・見逃し 0。Jev は見逃し 0 だが誤ページ 6〜27。
  → **順序のある答えが測れる量なら、聞くのではなく計算する。**
- **cause は判断が残る。ただし「ログ本文が原因を名乗っていないとき」だけ。**
  本文を伏せると runbook の正規表現は **8/10 → 4/10**、Jev は **24/30 → 21/30**。
  情報を抜いたときに何が残るかがその層の正味の貢献
  ([16](#16-eslint-の合否を実装を伏せて当てる) と同じ測り方)。
- **state は大きさではなく選び方。** 同じ件数・同じトークン数の生ログで、
  **うるさい順に選ぶと誤ページ 27 件・均等に選ぶと 6 件**(4.5 倍)。
  [21](#21-eslint-plugin-jev) の「文脈は judgment を穏やかにする」の逆向きで、
  **文脈が偏っていれば judgment は険しくなる**。
- **集計が生ログより安くて強い。** 2026 トークンで cause 24/30、
  生ログを足して 7441 トークンで 18/30。
- **観測データは 1 リクエストに入らない。** 5 分の窓が **16/16 で state 上限超過**、
  `log_flood` は 15,200 件のうち 107 件だけ送られる。
  そして **JSON の telemetry は 1 トークン ≒ 2.4 文字**(散文の 4 で見積もって全窓 400)。
- **「何も問題ない」は出てこない。** 逃げ道を別 noul にしても健全な 18 窓で発火 0〜4 件。
  異常検知では**沈黙は算術にしか担保できない**。
- **アラート文を state に入れるかは設計判断。** 入れると誤ページ 6 → 9 に増え、
  cause は 20 → 24 に良くなる([08](#08-skill-suggestion-cookbook-の追試) の
  「提案は助言として渡す」がそのまま)。
- **3 draw でページ判定が割れた窓は全 arm 0/16**([25](#25-閾値を当てはめる部品) の再確認)。

**効かなかったこと** [18](#18-claude-code-の-pretooluse-hook) の「保守側を採る」。
`page` に `user_visible` の同意を要求しても**1 件も変わらない**(ページする時は必ず同意している)。
そして `max(規則, Jev)` は Jev の過剰エスカレーションを引き継ぐだけだった。

**限界** シミュレータなのでログ本文が実物より診断的で、**runbook の成績は実物より高い**はず。
SLO ラベルは 4xx を数えないので、`auth_misconfig`(33% のログインが 401)は
実測 noise・人間なら ticket で、**この 1 窓は Jev に不利**。

## 28. 英語と日本語が同じことを言っているか

**試したこと** **このリポジトリの実物の対訳**(`eslint-plugin-jev` の
`README.md` / `README.ja.md`、1,244 行)を見出しの順で 24 セクションに整列させ、
400 文字以上の 20 対を使う。ラベルは 2 種類で、
実物の 20 対が `equivalent`(**faithful という仮定**)、
日本語側への決定的な文字列編集 8 種が `diverged`(構成上)。
8 種のうち 2 種(言い換え・箇条書きの段落化)は**翻訳者がやって良いこと**で `equivalent`。

**結果**

| | 正解 | 誤検出 | 見逃し |
| --- | --- | --- | --- |
| diff(測定値・識別子・長さ比) | 26/30 | **0** | 4(否定・追加・hedge ×2) |
| 判断(セクション対だけ) | **84/90** | **0** | 6(hedge ×2 の 3 draw) |
| 判断(+ 文書全体) | 26/30 | 0 | 4(**omission と terminology を落とす**) |

section arm は **2,101 トークン・181 ms・1 対 $0.00009**。文書全体の arm は 25,719 トークン。

**わかったこと**

- **層が割れる。** 数値と `識別子` は**差分の対象**で、規則が誤検出 0 で拾う。
  規則が落とすのは**否定の反転・無い約束の追加・hedge の強化**という「文の意味」だけ。
  判断はそのうち 2 つ(否定 2.69・追加 1.96)を埋める。**合わせて 8 クラス中 6。**
- **実物の翻訳には 1 件も発火しない**(0/60・平均 0.11)。
  言い換えも段落化も 0/3 なので、**翻訳者の裁量を違反として出さない**。
- **原子述語が「どこがどう違うか」まで返す。** omission で `omits` 0.95、
  addition で `adds` 0.98、数値差で `numbers_agree` 0.03。1 リクエストで場所が分かる。
- **文脈は答えの隠れ場所を与える。** 文書全体を state に足すと
  omission が **1.84 → 0.57**、terminology が **2.12 → 1.20**(トークンは 12 倍)。
  消えた文は文書のどこかにまだあるし、入れ替えた識別子も両方実在する。
  [21](#21-eslint-plugin-jev) の「文脈は精度を上げない」に**機構**が付いた形 ——
  「この範囲に無い」を聞くとき、範囲を広げるのは**質問を変えている**。
- **正書法が規則の敵。** 英語 "one request" 対 日本語「1 リクエスト」で、
  生の桁 diff は faithful な 20 対のうち **14 対**を誤検出する。
  綴られた数の正規化でも残り、**「測定値」に限って初めて誤検出 0**。
- **hedge の強化が盲点。** 「起こりうる」→「必ず起きる」が **0.43 で見逃し**。
  数値・否定・追加・省略は拾えるのに、確率的な保証が決定的な保証に変わるのは拾えない。
- **そして実物の対訳は faithful だった。** 20 セクション全部が 0.02〜0.31 で、
  **長さ比 0.49〜0.82 は省略ではなく日本語の圧縮**(上位を読んで確認)。
  行数差(697 対 547)から drift を疑った最初の見込みは外れ。

**効かなかったこと(そして訂正したこと)** `claim_strength` の 1 稿目
「ほとんど関係ありません」→「すべて関係ありません」は 0.15 で見逃しだが、
**日本語ではどちらも「関係ない」でモデルが正しい** ——
[24](#24-まだ存在しないルールを自然言語で書く) の「間違った質問への正しい答え」の
ラベル版。`number_changed` の 1 稿目も**例の lint 出力の行番号**を書き換えていて、
拾われはしたが誰も困らない差異だった。**両方の稿を記録に残してある。**

## 29. コンテキストに入らない skill カタログから選ぶ

**試したこと** [mizchi/skills](https://github.com/mizchi/skills) の
`skill-selector/references/catalog.md` —— 人が手で選別した実物の
**98 行 / 23 セクション**のカタログを相手に、14 プロジェクト × 74 skill =
**1,036 判断**を 7 通りの聞き方で取る。ラベルはカタログ自身のティア凡例
(T0 常に / T1 シグナル在り / T2 頼まれたら / T3 散文で触れる / T4 代替を挙げる)
から機械的に出し、判断に渡すのはプロジェクト側だけ ——
ファイルツリー・`CLAUDE.md` の行・依頼 1 段落。
skill 側はその skill 自身の `description:`(75 行で 22,583 文字 ≈ 9,410 トークン)。

**結果**

| arm | 1 リクエストの問数 | AP(T0 を落として) | リクエスト | 1 プロジェクトの入力トークン |
| --- | --- | --- | --- | --- |
| 語彙の重なり(無料) | — | 0.44 | 0 | 0 |
| `fanout`(いま必要か) | 74 | **0.55** | 14 | 20,019 |
| `applies`(対象領域か) | 74 | 0.53 | 14 | 21,203 |
| `batch10` | 10 | 0.53 | 112 | 24,089 |
| `solo`(skill は質問) | 1 | 0.53 | 1,036 | 51,295 |
| `single`(skill は state) | 1 | **0.46** | 1,036 | 50,851 |
| `usewhen`(カタログの 1 行) | 74 | **0.56** | 14 | 17,280 |
| `noul`(yes/no) | 74 | 0.54 | 14 | 17,133 |

**わかったこと**

**1. ファン・アウトの幅は「安い」ではなく「同じ答え」。**
74 問 1 リクエスト対 1 問 1,036 リクエストで、
**0.25 以内に 99.8% 一致・レベル一致 97%・平均差 0.032**。
[21](#21-eslint-plugin-jev) はバッチが値段としてほぼ無料だと測った。
ここで足せるのは**答えが動かない**ことと、
狭めると 2.4 倍払って同じ答えになることです。
「コンテキストに入らないカタログ」は state に積むのではなく**質問にする**。

**2. ただし置き場所は効く。** 同じ幅 1 で skill を state に移すと
一致は 53%、AP 0.53 → 0.46。
[21](#21-eslint-plugin-jev) [28](#28-英語と日本語が同じことを言っているか) の
「state に足すと甘くなる」と同じ向きだが、ここでは足さずに**移している**だけ。

**3. 方針は判断に聞くものではない。** T0 の 2 行は全 14 プロジェクトで正例 ——
**135 件の 21%** —— で、description には「常に入れる」と書けない。
カタログのティア列をコードで適用するだけで AP 0.41 → **0.70**。
判断に聞くと平均順位は 74 件中 41〜53 位。

**4. ラベルを何が決めるかで勝つ selector が変わる。**
正例を `policy` 28・`files` 77(シグナルがファイル名)・`ask` 30(依頼文だけ)に
分解すると、平均順位は `ask` で判断 **6.7 位**・重なり 29.0 位、
`files` で重なり **20.8 位**・判断 27.7〜31.3 位。
そして質問の高度も証拠に合わせるべきで、
`ask` は「いま必要か」、`files` は「対象領域か」のほうが良い。

**5. 人が書いた 1 行が skill 自身の description に勝つ。**
`Use when` 列に差し替えると AP 0.53 → 0.56、P@k 0.43 → 0.51、
文字数は 22,168 → **7,311**。形が違うからで、
`description:` は会話中の発火条件、`Use when` はプロジェクトの属性で書かれている。

**効かなかったこと(そして訂正したこと)** 2 つの selector を
**重み 1 つで混ぜる**のは失敗した。in-sample 0.42 がプロジェクト単位の
ホールドアウトで **0.35** —— 単独の両方(0.42 / 0.41)より悪く、
当てた重みは fold 間で 0.00〜1.00 に振れる。
[25](#25-閾値を当てはめる部品) が閾値について測ったことが混合重みでも起きる。
代わりに**経路**(カタログだけで決まる)にすると 0.70 になるが、
正直に T0 を落とすと 0.53 で**判断だけの 0.55 に届かない** ——
つまり跳ね上がりはほぼ全部ティア列で、`files` を grep に回す部分は元が取れていない。

**限界** プロジェクトは合成(シグナルの具体化)で、ラベルの粗さも残る ——
Node / TypeScript セクションの T1 5 行は `package.json` があれば全部 `want` だが、
各行の `Use when` はもっと細い。`dup-hunt` で
`check-similarity-ts` 2.93 対 `-mbt` 0.40 / `-py` 0.38 / `-rs` 0.27 と
**モデルは言語の合う 2 つだけを採り、そちらが正しい**。
落とした 83 件のうち 28 件は T0、45 件はこの粗さで、
残り 10 件も読むと同じ形(移植していないのに移植 skill、
`.github/` が無いのに CD skill)。全 arm で $0.1187。

## 30. 461 個の実在 skill から選ぶ道具

**試したこと** [29](#29-コンテキストに入らない-skill-カタログから選ぶ) の
正直な限界(74 skill・9,410 トークンは**まだ全部入る**)を潰す。
ロスターは **461 個**で、出どころは mizchi 自身の `skill-finder` が
探索順に挙げている先(anthropics/skills, obra/superpowers,
wshobson/agents, VoltAgent の subagent 群)と mizchi のリポジトリ群 ——
全部実在の公開 skill / subagent。ラベルは
[29](#29-コンテキストに入らない-skill-カタログから選ぶ) のまま
(カタログの 74 件が対象、残り **387 件は distractor**)。
そして道具として `skill-pick` を書き、実在の 2 リポジトリで回す。

**結果**

| | 1 問の入力トークン | 1 リクエストに入る問数 |
| --- | --- | --- |
| 通常の fan-out(criteria を 1 問ごとに繰り返す) | 251 | **260**(280 で 400) |
| criteria を state に 1 回だけ置く | 118 | **520**(560 で 400) |

| 構成 | recall | P@12 | リクエスト | $/プロジェクト |
| --- | --- | --- | --- | --- |
| 無作為に 60 件(対照) | 22% | 0.08 | 1 | $0.0006 |
| 語彙の重なりで 60 件 | 63% | 0.25 | 1 | $0.0006 |
| 前段なし(461 件) | 100% | 0.19 | 2 | $0.0047 |
| **重なり 60 件 + terse + 水準引き** | 63% | **0.30** | 1 | **$0.0003** |

**わかったこと**

**1. 「入らない」は大きさではなく書き方だった。** 1 問が運ぶ 251 トークンのうち
description は 131 トークンで、残りは**全問で同一の**タスク文と criteria。
state に 1 回置くだけで **461 問が 1 リクエスト 54,284 トークンに入り**、
答えはレベル一致 95%・平均差 0.057。**上限は質問数ではなくトークンなので、
同一文字列を質問から外すと上限そのものが 2 倍になる。**

**2. 前段の値打ちは recall ではなく precision。** k を増やすと
recall は 63% → 100% に上がるのに、P@12 は **0.25 → 0.19 に下がる**。
`worst`(欲しい行の最下位)は 50 位 → 322 位。

**3. 理由は distractor が正しいから。** 上位を読むと
`deployment-engineer` 3.00(ECS + Actions のプロジェクト)、
`dependency-manager` 3.00(`pnpm outdated` が溜まったプロジェクト)、
`test-automator` 3.00(フレーキー)—— **どれも当てはまる**。
`no` なのは「mizchi が curate していない」から。
2.5 以上を付けた割合はカタログ行 5% 対 distractor 2% で、
判断はカタログ行を 2.5 倍好むのに**母数が 5 倍あるので負ける**。
→ **curate されていないプールでは「候補を増やす」は「選択が良くなる」ではない。**

**4. 「どこでも高い」を引くと直る。** skill ごとの
**他 13 プロジェクトでの平均**を引くだけで、全件で AP 0.19 → **0.29**、
P@12 0.19 → 0.23。プールが大きいほど効く。判断に対する IDF。
水準の高い順トップ 8 のうち 7 件が distractor で、
唯一のカタログ行は [29](#29-コンテキストに入らない-skill-カタログから選ぶ) が
「5 プロジェクトで誤検出」と名指しした `security-expert`。

**5. 1 回測れば設計は何度でも試せる。** 幅で答えが動かないので
(ここでも再確認: 60 問 対 182 問でレベル一致 97%・0.25 以内 100%)、
ロスター全体を 1 回測った記録から**評価ループ 10 行が追加リクエスト 0 で出る**。

**効かなかったこと** IDF を 2 乗して「同じ語彙で書かれた 183 件の agent」を
強く割り引く版は P@12 +0.01・recall 同じで、**ほぼ無差別**。
description の第 1 文だけに当てる版は recall の天井が 67%(全文なら 85%)で、
**効く語は description の後ろにもある**。
そして無料の前段には**天井がある** —— 語彙の重なりは k をいくら増やしても
85% で止まり、欲しい行の 15% はプロジェクト文と語彙を 1 つも共有していない。

**限界** 387 件の distractor は「カタログに無い」で `no` にしているので、
P@12 の絶対値は「mizchi の curate した提案をどれだけ再現したか」であって
「良い提案か」ではない。実在 2 リポジトリの出力は読んだ ——
`jev-playground` の上位 8 件で正しいのは 3 件
(`justfile`, `moonbit-practice`, `moonbit-js-binding`)、
`similarity` は 1 位 `rust-engineer`(正しいがカタログ外)・
2 位が**そのリポジトリ自身が配る** `check-similarity-rs` で言語まで合っている。
全 arm で $0.1076。

## 31. 文書化されたゲートは聞く方が良いのか組み立てる方が良いのか

**試したこと** [multi-agent-orchestration](https://github.com/mizchi/skills/tree/main/multi-agent-orchestration)
は「判断しろ」ではなく**決定手続き**を書いている ——
`Go multi only if (1) or (2) holds and (4) is positive` という
4 つの名前つき条件上のブール式で、しかも
**`3 is not a reason to spawn.` が太字**。
38 シナリオ(うち 7 件は skill 自身の "Common mistakes" 表の全行、
4 件は条件 3 を規則に入れると答えが変わるように作ったもの)で、
同じ決定を **5 通りに読んで**比べた。
ラベルは skill の文そのままで、シナリオが 4 つの事実を宣言し、
本文はその事実を名前を出さずに述べる。

**結果**

| 読み方 | 正解 | | 誤りの向き(過剰 / 過少) |
| --- | --- | --- | --- |
| そのまま聞く(コストを先に述べる) | 22/38 | 58% | **+0 / −16** |
| そのまま聞く(何も述べない) | 30/38 | 79% | +4 / −4 |
| 組み立て `(1\|2)&4` | 30/38 | 79% | +2 / −6 |
| 組み立て `(1\|2\|3)&4` | 26/38 | 68% | +6 / −6 |
| 逃げ道 noul の反転 | 30/38 | 79% | +4 / −4 |
| キーワード(無料) | 17/38 | 45% | 罠 7 件中 5 件で落ちる |

**わかったこと**

**1. 組み立てても良くならない —— 同点。** 30/38 対 30/38 で、
**この実験の最初の仮説は外れた**。[07](#07-confidence-でエスカレーションする二層構成) で
二層構成の経済性が出なかったのと同じ形。
分解の値打ちは正解率ではなく **(a) 誤りの向きを選べること**
(組み立ては +2/−6 で保守的、素直に聞くのは +4/−4 で均衡)と
**(b) 4 つの原子が答えの理由になること**だった。

**2. 効いたのは質問の枠組みで、21 ポイント。** 同じ決定・同じ state・
同じ 1 リクエストで、**第 2 ワーカーのコストを先に述べると 58%**、
消すと **79%**。しかも述べた版の誤り 16 件は**全部「分けない」方向**。
種類ごとに割ると形が見える ——
コストを述べた版は「分けない」側で 6/7・6/6 と最良、
**分けるべき 22 件では 6/22**。
→ **あれは正解率の指標ではなく保守性のダイヤル。**

**3. 太字の 1 文は 4/4 対 0/4。** 条件 3 を規則に入れると、
原子が全部正しいまま((3) 0.89〜0.97、(1) 0.13〜0.20)
**4 件を全部落とす**。
[28](#28-英語と日本語が同じことを言っているか) や
[29](#29-コンテキストに入らない-skill-カタログから選ぶ) の
「ラベルが粗いとモデルの正解が誤りに見える」の**合成側の版**。

**4. 表 8 行をそのまま choice の criteria にすると 22/22。**
パターン同士の取り違えは 0 件で、skill が自分で名指しする 3 つの混同
(handoff 対 agent-as-tool、supervisor 対 dynamic DAG、fan-out 対 debate)も
起きない。漏れるのは「そもそも分けない」側だけ。

**5. 逃げ道は別の noul でなければならない。** 外すと分けるべきでない 16 件が
sequential 9 / fanout 5 / debate 2 に押し込まれ、
**confidence では見分けられない**(本物 0.87 対 強制 0.82、**AUC 0.601**)。
[17 §3](#17-タスクランナーから正しいタスクを選ぶ) の測り直しと値段。

**6. ばらつきは決定に届いていない。** 3 回引いてシナリオ内 sd 0.011〜0.014、
**0.5 をまたぐのは 38 件中 0〜1 件**、トポロジーは 0/38 で 1 度も変わらない。
[29](#29-コンテキストに入らない-skill-カタログから選ぶ) と
[30](#30-461-個の実在-skill-から選ぶ道具) が「未測定」と書いた項目。
ただしゼロではなく、`composed` は収集 1 回目 31/38・2 回目 30/38 で、
**その 1 件差はここで測ったまたぎ 1 件と整合する**。

**効かなかったこと(そして訂正したこと)** 「ブール式が書いてあるなら
分解した方が良いはず」という前提で始めて、**同点だった**。
そして条件 4 は字義通り読むと条件 1・2 から独立でなく
(並行にできる部分が無ければ「もう 1 人の利得」は 0)、
ゲートが `(1 or 2)` に潰れる —— **規模の事実として読み替えた**のが
本文で唯一の解釈。

**限界** 38 シナリオは私が書いた(4 つの事実はシナリオが宣言し、
ゲートは skill の文なのでラベルは私の意見ではないが、難易度は私が決めている)。
太字の 1 文の値打ちは **4 件**、罠は 7 件、分けるべきものは 22 件で、
どのセルも 4〜22 件ぶんの自信しかない。
トポロジーの 22/22 は上限に当たっているので、
**この corpus では書き方の比較ができない**。
152 リクエスト / $0.0064 / 平均 174 ms。

## 32. パッチはコードが作り、判断は並べるだけの修復ループ

**試したこと** TODO の「決定的なワークフローを生成してコーディングエージェントにする」を
やろうとしたら、**制約のほうが先に効いた** —— Jev は文字列を返さないので
**パッチを書けない**。なので形はこうなる:
`変異させる (コード) → 並べる (Jev) → 当てる (コード) → テストする (コード)`。
12〜28 行の JavaScript モジュール 21 件にバグを植え(全部赤から始まる)、
25 個の構文規則で 305 個の候補編集を機械的に生成し、
**どれが本当に緑にするかは 305 回 `node --test` を走らせて記録**。
ラベルは終了コードで、手書きのものは 1 つも無い。

**結果**

| 順序 | 平均テスト実行 | 一発 | リクエスト | 1 タスクのトークン |
| --- | --- | --- | --- | --- |
| 生成順(判断なし) | 3.00 | 5/16 | 0 | 0 |
| 無作為 | 7.69 | 2/16 | 0 | 0 |
| 失敗出力との語彙の重なり | 3.88 | 3/16 | 0 | 0 |
| `score`(候補ごとに 1 問) | **1.00** | **16/16** | 21 | 3,254 |
| `choice`(全候補で 1 問) | **1.00** | **16/16** | 21 | **1,554** |
| `noul`(候補ごとに 1 問) | 1.06 | 15/16 | 21 | 2,688 |

**わかったこと**

**1. 文字列を返せないモデルでも修復ループは書ける。**
判断が 1 か所に閉じ、残りは全部決定的で再現できる。
`--verify` で本物のプロセスに当て直しても **16/16 が 1 回で緑**。

**2. 一番安い形が一番良い。** `choice` の答えは
**全選択肢の確率**を持っているので、質問 1 つで完全な順序が出る。
候補が 32 個でも 1 問。トークンは候補ごとに聞く形の**半分以下**で結果は同じ。
[29 §4](#29-コンテキストに入らない-skill-カタログから選ぶ) のファン・アウトが
このリポジトリの定番だったが、**選択肢が相互排他なら `choice` 1 つのほうが安い**。

**3. 終了コードのラベルは gap を正にする。** 「そもそも直る候補が
入っているか」を上位値で見ると、`score` は解ける 16 件の 2.70 ±0.31 対
解けない 5 件の 0.99 ±0.61 で **gap +0.03・AUC 1.000**。
このリポジトリで gap が正になったのは初めて
([24](#24-まだ存在しないルールを自然言語で書く)
[25](#25-閾値を当てはめる部品)
[29](#29-コンテキストに入らない-skill-カタログから選ぶ)
[31](#31-文書化されたゲートは聞く方が良いのか組み立てる方が良いのか) は全部負)。

**4. ただし AUC 1.000 は閾値ではない。** gap 0.03 に対し、
同じ質問を 2 回引いたときの上位値の動きは**平均 0.043・最大 0.210**。
**次の draw が跨ぐ。**
[25](#25-閾値を当てはめる部品) の「draw より薄いマージンはマージンではない」の
一番きれいな実例。`noul` は gap 0.08 対 draw 0.018 で、**こちらは使える**かもしれない。
→ **順序は `choice`、「入っているか」は `noul`。** 別の質問。

**5. 「どれも駄目」を choice の確率で拾ってはいけない。**
確率は和が 1 なので全滅のときも誰かが高くなる —— gap −0.04・AUC 0.900。
同じことを noul に聞くと gap 0.08・AUC 1.000。
[17 §3](#17-タスクランナーから正しいタスクを選ぶ) の
「逃げ道は別の問いにする」が、確率の正規化という理由つきで出てくる。

**効かなかったこと(そして訂正したこと)** 無料の基準線を 2 つ書いて、
**どちらも予想を外した**。失敗出力との語彙の重なりは
生成順より**悪い**(3.88 対 3.00)—— 失敗出力はどの*関数*が壊れているかは
教えるが、どの*編集*が正しいかは教えない。
そして生成順が 3.00(無作為 7.69)だったのは、
カタログの規則を「よくあるバグを直すもの」から書いた結果
**生成順そのものが事前分布になっていた**から ——
`src/mutate.ts` のコメントに「賢い順序ではない」と書いてあったのを、
測って訂正した。

**限界** カタログは fix を含むように作った(規則を 5 個足して 1 個広げた)ので、
**これは修復システムではなく並べ替えの測定**。
"16/16 solved" は探索空間について何も言っていない。
バグは全部 1 行の構文レベルの誤りで、実際の分布ではない。
§4 の n は 16 と 5。繰り返しは 2 回なので draw の幅は下限。
そして**緑になった編集が意図した修正とは限らない** ——
`normalise` は 3 通りで緑になり、そのうち 1 つは配列の末尾を越えて読むのに
`undefined > best` が偽なので通る overfitting だった
(`score` はそれを 0.66 で 3 位に置いた)。
1,830 判断 / 126 リクエスト / $0.0132。
