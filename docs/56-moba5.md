# 56. 本格的な 5v5 MOBA と、採点できるベンチマーク

[02](02-moba.md) の 3v3 プロトタイプを**残したまま**、ジャンルが実際に遊ばれているサイズと
機構まで広げた別パッケージ(`moba5/`, `cmd/moba5`)を作り、
**「勝てるか」ではなく「どれだけ正しいか」を測れる**ようにした。

再現:

```bash
moon run --target native cmd/moba5 -- --bench --dry        # 採点表と床(API 不要)
moon run --target native cmd/moba5 -- --bench --repeat 5   # 同じ 124 問を 5 回、採点
moon run --target native cmd/moba5 -- --arena              # 5v5 集団戦の総当たり(API 不要)
moon run --target native cmd/moba5 -- --tournament         # 全試合の総当たり(API 不要)
moon run --target native cmd/moba5 -- --a jev --b smart --games 2 --max-ticks 30
moon run --target native cmd/moba5 -- --coherence --from-answers moba5/runs/wording.jsonl
                                                           # fight と retreat の truth を並べる(API 不要)
moon run --target native cmd/moba5 -- --from-answers moba5/runs/wording.jsonl
                                                           # 2 択と 3 択の比較を記録から再生(API 不要)
moon run --target native cmd/moba5 -- --from-answers moba5/runs/descriptions.jsonl
                                                           # 3 択を 4 通りの説明文で聞いた記録を再生(API 不要)
moon run --target native cmd/moba5 -- --wording --repeat 3 --answers moba5/runs/wording.jsonl
                                                           # その記録を取り直す(96 リクエスト、$0.02)
moon run --target native cmd/moba5 -- --descriptions --repeat 3 --answers moba5/runs/descriptions.jsonl
                                                           # 説明文 4 通りを取り直す(192 リクエスト、$0.04)
moon test --target native -p moba5                         # 53 本(API 不要)
```

3v3 側(`moba/`, `cmd/moba`, [02](02-moba.md) [10](10-jev-vs-jev.md)
[11](11-synergy.md) [12](12-comeback.md))は**1 行も変えていない**。

---

## 1. 何が足りなかったか

[02 §4](02-moba.md) が自分で挙げた限界は 4 つで、そのうち 3 つはサイズと機構の話だった:

- **相手が弱い。** 受け身のレーン bot 1 種しかなく、同じ bot 同士は毎回引き分けだった。
- **戦場の霧を活かしているか未検証。** `enemies_last_known` を state に入れてはいたが、
  **その答えが当たっているかを採点していなかった。**
- **1 tick = 1 手で、射程もスキルも無い**(4 つ目は決着 tick のばらつきの少なさ)。

そして**そこに書かれていない 4 つ目**がレポート全体の形を決めていた ——
**測れるものが勝敗しかなかった。** 6-0 は「この bot より強い」であって
「MOBA が上手い」ではないし、bot を書き換えれば数字が動く。
**どの判断が間違っていたかは言えない。**
[02 §4](02-moba.md) はこれを「スクリプト bot は強くない」という
**相手の問題**として書いていたが、**相手を強くしても解決しない**。

5v5 にする理由はそこにある。**観測 1 個に対して判断が 5 個**になるのは
[fan-out](00-api-notes.md#speculative-fan-out) の比率が上がるだけだが、
**機構を増やすと、シミュレータ自身が答えを持つ問いが増える。**
「この集団戦は勝てるか」は、**ルールが決定的なら再生してみれば分かる。**

## 2. 増やした機構と、それぞれが作る判断

| 機構 | 作られる判断 |
| --- | --- |
| **3 レーン + 両サイドのジャングル + 川**(23 ノード) | どこに居るか。川の 2 ノードは**どちらの陣地でもない**ので、寄れば必ずレーンを空ける |
| **レベルと経験値**(1〜6) | 誰にファームを渡すか。今の自分は相手より強いのか |
| **アイテム 5 種**(装備枠 3) | 相手が実際に出している damage type に対して何を買うか |
| **固有スキル + クールダウン** | **いつ使うか。**スタンは damage 0 で、相手の 1 ターンだけを消す |
| **射程** | 遠距離は隣ノードを**半分のダメージで殴り、何も返ってこない** |
| **ドラゴン / バロン** | 永続の小さな buff か、短時間の大きな buff か。両方レーンの外 |
| **ミニオンの押し合い** | **Farm がレーンを押す。**押していないレーンのタワーは殴り返してくる |
| **ワード** | 見えていない場所に、1 ターン払って視界を置く |
| **タワー 2 段 + ネクサス** | ネクサスは**1 レーンが完全に開通するまで**殴れない |

構造として一番効いたのは**ミニオンの規則**で、これは 1 行で書ける:

> **自陣のウェーブが居るレーンのタワーは、その champion を撃たない。**
> 撃つ対象がミニオンになるから。

これで「タワーに単騎で立つ」は必ず負ける取引になり、
「まず Farm でウェーブを押してから殴る」が正しい手順になる。
**マップが飾りでなくなる。** そしてミニオンは**タワーしか割れない**
(ネクサスには触らない)ので、**試合を終わらせるのは必ず champion** になる。

## 3. スループット: 3v3 より良くなった

`--games 2 --max-ticks 30` を 3 組(`jev-latest`、2026-09):

| | リクエスト | 決定したキャラ行動 | **行動/リクエスト** | ms/リクエスト | **ms/キャラ判断** |
| --- | --- | --- | --- | --- | --- |
| A=jev vs smart | 60 | 300 | **5.00** | 267 | **53** |
| A=smart vs B=jev | 60 | 300 | **5.00** | 262 | **52** |
| A=jev vs scripted | 60 | 274 | **4.57** | 231 | **51** |
| 合計 | 180 | 874 | **4.86** | 253 | **52** |
| *(参考)* [02](02-moba.md) の 3v3 | 79 | 218 | 2.76 | 210 | 76 |

**キャラ 1 体あたり 52 ms。** 3v3 の 76 ms より速い ——
選択肢が 5 倍に増えても、**state を 1 回しか送らないので 1 体あたりは下がる**。
入力は 1 試合(30 tick)で約 20 万トークン、**$0.008/試合**。

**不正な手は 874 判断すべてで 0 件。** これは [02 §2](02-moba.md) の主張の再検証で、
**行動の種類が 6 → 12 に増え、1 体あたりの選択肢が 20 前後になっても成立する。**
criteria がその場の合法手そのものなので、**不正手は表現できない。**

そして**新しい機構を実際に使っている**(行動の内訳、6 試合合計):
`farm` 472 / `poke` 133 / `objective` 67 / `hold` 67 / `ward` 52 /
`ability` 32 / `blink` 19 / `attack` 19 / `move` 10 / `recall` 3 / `structure` 0。
**poke 133 件**は 3v3 に存在しなかった手で、**遠距離が居る編成で自然に選ばれている**。
そして **`structure` が 0 件**なのは所見で、6 節に戻ってくる。

## 4. 採点できるベンチマーク

**31 シナリオに 124 問**、答えは**全部シミュレータが出す**。
1 シナリオ = 1 リクエスト(state 1 つに複数問)。

答えの出し方を 3 段階に分けて、**問ごとに明記した** ——
同じ強さのふりをさせないため:

| tier | 意味 |
| --- | --- |
| `rules` | **再生した。**集団戦を最後まで回した結果、ダイブを塔のダメージ込みで回した結果。異論の余地が無い |
| `arith` | ルールが定義する厳密な算術(塔の下で何 tick 耐えるか、チーム戦力、視界の外に何人居るか)。再生はしていないが判断でもない |
| `score` | `position_score` を**明示した horizon** で最大化する選択肢。**事実ではなく、明示した目的関数** |

`score` tier では**相手も強い側の baseline で動かす**(相手が何もしない前提でだけ
正しい macro の答えは答えではない)。**同点は同点として扱う**
(`truth_accepts`、`"a|b"` 形式)—— 選択肢を並べた順序を測ってしまわないため。
そして **`--repeat N` で同じ問いを N 回**聞く ——
モデルは確率的なので 1 回では差と引き分けが区別できず、
**自分で答えを変える問いの割合**が差の基準線になる
([37 §6](37-hermes.md) [41](41-versus.md) と同じ規律)。

### `fight` クラスは作り直した —— 手で選ばずに掃いて

前の版の `fight` は**偏っていて、数えたら分かった**:
**8 問中 7 問が「体の数が多い側が勝つ」**で、床の 0.88 はほぼそれだけ。
つまり**モデルの点数の大半は、モデルの要らない算術の点数**だった。

**手で差し替えると、私が期待した方に寄る。**だから掃いた ——
構成・レベル・体力・ノードの固定グリッド **540 通り**を全部 `simulate_fight` で
再生し、**体の数が結果を予測したかどうか**で 4 つのバケツに入れる:

| バケツ | 体が多い/同数 | 勝つ | 候補数 |
| --- | --- | --- | --- |
| `count_right_win` | yes | yes | 201 |
| `count_wrong_loss` | yes | **no** | 123 |
| `count_wrong_win` | **no** | yes | 26 |
| `count_right_loss` | no | no | 190 |

**各バケツから同数(4 問ずつ・計 16 問)取ると、
体を数える戦略はこのクラスで正確に 0.50**、
そして**「全部 yes と答える」も正確に 0.50** になる。
**どちらもテストで等式として固定してある**(`bench_wbtest.mbt`)——
バケツを 1 つ落として balance を装うことができないよう、
**4 つ全部がグリッドから到達可能なことも**同じテストが確かめる。

**一度目の掃きは別の偏り方をした。** グリッド順に「バケツが埋まるまで」取ると
**最初の構成ペアの中で 4 つ全部埋まってしまい、16 問が全部同じ 2 チーム**になった ——
体の数に対しては均衡で、それ以外については何も測らない。
いまは 2 パスで、**1 パス目は (構成ペア, ノード) ごとに 1 問まで**。
結果は **3 マッチアップ × 両サイド = 6 ペアリング**、mid_mid と riv_top の両方。
(`count_wrong_win` は候補が 26 しか無い最も細いバケツなので、
**4 問が全部 meta 対 glass_ad の変種**になっている —— これは限界。)

### `const` 列 —— 一番良い「定型答え」が何点取るか

床(状態を読むヒューリスティック)とは別に、
**そのクラスで一番多い正解を機械的に答えたら何点か**を出すようにした。
`fight` は構成上 0.50 だが、**入れた瞬間に別のクラスが引っかかった** ——
**`retreat` は 6 問中 5 問の正解が `walk_away`** で、
**「全部 walk_away」が 0.83** 取れていた。つまりゴム印とモデルを区別できない。
派生 fight シナリオに `retreat` を相乗りさせて **0.64** まで下げた
(それでもまだ高い。限界に書いた)。
**「どのクラスも定型答えで 5 分の 4 を超えられない」もテストにした。**

### `const` に対して読む

**これが `const` 列を足した理由。** 床でもランダムでもなく、
**ゴム印に対してどうか**:

| クラス | モデル | const | 読み |
| --- | --- | --- | --- |
| `lane` | **1.00** | 0.71 | **明確に上**。唯一、状態を読んでいると言える |
| `fight` | 0.63 | 0.50 | **16 問で 2 問分上** ≒ 標準誤差 1 個。**確定していない** |
| `power` | 0.54 | 0.48 | ほぼ同じ |
| `dive` / `macro` | 0.60 / 0.40 | 0.40 / 0.20 | 上だが各 5 問 |
| `ability` | 0.60 | 0.60 | **完全に同じ。**このクラスは何も区別していない |
| `fog` | 0.49 | 0.29 | 上。ただし 7 問 |
| `focus` | **0.26** | 0.32 | **下** |
| `retreat` | **0.41** | 0.64 | **下** |
| `item` | **0.17** | 0.50 | **下** |

**`lane` 以外に「ゴム印より明確に上」と言えるクラスは無い。**

### そして 13/16 —— 「負ける」と答えて「殴れ」と答える

`fight` の 0.63 の中身を見たら、**答えがほぼ定型**だった ——
**16 問中 14 問で `false`(勝てない)**。定型 `false` は構成上 0.50 なので、
**0.63 は「ゴム印 + 2 問」**でしかない。

**そして同じリクエストの、同じ局面についての `retreat` は 22 問中 21 問が
`fight_now`(殴れ)だった。** 並べると:

```
fight_1_count_right_win    fight true /false    retreat fight_now/fight_now
fight_5_count_wrong_loss   fight false/false    retreat walk_away/fight_now
fight_9_count_wrong_win    fight true /false    retreat walk_away/fight_now
...
13 of 16 derived fight states: answered "we do not win" AND "fight now"
```

**16 局面のうち 13 で、「この集団戦は勝てない」と答えた直後に
「いま殴れ」と答えている。** 同じ state・同じリクエスト・同じノードについて。

これは**正解率の問題ではなく整合性の問題**で、
**2 つの問いを同じリクエストに入れていなければ見えなかった** ——
[02](02-moba.md) が「観測 1 つに判断 N 個」を効率の話として始めた fan-out が、
**そのまま矛盾の検出器になっている。**
そして片方だけを測っていたら、
`fight` の 0.63 は「床を上回った」と読めてしまう。

### **その 13 は、モデル自身の周辺度数が強制していた**

**[TODO §1.12](../TODO.md) の切り分けを 2 つ走らせた**(どちらも API 不要、2.9 秒):

```
moon run --target native cmd/moba5 -- --coherence
```

**1. 真値の側で「勝てない ∧ 殴れ」が両立する頻度。**
同じ 16 局面について 2 つの truth を並べると:

- ルールが「outright には勝たない」と言うのは **8/16**(バケツ構成上ちょうど半分)。
- `position_score` が 8 tick 先で「殴る方が上」と言うのは **7/16**。
- **両方同時に正解になるのは 4 局面** —— `fight_13`〜`fight_16`、
  全部 `count_right_loss`(体の数でも負けると分かる側)。

**このレポートの初版はここを 6 と書いていた。手で数えた数字で、間違いだった** ——
いまは `coherence_rows()` が数え、
**その truth が `ask_fight` / `ask_retreat` のものと同一であることをテストが固定**している
(`Game::retreat_scores` を切り出したのはそのため。
真値のコピーが 2 つあると「truth が食い違う」が読めなくなる)。

**2. そして 13 は、比較する前に済んでいた数字だった:**

| | 「勝てない」 | 「殴れ」 | 両立 | 周辺度数が強制する下限 |
| --- | --- | --- | --- | --- |
| ルール | 8/16 | 7/16 | **4** | **0**(上限 7) |
| モデル(記録された 1 回) | 14/16 | 15/16 | **13** | **13** |

**14 + 15 − 16 = 13。** 16 局面で `false` を 14 回・`fight_now` を 15 回返したら、
**両立が 13 未満になる並べ方は存在しない。**
つまり **13 という数字は 2 つのゴム印の言い換え**で、
「整合性」について独立な証拠を 1 つも持っていない。
**ルール側の 4 は下限 0・上限 7 の内側なので、そちらは情報を持っている** ——
**同じ統計量が、一方では読めて他方では読めない。**

**3. それでも残るもの。** ルールが両立を許す局面は 4 つしか無いので、
**モデルの 13 組のうち少なくとも 9 組は、ルールが認めない組**
(緩い定義でも 10 組)。**符号検定** ——
このリポジトリの他の実験と同じ、discordant pair の正確両側検定
([43 §1a](43-finish.md) [53](53-fanout.md))—— では
食い違いは **9〜10 対 0〜1 の一方向で、p = 0.004〜0.012**。
範囲になるのは、記録された 1 回が `retreat` を**クラス合計でしか印字していない**から:
**唯一の `walk_away` がどの局面だったか分からない**。
`pairing_bounds` が**合計が許す並べ方を全部列挙**して両端を出し、
**どちらに置いても 0.05 の同じ側に落ちる**ことをテストが固定している
(合計同士が矛盾していたら `consistent: false` を返して、何も主張しない)。

**だから所見はこう書き直す** —— 「16 局面のうち 13 で矛盾した」ではなく:

> **`fight` に 14/16 で `false`、`retreat` に 15/16 で `fight_now` と答えた。
> その 2 つから両立 13 は自動的に出る。ルールが許すのは 4 なので
> 少なくとも 9 組は間違っている —— ただし
> どちらの問いの答えが間違っているのかは、この数字は言わない。**

### そして `fight` の閾値を動かしても、答えはそこに無かった

[TODO §1.12](../TODO.md) の 3 番目。「2 問が同じことを訊いていない」という読みが
正しいなら、**`fight` の閾値が厳しすぎる**のかもしれない ——
「outright に勝つ」を **「体の交換で負けない」(`a_deaths <= b_deaths`)** に緩めて、
同じ答えを両方の定義で採点した:

| 「勝つ」の定義 | 負ける局面 | 記録された 1 回 | ゴム印 | 差 |
| --- | --- | --- | --- | --- |
| outright に勝つ | 8/16 | **10/16** | 8/16 | **+2** |
| 体の交換で負けない | 6/16 | **8/16** | 6/16 | **+2** |

**2 つの定義は 16 局面のうち 14 で一致**し、
**ゴム印に対する差は両方とも +2。**
緩めて動いたのは点ではなく**基準線**(0.50 → 0.38)だけで、
**モデルのほぼ定型の `false` は「緩い問いへの正しい答え」でもない。**
**逃げ道はこの方向には無い。**

そして 10/16 の中身は指している ——
**モデルが `true` と答えた 2 問は両方 `count_wrong_win`
(体の数では負けるのに勝つ局面)で、両方正解。
体の数が当たる `count_right_win` の 4 問は全部外している。**
2 問と 4 問なので所見ではないが、**次に測るものはこの向き**。

### そして 3 択にしたら、モデルは自分でそう言った —— 73%

[TODO §1.12](../TODO.md) の 2 番目、**API が要る唯一の切り分け**。
`retreat` の選択肢が `fight_now` / `walk_away` の 2 択だと、
**「勝てないが殴るのが得」はどこにも置けない**。だから 3 択を並べた ——
`win_and_fight`(勝つから殴る)/ `lose_but_fight`(勝てないが殴る価値がある)/
`walk_away`。**オラクルは同じ**(同じ 2 つのスコア、同じ horizon)で、
**殴る側のラベルを `fight` の truth が決める**だけ。
だから 2 つの問いは構成上食い違えず、
**残りの差は全部モデルの答え**(`just replay-moba5-wording`)。

同じ 16 局面を、**1 回の中で両方の文言で聞く**(他の問いは同一、
違うのは 1 問だけ)。`--repeat 3`、96 リクエスト、**$0.02**:

| arm | run | 「勝てない」 | 殴る | 両立 | 周辺度数の下限 | retreat の答え |
| --- | --- | --- | --- | --- | --- | --- |

**選択肢を足してもゴム印はゴム印**だった。

**2. それでも、名前を与えたらモデルはそれを選んだ。**
同じリクエストの `fight` の答えと交差させると(48 答え = 16 局面 × 3 回):

| --- | --- | --- | --- |

  `lose_but_fight` を選んだ** —— 各 run で 10/14・11/14・9/13。
  **これは 2 択が粗かった**という読みで、**私の問いの側の問題**。
- **残り 11(27%)は `win_and_fight`** ——
  **同じリクエストで「勝てない」と言った直後に「勝つから殴る」**と答えた。
  **（ここで「文言に逃げ場はもう無い」と書いた。次の節でそれが消える。）**
- そして **「勝てる」と答えた 4 局面は 4/4 で `win_and_fight`** ——

**だから §1.12 の 2 通りの読みは、どちらも正しかった。割合が出た** ——
**73% は私の 2 択が粗かった分、27% は本当の矛盾。**

**3. ただし 3 択の正解率は下がった。** `retreat` 0.50 → **0.29**

`lose_but_fight` を 9〜11 回選んだのに、**truth は 4 局面しかない**。

**そして記録の側も直した。** `--wording --answers <file>` が

## 5. 戦場の霧: 初めて採点した ——「自信を持って外す」

[02 §6](02-moba.md) が次にやることとして挙げ、やらなかったのがこれ。
シミュレータは**見えていない敵がどこに居るか知っている**ので、
**試合中の毎 tick、無料で採点できる**(23 択)。

| 相手 | 見えない敵が居た tick | 正解 | 正解率 | 平均 confidence |
| --- | --- | --- | --- | --- |
| smart(jev が A) | 60 | 4 | **0.07** | 0.44 |
| smart(jev が B) | 54 | 1 | **0.02** | 0.43 |
| scripted(jev が A) | 25 | 9 | **0.36** | 0.56 |
| 合計 | 139 | 14 | **0.10** | — |

**ランダムは 1/23 = 0.043。** 0.10 はその 2 倍強だが、
**confidence 0.43〜0.56 はこの正解率に対して高い。**

[02 §3](02-moba.md) は同じ問い(当時 11 択)に 0.31〜0.58 が返るのを見て
**「情報がないときに自信を持たないのは望ましい」**と書いた。
**選択肢を 2 倍にして採点したら、confidence はほぼ同じで正解率は 0.10 だった。**
**採点していない confidence は、校正されているかどうかを言えない。**

**そして相手で 0.02 対 0.36 に分かれる。**
`scripted` はレーンに忠実なので**どこに居るか予測できる**が、
`smart` は集団で回るので**予測できない**。
**つまりこの数字の大半は相手の予測可能性の性質**で、
モデルの性質ではない —— [README の 33 番](README.md)
(「発言率は判断の性質ではなくコーパスの性質」)が別の題材で再現した形。
**霧の読みを 1 つの数字で報告するなら、相手を書かないと意味を持たない。**

ベンチマーク側の `fog` クラス(7 問・35 答え)は **0.49** で、
内訳は**「何人見えていないか」(数える問い)が高く、
「どのノードに居るか」(推論が要る問い)が低い**、という素直な分かれ方だった。

## 7. 編成: 集団戦に強い編成は、試合に強い編成ではない

`--arena`(1 ノードで 5v5、編成だけが変数)と
`--tournament`(全試合、policy を両側同じに固定)は**別の順位を出す**:

| comp | 前衛 | damage | CC | 回復 | 遠距離 | 集団戦 | **全試合(smart)** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| meta | yes | AD+AP | yes | yes | 3 | **12-0** (1 位) | 6-6 (**4 位**) |
| dive | yes | AD+AP | yes | yes | 1 | 10-2 (2 位) | 6-6 (5 位) |
| poke | yes | AD+AP | yes | yes | 3 | 8-4 (3 位) | 8-4 (2 位) |
| bruisers | yes | mono | yes | no | 0 | 6-6 (4 位) | **12-0** (**1 位**) |
| glass_ad | no | mono | no | no | 3 | 4-8 (5 位) | 7-5 (3 位) |
| glass_ap | no | mono | no | yes | 4 | 2-10 (6 位) | 0-12 (7 位) |
| classic | no | mono | no | no | 0 | 0-12 (7 位) | 3-9 (6 位) |

**`meta` は集団戦を 12-0 で勝って、試合では 4 位。**
**`bruisers`(前衛 5 枚、damage ほぼ無し)は集団戦 4 位で試合は 12-0。**
理由は機構から読める —— 前衛だけの編成は**攻城とレーンの圧力を耐える**ので、
**集団戦を捨てても構造物を先に割られない。**
[11](11-synergy.md) の「正しいシナジー」は**集団戦の話だった。**

そして `--draft`(生のステータスだけ渡して編成を選ばせる)は
**`meta` を選ぶ(conf 0.70)** —— **集団戦の正解で、試合の正解ではない。**
順位も集団戦側にほぼ合っている —— **1 位・2 位・7 位を正確に当て**、
残りは隣同士の入れ替え 2 組(`poke`↔`bruisers`、`glass_ad`↔`glass_ap`)だけ。
**モデルの答えは合っていて、私が当てさせた oracle が間違っていた。**
`--draft` は今のところ集団戦 oracle との比較なので、**そう書いてある。**

## 8. 環境を測ったら、環境にバグが 5 つ在った

**このプログラムの教訓([README の 35 番](README.md))が効いた場所。**
5v5 を「動いている」で済ませず、**不変条件をテストにした**ら 5 件出た。
どれも観察では見えず、**全部テストか対称性の検査で出た**:

1. **ノード名の表が 1 つずれていた。** `node_names` の並びが
   `adjacency` と定数(`RIV_TOP`/`RIV_BOT`)の前提とずれていて、
   **ログは「ドラゴンが riv_top に出現」と嘘を書いていた**(添字は正しいので挙動は正常)。
   observation に出る名前もずれるので、**モデルには嘘のマップが渡っていた。**
2. **マップは対称なのに、片側が無料で勝っていた。**
   A のジャングラーの初期位置が**バロン側**、B が**ドラゴン側**で、
   ドラゴンは tick 6・バロンは tick 24 に湧く ——
   **B は序盤の目標の隣から始まる。**mirror 戦は B がほぼ全勝した。
3. **そして直してもまだ B が勝った。** 原因は**隣接リストの並び順**。
   `a1_bot` から `b1_top` へは**自陣ベース経由でもレーン経由でも 6 hop** で、
   `step_toward` は同点を**リストの先に書いてある方**で割っていた ——
   A のリストは自陣側が先、B のリストは前方が先なので、
   **A の bot laner は tick 1 にレーンから後ろへ歩き出していた。**
   同点を「**同じ距離なら前に出る側**」で割る(`step_toward_prefer`)と、
   **7 編成中 5 編成で両サイドの結果が完全に鏡像**になった
   (勝者は 7/7 でサイドに依らない)。
4. **`Stun(1)` が何もしていなかった。** 着弾した tick の末尾で
   カウンタを減らしていたので、**1 tick のスタンは着弾と同時に切れていた。**
5. **ドラゴン 1 スタック(+7%)が 0 だった。** 整数除算で切り捨てていたので、
   攻撃力 15 未満の champion —— **序盤のほぼ全員** —— には効果が無かった。
   **マップの下半分が存在する理由が、序盤に登録されていなかった。**

2 と 3 は**勝率を無意味にする**種類のバグで、
**「A が勝った」の大半がサイドの話だった。**
今はマップの A↔B 対称性・両チームの初期位置・`step_toward` の同点処理が
**テストで固定してある**(`map_wbtest.mbt`)。

**ベンチマーク自身の不変条件もテストにした**(`bench_wbtest.mbt`):
正解が選択肢に入っていること、**選択肢の全部が正解ではないこと**、
問の名前がシナリオ内で一意(wire の key なので重複すると黙って 1 問落ちる)、
noul の正解が true/false 両方存在すること、
**床が全問正解でも全問不正解でもないこと**。
どれも欠けると**採点表は出るが意味を持たない。**

## 9. 正直な限界

- **`fight` の 0.63 は確定していない。** 定型 `false` が構成上 0.50 で、
  16 問での標準誤差が ±0.125 なので、**2 問分の差は誤差 1 個**。
  「上回った」と書けるだけの母数が無い。**閉じ方**は `FIGHT_PER_BUCKET` を
  上げるだけ(グリッドの最細バケツが 26 候補なので 6 まで伸ばせる)。
- **`count_wrong_win` バケツは候補が 26 しか無く、4 問全部が
  meta 対 glass_ad の変種**になっている。他の 3 バケツは 3 マッチアップに
  散っているので、**「体の数が間違っている側」だけ多様性が低い。**
- **`retreat` の `const` は 0.64、`lane` は 0.71** で、まだ高い。
  テストは「5 分の 4 を超えない」しか要求していないので、
  **このクラスは balance されてはいるが均衡ではない。**
- **`ability` はモデル・床・const が全部 0.60** で、
  **何も区別していないクラス**。5 問しか無い。
- **`score` tier の 5 問は事実ではない。** `position_score` の重み付けと
  horizon(8〜12 tick)を変えれば答えが変わり得る。**明示してあるので反論できる**、
  というのが提供できる最大限。そして **`retreat` はこの tier** なので、
  「負けると答えて殴れと答える」の後半は**私の目的関数に対する矛盾**であって
  ルールに対する矛盾ではない —— ただし
  **`fight` 側(`rules` tier)と食い違っていること自体は目的関数に依らない。**
  そして**「両立する 4 局面」も `RETREAT_HORIZON = 8` の性質**で、
  horizon を変えればこの 4 も動く。**`--coherence` は horizon を引数に取る
  `retreat_scores` を呼んでいるので、動かすのはコード 1 箇所。**
- ~~**整合性の側で足りないのは、記録の粒度。**~~ → **直した。**
  最初の `--coherence` はモデルの側を**クラス合計でしか持っていなかった**ので、
  `pairing_bounds` が並べ方を全部列挙して
  「結論が並べ方に依らない」を示す形にしてあった。
  いまは **`--wording --answers` が問ごとに 1 行**書き、
  **`--coherence --from-answers` が厳密な検定を出す** ——
  **3 回とも 9/0・p = 0.004** で、区間 [0.004, 0.012] の下端に一致した。
  **`pairing_bounds` はこの run には不要**(クラス合計しか無い最初の run のために残してある)。
- **3 択のモデル側も 3 draw。** `--repeat 3` なので
  「殴る」の周辺度数が動かなかったことは**3 回とも同じ**だが、
  **16 局面 × 3 回は 48 の独立標本ではない**(同じ 16 局面)。
  だから符号検定は **run ごとに掛けて 3 つ並べてある**。
  **閉じ方**: `--repeat` を上げるか `FIGHT_PER_BUCKET` を上げるか。
- **3 択の中央の選択肢は、私が書いた 1 文。**
  「勝てないが、殴る価値がある」を選んだ 73% は
  **その 1 文の関数であり得る**(`fight` の noul で
  **文言がクラスの点を 0.50 → 0.63 動かした**のと同じ機構)。
  **閉じ方は同じ** —— 3 つの説明文を書き換えて同じ 16 局面を測り直す。
  **やっていない。**
- **`item` クラスの正解は「常識」と食い違う。** 全員 magic の相手に対して
  前衛が買うべきものが `belt`(体力)で `cloak`(魔法防御)ではない、
  という答えが出る。シミュレータが集団戦を回した結果なので**正しい**が、
  **16 tick の集団戦という horizon の性質**であって一般的なアイテム論ではない。
  **horizon を変えて同じ 6 問を測れば決まる**([TODO §1.10](../TODO.md))。
- **同じリクエストに問いを足すと、他の答えが動いた。** 派生 fight シナリオに
  `retreat` を相乗りさせたら、**`fight` の自己一致が 1.00 → 0.88 に落ちた**
  (点数は 0.63 のまま)。[README の 32 番](README.md)
  (「1 リクエストに問を詰めても答えは動かない」は state が同じときの話)の
  **同じ state・別の問いという条件でも小さく動く**という例で、1 回の観測なので**仮説**。
- **床は「上手い bot」ではない。** 124 問それぞれに書いた
  ヒューリスティックの集まりで、**試合を通して強い policy ではない**
  (`smart` は `scripted` に 7 編成中 3 編成で負ける)。
- **試合は 30 tick 打ち切りで測った。** 決着まで(77〜150 tick)走らせると
  API コストが 4〜5 倍になる。**勝敗は構造物ダメージのタイブレーク**で、
  ネクサスが割れるところは見ていない ——
  そして 6 節の `structure` 0 件は、**攻城の段に入る前に切った**という
  読み方で説明できてしまう([TODO §1.11](../TODO.md))。
- **クラスは 5〜29 問で、まだ均等ではない。** `class mean` を併記したのは
  そのためだが、5 問のクラス(`dive` `macro` `ability`)の行は**向きの参考**で、
  有意ではない。
- **jev vs jev を独立プロセスで、はまだやっていない。**
  3v3 側には [10](10-jev-vs-jev.md) の referee + player 構成が在るが、
  5v5 用のプロセス分離は作っていない(`turn_message` は用意してある)。

## 10. この実験で確定したパターン

1. **勝敗は判断の質の測定ではない。** 同じ実行が **6-0 で勝ち**、
   採点すると**ゴム印より明確に上と言えるクラスが 10 のうち 1 つ**しか無い
   (4 節・6 節)。bot を相手にした勝率は**相手の弱点の形**を測っていて、
   **どの判断を直すかは 1 つも言わない。**
   そして**勝ち方の説明は行動の内訳に在った** ——
   874 手のうち `structure` 0 件・`farm` 472 件で、
   **構造物を一度も殴らずに相手の構造物だけが減っていた**(6 節)。
2. **正解率は「一番良い定型答え」に対して読む。** 床でもランダムでもなく。
   この列を足した瞬間に **`retreat` が 0.83** で引っかかり
   (「全部 walk_away」でモデルより上)、
   直したあとの表では **`focus` 0.26 / `retreat` 0.41 / `item` 0.17 が
   ゴム印の下**だと分かった。**足す前の版にはその行が無かった。**
3. **クラスが偏っていないかは、数えれば分かる。** 前の版の `fight` は
   **8 問中 7 問が体の数で決まって**いて、床の 0.88 はほぼそれだけだった。
   **直し方は手で差し替えることではなく掃くこと** —— 540 通りを再生して
   4 つのバケツに入れ、同数取れば**体を数える戦略が正確に 0.50**になり、
   **等式としてテストに固定できる**。そして
   **一度目の掃きは別の偏り方をした**(16 問が全部同じ 2 チーム)ので、
   **偏りの検査は 1 種類では足りない。**
4. **同じリクエストの 2 問を突き合わせると、整合性が測れる** ——
   **ただし共起の数を読む前に、周辺度数が何を強制しているか確かめる。**
   **16 局面のうち 13 で「勝てない」と答えて「いま殴れ」と答えた**のは事実だが、
   **`false` 14/16 と `fight_now` 15/16 からその 13 は自動的に出る**
   (14 + 15 − 16 = 13)—— **共起が下限に等しいとき、それは 2 つの
   周辺度数の言い換え**で、対の証拠ではない(4 節)。
   **同じ数字が、真値の側では読める**(4 は下限 0・上限 7 の内側)。
   **残るのは真値との比較**: ルールが両立を許すのは 4 局面なので
   **13 組のうち少なくとも 9 組は間違っている**(符号検定 p = 0.004〜0.012)。
   **確かめるコストは 1 行**で、確かめなかったコストは所見 1 つだった。
5. **「矛盾か、私の選択肢が粗いのか」は、選択肢を足しても割り切れない ——
   割合そのものが私の文言の関数だった。**
   2 択の `fight_now` を `win_and_fight` / `lose_but_fight` に割ったら
   **「勝てない」と言って殴った 41 局面のうち 30(73%)が中央**を選び、
   残り 27% を「文言の逃げ場が無い矛盾」と書いた。
   **同じ 3 択を 4 通りに書き換えたら、その割合は 56% / 59% / 74% / 100%** ——
   **1 つの文言では矛盾が 48 答え中 0 件**、別の文言では **44%**(4 節)。
   **並び順だけで 74% → 59%** も動く(文は 1 字も変えていない)。
   **効いたのは長さでも「弁護」でもなく、
   「outright には勝たない」の 1 句が中央に在るか**だった。
   そして**正解率はどの文言でも全部ゴム印の下**(0.31〜0.38 対 0.56)——
   **整合するようになることと正しくなることは別**。
   **変わらなかったのは周辺度数だけ** ——
   7 arm・21 run 全部で両立の数は下限に等しい(4 番)。
6. **点数が自分の文言の関数かどうかを確かめる。** `fight` の noul の 2 面を
   **3 節 対 1 節から 1 節ずつの鏡像に書き直しただけ**で、
   クラスの点が **0.50 → 0.63**、confidence が **0.53 → 0.28** に動いた ——
   **答えはどちらでもほぼ定型**だったので、
   動いたのは主に「どれだけ確信するか」。
   [51](51-question.md) はレバーが問いではなく事実だったと結論したが、
   **ここではレバーが問いだった。**
7. **1 回では読むな。** このレポートの最初の版は **22 問を 1 回ずつ**測って
   「calibration の向きが回によって反転する」を所見にしたが、
   **620 答えで測り直したら向きは安定して正しかった**(0.51 対 0.48)。
   **反転は標本の小ささの産物**だった。
   このリポジトリは他の実験で**ずっと `--repeat` を使ってきた**
   ([22](22-code-criteria.md) [25](25-thresholds.md) [31](31-orchestration.md))——
   **道具を持っていなかったのは私だけ。**
8. **それでも、採点していない confidence は校正の主張に使えない。**
   [02 §3](02-moba.md) は霧の読みの confidence を見て
   「情報がないときに自信を持たないのは望ましい」と書いたが、
   **採点したら 0.10 正解で confidence 0.43〜0.56** だった(5 節)。
9. **1 つの数字は相手の性質を含む。** 霧の読みは
   **`scripted` 相手 0.36・`smart` 相手 0.02〜0.07**(5 節)——
   **相手を書かない霧の正解率は意味を持たない**
   ([README の 33 番](README.md) が別の題材で再現)。
10. **決定的なルールは、それ自体が oracle になる。** 「この集団戦は勝てるか」は
    再生すれば答えが出る。**`copy()` と「1 手だけ強制して残りは baseline」を
    用意しておくと、問いの半分が採点可能になる**上に、
    **問いの偏りを掃いて選別する道具**にもなる(3 番)。
11. **criteria = 合法手は、行動空間を 5 倍にしても成立する。**
    874 判断で不正手 0 件、1 体あたりの選択肢は 20 前後(3 節)。
12. **環境の対称性はテストしろ。** mirror 戦がほぼ全部片側に落ちる状態で
    勝率を 3 本測っていた。**原因 2 つはどちらも「同点の割り方」**で、
    観察では見えない(8 節)。
13. **oracle を 2 つ作ると、片方が間違っていることが分かる。**
    集団戦の総当たりと全試合の総当たりは**別の順位**を出し、
    モデルは集団戦側に合っていた(7 節)。
14. **ベンチマークの不変条件もテストにする。** 現在 10 本 ——
    正解が選択肢に在る / 選択肢の全部が正解ではない / 問名が一意 /
    クラスは 5 問以上 / どのクラスも床が全問正解ではない /
    **どのクラスも定型答えで 5 分の 4 を超えない** /
    **解析の truth がベンチマーク自身の truth と同一** /
    **言い換えた問いが同じ問いになっている** /
    **言い換えた問いが意図した通りに違っている**(A/B の残り半分。
    2 つの arm が同一になる書き間違いは「文言は効かない」を無料で出す)/
    **共起が周辺度数の下限に等しいことを検出できる**。
    **後から足した 3 本は、足した瞬間に落ちた。**
    **採点表は出るが意味を持たない**という壊れ方は、数字を見ても気付けない。
    そして**後の 3 本は解析の側**で、
    **1 本目(truth が同一)を書いたのは `Game::retreat_scores` を
    切り出す理由がそれだった**から ——
    真値のコピーが 2 つあると「truth が食い違う」が読めなくなる。
