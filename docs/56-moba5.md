# 56. 本格的な 5v5 MOBA と、採点できるベンチマーク

[02](02-moba.md) の 3v3 プロトタイプを**残したまま**、ジャンルが実際に遊ばれているサイズと
機構まで広げた別パッケージ(`moba5/`, `cmd/moba5`)を作り、
**「勝てるか」ではなく「どれだけ正しいか」を測れる**ようにした。

再現:

```bash
moon run --target native cmd/moba5 -- --bench --dry        # 採点表と床(API 不要)
moon run --target native cmd/moba5 -- --bench --repeat 5   # 同じ 165 問を 5 回、採点
moon run --target native cmd/moba5 -- --arena              # 5v5 集団戦の総当たり(API 不要)
moon run --target native cmd/moba5 -- --tournament         # 全試合の総当たり(API 不要)
moon run --target native cmd/moba5 -- --a jev --b smart --games 2 --max-ticks 30
moon run --target native cmd/moba5 -- --coherence --from-answers moba5/runs/wording.jsonl
                                                           # fight と retreat の truth を並べる(API 不要)
moon run --target native cmd/moba5 -- --from-answers moba5/runs/wording.jsonl
                                                           # 2 択と 3 択の比較を記録から再生(API 不要)
moon run --target native cmd/moba5 -- --from-answers moba5/runs/descriptions.jsonl
                                                           # 3 択を 4 通りの説明文で聞いた記録を再生(API 不要)
moon run --target native cmd/moba5 -- --wording --repeat 3 --answers moba5/runs/wording.jsonl
                                                           # その記録を取り直す(96 リクエスト、$0.02)
moon run --target native cmd/moba5 -- --descriptions --repeat 3 --answers moba5/runs/descriptions.jsonl
                                                           # 説明文 4 通りを取り直す(192 リクエスト、$0.04)
moon test --target native -p moba5                         # 125 本(API 不要)
```

3v3 側(`moba/`, `cmd/moba`, [02](02-moba.md) [10](10-jev-vs-jev.md)
[11](11-synergy.md) [12](12-comeback.md))は**1 行も変えていない**。

**この稿は 3 段構えになっている。** 1〜9 節は最初の版 —— 5v5 にして、
採点できるようにして、測った記録。**10〜11 節が第 2 版**で、
「MOBA 風」を**ジャンルの本体に寄せた**ときに何が起きたかを書く ——
ドラゴンの元素と soul、装備のビルドパス、ラストヒット、ヘラルド・
タワーのプレート・インヒビター、ブッシュの視界、ロール 2 種以上の champion。
**12 節が第 3 版**で、**ジャングルの camp・カウンタージャングル・制御ワード**、
そして**測ったらマップが実リフトではなかった**話。
**数字は全部第 3 版のもので置き換えてある**(1〜9 節の表も)。

置き換えの過程で**環境のバグが 3 つ増えた**(8 節の 6〜8 番)。
2 つは第 2 版で、うち 1 つは**「チーム A は完全な互角の集団戦に必ず勝つ」** ——
ベンチマークの `fight` / `focus` / `retreat` の truth を
**系統的に片側へ寄せていた**。3 つ目は第 3 版で、
**blink の同点を隣接リストの並び順で割っていた** ——
**camp にタイマーを付けてジャングラーの目標が動いた瞬間に**表に出た。
**新しい機構が、それとは関係ない潜んでいたバグを掘り出す**、というのが
このリポジトリで一番役に立っている道具の使い方になった。

## 1. 何が足りなかったか

[02 §4](02-moba.md) が自分で挙げた限界は 4 つで、そのうち 3 つはサイズと機構の話だった:

- **相手が弱い。** 受け身のレーン bot 1 種しかなく、同じ bot 同士は毎回引き分けだった。
- **戦場の霧を活かしているか未検証。** `enemies_last_known` を state に入れてはいたが、
  **その答えが当たっているかを採点していなかった。**
- **1 tick = 1 手で、射程もスキルも無い**(4 つ目は決着 tick のばらつきの少なさ)。

そして**そこに書かれていない 4 つ目**がレポート全体の形を決めていた ——
**測れるものが勝敗しかなかった。** 6-0 は「この bot より強い」であって
「MOBA が上手い」ではないし、bot を書き換えれば数字が動く。
**どの判断が間違っていたかは言えない。**
[02 §4](02-moba.md) はこれを「スクリプト bot は強くない」という
**相手の問題**として書いていたが、**相手を強くしても解決しない**。

5v5 にする理由はそこにある。**観測 1 個に対して判断が 5 個**になるのは
[fan-out](00-api-notes.md#speculative-fan-out) の比率が上がるだけだが、
**機構を増やすと、シミュレータ自身が答えを持つ問いが増える。**
「この集団戦は勝てるか」は、**ルールが決定的なら再生してみれば分かる。**

## 2. 増やした機構と、それぞれが作る判断

| 機構 | 作られる判断 |
| --- | --- |
| **3 レーン + 4 つのジャングル区画 + 川**(23 ノード) | どこに居るか。川の 2 ノードは**どちらの陣地でもない**ので、寄れば必ずレーンを空ける。ジャングル区画の出口は**3 つだけ**(両隣のレーンの外タワーと川)で、**ベース間は 6 hop**、**ジャングルはリコールから 3 hop** —— 実リフトの距離(13 節) |
| **ジャングルの camp 4 つ**(所有者とタイマー付き) | どの camp に回るか、**相手の半分に踏み込むか**。camp は**丸ごと 1 回で取る**ので、取れば相手は `CAMP_RESPAWN` tick それを得られない |
| **ワード 2 種**(通常 / 制御) | **相手の視界を消すか、自分の視界を足すか。**制御ワードはゴールドを払い、**範囲内の相手のワードを壊す** —— ゲーム中で視界を減らせる唯一の手 |
| **レベルと経験値**(1〜6) | 誰にファームを渡すか。今の自分は相手より強いのか |
| **アイテム 11 種・2 段**(装備枠 3) | 相手の damage type に対して何を買うか、そして**いま部品を買うか完成品まで貯めるか** |
| **固有スキル + クールダウン** | **いつ使うか。**スタンは damage 0 で、相手の 1 ターンだけを消す |
| **射程** | 遠距離は隣ノードを**半分のダメージで殴り、何も返ってこない** |
| **元素ドラゴン 4 種 + soul / バロン / ヘラルド** | どの元素が**この 5 人に効くか**、soul まで何匹か、相手の 4 匹目を潰すか |
| **ミニオンの押し合い + ラストヒット** | **Farm がレーンを押す。**押していないレーンのタワーは殴り返してくる。そして**ゴールドはラストヒットした者に入る**ので、レーンに立って Farm 以外をする tick には**必ず値段が付く** |
| **ワードとブッシュ** | 見えていない場所に 1 ターン払って視界を置く。**ジャングル 4 ノードはブッシュ**で、隣に立っても中は見えない |
| **タワー 2 段 + プレート + ネクサス** | ネクサスは**1 レーンが完全に開通するまで**殴れず、**内タワーは 22 tick で戻ってくる**。外タワーには**プレート 5 枚**が乗っていて、**タワーを折らなくてもゴールドになる** |
| **ロールごとに 2 種以上の champion**(12 種) | 同じ枠に**別の成長率**の選択肢があるので、「いま戦うか育ててから戦うか」に**tick 依存の答え**が出る |

構造として一番効いたのは**ミニオンの規則**で、これは 1 行で書ける:

> **自陣のウェーブが居るレーンのタワーは、その champion を撃たない。**
> 撃つ対象がミニオンになるから。

これで「タワーに単騎で立つ」は必ず負ける取引になり、
「まず Farm でウェーブを押してから殴る」が正しい手順になる。
**マップが飾りでなくなる。** そしてミニオンは**タワーしか割れない**
(ネクサスには触らない)ので、**試合を終わらせるのは必ず champion** になる。

## 3. スループット: 3v3 より良くなった

`--games 2 --max-ticks 30` を 3 組・2 巡(`jev-latest`、2026-09):

| | リクエスト | 決定したキャラ行動 | **行動/リクエスト** | ms/リクエスト | **ms/キャラ判断** |
| --- | --- | --- | --- | --- | --- |
| A=jev vs smart | 120 | 600 | **5.00** | 261 | **52** |
| A=smart vs B=jev | 120 | 600 | **5.00** | 258 | **52** |
| A=jev vs scripted | 120 | 551 | **4.59** | 260 | **56** |
| 合計 | 360 | 1751 | **4.86** | 260 | **53** |
| *(参考)* [02](02-moba.md) の 3v3 | 79 | 218 | 2.76 | 210 | 76 |

**キャラ 1 体あたり 53 ms。** 3v3 の 76 ms より速い ——
選択肢が 5 倍に増えても、**state を 1 回しか送らないので 1 体あたりは下がる**。
入力は 1 試合(30 tick)で約 24 万トークン、**$0.010/試合**。
**機構を 9 つ足しても 1 体あたりの時間は動かない**(52 → 53 → 53 ms)——
増えたのは state の中身で、リクエストの数ではない。

**不正な手は 1751 判断すべてで 0 件。** これは [02 §2](02-moba.md) の主張の再検証で、
**行動の種類が 6 → 13 に増え、1 体あたりの選択肢が 20 前後になっても成立する。**
criteria がその場の合法手そのものなので、**不正手は表現できない。**
第 2 版で**アイテムが 5 種から 11 種**になり、
第 3 版で**行動の種類に制御ワードが増えた**あとも、**0 件のままだった。**

そして**新しい機構を実際に使っている**(行動の内訳、12 試合 1751 手):
`farm` 1652(**94%**)/ `control_ward` 25 / `ward` 20 / `ability` 18 /
`blink` 14 / `hold` 12 / `attack` 4 / `move` 3 / `objective` 2 / `recall` 1。
**`farm` が 95%** で、第 1 版の 54% から上がっている ——
**ラストヒットがレーンに立つ tick に値段を付けた**ので、
「レーンに居るなら Farm」が以前より正しくなった。
`poke` が消えたのはその裏側で、**ポークは無料の手ではなくなった**。
そして **`control_ward` が 25 手** —— 第 3 版で足した行動を、
**モデルはゴールドを払って使っている**。
ただし**「使った」と「効いた」は別**で、
25 手のうち何手が実際に相手のワードを消したかは数えていない
(行動の内訳は種類しか数えない)。6 節と 9 節に戻ってくる。

## 4. 採点できるベンチマーク

**47 シナリオに 165 問・16 クラス**、答えは**全部シミュレータが出す**。
1 シナリオ = 1 リクエスト(state 1 つに複数問)。
第 1 版は 31 シナリオ 124 問 10 クラスで、**増えた 6 クラスは第 2 版の機構のもの**
(`cs` `drake` `brush` `siege`、11 節。`jungle` `vision`、12 節)。

答えの出し方を 3 段階に分けて、**問ごとに明記した** ——
同じ強さのふりをさせないため:

| tier | 意味 |
| --- | --- |
| `rules` | **再生した。**集団戦を最後まで回した結果、ダイブを塔のダメージ込みで回した結果。異論の余地が無い |
| `arith` | ルールが定義する厳密な算術(塔の下で何 tick 耐えるか、チーム戦力、視界の外に何人居るか)。再生はしていないが判断でもない |
| `score` | `position_score` を**明示した horizon** で最大化する選択肢。**事実ではなく、明示した目的関数** |

`score` tier では**相手も強い側の baseline で動かす**(相手が何もしない前提でだけ
正しい macro の答えは答えではない)。**同点は同点として扱う**
(`truth_accepts`、`"a|b"` 形式)—— 選択肢を並べた順序を測ってしまわないため。
そして **`--repeat N` で同じ問いを N 回**聞く ——
モデルは確率的なので 1 回では差と引き分けが区別できず、
**自分で答えを変える問いの割合**が差の基準線になる
([37 §6](37-hermes.md) [41](41-versus.md) と同じ規律)。

### `fight` クラスは作り直した —— 手で選ばずに掃いて

前の版の `fight` は**偏っていて、数えたら分かった**:
**8 問中 7 問が「体の数が多い側が勝つ」**で、床の 0.88 はほぼそれだけ。
つまり**モデルの点数の大半は、モデルの要らない算術の点数**だった。

**手で差し替えると、私が期待した方に寄る。**だから掃いた ——
構成・レベル・体力・ノードの固定グリッド **540 通り**を全部 `simulate_fight` で
再生し、**体の数が結果を予測したかどうか**で 4 つのバケツに入れる:

| バケツ | 体が多い/同数 | 勝つ | 候補数 |
| --- | --- | --- | --- |
| `count_right_win` | yes | yes | 201 |
| `count_wrong_loss` | yes | **no** | 123 |
| `count_wrong_win` | **no** | yes | 26 |
| `count_right_loss` | no | no | 190 |

**各バケツから同数(4 問ずつ・計 16 問)取ると、
体を数える戦略はこのクラスで正確に 0.50**、
そして**「全部 yes と答える」も正確に 0.50** になる。
**どちらもテストで等式として固定してある**(`bench_wbtest.mbt`)——
バケツを 1 つ落として balance を装うことができないよう、
**4 つ全部がグリッドから到達可能なことも**同じテストが確かめる。

**一度目の掃きは別の偏り方をした。** グリッド順に「バケツが埋まるまで」取ると
**最初の構成ペアの中で 4 つ全部埋まってしまい、16 問が全部同じ 2 チーム**になった ——
体の数に対しては均衡で、それ以外については何も測らない。
いまは 2 パスで、**1 パス目は (構成ペア, ノード) ごとに 1 問まで**。
結果は **3 マッチアップ × 両サイド = 6 ペアリング**、mid_mid と riv_top の両方。
(`count_wrong_win` は候補が 26 しか無い最も細いバケツなので、
**4 問が全部 meta 対 glass_ad の変種**になっている —— これは限界。)

### `const` 列 —— 一番良い「定型答え」が何点取るか

床(状態を読むヒューリスティック)とは別に、
**そのクラスで一番多い正解を機械的に答えたら何点か**を出すようにした。
`fight` は構成上 0.50 だが、**入れた瞬間に別のクラスが引っかかった** ——
**`retreat` は 6 問中 5 問の正解が `walk_away`** で、
**「全部 walk_away」が 0.83** 取れていた。つまりゴム印とモデルを区別できない。
派生 fight シナリオに `retreat` を相乗りさせて **0.64** まで下げた
(それでもまだ高い。限界に書いた)。
**「どのクラスも定型答えで 5 分の 4 を超えられない」もテストにした。**

- **自己一致は 147/165**(0.89)。18 問が同じ問いに違う答えを返す ——

  クラスの問題数で重み付けされ、その問題数は
  「どのシナリオがそのクラスを答えられたか」の偶然
  (`power` はほぼ全ての state に乗るが `macro` はほとんど乗らない)。
  **食い違ったら class mean を読む。**

### `const` に対して読む

**これが `const` 列を足した理由。** 床でもランダムでもなく、
**ゴム印に対してどうか**:

| クラス | モデル | const | 床 | 読み |
| --- | --- | --- | --- | --- |
| `lane` / `brush` | **1.00 / 1.00** | 0.71 / 0.33 | 0.86 / 0.50 | **満点が 2 つ。**`brush` は第 2 版の 0.67 から上がった(下記) |
| `siege` / `vision` | **0.80 / 0.80** | 0.33 / 0.40 | 0.33 / 0.80 | `siege` は床の 2.4 倍、`vision` は**床とちょうど同じ** |
| `jungle` | **0.70** | 0.33 | 0.50 | **上**。ただし 6 問 |
| `fight` | 0.68 | 0.50 | 0.50 | **16 問で 3 問分上**。まだ標準誤差 2 個ぶん |
| `cs` | 0.67 | 0.33 | 0.75 | **床に負ける**(下記) |
| `dive` | 0.60 | 0.40 | 0.80 | const より上、床より下 |
| `fog` | 0.57 | 0.29 | 0.57 | const の 2 倍、床とちょうど同じ |
| `retreat` / `power` | 0.50 / 0.46 | 0.50 / 0.34 | 0.64 / 0.34 | `retreat` は **const と完全に同じ** |
| `macro` / `ability` | 0.40 / 0.40 | 0.20 / 0.60 | 0.40 / 0.40 | `ability` は**const より下**、`macro` は床とちょうど同じ |
| `item` / `drake` | **0.37 / 0.33** | 0.50 / 0.17 | 0.50 / 0.33 | `item` は**下**(3 版とも) |
| `focus` | **0.23** | 0.41 | 0.50 | **最下位。**3 版とも床と const の下 |

**「ゴム印より明確に上」は 5 つになった** —— `lane` `brush` `siege` `vision`
`jungle`。第 1 版は `lane` だけ、第 2 版は `lane` と `siege` だった。
**そして増えた 4 つは全部、直前に足した機構のクラス**だ ——
これは 3 版通じて一番はっきりした規則性で、11 節で書いた
「規則が新しいほどモデルが床に対して有利」がもう一度出ている:
**床のヒューリスティックは新しい規則を知らない**ので、
`smart` はプレートの枚数もブッシュの視界も camp のタイマーも見ない。
**機構を足すと、その機構のクラスでモデルが勝つ。**
**これはモデルの性質ではなく、床の書かれた時点の性質。**

**`brush` が 0.67 から 1.00 に上がったのはマップを直したから**(13 節)。
ジャングル区画の出口が 6 本から 3 本になって、
**「どのノードが伏せられるか」が実際に絞れる形になった** ——
第 2 版のマップではジャングルがベースにもレーンの内側にも繋がっていたので、
ブッシュの隣接が広すぎて問いが曖昧だった。
**問題を変えていないのに点数が上がった**のは、**マップが問題の一部**だったから。

そして**第 2 版の 4 クラスは 2 勝 2 敗で、勝ち方と負け方の両方に理由がある**
(第 3 版で足した `jungle` `vision` は 13 節):

- **`siege` 0.80 対床 0.33、`brush` 1.00 対床 0.50。**
  どちらも**規則が新しい**クラスで、
  **床のヒューリスティックはその規則を知らない** ——
  `smart` はプレートの枚数を見ないし、ブッシュの視界も使わない。
  **新しい機構は、まず床に対して有利に出る。**
  ただし `siege` の 6 問は「プレートは何ゴールドか」「ゲートが閉まる前に着くか」で、
  どちらも**状態に書いてある数字の足し算**だ ——
  **算術のクラスでは強い**、というのはこの表の他の行でも繰り返されている。
- **`cs` 0.67 対床 0.75。** ここは逆で、**床が強い** ——
  `smart` は `minions_ripe_here` を読んで farm するかを決めているので、
  **「いま farm はいくらか」を構成上ただで当てる**(12 問中 9 問)。
  **ヒューリスティックが規則の一部なら、そのクラスの床は天井に近い。**
  モデルが落としているのは「3 tick 立ち続けたら何ゴールド損か」の側で、
  **ウェーブは 1 tick に 1 匹補充される**ので
  「いま低い 2 匹 × 3 tick = 6 匹」ではなく **4 匹**が答えになる。
- **`drake` 0.33 対床 0.33 —— 下から 2 番目で、外し方が揃っている。**
  「この 5 人にはどの元素が効くか」の 3 問で、
  **モデルは 2 問とも `mountain`(被ダメージ 6% 減)と答えた。**
  シミュレータの答えは `infernal` と `ocean` ——
  相手が紙装甲の編成では**先に殺す方が勝ち**、
  そして 2 問目は**その 4 匹目が soul になる状態**で、
  ocean の soul は**敵が同じノードに居ても回復する**(他に何も無い効果)。
  **モデルはそれを勘定に入れていない** ——
  同じ state の「あと何匹で soul か」にも `1` と答えている(正解 `0`)。
  **4 匹目が soul だと気づいていないのが、2 問の外れの共通原因。**

### そして 13/16 —— 「負ける」と答えて「殴れ」と答える

`fight` の 0.63 の中身を見たら、**答えがほぼ定型**だった ——

### **その 13 は、モデル自身の周辺度数が強制していた**

## 5. 戦場の霧: 初めて採点した ——「自信を持って外す」

| --- | --- | --- | --- | --- |
| smart(**jev が A**) | 120 | 30 | **0.25** | 0.29 |
| smart(**jev が B**) | 120 | 1 | **0.008** | 0.28 |
| scripted(jev が A) | 72 | 7 | **0.10** | 0.27 |
| 合計 | 312 | 38 | **0.12** | — |

**ランダムは 1/23 = 0.043。** 全体の 0.12 はその 2.8 倍だが、
**内訳が壊れている** —— **同じ相手に対して、A 側 0.25 と B 側 0.008。**
30/120 対 1/120 で、**2 巡とも同じ**だった。
そして **confidence は両側で 0.28〜0.29 と同じ**なので、

[02 §3](02-moba.md) は同じ問い(当時 11 択)に 0.31〜0.58 が返るのを見て

**採点していない confidence は、校正されているかどうかを言えない。**

**第 1 版はここで 0.02 対 0.36 に分かれ**、
「`scripted` はレーンに忠実なので予測でき、`smart` は集団で回るので予測できない ——
**この数字の大半は相手の予測可能性の性質で、モデルの性質ではない**」と書いた。
**その結論は取り下げた。** 第 1 版の測定は
**同じ相手に対して A 側 0.35〜0.43 と B 側 0.12 にも割れていて**、
マップは A↔B 対称で相手の policy も同じなのでそれは有り得ない ——
原因は 8 節の 6 番、**チーム A が完全な互角の集団戦に必ず勝っていた**ことだった。

**そして第 3 版で、その片側差が戻ってきた。しかも大きくなった** ——
**A 側 0.25 対 B 側 0.008。** 今度は**エンジンを先に潰した**:

- **mirror 戦が毎 tick mirror である**(8 節、9 編成 × 150 tick、
  位置・体力・経験値・復帰・キル・装備・CS・camp・ワード・プレート、全フィールド)
- **両チームが鏡像の情報を受け取っている** —— A が見えるノードは
  B にとってその鏡像で、**ノードごとに一致する**
  (見えるノードの「数」が一致するだけでは、
  両チームが別の半分を見ていても通ってしまう)。そして
  **隠れている敵の数も両側で同じ**で、これが fog の問いの入力そのもの
- **回避が両側で同じに効く** —— 攻撃から歩いて逃げる champion は
  どちらのチームでもダメージを受けない。
  行動ループの中で位置は champion id 順に書き換わるので、
  **id が先のチームが得をしていないか**を両方向で測った

**3 つとも緑なので、非対称性はルールにも、policy に渡される state にも無い。**
**残るのは読み方**で、いちばんもっともらしい機構は素直なもの:
**B 側の視界は鏡像で、自陣は `b_base`、前進は番号の小さい方**。
**これは容疑者であって、確定ではない** ——
切り分けるには**同じ問いをラベルだけ入れ替えて聞く**必要があり、
それは測定であってテストではない([TODO §1.13](../TODO.md))。

**8 節の主題は形を変えて残る**: **測った差に説明を付ける前に、
その差が環境のバグでないことを確かめる。**
第 1 版はそれをやらずに説明を書き、第 3 版は**先に 3 本テストを書いた** ——
**同じ 3 倍の差に対して、1 度目は所見を 1 つ失い、
2 度目はエンジンを除外できた。**

ベンチマーク側の `fog` クラス(7 問・35 答え)は **0.57** で、
内訳は**「何人見えていないか」(数える問い)が高く、
「どのノードに居るか」(推論が要る問い)が低い**、という素直な分かれ方は変わらない。
自己一致 **0.43** で 16 クラス中最低 —— **同じ問いに毎回違う答えを返す。**
**試合中の 0.12 とベンチマークの 0.57 が食い違うのは選択肢の数**で、
試合中は 23 択、ベンチマークは数える問いを含む 7 問。**別の問いを測っている。**

| A=jev vs B=smart ×4 | **jev 4-0** | A=1130 / B=826 ×4 |
| A=smart vs B=jev ×4 | **jev 4-0** | A=874, 830, 874, 830 / B=1130 |
| A=jev vs B=scripted ×4 | **jev 4-0** | A=1130, 1122 / B=850, 802, 830, 802 |

**両サイドから、両方の bot に勝ち、12 試合すべて自陣の構造物に 1 点も入っていない**
(1130 が満額)**。**
[02](02-moba.md) の 6-0 と同じ形の結果が、**5 倍広い行動空間でも、
機構を 6 つ足した後でも出る。**

**そしてこれが本稿の要点。** 同じ実行の中で:

- 試合は **12-0** で勝つ
- 採点すると **0.54**(class mean 0.59)、手書きの床 **0.53**(同 0.55)と**ほぼ同じ**
- **16 クラスのうち「ゴム印より明確に上」は 5 つ**で、
  **その 4 つは直前に足した機構のクラス**
- **16 局面のうち 13 で「勝てない」と答えて「殴れ」と答える**
- 元素の選択(`drake`)は **0.33**、**4 匹目が soul だと気づいていない**

**勝つことと正しいことは別の測定で、3v3 は前者しか見ていなかった。**
矛盾ではない —— bot の弱点は判断の質と関係ない場所に在り得るし、
1 tick の誤りは次の tick に取り返せる。

**そして行動の内訳が勝ち方を説明する** ——
12 試合 1751 手のうち **`farm` が 1652 手(94%)で `structure` は 0 手**。
つまり**ほとんど構造物を殴っていない**のに、
**相手の構造物だけが減って自陣は満額**だった。
2 節のミニオン規則がそうさせている: Farm がレーンを押し、
押されたレーンのミニオンがタワーを削る。
**モデルは 30 tick を farm に使い、ミニオンに攻城させた。**
これは巧いのか、それとも**30 tick では攻城の段に入っていないだけ**なのか ——
**いまの打ち切りでは区別できない**(9 節、[TODO §1.11](../TODO.md))。

**第 1 版との差が 2 つあり、どちらも足した機構が説明する:**

- **`farm` が 54% から 89% に上がった。** ラストヒットが
  **レーンに立って Farm 以外をする tick に値段を付けた**ので、
  「レーンに居るなら Farm」が以前より正しくなった。
  その裏で **`poke` が 133 手から 0 手に消えた** ——
  **ポークはもう無料の手ではない**(1 回のポークはウェーブ 1〜3 匹と引き換え)。
  **モデルはその値段を読んでいる**、というのがこの数字のいちばん素直な解釈だが、
  「farm が常に合法で常に何かは払う」という**別の説明も同じ数字を出す。**
- **`structure` は第 3 版で 10 手から 0 手に戻った。** マップを直して
  **ベース間が 4 hop から 6 hop になった**ので、
  30 tick ではタワーに辿り着く前に終わる ——
  **プレートを読めるようになったかどうかは、この打ち切りでは分からない。**
- **そして `control_ward` が 25 手出た。** 第 3 版で足した行動で、
  **モデルはゴールドを払って相手の視界を消しに行っている** ——
  ただし 25 手のうち何手が実際に相手のワードを消したかは数えていない
  (行動の内訳は種類しか数えない)。**「使った」と「効いた」は別。**

## 7. 編成: 集団戦に強い編成は、試合に強い編成ではない

`--arena`(1 ノードで 5v5、編成だけが変数)と
`--tournament`(全試合、policy を両側同じに固定)は**別の順位を出す**:

編成は 9 種になり(`early` と `late` が第 2 版で増えた)、
集団戦は**レベル 1 とレベル 6 の 2 段**で回す:

| comp | 前衛 | damage | CC | 回復 | 遠距離 | 集団戦 L1 | 集団戦 L6 | **全試合(smart)** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| late | yes | AD+AP | yes | yes | 3 | **16-0** (1 位) | **16-0** (1 位) | 8-8 (7 位) |
| meta | yes | AD+AP | yes | yes | 3 | 14-2 (2 位) | 12-4 (3 位) | 8-8 (5 位) |
| dive | yes | AD+AP | yes | yes | 1 | 12-4 (3 位) | 14-2 (2 位) | 8-8 (6 位) |
| poke | yes | AD+AP | yes | yes | 3 | 10-6 (4 位) | 10-6 (4 位) | 5-11 (**8 位**) |
| bruisers | yes | mono | yes | no | 0 | 8-8 (5 位) | 4-12 (7 位) | 4-12 (**9 位**) |
| early | yes | AD+AP | no | yes | 2 | 6-10 (6 位) | 4-12 (8 位) | **10-6** (3 位) |
| glass_ad | no | mono | no | no | 3 | 4-12 (7 位) | 6-10 (5 位) | **10-6** (**1 位**) |
| glass_ap | no | mono | no | yes | 4 | 2-14 (**8 位**) | 6-10 (6 位) | **10-6** (**2 位**) |
| classic | no | mono | no | no | 0 | 0-16 (9 位) | 0-16 (9 位) | 9-7 (4 位) |

**第 1 版の結論はそのまま立っている。第 3 版のマップでは、もっと極端になった** ——
**集団戦の順位と全試合の順位がほぼ逆になった:**
**`glass_ap`(前衛なし・魔法のみ)は集団戦 2-14 の 8 位で、全試合 2 位。**
**`glass_ad` は集団戦 7 位で全試合 1 位。**
**`late`(集団戦 16-0 の 1 位)は全試合 7 位、`bruisers` は 9 位。**
そして **`classic`(3v3 の均一 champion 5 体)は集団戦 0-16 の最下位で全試合 4 位。**

理由はマップから読める —— **ベース間が 6 hop になり、
ジャングルの短絡が無くなった**ので、
**構造物を割る側の試合は「レーンを押し切る」勝負**になった。
遠距離が多くて押しの強い編成(`glass_ap` は遠距離 4 枚)が
**集団戦を捨てても先にタワーを割る。**
[11](11-synergy.md) の「正しいシナジー」は**集団戦の話だった**、を
**マップを長くしたらさらに強く再現した。**

**そしてこれは編成バランスの所見ではなく、oracle が 2 つある所見**だ ——
どちらの順位も「正しい」。**`--draft` がどちらに合うかを測る**のが
7 節の元々の主題で、**それはマップを変えるたびに測り直しになる。**

**レベルを 2 段にしたのは第 2 版の成長率のため。**
`bruisers` は **L1 で 5 位・L6 で 7 位**、`glass_ap` は **L1 で 8 位・L6 で 6 位** ——
成長率が archetype ごとに違うので、**同じ 2 編成の勝敗がレベルで入れ替わる。**
1 段でしか回していなかった第 1 版は、**この軸が在ることを表に出せなかった。**

そして `--draft`(生のステータスだけ渡して編成を選ばせる)は
**`meta` を選ぶ(conf 0.70)** —— **集団戦の正解で、試合の正解ではない。**
順位も集団戦側にほぼ合っている —— **1 位・2 位・7 位を正確に当て**、
残りは隣同士の入れ替え 2 組(`poke`↔`bruisers`、`glass_ad`↔`glass_ap`)だけ。
**モデルの答えは合っていて、私が当てさせた oracle が間違っていた。**
`--draft` は今のところ集団戦 oracle との比較なので、**そう書いてある。**

## 8. 環境を測ったら、環境にバグが 8 つ在った

**このプログラムの教訓([README の 35 番](README.md))が効いた場所。**
5v5 を「動いている」で済ませず、**不変条件をテストにした**ら 8 件出た
(1〜5 が第 1 版、6〜7 が第 2 版、**8 が第 3 版**)。
どれも観察では見えず、**全部テストか対称性の検査で出た**:

1. **ノード名の表が 1 つずれていた。** `node_names` の並びが
   `adjacency` と定数(`RIV_TOP`/`RIV_BOT`)の前提とずれていて、
   **ログは「ドラゴンが riv_top に出現」と嘘を書いていた**(添字は正しいので挙動は正常)。
   observation に出る名前もずれるので、**モデルには嘘のマップが渡っていた。**
2. **マップは対称なのに、片側が無料で勝っていた。**
   A のジャングラーの初期位置が**バロン側**、B が**ドラゴン側**で、
   ドラゴンは tick 6・バロンは tick 24 に湧く ——
   **B は序盤の目標の隣から始まる。**mirror 戦は B がほぼ全勝した。
3. **そして直してもまだ B が勝った。** 原因は**隣接リストの並び順**。
   `a1_bot` から `b1_top` へは**自陣ベース経由でもレーン経由でも 6 hop** で、
   `step_toward` は同点を**リストの先に書いてある方**で割っていた ——
   A のリストは自陣側が先、B のリストは前方が先なので、
   **A の bot laner は tick 1 にレーンから後ろへ歩き出していた。**
   同点を「**同じ距離なら前に出る側**」で割る(`step_toward_prefer`)と、
   **7 編成中 5 編成で両サイドの結果が完全に鏡像**になった
   (勝者は 7/7 でサイドに依らない)。
4. **`Stun(1)` が何もしていなかった。** 着弾した tick の末尾で
   カウンタを減らしていたので、**1 tick のスタンは着弾と同時に切れていた。**
5. **ドラゴン 1 スタック(+7%)が 0 だった。** 整数除算で切り捨てていたので、
   攻撃力 15 未満の champion —— **序盤のほぼ全員** —— には効果が無かった。
   **マップの下半分が存在する理由が、序盤に登録されていなかった。**
6. **チーム A は完全な互角の集団戦に必ず勝っていた。** これが一番深い ——
   キルは経験値を払い、経験値はレベルを上げ、レベルは最大体力を上げて
   `refresh_hp` が**差分を現在体力に足す**。死亡判定は
   **その支払いと同じループの中で 1 体ずつ**行われていたので、
   **体力が -6 になった champion が、自分が取ったキルの経験値で 8 まで戻され、
   ループがそこに来たときに「生きている」と読まれていた。**
   どちらが生き残るかは `champ_dmg` がどの順で 2 体を持っていたか ——
   **行動した順、つまり champion id の順** —— で決まる。**A が先に動く。**
7. **相打ちした 2 体が 1 tick ずれて復帰していた。** 6 番の 1 段下。
   復帰タイマーは `RESPAWN_BASE + level` で、**支払いが既に落ち始めた後に読まれる**
   ので、2 体目のタイマーは**1 体目のキルでレベルが上がった後の値**になっていた。
   `dive` の mirror 戦は tick 16 で**片方のジャングラーが自陣に戻り、
   もう片方はまだ川に転がっている**状態になった。
8. **blink の同点を、隣接リストの並び順で割っていた。** 3 番と同じ種類が
   1 手ずれた場所に残っていた —— `smart_action` は
   **距離が改善する最初の blink** を返していて、
   その「最初」は `blink_targets` がリストを組む順、
   つまり `adjacency` の順で、**それはマップの左右で鏡像になっていない。**
   mirror 戦で **A のジャングラーが a1_top から自陣へ blink し、
   B のジャングラーが b1_top から川へ blink した** ——
   他のフィールドは全部一致していた。
   いまは**一番良い blink を取り、同点は「相手ベースに近い方」で割る**
   (歩きの `step_toward_prefer` と同じ規則)。
   **camp にタイマーを付けてジャングラーの目標が動いた瞬間に表に出た** ——
   **潜んでいたバグを、別の機構が掘り出した。**

2 と 3 は**勝率を無意味にする**種類のバグで、
**「A が勝った」の大半がサイドの話だった。**
今はマップの A↔B 対称性・両チームの初期位置・`step_toward` の同点処理が
**テストで固定してある**(`map_wbtest.mbt`)。

**6 と 7 は、それより広い範囲を汚していた。** `simulate_fight` は
`fight` / `focus` / `retreat` の truth の出処なので、
**互角の集団戦で系統的に A が勝つのは、ベンチマークの大半が系統的に片側へ寄る**ことだった。
そして 5 節の「霧の読みは相手の予測可能性の性質」という結論も、
**大半はこのバグの性質だった。**

**見つけ方は 1 つのテストだった:「mirror 戦は毎 tick mirror である」。**
同じ編成同士・両側同じ policy なら、状態は**自分の鏡像**でなければならない
—— champion の位置と体力と経験値と復帰タイマー、レーンの押し、
構造物の体力とプレート、ドラゴンのスタック、buff の残り、盤上のワードの数、全部。
**書いたその日に 2 件出た**(`mirror_wbtest.mbt`)。
いまは**9 編成すべての mirror 戦が 150 tick 完全に対称**で、
**どのノードのどの互角の集団戦も引き分け**(`fight_is_won` が両側で false)。

**そして 6 と 7 は公表済みの数字を 1 つも動かさなかった。**
派生 fight の 16 局面は体力とレベルをずらして作ってあるので、
**そのどれも「完全な互角」ではない** ——
`--bench --dry` の表と `--coherence` の表は**直前と直後でバイト単位で同じ**だった。
**プレイからは到達できて、問題集からは到達できないバグ**だったので、
**問題集を増やしても見つからなかった。**

**mirror テストは第 3 版で 2 つ広がった。**
camp とそのタイマー・`camps_lost`・champion ごとの camp 数、
そして**ワードを種類と鏡像ノードごと**に照合する ——
制御ワードが片側だけで掃いた状態は、まさにこのテストが見るためのもの。
そして**「両チームが鏡像の情報を受け取っている」**を別のテストにした ——
A が見えるノードは B にとってその鏡像、ノードごとに一致、
隠れている敵の数も両側同じ。
**これは 5 節の片側差を説明する前に、エンジンを除外するために書いた。**

**ベンチマーク自身の不変条件もテストにした**(`bench_wbtest.mbt`):
正解が選択肢に入っていること、**選択肢の全部が正解ではないこと**、
問の名前がシナリオ内で一意(wire の key なので重複すると黙って 1 問落ちる)、
noul の正解が true/false 両方存在すること、
**床が全問正解でも全問不正解でもないこと**。
どれも欠けると**採点表は出るが意味を持たない。**

## 9. 正直な限界

- **`fight` の 0.68 は確定していない。** 定型 `false` が構成上 0.50 で、
  16 問での標準誤差が ±0.125 なので、**3 問分の差は誤差 1 個**。
  「上回った」と書けるだけの母数が無い。**閉じ方**は `FIGHT_PER_BUCKET` を
  上げるだけ(グリッドの最細バケツが 26 候補なので 6 まで伸ばせる)。
- **`count_wrong_win` バケツは候補が 26 しか無く、4 問全部が
  meta 対 glass_ad の変種**になっている。他の 3 バケツは 3 マッチアップに
  散っているので、**「体の数が間違っている側」だけ多様性が低い。**
- **`retreat` の `const` は 0.50、`lane` は 0.71** で、まだ高い。
  テストは「5 分の 4 を超えない」しか要求していないので、
  **このクラスは balance されてはいるが均衡ではない。**
- **`ability` はモデル・床・const が全部 0.60** で、
  **何も区別していないクラス**。5 問しか無い。
- **`score` tier の 5 問は事実ではない。** `position_score` の重み付けと
  horizon(8〜12 tick)を変えれば答えが変わり得る。**明示してあるので反論できる**、
  というのが提供できる最大限。そして **`retreat` はこの tier** なので、
  「負けると答えて殴れと答える」の後半は**私の目的関数に対する矛盾**であって
  ルールに対する矛盾ではない —— ただし
  **`fight` 側(`rules` tier)と食い違っていること自体は目的関数に依らない。**
  そして**「両立する 4 局面」も `RETREAT_HORIZON = 8` の性質**で、
  horizon を変えればこの 4 も動く。**`--coherence` は horizon を引数に取る
  `retreat_scores` を呼んでいるので、動かすのはコード 1 箇所。**
- ~~**整合性の側で足りないのは、記録の粒度。**~~ → **直した。**
  最初の `--coherence` はモデルの側を**クラス合計でしか持っていなかった**ので、
  `pairing_bounds` が並べ方を全部列挙して
  「結論が並べ方に依らない」を示す形にしてあった。
  いまは **`--wording --answers` が問ごとに 1 行**書き、
  **`--coherence --from-answers` が厳密な検定を出す** ——

## 10. 第 2 版: 「MOBA 風」をジャンルの本体に寄せる

第 1 版の 2 節の表は**機構の名前としては MOBA だが、中身は 1 段浅い** ——
ドラゴンは 1 種、アイテムは全部同じ値段、ミニオンは触らなくてもゴールドが入り、
ジャングルは通路で、champion はロールごとに 1 種だった。
**6 つ足した。** 順番は「そのルールが**新しい判断**を作るか」で選んだ:

| 足したもの | 作られる判断 | 実装で効いた点 |
| --- | --- | --- |
| **ロールごとに 2 種以上の champion**(12 種) | 同じ枠に別の**成長率**の選択肢 | `bully`(攻撃 17・成長 5%)は `marksman`(13・19%)に**L1 で勝って L6 で負ける** —— 「いま戦うか」に tick 依存の答えが出る |
| **ブッシュの視界** | 通れる道か、伏せられる場所か | **隣に立っても中が見えない**(ワードだけが外から見る手段)。川は**わざとブッシュにしていない** —— オブジェクトのタイマーは両チームが読めないと計画できない |
| **ラストヒット** | レーンに立つ tick ごとの値段 | ゴールドは**最後の一撃**に入る。取らなかった分は自軍のウェーブが処理して**誰にも入らない**ので、ポークもローテーションも**正確に数えられる値段**を持つ |
| **元素ドラゴン 4 種 + soul** | どの元素か、soul まで何匹か、相手の 4 匹目を潰すか | 4 元素は**エンジンの 4 つのレバーを 1 つずつ**動かす(与ダメージ・被ダメージ・回復・クールダウン)。4 匹目で soul |
| **装備 2 段(部品 → 完成品)** | いま部品を買うか完成品まで貯めるか | 部品は安く早く、完成品は**ゴールド効率が良い**。完成品は部品を**食う**ので、装備枠 3 の中で**2 部品持ちは枠の 2/3 を占めて待つ** |
| **ヘラルド / プレート / インヒビター** | 3 つの時計 | プレートは**タワーを折らなくても払う**(tick 40 で落ちる)、内タワーは**22 tick で戻る**(その間レーンが開く)、ヘラルドは **tick 70 に去る** |

**そして 3 つは「実装したが起きていなかった」。**
テストが全部通り、型も通り、**プレイでは一度も起きない** ——
この失敗の形が第 2 版で一番学びが大きかった:

- **soul は到達不可能だった。** `team_plan` が「自軍のウェーブが居るレーンの
  タワー」を**無条件にオブジェクトより前**に置いていて、
  bot はほぼ毎 tick どこかのレーンを持っているので、
  **その分岐はオブジェクトに対する常時拒否権**だった。
  128 tick の試合でドラゴン 1 匹・バロン 1 匹。**4 匹は起きない。**
- **直したら逆に振れた。** 「無料のタワー」に 1 つの値段を付けたら
  **川が毎回勝ち**、champion がタワーに触らなくなり、
  **1 試合でプレートが 1 枚も落ちなかった。**
- **さらに直したら両チームが川に立ったまま動かなくなった。**
  150 tick、全員がバロンピットに駐車、全レーンの押しが 0、**構造物の破壊が 0 件。**
  「欲しい」と「取れる」を区別していなかった。

いまは**1 つの比較**になっている: `tower_value`(**タワーに実際に乗っている
プレートを読む**)対 `objective_value`、どちらも**到達可能性の関門付き**
(タワーは自軍のウェーブ、オブジェクトは `can_contest` ——
**シミュレータに「その集団戦は取れるか」を聞く**)。
**分岐の順序は「たいていはこうだが、これは違う」と言えない。数字は言える。**

そして**そこから試合の段構えが出てきた**、書かずに:
**プレートが乗っている間はレーン**(5 枚 = 全員に 140 ゴールドで、
どの単体のドラゴンより大きい)、**tick 40 でプレートが落ちたら川**
(ドラゴンと soul)、**tick 70 からバロン**。
**LoL の時間割が、1 つの比較から落ちてきた。**

**テストの形も変わった。** 各機構の単体テストの最後に
**「これはプレイで起きるか」を 1 本置く** ——
9 編成の総当たり 72 試合で、
**プレートは 306 枚落ち**(プレートが有効な tick の間に)、
**ゲートは 74 回開いて 40 回閉じ**、**ヘラルドは取られ**、
**soul は 72 試合中 2 回**(LoL の実際の頻度に近い)、
**部品 1133 個・完成品 601 個**が買われる。
**単体テストは「規則が正しいか」を言い、これは「規則が在るか」を言う。**

## 11. 新しい 4 クラス

機構を足したら**問題集が古くなった** —— 124 問は
「足す前のゲーム」を測っていた。**4 クラス 29 問を足して 153 問**:

| クラス | 問 | truth の出処 |
| --- | --- | --- |
| `cs` | 12 | **算術**(いま farm はいくらか)と**再生**(3 tick 立ち続けたら何ゴールド損か、farm/poke/hold のどれが 1 tick 分得か) |
| `drake` | 6 | **再生**(4 元素を 1 つずつコピーに与えて集団戦を回す)と**算術**(soul まで何匹) |
| `brush` | 6 | **算術**(視界マスク ∩ ブッシュ)と**再生**(どのワードが一番多く見せるか、その伏せに踏み込んで生き残るか) |
| `siege` | 6 | **算術**(プレートはいくらか、ゲートが閉まる前に着くか) |

**`cs` の「3 tick 分の損」は再生で出している**、算術で出していない ——
**ウェーブは 1 tick に 1 匹補充される**ので
「いま低い 2 匹 × 3 tick = 6 匹」ではなく **4 匹**が正解で、
**この文の算術を私が間違える可能性があるから**シミュレータに聞いている。

**2 つ直した。** どちらも**問題集の側のバグ**で、数字は出ていた:

- **`siege_plates` は存在しないタワーについて聞いていた。** シナリオが
  相手の mid 外タワーにプレートを乗せ、**2 行後にそれを折ってレーンを開けて**いた
  ので、3 つの state すべてで**別のレーンの手付かずのタワーの枚数(140)**が
  正解になっていた。プレートを top に、開いたゲートを mid に分けたら
  正解は **140 / 56 / 0** になり、**床が 4/6 から 2/6 に落ちた** ——
  つまりそれまで**床は 3 問を無料で取っていた。**
- **`sc_brush` は 2 つの state で同じブッシュを照らしていた**ので、
  「どれが伏せられるか」の答えが 2 問とも同じだった ——
  **1 つの state を 2 回測っていた。**

**どちらも「クラスに 5 問以上」「定型答えが 5 分の 4 を超えない」を通っていた。**
不変条件のテストは**問題集が壊れていること**は捕まえるが、
**問題集が同じことを 2 回聞いていること**は捕まえない。

## 12. 第 3 版: ジャングル、視界の奪い合い、そしてマップが梯子だった

第 2 版まで、**ジャングルと視界は名前だけ在って中身が無かった**:

- **ジャングルモンスターが居なかった。** ジャングルのノードは
  **champion が立っている間ずっと 16 ゴールド/tick を払う定額**で、
  取る対象も湧き直しも所有者も無い。
  つまり**「どの camp に回るか」という問いが存在しなかった** ——
  1 ノードに居座るのが最適で、答えは毎試合毎 tick 同じだった。
- **カウンタージャングルが不可能だった。** `a_jg_top` は
  **B にも A と同じ額を払う**ので、そこで farm しても**誰からも何も奪わない**。
- **視界は足すことしかできなかった。** `PlaceWard` が唯一の視界の手で、
  **相手のワードを消す行動がゲーム中に 1 つも無かった。**

足したもの:

| 機構 | 作られる判断 |
| --- | --- |
| **camp 4 つ**(1 ジャングルノードに 1 つ、所有者付き) | `Farm` で**丸ごと 1 回**取り(30 ゴールド + 22 xp)、**8 tick 下がる**。下がっている camp を farm すると**何も払われない**。**ジャングルには受動収入が無い**ので、そこに立つのは camp を取っているか tick を捨てているかのどちらか |
| **カウンタージャングル** | 相手側の camp を取ると**同額もらえて、相手は同じ 8 tick それを失う**。`camps_lost` はチーム単位で、**損をした側で数える** |
| **制御ワード** | **75 ゴールド**(アイテムと同じ財布)、視界は 24 tick、そして**着地した瞬間に範囲内の相手のワードを全部壊す**。以後その範囲に置かれた相手の通常ワードも tick 末に消える。制御ワード同士は**後に置いた方が勝つ** |

**そして測ったらマップが実リフトではなかった。** 距離を出したら:

- **ベースが両方のジャングル区画に直結**していて、
  ジャングル区画は**6 近傍**(ベース + 2 レーン × 2 ノード + 川)
- 結果、**自陣ベースが任意の 2 レーン間の 2 hop テレポート**、
  **ジャングラーはリコール後 camp まで 1 hop**、
  そして**ジャングルが全経路を短絡するのでベース間が全レーン 4 hop 同距離**

**同じ長さのレーン 3 本を高速道路が繋いでいるのはサモナーズリフトではなく、梯子だ。**

直した形は実リフトそのもの —— **ジャングル区画の出口は 3 つ**
(両隣のレーンの**外タワー**、つまり争う側の端、と川)、
**ベースの出口は 3 つ**(自陣の内タワー 3 本)。結果:

| ノード | バロンまで | ドラゴンまで |
| --- | --- | --- |
| `a1_top` | **2** | 4 |
| `a1_mid` | **2** | **2** |
| `a1_bot` | 4 | **2** |

**mid だけが両オブジェクトから等距離** —— だから mid が回るレーンになる。
top はバロンに近くドラゴンから遠く、bot はその逆 ——
だから**ドラゴンはマップの下半分を引き、バロンは上半分を引く。**
`a2_bot` はバロンまで **5 hop** で、これがマップの対角。
そして**ベース間は 6 hop、ジャングルはリコールから 3 hop** になった。

**まだ言えていないこと**: **mid はベース間の hop 数では短くない。**
実リフトでは mid は対角で純粋に短いが、
**1 レーン 5 ノードでは対角を表現できない** ——
top と bot に 6 つ目のノードを足す話になる。
**このサイズのホップグラフは「中心性」は買えるが「長さ」は買えない**、
と `map.mbt` の docstring に書いてある。

### 足した機構が、潜んでいたバグを掘り出した

**camp にタイマーを付けた瞬間に mirror 戦が壊れた**(8 節の 8 番)。
原因は camp ではなく **blink の同点処理**で、
`smart_action` は**距離が改善する最初の blink** を返していた ——
その「最初」は `adjacency` の並び順で、**左右で鏡像になっていない。**
**camp がジャングラーの目標を動かすまで、その経路が選ばれていなかっただけ。**

**これが 3 版通じて一番役に立った道具の使い方だ:**
**「mirror 戦は毎 tick mirror である」を全フィールドに広げておくと、
新しい機構を足すたびに、その機構とは関係ないバグを掘り出してくれる。**

### そして camp も 1 度死んでいた

第 2 版の 3 機構と同じ失敗をもう一度した ——
**最初の camp はプレイで動かなかった。**
ジャングラーが集団から離れるのは計画が最後の分岐まで落ちたときだけで、
**組み替えた計画はそこまで落ちない**ので、
150 tick で camp が 3 つ、カウンタージャングルは 0 回だった。
いまは **`Plan::grouped`** が
「この集合はチーム全員を要るか」(オブジェクト戦・落ちるタワーの防衛・開いたネクサス)を
持っていて、**要らないならジャングラーは farm に行く。**
**72 試合で camp が 100 個以上、カウンタージャングルも両ワードも発生する** ——
これが `jungle_wbtest.mbt` の最後のテストが見ているもので、
**このテストが `Plan::grouped` を存在させた。**

### 新しい 2 クラス

| クラス | 問 | truth の出処 |
| --- | --- | --- |
| `jungle` | 6 | **再生**(どの camp に回るか —— 各選択をコピーで強制して 10 tick 回す。相手の半分に踏み込んで生き残るか —— ブッシュの規則とカウンタージャングルが 1 問になる)と**算術**(あの camp は何 tick で戻るか) |
| `vision` | 5 | **算術**(どこに制御ワードを置けば相手の視界を最も削れるか。そして**そもそも 75 ゴールド払う価値が在るか**) |

**`vision` の 2 問目が一番効く** —— 相手が範囲内にワードを持っていなければ
**答えは false** で、**「常に制御ワードを買う」は外すたびに 75 ゴールド**。
床はまさにそれを答える。

そして **`vision_pit_is_dark` は sweep の問いを落とした** ——
相手のワードが全部範囲外だと**どの候補も 0 枚**なので、
`truth` が選択肢を全部受け入れて縮退する。
**それが正しい結果**で、その state は床が外す kind の問いだけを残した。

## 13. この実験で確定したパターン

1. **勝敗は判断の質の測定ではない。** 同じ実行が **12-0 で勝ち**、
   採点すると**ゴム印より明確に上と言えるクラスが 16 のうち 5 つ**、
   **そのうち 4 つは直前に足した機構のクラス**(4 節・6 節)。
   bot を相手にした勝率は**相手の弱点の形**を測っていて、
   **どの判断を直すかは 1 つも言わない。**
   そして**勝ち方の説明は行動の内訳に在った** ——
   1751 手のうち `farm` 1652 件(94%)・`structure` 0 件で、
   **構造物を一度も殴らずに相手の構造物だけが減っていた**(6 節)。
2. **正解率は「一番良い定型答え」に対して読む。** 床でもランダムでもなく。
   この列を足した瞬間に **`retreat` が 0.83** で引っかかり
   (「全部 walk_away」でモデルより上)、
   第 3 版の表では **`focus` 0.23 / `item` 0.37 / `ability` 0.40 が
   ゴム印の下**だと分かった。**足す前の版にはその行が無かった。**
3. **クラスが偏っていないかは、数えれば分かる。** 前の版の `fight` は
   **8 問中 7 問が体の数で決まって**いて、床の 0.88 はほぼそれだけだった。
   **直し方は手で差し替えることではなく掃くこと** —— 540 通りを再生して
   4 つのバケツに入れ、同数取れば**体を数える戦略が正確に 0.50**になり、
   **等式としてテストに固定できる**。そして
   **一度目の掃きは別の偏り方をした**(16 問が全部同じ 2 チーム)ので、
   **偏りの検査は 1 種類では足りない。**
4. **同じリクエストの 2 問を突き合わせると、整合性が測れる** ——
   **ただし共起の数を読む前に、周辺度数が何を強制しているか確かめる。**
   **16 局面のうち 13 で「勝てない」と答えて「いま殴れ」と答えた**のは事実だが、
   **`false` 14/16 と `fight_now` 15/16 からその 13 は自動的に出る**
   (14 + 15 − 16 = 13)—— **共起が下限に等しいとき、それは 2 つの
   周辺度数の言い換え**で、対の証拠ではない(4 節)。
   **同じ数字が、真値の側では読める**(4 は下限 0・上限 7 の内側)。
   **残るのは真値との比較**: ルールが両立を許すのは 4 局面なので
   **13 組のうち少なくとも 9 組は間違っている**(符号検定 p = 0.004〜0.012)。
   **確かめるコストは 1 行**で、確かめなかったコストは所見 1 つだった。
5. **「矛盾か、私の選択肢が粗いのか」は、選択肢を足しても割り切れない ——
   割合そのものが私の文言の関数だった。**
   2 択の `fight_now` を `win_and_fight` / `lose_but_fight` に割ったら
   **「勝てない」と言って殴った 41 局面のうち 30(73%)が中央**を選び、
   残り 27% を「文言の逃げ場が無い矛盾」と書いた。
   **同じ 3 択を 4 通りに書き換えたら、その割合は 56% / 59% / 74% / 100%** ——
   **1 つの文言では矛盾が 48 答え中 0 件**、別の文言では **44%**(4 節)。
   **並び順だけで 74% → 59%** も動く(文は 1 字も変えていない)。
   **効いたのは長さでも「弁護」でもなく、
   「outright には勝たない」の 1 句が中央に在るか**だった。
   そして**正解率はどの文言でも全部ゴム印の下**(0.31〜0.38 対 0.56)——
   **整合するようになることと正しくなることは別**。
   **変わらなかったのは周辺度数だけ** ——
   7 arm・21 run 全部で両立の数は下限に等しい(4 番)。
6. **点数が自分の文言の関数かどうかを確かめる。** `fight` の noul の 2 面を
   **3 節 対 1 節から 1 節ずつの鏡像に書き直しただけ**で、
   クラスの点が **0.50 → 0.63**、confidence が **0.53 → 0.28** に動いた ——
   **答えはどちらでもほぼ定型**だったので、
   動いたのは主に「どれだけ確信するか」。
   [51](51-question.md) はレバーが問いではなく事実だったと結論したが、
   **ここではレバーが問いだった。**
7. **1 回では読むな。** このレポートの最初の版は **22 問を 1 回ずつ**測って
   「calibration の向きが回によって反転する」を所見にしたが、
   **620 答えで測り直したら向きは安定して正しかった**(0.51 対 0.48)。
   **反転は標本の小ささの産物**だった。
   このリポジトリは他の実験で**ずっと `--repeat` を使ってきた**
   ([22](22-code-criteria.md) [25](25-thresholds.md) [31](31-orchestration.md))——
   **道具を持っていなかったのは私だけ。**
8. **それでも、採点していない confidence は校正の主張に使えない。**
   [02 §3](02-moba.md) は霧の読みの confidence を見て
   「情報がないときに自信を持たないのは望ましい」と書いたが、
   **採点したら 0.10 正解で confidence 0.43〜0.56** だった(5 節)。
9. ~~**1 つの数字は相手の性質を含む。**~~ → **撤回した。**
   第 1 版は霧の読みが **`scripted` 相手 0.36・`smart` 相手 0.02〜0.07** に
   割れるのを見て「相手の予測可能性の性質」と書いたが、
   **同じ相手に対して A 側 0.35〜0.43・B 側 0.12 にも割れていた** ——
   マップは対称で相手の policy も同じなので**有り得ない**。
   原因は**エンジンが互角の集団戦を必ず A 側に落としていた**ことで(8 節の 6 番)、
   直したら**片側 3 倍の差は p ≈ 0.14 まで縮んだ。**
   **残るのはもっと弱い一般則**: **測った差に説明を付ける前に、
   その差が環境のバグでないことを確かめる。**
   片側 3 倍は**説明が付けられる程度にもっともらしかった**ので、
   説明を書いてしまった。
10. **決定的なルールは、それ自体が oracle になる。** 「この集団戦は勝てるか」は
    再生すれば答えが出る。**`copy()` と「1 手だけ強制して残りは baseline」を
    用意しておくと、問いの半分が採点可能になる**上に、
    **問いの偏りを掃いて選別する道具**にもなる(3 番)。
11. **criteria = 合法手は、行動空間を 5 倍にしても成立する。**
    1751 判断で不正手 0 件、1 体あたりの選択肢は 20 前後(3 節)。
    **アイテムを 5 種から 11 種にし、行動の種類を 12 から 13 に増やしても
    0 件のまま。**
12. **環境の対称性はテストしろ —— 状態の 1 つの場ではなく、全部で。**
    第 1 版は mirror 戦が**ほぼ全部片側に落ちる**状態で勝率を 3 本測っていた
    (原因 2 つはどちらも「同点の割り方」)。
    第 2 版は**「mirror 戦は毎 tick mirror である」を 1 本のテストにした** ——
    位置・体力・経験値・復帰タイマー・キル数・装備・CS・クールダウン・
    ワードの残り・レーンの押し・構造物とプレート・ドラゴン・buff、**全部**。
    **書いたその日に 2 件出て、両方とも「死亡判定と支払いの順序」だった**:
    キルの経験値でレベルが上がると体力が増えるので、
    **体力 -6 の champion が自分のキルで 8 まで戻され生き残っていた。**
    **1 つの不変条件を全フィールドに広げるのが、いちばん安いバグ検出器**だった。
    そして**そのバグは公表済みの数字を 1 つも動かさなかった** ——
    **プレイからは到達できて、問題集からは到達できなかった**(8 節)。
13. **oracle を 2 つ作ると、片方が間違っていることが分かる。**
    集団戦の総当たりと全試合の総当たりは**別の順位**を出し、
    モデルは集団戦側に合っていた(7 節)。
14. **「規則が正しいか」と「規則が在るか」は別のテスト。**
    第 2 版で足した 6 機構のうち **3 つは実装した直後、プレイで一度も起きなかった** ——
    単体テストは全部通り、型も通り、**128 tick の試合でドラゴンが 1 匹**だった
    (10 節)。原因は `team_plan` の**分岐の順序が常時拒否権**になっていたことで、
    **分岐の順序は「たいていはこうだが、これは違う」と言えない。数字は言える。**
    いまは各機構のテストの最後に**「これはプレイで起きるか」を 1 本**置いてある
    (72 試合でプレートが 306 枚、soul が 2 回、部品 1133 個)。
    **そして直し方も 2 回間違えた** —— 川に 1 つの値段を付けたら
    **champion がタワーに触らなくなり**、到達可能性の関門を付け忘れたら
    **両チームが川に駐車して 150 tick 何も起きなかった。**
15. **ベンチマークの不変条件もテストにする。** 現在 10 本 ——
    正解が選択肢に在る / 選択肢の全部が正解ではない / 問名が一意 /
    クラスは 5 問以上 / どのクラスも床が全問正解ではない /
    **どのクラスも定型答えで 5 分の 4 を超えない** /
    **解析の truth がベンチマーク自身の truth と同一** /
    **言い換えた問いが同じ問いになっている** /
    **言い換えた問いが意図した通りに違っている**(A/B の残り半分。
    2 つの arm が同一になる書き間違いは「文言は効かない」を無料で出す)/
    **共起が周辺度数の下限に等しいことを検出できる**。
    **後から足した 3 本は、足した瞬間に落ちた。**
    **採点表は出るが意味を持たない**という壊れ方は、数字を見ても気付けない。
    そして**後の 3 本は解析の側**で、
    **1 本目(truth が同一)を書いたのは `Game::retreat_scores` を
    切り出す理由がそれだった**から ——
    真値のコピーが 2 つあると「truth が食い違う」が読めなくなる。
16. **新しい機構は、それとは関係ない潜んでいたバグを掘り出す ——
    不変条件を全フィールドに広げておけば。**
    第 3 版で camp にタイマーを付けた瞬間に mirror 戦が壊れたが、
    原因は camp ではなく **blink の同点処理**だった(8 節の 8 番)——
    `smart_action` は距離が改善する**最初の** blink を返していて、
    その「最初」は `adjacency` の並び順で、**左右で鏡像になっていない。**
    **camp がジャングラーの目標を動かすまで、その経路が選ばれていなかっただけ。**
    第 1 版から数えて**同じ「同点をリスト順で割る」バグが 3 件目**で、
    3 件とも別の場所に在った(経路・死亡判定・blink)。
    **「mirror 戦は毎 tick mirror である」を全フィールドに広げておくのが、
    このリポジトリで一番安いバグ検出器**になった。
17. **片側差を見たら、説明を書く前にエンジンを 3 回疑う。**
    霧の読みは **A 側 0.25 対 B 側 0.008** で、第 1 版の同じ形の差は
    **エンジンのバグだった**(8 節の 6 番)。第 3 版は説明の前に 3 本書いた ——
    **mirror 戦が毎 tick mirror**、**両チームが鏡像の情報を受け取っている**
    (ノードごとに一致。「見えるノードの数が同じ」では
    両チームが別の半分を見ていても通る)、**回避が両側で同じに効く**。
    3 つとも緑なので**非対称性はルールにも state にも無い** ——
    残るのは読み方で、**容疑者は「B 側の視界は鏡像」**。
    **1 度目は所見を 1 つ失い、2 度目はエンジンを除外できた。**
18. **マップは問題の一部。** 第 3 版でジャングルの接続を直したら、
    **問いを 1 文字も変えずに `brush` クラスが 0.67 から 1.00 に上がった**
    (12 節)。ジャングル区画の出口が 6 本から 3 本になって
    **「どのノードが伏せられるか」が絞れる形になった**だけだ ——
    **点数が環境の形の関数**だという、5 番(文言の関数)の空間版。
    そして**測るまで気づかなかった**: 距離を出したら
    **ベース間が全レーン 4 hop 同距離**で、自陣ベースが
    **任意の 2 レーン間の 2 hop テレポート**だった ——
    **同じ長さのレーン 3 本を高速道路が繋いでいるのは梯子**で、リフトではない。
19. **その不変条件は「同じことを 2 回聞いていること」を捕まえない。**
    第 2 版で足した 4 クラスのうち 2 つに、**問題集の側のバグ**が在った ——
    `siege_plates` は**シナリオが 2 行後に折るタワー**について聞いていて
    3 つの state すべてで別のタワーの枚数が正解になり、
    `sc_brush` は**2 つの state で同じブッシュを照らして**いたので
    2 問の答えが同じだった。
    **どちらも「クラスに 5 問以上」「定型答えが 5 分の 4 を超えない」を通っている。**
    見つけたのは**モデルの答えを問ごとに眺めた**とき ——
    **同じ truth が 3 回並んでいるのは、表では 1 行にしか見えない**(11 節)。
