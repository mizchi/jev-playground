# 59. 自然言語からテストを生成する(生成できたかではなく、壊れたときに落ちるか)

「文章 1 本からテストを作る」は簡単なほうの半分で、**価値のない半分**でもある。
クリック列を再生して最終 URL を見るテストは、**注文を記録しなくなったアプリに
対して緑のまま通る**。`#/confirm` には着くからだ。壊れたのは遷移ではない。

再現:

```bash
cd experiments/browser-chaos
npm install
npx tsx src/check-bugs.ts                           # 仕込んだバグの健全性(API 不要)
TYPESAFEAI_API_KEY=... npx tsx src/run-testgen.ts   # 生成 + 採点
TYPESAFEAI_API_KEY=... npx tsx src/run-testgen.ts --repeat 5            # §4.5 生成 5 回
TYPESAFEAI_API_KEY=... npx tsx src/run-testgen.ts --repeat 5 --routes   # §4.6 経路 4 通り
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --repeat 6       # §4.7 なぜ 1 経路か
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --decompose --repeat 6      # §4.8 採番 vs 画面テキスト
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --label-position --repeat 6 # §4.8 ラベル x 位置
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --long-list --repeat 6      # §4.9 候補 46 個でも成り立つか
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --filler-vocab --repeat 6   # §4.10 なぜ filler で確信が上がるか
```

---

## 結論先に

入力はこの 1 文だけ。

> Buy a Widget: put one in the cart, work through every checkout step, and place the order.

出力は 2 本の Playwright spec。採点は**ミューテーション**で、5 つの変異を仕込んだ
アプリに対して落ちるかどうかで測る(うち 3 つは本物のバグ、2 つは**壊れていない**)。

| spec | clean | cart | order | gate | label | slow | 捕まえた /3 | 見逃し | 脆い |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| replay(クリック列 + 最終 URL) | pass | **FAIL** | pass | pass | pass | pass | **1** | **2** | 0 |
| asserted(+ 事後条件) | pass | **FAIL** | **FAIL** | pass | pass | pass | **2** | 1 | 0 |

**`order` が分かれ目。**注文を記録しないが `#/confirm` には着くバグで、
**replay は通してしまう**。最終 URL だけを見ているから当然である。
事後条件のほうは `ordered=true` を見ているので落ちる。

**どちらも `gate` を見逃す。**これはメール必須のチェックが消えたバグで、
ハッピーパスはメールを埋めるので**チェックが消えたこと自体に触れない**。
positive なテストは、**欠けた negative チェック**を原理的に見つけられない。

コストは **16 コール / 15,417 入力トークン / $0.00065**。

この表は**生成 1 回**の結果である。後から 5 回独立に生成し
([§4.5](#45-追記-5-回独立に生成させた--差は成果物ではなく方式だった))、
さらに**経路が 4 通りある盤面**でも測った
([§4.6](#46-追記-経路が複数ある盤面を作って測った))。
1 → 2 の差は 5/5 で再現し、**経路は 1 つも散らばらなかった**。

## 1. 何を分担させたか

事後条件の作り方をこう割った。

- **候補はコードが出す。** ハーネスは各ステップの前後で status 行と `<h1>` を
  すでに知っている。**変わったものだけ**が候補になる。前から成り立っていた事実は
  「その操作が効いた証拠」になり得ないし、そういう assertion で埋まった suite が
  永久に緑になる原因である。モデルが捏造した事実はここを通れない。
- **どれが「結果」なのかは聞く。** 「status が `cart=1` になった」はカートに
  入れた結果。「見出しが Products になった」は真だが、クリックが何もしなくても
  真だった。これを分けるのはアプリについての判断で、モデルに払う価値がある半分。
  1 候補 1 `noul`。

57 と 58 と同じ分担で、**抽出は決定的に、判断はモデルに、逆はやらない。**

実際に何を残したか(`--verbose` の出力そのまま):

```
    drop 0.00  the app now reports cart=0
    drop 0.00  the app now reports email=empty
    drop 0.00  the app now reports address=empty
    drop 0.00  the app now reports ordered=false
    keep 0.88  the screen is now "Products"
    keep 0.95  the app now reports cart=1
    ...
    keep 0.94  the app now reports ordered=true
    keep 0.91  the screen is now "Order placed — thank you!"
```

1 手目(`link "Products"` のクリック)で status 行が初期値として現れるので、
候補には `cart=0` `email=empty` `address=empty` `ordered=false` が並ぶ。
**4 つとも 0.00 で落とされた。**「リンクを踏んだ結果カートが空になった」は
偽であり、それを assert したテストは何も証明しない。判断としては正しい。

そして 9 手のうち 2 手は `(no observable change to assert)` になった。
`#email` に入力する手で、**画面テキストも status も変わらない**(値は input の
`value` に入るだけ)。docs/05 §3 で踏んだのと同じ盲点で、ここでは害はない——
次の手の `email=set` が同じことを検査している。

## 2. 生成物

```ts
// GENERATED by experiments/browser-chaos (docs/59) — asserted variant.
// Goal given to the explorer, in words:
//   Buy a Widget: put one in the cart, work through every checkout step, and place the order.

  await page.locator("#next2").click();
  // the screen is now "Checkout — step 3 of 3" (consequence 0.90)
  await expect(page.locator("h1")).toContainText("Checkout — step 3 of 3");
  // the app now reports address=set (consequence 0.81)
  await expect(page.locator("#status")).toContainText("address=set");

  await page.locator("#place").click();
  // the app now reports ordered=true (consequence 0.94)
  await expect(page.locator("#status")).toContainText("ordered=true");
  // the screen is now "Order placed — thank you!" (consequence 0.91)
  await expect(page.locator("h1")).toContainText("Order placed — thank you!");
```

ロケータは **id があれば `#id`、無ければ `getByRole(role, { name })`**。
探索中に使っている `[data-probe-idx="n"]` は**ファイルに書けない**——
プローブが毎ステップ刻み直す属性で、次の手で別の要素に付く。
「いま操作する方法」と「あとで見つける方法」は別物で、
後者を持っていなかったので `ProbedCandidate.locator` を足した。

これが `label`(Continue ボタンを改名する変異)で脆くならなかった理由でもある。
その 2 つは id を持っているので `#next1` / `#next2` で引かれ、改名は当たらない。
nav のリンクは id が無いので `getByRole` になるが、そちらは改名していない。
**id のある要素を id で引く**だけで、脆さの大半は消える。

## 3. 採点の作り方(ここでも自分のバグを 3 つ踏んだ)

### 3.1 全部 FAIL、clean も含めて

最初の採点表は 12 マス全部 FAIL だった。原因は
`net::ERR_ABORTED`——**アプリを配っているのがこのプロセス自身**で、
`execFileSync` がイベントループを止めていた。リクエストに答える人がいない。

> **全部落ちる採点ハーネスは、何も生成できていない生成器と見分けがつかない。**

`execFile` を promisify して直った。

### 3.2 生成したテストが、生成元のアプリに対して落ちる

次は replay だけが全マス FAIL。最終 URL の assertion を
`steps[last].hash` から作っていたが、`StepLog.hash` は**そのステップが始まった
場所**なので、最後の手の `hash` は `#/checkout-3` である。
`#/confirm` を名乗るべきところで 1 画面手前を名乗っていた。
`hashAfter` を記録して直した。

どちらも「もっともらしい表」を出してくるバグで、58 §2.3 と同じ種類。
**採点側が壊れているときは、実験は失敗せずに結果を返す。**

### 3.3 追記: 「壊れていない」対照の `?bug=slow` が、最初から壊れていた

3 つ目は**対照側**だった。`?bug=slow` は「全レンダを 400ms 遅らせるが何も壊さない」
はずの非バグで、本稿は `brittle 0` の根拠にこれを使っている。
[§4.6](#46-追記-経路が複数ある盤面を作って測った) の盤面で初めて露出した ——
そこでは生成された spec の最初の操作が**着地画面**にあるので。

**版 1(本稿の測定に使った版):** 遅延したレンダがガードに再入して
また遅延する。永久に。`#view` の長さが clean で 385、`slow` で **0**、
2.5 秒待っても 0 —— **画面が一度も描かれない**。
ここまでのウォーカーは全部、最初のコントロールに**ハッシュ遷移で**到達していて、
hashchange が 2 度目の `render()` を呼び、そちらはガードを素通りして描画する。
だから**着地画面で操作しない限り見えなかった**。
出方は `brittle 5` で、つまり**生成物の脆さとして**現れた。

**版 2(私の 1 回目の修正):** 空白画面は直ったが、1 操作につき 2 回描く
(素通り分 + 400ms 分)。`render()` は innerHTML を差し替えるので、
2 回目が **Playwright が解決済みのボタンを切り離す** —— クリックは
リスナのないノードに当たり、画面が進まない。
出方は `asserted` が 5 試行中 4 回 `slow` で落ちる、つまり**flaky な spec として**。
推測せずに失敗を捕まえたら、assertion が **9 回リトライして毎回
`<h1>Checkout — step 1 of 3</h1>`** を読んでいた ——
遅れているのではなく、**進んでいない**。

**版 3(合体させる):** 遅延中の呼び出しはタイマーを張り直すだけにし、
発火した 1 回が描く。linear の asserted を `?bug=slow` に 5 回当てて **5/5 pass**
(版 2 では 2/5)。

> **5 行の「何も壊さない」対照を 3 版書いて、間違っていた 2 版はどちらも
> エラーではなく「もっともらしい数字」を返した。** 空白画面は brittle に、
> 二重描画は flaky に化けた。どちらも**着地画面から始まる盤面**でしか
> 踏めないので、2 本のレポートが対照の壊れたまま出ている。
> → `check-bugs.ts` に「全変異が**ハッシュ遷移なしで**着地画面を描く」を追加した。
> 58 §2.3 が「解決しないセレクタが効かないボタンに化ける」で、これは
> **壊れた対照が生成物の欠点に化ける**。同じ形が 3 回目である。

## 4. 変異の選び方

`?bug=NAME` で 1 つずつ壊す。**3 つは本物のバグ、2 つは壊れていない**——
後者が無いと「たくさん落ちるテスト」が良いテストに見えてしまう。

| 変異 | 中身 | 本物? | 誰が捕まえるべきか |
| --- | --- | --- | --- |
| `cart` | カートに入らなくなる | ✔ | 誰でも(フローが物理的に進めない) |
| `order` | `#/confirm` に着くが注文を記録しない | ✔ | **事後条件を持つものだけ** |
| `gate` | checkout 2 がメール必須をやめる | ✔ | **negative テストだけ** |
| `label` | Continue ボタンを改名 | ✘ | 誰も(落ちたら脆い) |
| `slow` | 全 render を 400ms 遅らせる | ✘ | 誰も(落ちたら待ちが足りない) |
| `express` | **express 経路でだけ**住所を記録しない | ✔ | **その経路を通った spec だけ**([§4.6](#46-追記-経路が複数ある盤面を作って測った)、`?routes=1` のときのみ) |

`check-bugs.ts` が、この分類を**仮定ではなく実測**で固定している。id で
ハッピーパスを歩いて、clean は `ordered=true` で `#/confirm`、`order` は
`#/confirm` なのに `ordered=false`、`cart` は checkout ボタンに到達できない、
までを assert してある。**変異がハッピーパスから見えないこと自体**も
assert している(`gate`)——見えない変異で生成器を採点するのは不公平なので。

## 4.5 追記: 5 回独立に生成させた —— 差は成果物ではなく方式だった

「捕まえたバグ 1 → 2」は**生成 1 回ずつ**の結果だった。
[04 §1](04-agent-built-prompts.md#1-結果-書かせたままでは当たらないばらつきが巨大) が
同じリポジトリで「同じプロンプトで 10/24〜23/24 に振れる」を測っているので、
**n=1 では方式の差と成果物の当たり外れが区別できない。** 5 回回した
(`--repeat 5`、探索 seed は 7〜11 で毎回違う):

| spec | 捕まえた /3(各試行) | 平均 | brittle | clean で誤検出 |
| --- | --- | --- | --- | --- |
| replay | 1, 1, 1, 1, 1 | **1.00** | 0 | 0 |
| asserted | 2, 2, 2, 2, 2 | **2.00** | 0 | 0 |

**5/5 で asserted > replay。** 捕まえた集合まで毎回同一だった ——
`replay` は `cart` だけ、`asserted` は `cart` と `order`。
有効手 9 手・採用した assertion 10 個・ゴール到達 5/5 も**全試行で一致**。
80 コール / 77,085 トークン / **$0.00324**。

→ **この主張については n=1 の心配は当たらなかった。** 差は方式にあり、
機構(replay は最終 URL しか見ない)がそのまま出ている。
`gate` の見逃しも 5/5 で、こちらも機構どおり(§4)。

> [!NOTE]
> **ただし「生成は安定している」とは読まないこと。** ここが安定したのは
> **盤面がほぼ一意だから**である —— ゲート付きの直線フローで、
> 注文までの 8 手はどれも選択の余地が小さい。だから seed を変えても
> 有効手が 9 手で揃う。[04](04-agent-built-prompts.md) が振れたのは
> **質問設計**という遥かに自由な作業で、そこと比べてはいけない。
> **ゴールへの経路が複数ある盤面**が本当のテストで、それを
> [§4.6](#46-追記-経路が複数ある盤面を作って測った) で作って測った ——
> **経路は増えず、見えない範囲が増えた。**

## 4.6 追記: 経路が複数ある盤面を作って測った

[§4.5](#45-追記-5-回独立に生成させた--差は成果物ではなく方式だった) の安定は
**盤面が一意だったから**かもしれない、というのが残った疑いだった。
`?routes=1` で**ゴールへの経路を 4 通り**にした:

| | 選択肢 |
| --- | --- |
| カートに入れる | `#/products` の「Add Widget to cart」 / `#/home` の「Buy Widget now」(入れて遷移まで) |
| 決済する | 3 ステップの checkout / `#/express`(1 画面に両フィールド + Place order) |

`#/express` は**フィールドの順番も自由**なので、経路を変えずに手順列だけ
変えることもできる。そして採点できるようにするため、**検証を経路ごとに置いた** ——
`?bug=gate` は 3 ステップ側しか通らないチェックを弱め、新しい
`?bug=express` は express 側でだけ住所を記録しなくする。
**spec は自分が通った経路のバグしか捕まえられない。**

3 掃引、各 5 回独立生成(`?bug=slow` を直した後の数字):

| 盤面 / ゴール | 手数 | 捕まえた(replay / asserted) | 見逃し | brittle | 経路 | 相異なる経路 |
| --- | --- | --- | --- | --- | --- | --- |
| linear(§4.5 の再現) | 9 | 1 / 2 | 2 / 1 | 0 | `products+steps` | **1/5** |
| routes、元のゴール文 | 7 | 1 / 2 | 3 / 2 | 0 | `buynow+steps` | **1/5** |
| routes、経路を名指さないゴール文 | 7 | 1 / 2 | 3 / 2 | 0 | `buynow+steps` | **1/5** |

**経路は 1 つも散らばらなかった。** 4 通り用意して 5/5 が同じ経路、
手順列まで 5/5 同一である。

**ゴール文のせいではない。** 元の文には
「work through every checkout step」という **3 ステップ側を名指す句**があったので、
それを落としただけの `--neutral-goal` を走らせた ——
**結果は 1/5 のまま**で、`buynow+steps` も変わらなかった。
(この確認を省くと、測っていない要因について結論を書くことになる。本稿が
[§6](#6-正直な限界) で直された種類の誤りである。)

**ただし選好は盤面で変わった。** linear では `products+steps`(9 手)、
routes では `buynow+steps`(7 手)。新しいコントロールは**見えていて使われている** ——
カートへの近道は取り、決済の近道は取らない。

そして本題:

> **`?bug=express` は 5/5 で見逃された。** 通らなかった経路のバグは
> **構造的に見えない**。本物のバグの分母が 3 → 4 に増えて、
> `asserted` の得点は 2 のままである。
> → **経路を増やすと、ばらつきではなく「見えない範囲」が増えた。**

だから §4.5 の安定は**方式の再現性ではなく、経路の再現性**だった。
**試行をまたいで点が動かないことは、カバレッジの証拠にならない** ——
動かないのは通る道が同じだからで、カバレッジはその道に閉じている。

```bash
npx tsx src/run-testgen.ts --repeat 5                          # linear
npx tsx src/run-testgen.ts --repeat 5 --routes                 # 4 経路
npx tsx src/run-testgen.ts --repeat 5 --routes --neutral-goal  # + 経路を名指さない
```

**副産物:** この盤面が [§3.3](#33-追記-壊れていない対照の-bugslow-が最初から壊れていた) の
対照のバグを 2 つ露出させた。着地画面から始まる経路が存在しなかったので、
それまで踏めなかった。

## 4.7 追記: なぜ 1 つの経路に寄るのかを測った

[§4.6](#46-追記-経路が複数ある盤面を作って測った) は「経路が散らばらない」で終わって、
**理由は測っていない**と書いた。理由の候補は 3 つあった。
経路を決めているのは**カート画面の 1 判断**だけなので、
7 手の実行を回さずにそこだけ聞く(1 条件 1 リクエスト × 6 回)。

**argmax ではなく分布を読む。** 「0.51 対 0.49 を argmax が割った」と
「0.69 対 0.31」は、同じ 6/6 のまったく違う説明である。

| 条件 | 画面上の順 | 選んだ | p(3 ステップ) | p(express) |
| --- | --- | --- | --- | --- |
| `base` | checkout > express | **checkout 6/6** | 0.690 | 0.310 |
| `no-multistep`(指示句を削除) | checkout > express | **checkout 6/6** | 0.675 | 0.325 |
| `express-first`(`?exfirst=1`) | **express > checkout** | **checkout 6/6** | **0.888** | 0.112 |
| `labels-swapped`(`?exswap=1`) | checkout > express | **express 6/6** | 0.100 | **0.900** |
| `express-only`(checkout を出さない) | express | express 6/6 | 0.000 | 1.000 |

**答えはラベルだった。** `labels-swapped` は 2 つのボタンの**文字列だけ交換**して
id は動かさない。すると**選ばれる id が入れ替わる** ——
p(express) が 0.310 → **0.900**。
つまりドライバは**経路を選んでいない。「Proceed to checkout」というラベルを選んでいる。**

3 つの候補のうち 2 つは外れた:

- **位置ではない。** express を先に描いても **checkout 6/6** のままで、
  しかも p(3 ステップ)が 0.690 → **0.888 に上がった**。
  文書順のバイアスなら逆に動くはずである。
  (**なぜ強まるのかは分からない。** n=6 で安定しているが機構は持っていないので、
  観測として置く。)
- **指示句でもない。** picker の instructions にある
  「prefer advancing a multi-step flow over restarting it」は
  **この盤面より前に**書かれたもので、3 ステップ側を名指している ——
  [§4.6](#46-追記-経路が複数ある盤面を作って測った) の `--neutral-goal` は
  **ゴール文しか触らないのでここに当たらない**。これが本命だと思って削ったが、
  0.690 → 0.675 で**ほぼ動かなかった**。
- **同点でもない。** `base` は 0.690 / 0.310 で、コイン投げを argmax が割った形ではない。
- **能力の問題でもない。** express だけ出せば **1.000** で選ぶ。
  認識できていないのではなく、「Proceed to checkout」があるときに選ばれないだけ。

> **ラベルが経路を決めている。** ゴールは結果を名指し(「place the order」)、
> コントロールは遷移で名付けられている。「Proceed to checkout」は
> **その遷移の正規の名前**に見え、「Express checkout」は**変種**に見える。

## 4.8 追記: `express-first` が強まる理由 —— 後に描かれたほうが得をする

[§4.7](#47-追記-なぜ-1-つの経路に寄るのかを測った) は
「express を先に描くと p(3 ステップ)が 0.690 → 0.888 に**上がる**。理由は分からない」
で終わった。まず、**`express-first` は 1 要因ではなかった**。
`data-probe-idx` は文書順に刻まれるので、`?exfirst=1` は 2 つを同時に動かす:

- **採番** —— express が小さい index を取り、criteria マップでも先に来る
- **画面テキスト** —— `#view` の innerText が Express を先に並べる

§4.7 がこれを「位置」と呼んだのは不正確で、実際は両方である。
両方の実ページを読み込んで、**候補マップを一方から・画面テキストを他方から**送る 2×2:

| 腕 | 候補 | 画面テキスト | p(3 ステップ) | p(express) |
| --- | --- | --- | --- | --- |
| base | base | base | 0.688 | 0.312 |
| **採番だけ** | ex | base | **0.827** | 0.173 |
| **画面テキストだけ** | base | ex | **0.805** | 0.195 |
| exfirst | ex | ex | 0.888 | 0.112 |

**2 つのチャネルは同じ向きに押していて、ほぼ足し算**(+0.139 と +0.117 で、
両方だと +0.200。1 に近づくぶん頭打ち)。
(混合腕では候補マップと画面テキストが順序について食い違う ——
ブラウザが作らないページである。分解の代償で、両端は実ページ。)

### それで、押しているのは何なのか

同じ向きということは、**「位置」そのもの**が効いている。
では何に対して効くのか —— ラベルか、経路か、それとも**順番の後ろ**か。
ラベル × 位置の 2×2 を実ページ 4 枚で回し、**ラベル単位で**質量を読んだ:

| セル | 描画順 | 選んだ | p("Proceed") | p("Express") |
| --- | --- | --- | --- | --- |
| P 先 / E 後 | P>E | P 6/6 | 0.680 | 0.320 |
| E 先 / P 後 | E>P | P 6/6 | **0.892** | 0.108 |
| **ラベル交換** E 先 / P 後 | E>P | P 6/6 | **0.903** | 0.097 |
| **ラベル交換** P 先 / E 後 | P>E | P 6/6 | 0.702 | 0.298 |

**順番を揃えると、ラベル交換は何も動かさない**(0.680 対 0.702、0.892 対 0.903)。
動かすのは描画順だけで、しかも**対称**:

```
"Proceed" を先 → 後(通常ラベル):   0.680 → 0.892   (+0.212)
"Proceed" を後 → 先(ラベル交換):   0.903 → 0.702   (−0.202)
```

> **`express-first` は 3 ステップ経路を強くしていない。
> 「Proceed to checkout」を 2 番目に移しただけで、後に描かれた候補が
> 約 +0.21 得をする。** ラベルにも経路にも依らない。
> 2 つのボタンで確率質量の 100% を分け合っている(残り 14 候補は ~0)ので、
> これは純粋な 2 択の中の**順序効果**である。

つまり §4.7 の 2 つの答えは層になっている:

1. **どちらが選ばれるか**はラベルが決める(「Proceed to checkout」が勝つ、4 セル全部で 6/6)。
2. **どれだけの差で勝つか**は描画順が決める(後ろが +0.21)。

→ **候補の並び順は中立ではない。** [62 §6.1](62-browser-accuracy.md#61-ゴールに対する語彙検索は使えない) は
「文書順は切り詰めの基準として強い」(先頭 20 件で recall 10/10)だったが、
**同じ文書順が選択の重みも動かしている**。
絞り込みで順番を変える機構(検索・視野・再ランク)は、
**候補集合を変えるだけでなく判断も動かす**。

```bash
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --decompose --repeat 6
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --label-position --repeat 6
```

各 24 コール / 19,152 トークン / **$0.00080**。

## 4.9 追記: 長いリストでは成り立たなかった —— +0.21 は短いリストの話

[§4.8](#48-追記-express-first-が強まる理由--後に描かれたほうが得をする) は
**16 候補の隣接 2 択**で測った。限界として「長いリストで成り立つかは未測定」と
書いたので、測った。`?wide=40` が 40 個の filler を足して**候補 46 個**にする。

### Part 1: 実ページ、ブロック位置 × 並び順

`?fillerpos=before` で filler を先に置くと 2 つの候補がリストの後方に移る ——
**絶対位置の対照が既存のフラグで作れる**。

| セル | 2 候補のスロット | 選んだ | p("Proceed") | p("Express") | p(他 44 個) |
| --- | --- | --- | --- | --- | --- |
| 前ブロック、P 先 | P@10 E@11 | P 6/6 | 0.897 | 0.103 | **0.000** |
| 前ブロック、E 先 | E@10 P@11 | P 6/6 | 0.948 | 0.052 | 0.000 |
| 後ブロック、P 先 | P@50 E@51 | P 6/6 | 0.900 | 0.100 | 0.000 |
| 後ブロック、E 先 | E@50 P@51 | P 6/6 | 0.922 | 0.078 | 0.000 |

```
並び順の効果(前ブロック): 0.897 → 0.948  (+0.052)
並び順の効果(後ブロック): 0.900 → 0.922  (+0.022)
ブロック位置の効果:        0.897 → 0.900  (+0.003)
```

> **§4.8 の +0.21 は 16 候補での数字で、46 候補では +0.05 / +0.02 に縮む。**
> そして**絶対位置はまったく効かない**(+0.003)——
> 「リストの後ろほど強い」ではなかった。**隣接 2 つの相対順序**の話で、
> それも**リストが伸びると薄まる**。

> [!IMPORTANT]
> **追記:** [§4.10](#410-追記-filler-で確信が上がる理由--語彙ではなく個数そして-003-は誤差) で
> 同じセルを 2 回回して**誤差の床が 0.04 だと分かった**。
> それを当てると上の読み方は 1 段強くなる ——
> 46 候補での **+0.022(後ブロック)は床の下**、**+0.052(前ブロック)も床のすぐ上**。
> 「薄まる」というより **46 候補では並び順の効果は誤差と区別できない**、が正しい。
> 16 候補の +0.21 は床の 5 倍なので、そちらは残る。

### Part 2: 間隔(候補マップのみ)

間隔はどのページでも作れないので、マップを並べ替えて送った
(画面テキストは**送っていない** —— 矛盾するので。§4.8 の分解でいう
マップ側チャネルだけの測定)。

| 配置 | p("Proceed") | p("Express") |
| --- | --- | --- |
| P → E、間隔 1 | 0.972 | 0.028 |
| E → P、間隔 1 | 0.973 | 0.027 |
| P → E、間隔 45 | 0.973 | 0.027 |
| E → P、間隔 45 | 0.978 | 0.022 |

間隔 1 / 5 / 15 / 45 のどれでも並び順の効果は **±0.005**、つまり無い。

> [!NOTE]
> **ただしこの Part 2 は検出力が無い。** 画面テキストを送っていないので
> p("Proceed") が最初から **0.97** で、+0.05 の効果が乗る余地がほぼ無い。
> 「間隔は効かない」と読んではいけない ——
> **飽和した条件では測れていない**、が正しい。

### 副産物: 44 個の filler は質量を 1 つも取らない

全セルで p(他 44 個) = **0.000**。この filler は
[62 §6.1](62-browser-accuracy.md#61-ゴールに対する語彙検索は使えない) のために
**ゴールの語彙から意図的に**作られていて、語彙検索では正解より上に来る。
それでも**モデルは 1 つも選ばない**。
→ **語彙類似で上に来るものと、モデルが選ぶものは別**という 62 §6.1 の非対称が、
retrieval 側ではなく**確率質量の側**で確認された形。

そして候補を 16 → 46 に増やすと p("Proceed") は **0.680 → 0.897 に上がった**。
無関係なコントロールを 40 個足したほうが**正解への確信が強い**。
(機構は持っていない。観測として置く。)

## 4.10 追記: filler で確信が上がる理由 —— 語彙ではなく**個数**、そして 0.03 は誤差

[§4.9](#49-追記-長いリストでは成り立たなかった--021-は短いリストの話) の副産物
「無関係なコントロールを 40 個足すと p("Proceed") が 0.680 → 0.897 に**上がる**」の理由。

まず **40 個が算術で効くことはあり得ない** —— filler は質量を 0.000 しか取らないので、
2 候補の**比**を動かせない。残るのは中身か個数である。

### 仮説: 語彙の希釈(→ 外れた)

既定の filler は**ゴールの語彙から意図的に**作られていて、`?wide=40` では
"checkout" を含むラベルが 8 個、"express" を含むラベルが 8 個並ぶ ——
つまり両候補が同じだけ薄められる。`?fillervocab=` でこの対称性を崩した:

| セル | 候補数 | p("Proceed") run 1 | run 2 |
| --- | --- | --- | --- |
| filler なし | 16 | 0.712 | **0.673** |
| 8 個、mixed | 24 | 0.798 | 0.810 |
| 40 個、mixed | 56 | 0.878 | 0.887 |
| 40 個、neutral(ゴール語彙なし) | 56 | 0.853 | 0.855 |
| 40 個、express(全ラベルに "express") | 56 | 0.878 | 0.872 |
| 40 個、checkout(全ラベルに "checkout") | 56 | 0.853 | **0.868** |

**語彙は効いていない。** 4 プールの幅は **≤0.032** で、しかも
**2 回の実行で順序が入れ替わる**(run 1 では checkout = neutral = 0.853 ときれいに
並んだが、run 2 では 0.868 と 0.855 に散る)。
希釈仮説の予測は「express プールで上がり、checkout プールで下がる」だったが、
**その向きには動かなかった**。

> [!IMPORTANT]
> **同じセルを 2 回回したら 0.712 → 0.673 と 0.04 動いた。**
> これが誤差の床で、**語彙の差 0.03 はその下**である。
> 1 回目の「checkout と neutral が 0.853 でぴったり一致」は偶然だった ——
> **再実行しなければ、それを機構として書いていた。**
> (この repo で 3 回目の同型の失敗:
> [58 §2.3](58-coverage-guidance.md#23-セレクタが-1-つも当たっていなかったこれが一番痛い)、
> [§3.3](#33-追記-壊れていない対照の-bugslow-が最初から壊れていた)。)

### 効いているのは個数。しかも 2 チャネルある

filler は**候補**と**画面テキスト**を同時に増やす。両ページを捕まえて交差させた
(交差セルは 2 つが食い違う。§4.8 と同じ代償):

| | 画面テキスト 16 | 画面テキスト 56 |
| --- | --- | --- |
| **候補 16 個を提示** | 0.673 | 0.783 |
| **候補 56 個を提示** | 0.845 | 0.887 |

```
提示数 16 → 56(テキスト 16): +0.172
提示数 16 → 56(テキスト 56): +0.104
テキスト 16 → 56(提示 16):   +0.110
テキスト 16 → 56(提示 56):   +0.042
```

**提示する候補数のほうが大きいチャネル**(+0.10〜+0.17)で、
画面テキストも効く(+0.04〜+0.11)。どちらも同じ向きで、やや頭打ち。

**機構は分かっていない。** 「無関係な選択肢を増やすと 2 択の確信が上がる」
という観測で、なぜそうなるかはここからは言えない。
語彙でないこと・提示数が主チャネルであることまでが測れた範囲である。

### 副産物: 「絞って提示する」は confidence を下げる

上の表の **「候補 16 個を提示 / 画面テキスト 56」= 0.783** は、
[62 §6.4](62-browser-accuracy.md#64-テキストではない絞り方が答えだった) の絞り込みそのものである ——
**ページには 56 個あるが、提示するのは 16 個**。
全部提示した 0.845 より **0.06 低い**。

62 §6.4 は「視野で絞るとトークン −67%、精度は同じ」だった。

> [!IMPORTANT]
> **ただしこれは 62 §6.4 の盤面には転移しなかった。**
> あちらの `viewport` 腕で同じことを測り直したら
> **平均 conf 0.76 対 0.77 で、誤差の床の内側**だった
> ([62 §6.4 の追記](62-browser-accuracy.md#64-テキストではない絞り方が答えだった))。
> 違いは候補数の領域である —— ここは **2 候補が質量の 100% を分け合う** 56 → 16 で、
> confidence は実質「2 択の差」。あちらは 214 → 58-64 で、どちらの腕も候補が数十個あり、
> [§4.9](#49-追記-長いリストでは成り立たなかった--021-は短いリストの話) が
> 「数十個あると順序も個数も誤差に埋まる」と測った領域に入っている。
> → **同じ機構でも、候補数の領域が違えば数字は移らない。**
> 「絞ると confidence が下がる」は**候補が少ないときの話**として読むこと。

```bash
TYPESAFEAI_API_KEY=... npx tsx src/run-route-choice.ts --filler-vocab --repeat 6
```

## 5. わかったこと

1. **「生成できた」は結果ではない。** クリック列 + 最終 URL の spec は
   3 つのバグのうち 1 つしか捕まえず、注文を記録しないアプリに対して緑だった
   (結論先に)。
2. **事後条件が差の全部。** 同じクリック列で、捕まえた数が 1 → 2 になる。
   差分は「アプリが自分で印字している状態」を見るかどうかだけ(§2)。
   **5 回独立に生成させて 5/5 で同じ差**、捕まえた集合まで毎回同一だった(§4.5)。
   経路を 4 通りにした盤面でも **5/5 で同じ差**(§4.6)。
3. **候補は前後の差分から出す。** 前から真だった事実は証拠にならない。
   実際、初期状態 4 件はモデルが 0.00 で落とした(§1)。
4. **positive なテストは、欠けた negative チェックを見つけられない。**
   `gate` は両方が見逃した。ハッピーパスがメールを埋めてしまうから(§4)。
5. **「いま操作する方法」と「あとで見つける方法」は別物。** 毎ステップ刻み直す
   属性セレクタは探索には正しく、ファイルには書けない(§2)。
6. **id のある要素を id で引くだけで、改名に対する脆さは消える**(§2)。
7. **試行をまたいで点が動かないことは、カバレッジの証拠ではない。**
   経路を 4 通りにしても**選ばれる経路は 5/5 で同一**(ゴール文から経路を名指す句を
   落としても同じ)。安定していたのは方式ではなく**通る道**で、
   通らなかった経路のバグ(`?bug=express`)は **5/5 で見逃された**(§4.6)。
   → **経路を増やすと、ばらつきではなく見えない範囲が増える。**
8. **経路を決めているのはラベルである。** 2 つのボタンの**文字列だけ交換**すると
   選ばれる経路が入れ替わる(p(express) 0.310 → **0.900**)。
   位置(express を先に描く)でも、picker の指示句(「multi-step flow を優先」)でも、
   同点でもなかった —— どれも 6/6 で 3 ステップ側のままだった(§4.7)。
   → **カバレッジを広げたいならラベルを変えるしかなく、逆に文言の変更は
   カバレッジを静かに動かす。**
9. **候補の並び順は中立ではない。ただし候補が少ないときだけ。**
   隣接 2 つを入れ替えると 16 候補では **+0.21**(対称、ラベルにも経路にも依らない)。
   ただし **46 候補では +0.05 / +0.02 に薄まり、リスト内の絶対位置は +0.003 で効かない**
   (§4.8, §4.9)。
   → §4.7 と合わせて 2 層:**どちらが勝つかはラベル、どれだけの差で勝つかは順番。**
   → 絞り込みで順番を変える機構は候補集合だけでなく判断も動かすが、
   **それが問題になるのは候補が少ないときである。**
10. **誤差の床を測らずに 0.03 の差を解釈してはいけない。**
   同一条件を 2 回回すと **0.04 動いた**(0.712 と 0.673)。
   1 回目に「checkout プールと neutral プールが 0.853 でぴったり一致」と出て、
   **機構として書きかけた** —— 2 回目で順序が入れ替わり、噛み合わせが偶然だと分かった(§4.10)。
   → **再実行が唯一の検出器**で、[58 §2.3](58-coverage-guidance.md#23-セレクタが-1-つも当たっていなかったこれが一番痛い) と
   [§3.3](#33-追記-壊れていない対照の-bugslow-が最初から壊れていた) に続く 3 回目の同型。
11. **無関係な候補を増やすと 2 択の確信が上がる。効くのは個数で、語彙ではない。**
   候補 16 → 24 → 56 で p が **0.673 → 0.810 → 0.887**。
   提示数と画面テキストの 2 チャネルがあり、**提示数のほうが大きい**(+0.10〜+0.17 対 +0.04〜+0.11)。
   ゴール語彙を仕込んだ filler と無関係な filler の差は **≤0.032 = 誤差の床の下**(§4.10)。
   **機構は分かっていない。**
12. **「絞って提示する」が confidence を下げるのは、候補が少ないときだけ。**
   56 個のうち 16 個だけ提示すると **0.845 → 0.783**(§4.10)。
   ただし [62 §6.4](62-browser-accuracy.md#64-テキストではない絞り方が答えだった) の
   214 → 58-64 で測り直したら **0.76 対 0.77 で床の内側**、つまり**転移しない**。
   → **機構が同じでも候補数の領域が違えば数字は移らない。**転移させる前に測る。
13. **「壊れていない」対照も採点対象である。** `?bug=slow` は 3 版書いて
   2 版が壊れていて、どちらも**エラーではなく数字**を返した ——
   空白画面が `brittle 5` に、二重描画が `flaky 4/5` に化けた(§3.3)。
   → **対照が壊れると、生成物の欠点として現れる。**

- ~~**この安定は盤面が一意だからかもしれない。**~~ → [§4.6](#46-追記-経路が複数ある盤面を作って測った) で
  4 経路の盤面を作って測った。**経路は散らばらず 1/5**、ゴール文から経路を名指す句を
  落としても同じ。残った限界は**なぜ 1 つに寄るのか**で、そこは測っていない ——
  `buynow` を取って `express` を取らない理由(flow ヒントの並び順か、
  「Proceed to checkout」の語の強さか)を分ける対照は置いていない。
- ~~**なぜ 1 つの経路に寄るのかは測っていない。**~~ → [§4.7](#47-追記-なぜ-1-つの経路に寄るのかを測った) で
  測った。**ラベル**である(文字列を交換すると経路が入れ替わる)。指示句は外れた。
- ~~**express を先に描くと強まる理由が分からない。**~~ → [§4.8](#48-追記-express-first-が強まる理由--後に描かれたほうが得をする) で
  測った。**`express-first` は 1 要因ではなく**(採番と画面テキストの 2 つ)、
  どちらも同じ向きに押す。押しているのは**描画順**で、
  **後ろの候補が約 +0.21 得をする** —— ラベル交換で順番を揃えると差は消える。
- ~~**「リストの後ろほど強い」が長いリストで成り立つかは測っていない。**~~ →
  [§4.9](#49-追記-長いリストでは成り立たなかった--021-は短いリストの話) で測った。
  **成り立たない** —— 46 候補では +0.05 / +0.02 に薄まり、絶対位置は +0.003。
  残った限界は**間隔**で、離した配置は画面テキストと矛盾するのでマップだけで送ったところ
  p が 0.97 で飽和し、**検出力の無い条件**になった。「間隔は効かない」とは言えない。
- ~~**候補を 40 個足すと確信が上がる理由が分からない。**~~ →
  [§4.10](#410-追記-filler-で確信が上がる理由--語彙ではなく個数そして-003-は誤差) で
  **語彙ではなく個数**だと分かった(語彙の差は誤差の床の下)。提示数が主チャネル。
  ただし**なぜ個数で上がるのかという機構は依然として不明**で、
  そこは「測れた範囲の外」として残す。
- **誤差の床は 0.04、対照は 6 回ずつ。** §4.7〜§4.10 の数字はこの粒度で読むこと。
  0.04 を下回る差(指示句の 0.015、ラベル交換の 0.022、語彙の 0.032、間隔の 0.005)は
  **効果が無いのではなく、この n では区別できない**。
- **1 盤面・1 ゴール文・ラベル 1 組。** 「Proceed to checkout」対「Express checkout」
  という**この語の組**で測っており、どの語がどれだけ強いかの地図は無い。
  [17](17-task-picker.md#2-結果--名前だけで-90説明文を足すと-100) の
  「名前が嘘をつく項目」と同じ穴で、**嘘のラベルを疑う材料はドライバに無い**。
- **経路ごとのバグは 1 つしか置いていない。** `?bug=express` 1 件で
  「通らなかった経路は見えない」を示しているが、**見えない範囲の大きさ**
  (実アプリで経路固有の検証がどれだけあるか)は測っていない。
- **`?bug=slow` の数字は 3 版目のもの。** 版 1・版 2 で出た `brittle 5` /
  `flaky 4/5` は**対照のバグ**で、本稿の表には入れていない(§3.3)。
  逆に言えば、**それ以前の版で測った brittle 0 も対照が壊れた状態の数字**だった ——
  結論は変わらなかったが、根拠は §4.6 の再測に置き換えてある。
- **変異は 5 つで、本物のバグは 3 つ。** `cart` / `order` / `gate` だけが
  実際の欠陥で、`label` と `slow` は壊れていない対照。
  **「捕まえた /3」の分母が 3** なので、1 件の増減が 33 ポイント動く。
- **改名の脆さは 1 種類しか試していない。** `label` はラベル文字列の改名 1 つで、
  DOM 構造の変更・要素の入れ替え・id の変更は入っていない。
  「id で引けば脆さは消える」(§5 の 6)は**その 1 変異の上での話**。
- **アプリもバグもこちらが書いた。** ハッピーパスが 8 手で、
  `gate` を見逃すのは**ハッピーパスがメールを埋めるから**である(§4)。
  これは positive テストの原理的な穴だが、
  **穴の大きさ(実アプリでどれだけの negative チェックが該当するか)は測っていない**。

## 7. 次に試すこと

- **negative テストを生成する。** `gate` を捕まえるには「ステップを飛ばすと
  止まること」を確かめる spec が要る。探索側には材料がある——`#/checkout-2` に
  直行して弾かれた履歴を持っているので、「弾かれた」も assert できる。
- 事後条件の閾値。いまは `> 0.6` で切っているが、0.79〜0.95 と 0.00 に
  綺麗に割れていて、中間が 1 件も無い。**gap が広いので閾値はどこでも同じ**
  ——[24 §1](24-adhoc-rules.md#1-読むのは閾値ではなく-gap) と同じ読み方。
- 変異を増やしたときの見逃し率。いまは 5 件で、`order` 型(遷移は正しいが
  状態が間違っている)が 1 件しかない。
