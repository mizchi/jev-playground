## A. confidence でエスカレーションする二層構成 ★検証済み → [07](07-escalation.md)

> **追記: 実際に測ったら「最有望」は外れだった。**
> チェスでは confidence が品質を順序付ける(ρ = -0.47)が、
> 分布が低い側に潰れているので**安い運用点が存在しない**(下位 5% を回してもランダムと同等)。
> シェルコマンド判定では第二段のほうが弱く、confidence も誤りを予測しなかった。
> 詳細と、必要条件 3 つの整理は [07](07-escalation.md)。以下は提案時点の記述。

[03](03-chess.md#3-confidence-が難しさを測っている) で、confidence が
**局面の難しさではなく判断の難しさ**を測っていることが見えました。
序盤の展開手は 0.14〜0.31、駒の取り合いは 0.81〜0.93。
[02](02-moba.md#confidence-が判断の質を区別している) でも同じで、
建物攻撃 0.68〜0.84 に対し殴り合いは 0.27〜0.52。

つまり **「Jev が迷った局面だけ高いモデルか探索に回す」** が素直に書けます。

```
jev で判断 → conf >= 0.7 ならそのまま採用(数百 ms、$0.00005)
           → conf <  0.7 のときだけ Opus か αβ 探索(数秒、$0.01)
```

測るべきは**コストと品質のトレードオフ曲線**: 閾値を 0 から 1 に動かしたとき、
エスカレーション率と勝率(あるいは正解率)がどう動くか。
チェスなら Stockfish を入れて centipawn loss で測れる。

これが効けば「System One / System Two の役割分担」を数字で示せるので、
この探索全体の中で一番価値が高いと思います。

> **追記: 部品にした。そして当てはめの半分は自己申告だった。**
> [22](22-code-criteria.md) の 8 指標を**当てはめていない標本で採点し直す**と、

> 下に書いた「ホールドアウトを切って当てはめる部品」はそのまま正しかったのですが、
> 提案時に書いていなかった、実際に一番効いたことが 2 つあります:
> **(1) 置き場所に名前を付ける** —— 「clean の最大値 +0.01」は最も自然に見えて最も脆く、
> **gap の中央に置くと同じ検出で誤検出が 24 → 7** になる。
> **(2) 部品が最初に返すのは閾値ではなく「当てはめるべきか」**
> ([24](24-adhoc-rules.md) の gap を `advise` にした)。22 の 8 問は
> 5 問が wide-gap・3 問が overlapping で、**本当に校正が効く形は 1 問も無かった**。
> そして署名は下の `Map[String, Array[Double]]` ではなく
> `Sample[] → Placed` になりました(置き方が引数)。
> 置いた先も `lib`(MoonBit)ではなく `experiments/shared/thresholds.ts` ——
> ラベル付きの記録が TS 側にしかないので。以下は提案時点の記述。

[04](04-agent-built-prompts.md#2-原因は設計ではなく閾値だった) の結論そのまま。
`score` の期待値とラベルから閾値を引くヘルパを `lib` か `report` に置く:

pub fn fit_thresholds(
  values : Array[Double],
  labels : Array[Int],
  n_classes : Int,

```

これがあると [01](01-shell-risk.md)・[02](02-moba.md)・[04](04-agent-built-prompts.md) が
同じ形で校正できます。実測では閾値を合わせ直すだけで **10〜22 → 21〜22 に収束**しました。
**設計より校正のほうが効く**ので、部品にする価値がある。

> **追記: [22](22-code-criteria.md) でこれが最優先になった。** さらに
> [22 §11.4](22-code-criteria.md#114-当てはめた閾値は予告どおり壊れたそして直せた) で
> **当てはめた閾値が実際に壊れた** —— 10 関数足したら

> **ホールドアウトを切って当てはめる部品**が要る。署名もこう変わる:

## C. Claude Code の permission hook として実装する ★検証済み → [18](18-permission-hook.md)

> **追記: 実装した。当たり。** [01](01-shell-risk.md) の 24 コマンドに対して 68/72(94.4%)、
> **median 329 ms**(node 起動込み)、1 コマンド **$0.000032**。
> 下に書いた「レイテンシは hook として実用範囲」「hook は文脈を持っている側」は
> どちらもそのとおりで、`rm -rf ./build` 対 `rm -rf ./data` が
> 0.59 対 1.98 に分かれる(設定ファイルに本番 mount と書くだけ)。
>
> 提案時に書いていなかった、実際に重要だったこと 3 つ:
> **(1) ゲートは狭める方向にだけ使う**(`allow` を返すとユーザーの permission ルールを
> 上書き承認してしまう)。**(2) 全失敗経路を「判断なし」に落とす**(allow に倒せば黙って承認、
> deny に倒せば障害で停止)。**(3) リトライしない**(hook ではリトライが予算を食い潰す)。
>
> そして**実運用の形にしたら、コーパスでは出ないバグが 1 発目で出た** ——
> [01](01-shell-risk.md) の `exfiltrates` の文言をそのまま使うと
> **普通の `git push` が deny される**。詳細は [18](18-permission-hook.md)。
>
> `cmd/` の MoonBit バイナリではなく**依存ゼロの Node スクリプト**にしました。
> 理由は起動時間で、`tsx` を噛ませるだけで 200〜300 ms 増えて予算の大半が消えます。
> 以下は提案時点の記述。

[01](01-shell-risk.md) は「エージェントの実行許可ゲート」として作ったので、
そのまま `PreToolUse` hook にできます。Bash コマンドを state に、
`permission` の score を閾値で読んで allow / ask / deny を返す。

- レイテンシ 250 ms は hook として実用範囲(体感に乗らない)
- コストは 1 コマンド $0.00002 程度
- [01 の 2 節](01-shell-risk.md#2-同じコマンドでも文脈で判断が変わる)のとおり、
  hook は cwd・ブランチ・保護設定を**持っている側**なので、構造化 state の利点が最大に出る

`.claude/settings.json` の hook から叩く小さなバイナリを `cmd/` に置けば完結します。
**この探索の中で唯一、明日から自分が使えるもの**。

## D. state の ablation ツール

[05](05-browser-chaos.md#2-効いたのは質問ではなく-state-だった) で、
**質問は一字も変えずに state だけ 4 回作り直して**ようやく通りました。
つまり作業の中身は state 設計で、そこには測る道具がありません。

state のフィールドを 1 つずつ落として同じコーパスを流し、正解率の差を出すツール:

```
field                     accuracy without it
screen_text               23/24 -> 14/24   ← 効いている
states_seen               23/24 -> 22/24
recent_actions            23/24 -> 23/24   ← 落としてよい
```

トークンを払う価値のあるフィールドだけ残せるので、**コストと精度の両方に効く**。
どの実験にも使えるので、B と並んで部品化する価値があります。

## E. リポジトリ丸ごとの map-reduce トリアージ

launch post が挙げている「map-reducing over big data」を、手元のリポジトリでやる。
1 ファイル(または 1 関数)を state に、複数軸を 1 リクエストで:

- `is_dead_code` / `is_security_sensitive` / `needs_tests` / `is_generated`
- `complexity`(score)/ `owner_team`(choice)

[fan-out の実測](00-api-notes.md#speculative-fan-out)どおり、軸を増やすコストは質問文だけ。
入力 $0.042/MTok なので、**数千ファイルのリポジトリでも数十セント**で回ります。
`chaosbringer` の `heatmap.ts` / `clusters.ts` のような集計と相性が良さそう。

正解ラベルは `git log`(実際に消えたファイル = dead code だった)から作れるので、
**評価が自動で用意できる**のが良い点です。

## G. Jev を LLM-as-judge に置く ★判定部分は検証済み → [16](16-eslint-oracle.md) / [21](21-eslint-plugin-jev.md)

launch post の "score, judge, verify, guardrail"。CI で毎 diff に対して走らせる:

- `is_breaking_change` / `needs_migration_note` / `touches_security` (noul)
- `review_priority`(score、順序あり)
- `owning_team`(choice)

速度(200 ms)と価格が効くので、**全 PR・全ファイルに回せる**のが普通の LLM judge と違う点。
[00](00-api-notes.md#closed-world) の逃げ道の選択肢は必須(範囲外の diff が来る)。

> **`review_priority` の部分は [21](21-eslint-plugin-jev.md) で検証済み。**
> 関数単位の score を ESLint プラグインにして実測: 関数 1 個 $0.000017、
> 1000 関数のリポジトリを 20 リクエスト弱で丸ごと判定できる
> —— 「全ファイルに回せる」は本当だった。
> 精度は **自信のある指摘の 15/15 が本物で誤検出 0、ただし 12 バグ中 5 個しか捕まえない**。
> 残っているのは **diff 単位**(ファイル単位ではなく変更単位)と
> `owning_team` の choice。

## H. 役割分担を先に決める二段構え(MOBA の続き)

[02 の 6 節](02-moba.md#6-次に試すこと)に書いた話。今は 3 体の行動を独立に聞いているので、
**3 体が同時に「自分が足止めする」と答える**可能性が構造的にあります。

1 問目で `choice`「誰が足止めするか」を決め、2 問目以降で各自の行動を聞く二段構え
(同じリクエスト内では依存関係を作れないので 2 往復)と、
今の 1 往復を比べる。**並列評価に依存関係を持ち込むときの一般形**なので、
MOBA 以外にも効く知見になりそうです。

## J. タスクランナーから「正しいタスク」を選ばせる ★検証済み → [17](17-task-picker.md)

> **追記: 検証したら当たりだった。** 名前だけで 53 タスクから 90.0%、133 タスクでも 85.6%。
> **1 行の説明を足すと 100%**(実際のコマンドを見せても同じなので、散文で情報が尽きている)。
> 外すのは予測どおり**名前が内容と食い違うタスクだけ**。
> 下の注意点 1(閉じた世界)はそのまま起きて、**逃げ道なしでは該当なし 0/18**。
> ただし**逃げ道の作り方に差があった**: 別の noul で聞くと 18/18 だが、
> `choice` の選択肢に混ぜると 16/18 で、さらに答えのある難問までそこへ逃げる。
> 注意点 2(255 上限)は 133 までしか触っていない。
> 一方で**リポジトリの文脈は 1 件も効かなかった**(ゴール文が意図を明示しているため)。
> 詳細は [17](17-task-picker.md)。以下は提案時点の記述。

コンテキスト(作業内容・直前の失敗・変更されたファイルなど)を与えて、
**タスクランナーに大量にあるタスクのうち正しいものを Jev が選べるか**。

これは [00](00-api-notes.md#name-only) の**選択肢名だけの `choice`** がそのまま効く形で、
`package.json` の `scripts`・`Makefile` のターゲット・`moon` のタスクは
**名前がすでに説明になっている**(`test:unit`・`lint:fix`・`build:prod`)。
20 択で 441 トークンだったので、100 タスクでも 1 リクエストに収まる。

測り方:

- state = 何をしたいか + リポジトリの状況(変更ファイル、直前のコマンドと終了コード)
- criteria = 実在するタスク名(名前だけ、説明なし)。**候補をその場の実在タスクに限る**と
  [02](02-moba.md#2-結果)・[03](03-chess.md#2-一番の発見-反則手が表現できないことの価値) と同じで
  **存在しないタスクが表現不能**になる
- 正解ラベルは人手か、`scripts` のコメント/CI 設定から作る

注意点が 2 つあり、どちらも既知の落とし穴に当たる:

1. **[00](00-api-notes.md#closed-world) の閉じた世界。**「どのタスクでもない」
   (新しくコマンドを書くべき)を表現する逃げ道が必須。`choice` は必ず選ぶので、
   無関係な依頼に対して自信のある誤答が出る。
2. **タスク数の上限。** `choice` は 255 が実測上限。モノレポの `scripts` は
   これを超えうるので、超えたときの方針(名前の前方一致で絞る? 二段階にする?)が要る。

[16](16-eslint-oracle.md) と近い形(**実装を見せずに名前と基準だけで判断させる**)なので、
16 の結論がそのまま予測になる: **名前が説明として十分なタスクは当たり、
名前が嘘をついているタスク(`test` が実際は lint も走る)で外す**はず。
効けば「エージェントがどのコマンドを打つか」の最初の一手が 200 ms・$0.00005 で決まる。

4. ~~**[21](21-eslint-plugin-jev.md) が落とした 6 個を狙って質問する。**~~
   → **[22](22-code-criteria.md) で実施。戻ったのは 2 個だけだった。**
   `api_default` という原子 noul を名指しで投げて、`.sort()`(0.32)と
   `setUTCMonth`(0.27)は戻ったが、`splice(at)` は **0.12**、`/g` なしは **0.09**、
   `await` 忘れは 0.22 —— **ちょうど正しい問いに自信をもって「いいえ」**。
   質問設計の問題ではなく、観察できていない。副産物として
   **閾値を質問単位で引く必要がある**ことが出た(共通 0.80 で 13/36、質問ごとで 24/36)。
   → 保留セットの作り直しも **[22 §11](22-code-criteria.md#11-追記--保留セットを作り直して穴の深さを測った) で実施。**
   軸が 2 本あって(列挙されているか / 関数の中だけ読めば分かるか)、
   **easy では naming が無価値、hard では 2.6 倍**。穴の深さは約 32 ポイント。
   さらに **8 指標のうち抜いて困るのは `api_default` 1 個だけ**で、
   残り 7 個は隣か汎用が埋める —— **指標は互いに重複している**。
   残っている宿題: **`api_default` だけを深掘りする**。
   1 個で hard バグの本体を担いでいるので、これを
   「どの API か」で分割したら当たるのか、それとも
   [22 §3](22-code-criteria.md#3-落とした-6-個のうち戻ったのは-2-個) の
   0.09 が System One の境界なのか。
5. **`judge.mjs` の出荷閾値を `auto` に差し替える。**
   [25 §3](25-thresholds.md#3-境界ではなく-gap-の真ん中に置く) の測り方では
   同じ検出で誤検出が 1/3 になります。別変更にしてあるのは
   [21](21-eslint-plugin-jev.md)・[22](22-code-criteria.md) の表が現行の数字に対して
   書かれているからで、差し替えるならレポートの数字も引き直す必要があります。
6. **penalty を実測する。** [25 §5](25-thresholds.md#5-閾値をコストの関数にする23-11-の宿題) で
   自由なパラメータは「見逃し 1 件の値段」1 個になりました。
   CI の赤 → 修正コミットまでの時間はこのリポジトリでも測れるので、
   そこまで行けばパラメータは 0 個になります。
7. **`fit` verdict の問いを探す。** 測った 8 問はすべて wide-gap か overlapping で、
   **「分かれてはいるが狭い」= 校正が本当に効く形が 1 つも無かった**。
   校正の効果そのものを測るには、まずその形の問いを見つける必要があります。
8. **文脈は「穏やかにする」のか。** [21 §6](21-eslint-plugin-jev.md#6-ファイルの文脈は精度を上げない下げる) で
   ファイル全体を state に入れると **clean の score が上がって**(0.88 → 1.08)
   誤検出が 1/5 に減った。これが「文脈は judgment を穏やかにする」の一般則なら、
   D の ablation は**「効く/効かない」ではなく「どちらの誤りを減らすか」**で測るべき。
