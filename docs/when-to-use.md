# どういう時に使えるか —— Jev を入れる条件、入れない条件

Jev は**判断だけを返す**モデルです。入れるかどうかは「賢いか」ではなく、
**速さと値段と、答えの形が、その場所に合うか**で決まります。

| | 何が書いてあるか |
| --- | --- |
| **when-to-use.md**(ここ) | **どういう時に使えるか** —— 入れる条件と、入れない条件 |
| [fit.md](fit.md) | **向いているケース** —— 効く問題の形と、効かない問題の形 |
| [tuning.md](tuning.md) | **チューニング** —— 答えの形・質問・state・閾値・合成・運用・計測・行動 |
| [case-studies.md](case-studies.md) | **ケーススタディ** —— 題材ごとに、何が効いて何が効かなかったか(MOBA を含む 13 件) |

---

## Jev が返すもの

- **`noul`(述語の確率)・`choice`(列挙した選択肢から 1 つと、全選択肢の確率)・`score`(順序つきの段と confidence)の 3 種類だけ**です。
  **文字列は返しません**([fit.md](fit.md#0-そもそも向いている問題か))。
- 入力 **$0.042/MTok**・出力無料・レイテンシ **125〜730 ms**([summary](summary.md))。
- 上限は**リクエスト全体 64Ki トークン**と**state だけで 32Ki トークン**の独立 2 枠で、先に詰まるのは state の側です。
  255 は `choice` の選択肢の上限で、質問数の上限ではありません。どれも公式スキーマに書かれていません
  ([00](00-api-notes.md#token-ceilings))。
- **質問は束ねるほど得です。** 20 問を 20 回に分けると **5227 ms・8277 トークン**、
  1 リクエストにすると **246 ms・1000 トークン**で、答えは動きません
  ([tuning §3](tuning.md#3-1-リクエストに詰めるほぼ考えなくてよい))。

## 速さと値段が変えること

[summary の結び](summary.md#結局この速度と価格は何を変えたか)から:

- **全部に回せる。** 関数 1 個 **$0.000017**(2 問)/ **$0.000055**(10 問)。
  1000 関数のリポジトリを丸ごと 1 回判定して **$0.017〜$0.055**、リクエストは 20 本弱。
  サンプリングして眺めるのではなく、全件に回す設計が選べます。
- **人の操作に間に合う。** エージェントの Bash 1 回ごとに挟む hook で、
  出荷配線(コマンドごとに node 起動込み)のまま **391 コマンド中央値 371 ms・p99 568・超過 0**
  (予算は **2,500 ms**)。
- **迷ったら聞いておける。** 質問を足すコストは質問文のトークンだけなので、
  使うか分からない述語も込みで 1 回投げて、要るものだけコードで拾えます。
- **閾値がこちら側に残る。** 確率が返るので、判定を変えるのに API 呼び出しが要りません。
  代わりに**校正が自分の責任**になり、そこが一番手間です([tuning §4](tuning.md#4-閾値を決めるここが一番手間))。

**そして速さは品質の主張になりません。** 本物のエージェントの 5 コンポーネントで
**26〜103 倍**速いのは一貫していましたが、**品質で Jev が明確に勝っている列は 1 つも在りません**でした
([42](42-versus-rest.md))。**正しい売り方は「安くて速いから、迷ったら聞いておける」で、「賢い」ではない**、
というのがこのリポジトリの結論です。

## 入れてよい条件 —— 7 つとも「はい」なら

1. **答えが型付きの判断である。** 選択肢が列挙できる、順序がある、独立した述語の束である
   —— 問題の形は [fit.md](fit.md) で確かめる。
2. **規則で書ける部分は、もう規則に出してある。** 依存グラフや SLO のように**答えが計算できる部分**を
   判断に混ぜると、有料で不正確になります([tuning §4.6](tuning.md#46-答えが測れる量の関数なら聞かずに計算する)、
   [23 §5](23-task-filter.md#5-グラフはプロンプトではなくコードに置く))。
3. **失敗の落とし先が決まっている。** API が落ちたとき・時間切れのときに
   「判断なし = 通常フロー」に落とせる場所か([tuning §6.1](tuning.md#61-失敗の落とし先を精度より先に決める))。
4. **閾値を引く小さなラベル付きの標本を作れる。** 同じプロンプトでエージェントに質問を書かせると
   **10/24〜23/24** に振れ、閾値を合わせ直すだけで **21〜22** に収束しました
   —— **設計より校正が効きます**([tuning §4.5](tuning.md#45-ラベル付きの小さなコーパスが一番効く投資))。
5. **判断の前提を state に構造化して渡せる。** 32Ki に収まり、判断に要る事実が
   コードの側に在ること([tuning §3](tuning.md#3-1-リクエストに詰めるほぼ考えなくてよい))。
6. **数が多いか、遅延に厳しい。** 全件に回したい、人の操作に挟みたい ——
   **Jev を選ぶ理由はここで生まれます。** 件数が少なく品質だけが問題なら、他のモデルと並べて比べてから。
7. **記録と再生ができる。** 同じ入力で答えが揺れるので、record / replay が無いとテストが書けません
   ([tuning §7](tuning.md#7-測り続ける))。

## 入れないほうがいい時

| 状況 | 代わりに | 実測 |
| --- | --- | --- |
| 答えが測れる量の関数 | 計算する | SLO の 1 行の規則が **16/16・誤ページ 0**、同じ窓を Jev に聞くと誤ページ **6〜27 件**([27 §3](27-otel-triage.md#3-severity--算術が完勝する)) |
| 文字列が要る | 生成モデル。行動なら値をコード側か選択肢に | Jev は文字列を返さない([tuning §8.2](tuning.md#82-target-は要素ではなく実行単位にする)) |
| 閾値の境界に乗った決定を、そのまま自動化したい | 境界帯は人へ | 些細な入力差で決定が入れ替わる([09 §3](09-guardrails.md#3-cookbook-の-15-ケースの再現)) |
| その判断に仕事が無い | 入れる前に、判断が要る事例がどれだけ在るかを数える | 端から端まで走らせた gate は **978 コマンド中 12 件**しか発言しなかった([43](43-finish.md)) |
| 部品の良し悪しを完遂率で決めたい | 完遂以外の指標を先に決める | Bash が在るとエージェントは緑まで回すので、**完遂が天井**になる([54](54-ceiling.md)) |

## 置き場所の決め方

```
規則で書けるか ──── はい → コード(判断に混ぜない)
  └ いいえ
      文字列が要るか ── はい → 生成モデル
        └ いいえ(選ぶ・順序づける・真偽を言う)
            数が多い / 遅延に厳しい ── はい → Jev(閾値はコード側に、失敗は通常フローに)
              └ いいえ → Jev でも他のモデルでもよい。同じ標本で品質を並べて比べる
```

題材ごとの実際の置き方は [case-studies.md](case-studies.md) にあります。
