# 10. Jev vs Jev(独立プロセスで対戦)

[02](02-moba.md) は Jev をスクリプト bot と戦わせただけで、**Jev 同士**は測っていなかった
([02 §6](02-moba.md#6-次に試すこと)の宿題)。しかも 1 プロセス内だった。
ここでは 2 チームを**別々の OS プロセス**として動かし、互いを一切見せずに対戦させる。

再現:

```bash
TYPESAFEAI_API_KEY=... scripts/jev-vs-jev.sh --games 6 --max-ticks 45
scripts/jev-vs-jev.sh --games 1 --max-ticks 16 --verbose   # 毎手の判断を見る
```

---

## 1. 構成 — 視界の霧を「配線」で強制する

3 プロセス:

| プロセス | 役割 | Jev |
| --- | --- | --- |
| `cmd/moba_referee` | 権威ゲームを保持。TCP で待ち受け、毎 tick 各チームに**そのチームの観測と合法手だけ**送る | 使わない |
| `cmd/moba_player` ×2 | 1 チーム・1 Jev クライアント。referee としか話さない | 各自が持つ |

[02](02-moba.md) の 1 プロセス版でも観測はチームごとに分けていたが、それは**規律**だった。
ここでは相手チームのデータが**ワイヤーに乗らない**ので、player プロセスは
構造的に相手を見られない。視界の霧がプロセス境界で強制される。

protocol は行区切り JSON(`turn` / `actions` / `over` / `bye`)。referee が観測と合法手を送り、
player は Jev に問うて選んだ行動文字列を返す。**合法手は referee が計算して渡す**ので、
player は渡された選択肢しか名指しできない([02](02-moba.md#2-結果)の「不正手が表現不能」がプロセスを跨いでも保たれる)。

## 2. 結果 — 独立させると決着する

6 ゲーム、`A 2 — 4 B`、**全ゲーム決着・引き分けゼロ**:

```
game 1: A  28 ticks     game 4: B  27 ticks
game 2: B  31 ticks     game 5: A  30 ticks
game 3: B  29 ticks     game 6: B  33 ticks
```

これが一番の結果。[02](02-moba.md#4-正直な限界)で
**スクリプト bot 同士は 3/3 引き分け・建物ダメージ 0** だった。決定的な方針 × 対称マップだと
両者が鏡写しに動いて膠着するからだ。

**Jev 同士は膠着しない。** 2 つの独立プロセスの Jev は同じ観測でも同じ手の分布を出さないので、
スクリプトを固めた鏡が形成されない。**独立性そのものが対称性を破っている。**
「Jev は強いか」ではなく「独立した 2 エージェントは実際に噛み合った試合を生むか」に対する
yes がこの実験の答え。

## 3. 並行性 — 1 tick ≈ 1 リクエスト、2 つ分の和ではない

referee は 2 チームの turn を `with_task_group` で並行送受信するので、
2 つの player プロセスが Jev 呼び出しを**並列**に走らせる。実測:

| | |
| --- | --- |
| ms/tick(referee 実測、6 ゲーム) | 255〜369 ms |
| ms/request(各 player 自己申告) | 240〜258 ms |

**tick あたりの実時間が 1 リクエストのレイテンシとほぼ同じ。** 逐次なら 2 リクエスト分
(約 500 ms)かかるところが、独立プロセスの並行実行で片方分に収まっている。
プロセスを分けたことがそのまま速度になっている。

コストは 6 ゲームで各 player 約 167 リクエスト・約 30 万入力トークン
= **1 サイド約 $0.012、両者で $0.025**。

## 4. 3 体は協調するか(02 §6 の宿題)

[02 §6](02-moba.md#6-次に試すこと)で、3 体の行動を独立に聞くと
「3 体とも『自分が足止めする』と答えて破綻する」恐れを挙げていた。
verbose の冒頭(A チーム):

```
tick1  champ0: move_m_top (0.82)   champ1: move_m_jg (0.79)   champ2: move_m_bot (0.60)
       [read] danger=0.07/3  unseen-at=b_jg
tick2  champ0: move_b_top (0.33)   champ1: attack_champ_4      champ2: move_a_bot (0.28)
       [read] danger=0.90/3  unseen-at=b_base
tick3  champ0: attack_structure    champ1: attack_champ_4      champ2: attack_champ_5
```

**破綻しなかった。** 3 体はレーンに散開し(top→m_top, jungle→m_jg, bot→m_bot)、
接敵してから収束して建物と敵に取り付く。役割分担を明示的に決めさせていないのに、
**各チャンピオンに「自分は何をするか」を別々に聞くだけで自然にレーンが割れた**。
理由はおそらく state に各自の `role`(top/jungle/bot laner)と `hops_to_enemy_base` が入っていて、
同じ観測でもチャンピオンごとに別の最善手になるから。二段構え(先に「誰が足止め」を choice で決める)は
今回は不要だった。

その後の試合展開も MOBA になっている(referee のイベントログ):

```
t11: A_jungle killed B_jungle at m_jg
t12: A_top destroyed the tower at b_top
t13: B_top destroyed the tower at a_top
t15: B_top killed by the tower at a_base; A_top killed by the tower at b_base
```

キル・タワー破壊・タワーダイブの相打ちまで出ている。

## 5. 正直な限界

- **resolution に微小な先手有利がある。** `step` は行動を champ id 順(A が 0-2、B が 3-5)に
  解決するので、相互キルのとき低 id = A の攻撃が先に入る。6 ゲーム中 2 つ(game 1, 5)は
  両陣営の建物が同 tick に全壊し、構造体の走査順(B の base が最後)で A 勝ちになった。
  **A に有利な人工物**だが、それでも通算は B が 4-2 で勝っており、支配的ではない。
  厳密にやるなら相互キルを同時処理にすべき。
  → **[§8](#8-追記--同時処理に直して-20-ゲームで測り直す) で直して測り直した。**
- **6 ゲームは少ない。** A/B バランスの 2-4 は有意ではない。決着する(引き分け 0/6)ことと
  並行性は明確だが、勝率の主張はできない。
- **MoonBit の player は Jev 失敗をリトライしない**(TS クライアントには入れた)。
  6 ゲームで A が 2 tick・B が 5 tick、transient 失敗でそのチームがその tick 全員 hold した。
  試合を壊すほどではないが、`lib` 側にもリトライを入れるべき。
- スクリプト bot が弱い点は [02](02-moba.md#4-正直な限界)のまま。ここは Jev 同士なので
  その問題は無いが、代わりに「両者とも同じ弱い前提の player ロジック」を共有している。

## 6. この実験で確定したこと

1. **独立させると膠着が解ける。** スクリプト鏡は 3/3 引き分け、Jev 同士は 6/6 決着。
   対称ゲームで意味のある試合を生むのは、モデルの強さではなく**エージェントの独立性**だった。
2. **プロセス分離 = 並行 = 速度。** 2 サイドを別プロセスにしたことで 1 tick が
   1 リクエストのレイテンシに収まった(逐次の半分)。マルチエージェントを別プロセスで組む
   一般的な利点が、そのまま出ている。
3. **視界の霧はプロセス境界で強制できる。** 相手の観測をワイヤーに乗せないので、
   player は構造的に相手を見られない。規律ではなく設計で保証される。
4. **独立な per-champion choice で役割分担が自然に出る**(4 節)。
   state に各自の役割を入れておけば、明示的な調停なしにレーンが割れた。

## 8. 追記 — 同時処理に直して 20 ゲームで測り直す

[§5](#5-正直な限界) の先手有利を消し(相互キルの同時解決。機構は [11 §1](11-synergy.md#1-相互キルの同時処理))、
20 ゲームで測り直した。sim は [11](11-synergy.md) でチャンピオンに多様性を入れた後のものだが、
ここは [02](02-moba.md)/本編と揃えて**均一チャンピオン(`classic` ×3)**で走らせている。

再現:

```bash
scripts/jev-vs-jev.sh --games 20 --max-ticks 45 --replay out/jev20
moon run --target native cmd/moba_replay -- --file out/jev20.g1.jsonl   # 1 戦を再生
```

結果: **A 8 — 10 B、引き分け 2**、20 戦すべて 45 tick 上限で構造体ダメージ判定。マージンは僅差:

```
game 1  B 132-198   game 6  draw 154   game 11 A 186-182  game 16 B 178-186
game 2  A 170-162   game 7  B 162-170  game 12 B 159-170  game 17 B 170-182
game 3  B 178-194   game 8  B 178-202  game 13 draw 178   game 18 B 166-174
game 4  A 170-162   game 9  A 170-162  game 14 B 156-178  game 19 A 161-153
game 5  A 154-150   game 10 B 178-186  game 15 A 166-141  game 20 A 178-162
```

分かったこと:

- **先手有利の人工物が消えた。** 本編の 6 ゲーム A2-4B は、A に有利な resolution 順の**上での**数字だった。
  同時処理後は A8-10B(決着 18 戦の 8:10 は有意でない。二項検定で p≈0.8)で、サイド有利は見えない。
  対称 scripted 同士が [11 §1](11-synergy.md#1-相互キルの同時処理) のとおり 350-350 で割れなくなったのと整合する。
- **引き分けが出るようになった。** 同時処理は完全な構造体タイ(game 6 = 154-154、game 13 = 178-178)を
  起こしうる。旧 id 順はこれを人工的に割っていた。本編の「全ゲーム決着・引き分けゼロ」は**成り立たなくなった**が、
  それが正しい挙動。
- **決着の質が変わった。** [11 §2](11-synergy.md#2-チャンピオンに多様性を持たせる) で前衛のタワーダイブを差別化するため
  タワーダメージを上げたので、base を割り切るのが高コストになり、試合は上限まで構造体を削り合う接戦になった
  (本編は base kill が ~30 tick)。別レジームだが、A/B バランスの測定という目的には影響しない。
- **並行性は不変。** ~190 ms/request、tick ≈ 1 リクエスト([§3](#3-並行性--1-tick--1-リクエスト2-つ分の和ではない))。
  20 ゲームで両者 ~167 万 / 162 万 入力トークン(**1 サイド ~$0.07**)。
- **リトライが要った。** リトライ無しだと 20 ゲーム分の負荷でレート制限に当たり、両 player が全 hold して
  **350-350 の膠着**になった([§7](#7-次に試すこと) の宿題)。`lib` にバックオフ付きリトライ(429/5xx/ネットワーク)を
  入れて解決。これは Jev の性質ではなく**クライアント側の運用**の問題で、[07](07-escalation.md) や TS 側で
  既に入れていたものを MoonBit 側にも入れた形。
