# 13. タスクランナーの大量のタスクから「正しいタスク」を選べるか

[06 の提案 J](06-ideas.md) の検証。コンテキストを与えて、タスクランナーに大量にある
タスクのうち**正しいものを Jev が選べるか**を測る。

[16](16-eslint-oracle.md) と**同じ形**で作った: Jev に見せるのは**タスク名**だけで、
正解は**そのタスクのコマンドが実際に何をするか**で決まる(コマンドは伏せる)。
つまり名前が仕様、コマンドが実装。**名前がコマンドを誇張する/過小に言うタスク**が
near-miss になる。[16](16-eslint-oracle.md) からの予測は
「名前が自分を説明しているタスクは当たり、名前が嘘をつくタスクで外す」。

再現:

```bash
cd experiments/task-picker && npm install
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --repeat 3 --scale     # 648 リクエスト、$0.046
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --no-context           # state の ablation
```

---

## 結論(先に)

**名前だけで 81/90(90.0%)。1 行の説明を足すと 90/90(100%)。**

予測どおり、**外すのは名前が嘘をつくタスクだけ**だった。
`direct` 36/36・`decoy` 27/30 に対し `lying` 18/24 で、
説明文を足すと `lying` も **24/24** になる。

そしてこの実験の一番の収穫は**逃げ道の作り方**だった。
[00](00-api-notes.md#closed-world) は「`choice` は必ず選ぶので逃げ道を用意せよ」と
書いているが、**逃げ道の作り方 2 通りには大きな差があった**:

| 逃げ道の作り方 | 該当なし 18 件の検出 | 答えのある 90 件への副作用 |
| --- | --- | --- |
| 作らない | **0/18** | — |
| **別の noul で聞く**(`applicable`) | **18/18(100%)** | 正解を 6 件捨てる |
| `choice` に「該当なし」を混ぜる | 16/18(88.9%) | **`lying` が 18/24 → 15/24 に悪化** |

**逃げ道は選択肢ではなく別の問いにする。** 選択肢に混ぜると、
難しいが答えのあるケースでそこへ逃げる(`precommit` が正解の問題で
3/3 とも「該当なし」を conf 0.50 で選んだ)。

**説明文 + noul ゲートの組み合わせで 36 シナリオ全部・108 判定が 108/108(100%)。**

## 1. しくみ

タスクランナーのロスターは実在の monorepo の `package.json` scripts に似せて作った
(`src/roster.ts`)。各タスクは `{ name, command, description }` を持ち、
**Jev に見せるのは arm ごとに決めた分だけ**。

```
core   14 タスク   dev / build / test / lint / typecheck / e2e / db:migrate ...
medium 53 タスク   + test:unit / check / ci / precommit / verify / smoke / codegen:graphql ...
large 133 タスク   + パッケージ別(web:build / api:test / sdk:typecheck ...)
```

`choice` のサーバー上限は 255([00](00-api-notes.md#name-only))なので、
large はその半分強 —— 実際の monorepo の script 一覧が届く程度の規模。

設計はこのリポジトリの 2 つの定石をそのまま使った:

- **`choice` の criteria はその場の合法手だけ。** 実在するタスク名を**説明なしで**並べる
  ([00](00-api-notes.md#name-only) の name-only choice)。
  ロスターに無いタスクは**表現不能**になる([02](02-moba.md#2-結果)・
  [03](03-chess.md#2-一番の発見-反則手が表現できないことの価値))。
- **判断に要る文脈は構造化 state に載せる**([01](01-shell-risk.md#2-同じコマンドでも文脈で判断が変わる))。
  arm が変えるのは **state のタスク表の詳しさ**で、criteria は全 arm で同じ。
  こうすると逃げ道用の noul も pick と同じ情報を見ることになる。

1 リクエストに 2 問を束ねる(fan-out):

| 質問 | 型 | 内容 |
| --- | --- | --- |
| `pick` | choice | ロスターのタスク名から 1 つ選ぶ |
| `applicable` | noul | 「この一覧のどれかが単独でゴールを達成する」 |

arm:

| arm | タスクについて見せるもの |
| --- | --- |
| `names` | 名前だけ(`package.json` のキー一覧そのまま) |
| `names_escape` | 名前だけ + `choice` に「(none of these)」を追加 |
| `descriptions` | 名前 + 1 行の説明(良い README が書く程度) |
| `commands` | 名前 + **実際のコマンド**(実装を開示した上限) |

### シナリオ

36 件(`src/scenarios.ts`)。30 件は答えがあり、**6 件は答えが無い**。

- `direct` (12) — 名前がゴールをそのまま言っている
- `decoy` (10) — 字面の近い別タスクがあって、それが誤り
- `lying` (8) — **正解の名前が内容を言っていない**、または
  良い名前のタスクが別のことをする
- `escape` (6) — **ロスターのどれもやらない**(依存追加・リネーム・PR 作成・
  bisect・本番のロールバック・新規テストの執筆)

`lying` の中身が本題なので、ロスターに仕込んだ嘘を挙げておく:

| タスク | 名前から読めること | 実際のコマンド |
| --- | --- | --- |
| `test` | テストを走らせる | `vitest run && playwright test`(ブラウザ suite まで走る) |
| `check` | 何かを確認する | `eslint && tsc --noEmit && vitest run`(**push 前に欲しいのはこれ**) |
| `precommit` | commit 前のゲート | `lint-staged`(**staged のファイルだけ**、テストは走らない) |
| `verify` | 広く検証する | `tsc --noEmit -p tsconfig.strict.json`(strict 型検査だけ) |
| `build:docs` | ドキュメントサイトを建てる | `typedoc`(API リファレンスの生成) |
| `deploy:prod` | 本番に反映する | 前進デプロイのみ。**ロールバックはできない** |

答えが 2 つ許されるシナリオは 1 件だけ(`dev_server` = `dev` か `dev:web`。
ロスターに同じ効果のタスクが実在し、名前だけで区別しようがない)。

## 2. 結果 — 名前だけで 90%、説明文を足すと 100%

medium(53 タスク)、3 回、答えのある 30 シナリオ × 3 = 90 判定:

| arm | top-1 | | top-3 | mean confidence |
| --- | --- | --- | --- | --- |
| `names` | 81/90 | 90.0% | 84/90 | 0.913 |
| `names_escape` | 81/90 | 90.0% | 85/90 | 0.893 |
| **`descriptions`** | **90/90** | **100.0%** | 90/90 | 0.984 |
| `commands` | **90/90** | **100.0%** | 90/90 | 0.974 |

**コマンドを見せても説明文と同じ 100%。** [16](16-eslint-oracle.md) で
「既定オプションまで渡すと逆に悪化した」のと違って、ここでは
**実装の開示が説明文を超える上積みを持たない** —— 1 行の散文で情報が尽きている。

種類別に割ると、差がどこにあるかが完全に見える:

| arm | `direct` | `decoy` | `lying` |
| --- | --- | --- | --- |
| `names` | **36/36** | 27/30 | 18/24 |
| `names_escape` | **36/36** | **30/30** | 15/24 |
| `descriptions` | **36/36** | **30/30** | **24/24** |
| `commands` | **36/36** | **30/30** | **24/24** |

**名前が自分を説明しているタスクは名前だけで完璧に選べる(36/36)。
落ちるのは名前が嘘をつくところだけで、1 行の説明がそれを完全に埋める。**
[16](16-eslint-oracle.md) の予測がそのまま当たった。

`names` arm が 3 回とも外した 3 件:

```
strict_types    「strict の tsconfig で型検査したい」
                → typecheck を conf 0.99 で選ぶ(正解 verify)   ← 自信のある誤答
pre_push_gate   「push 前に lint と型と unit だけ。ブラウザ suite は待てない」
                → ci を conf 0.36 で選ぶ(正解 check)           ← 迷っている
api_reference   「TypeScript のソースから API リファレンスを生成したい」
                → build:api を conf 0.52 で選ぶ(正解 build:docs)
```

**confidence が誤りの種類を分けている。**`strict_types` は
`typecheck` と `verify` のどちらが strict かが名前から**原理的に読めない**ので
0.99 で間違える([00](00-api-notes.md#closed-world) の「範囲外入力が
conf 0.96 で誤ルーティング」と同じ形)。一方 `pre_push_gate` は 0.36 で、
**迷っていること自体は正しく報告している**。

## 3. 逃げ道は「選択肢」ではなく「別の問い」にする

答えの無い 6 シナリオ × 3 回 = 18 判定:

| arm | 逃げ道なし(raw) | noul ゲート | p(applicable) 該当なし | p(applicable) 答えあり |
| --- | --- | --- | --- | --- |
| `names` | 0/18 | **18/18** | 0.113 | 0.741 |
| `names_escape` | 16/18 | **18/18** | 0.113 | 0.744 |
| `descriptions` | 0/18 | **18/18** | 0.071 | **0.953** |
| `commands` | 0/18 | **18/18** | 0.075 | 0.899 |

**逃げ道を作らないと 0/18。** `choice` は必ず選ぶので、
「`zod` を依存に追加したい」に対して必ずどれかのタスクを答える。
[00](00-api-notes.md#closed-world) の警告そのままで、ここでも例外なく起きた。

**別の noul で聞くと全 arm で 18/18(100%)。** 該当なしで 0.07〜0.11、
答えありで 0.74〜0.95 と分離が大きく、閾値 0.5 は谷の真ん中にある。

そして **`choice` に「(none of these)」を混ぜるのは劣る**:

- 検出が 16/18 にしかならない(noul ゲートは 18/18)
- **答えのある難問でそこへ逃げる。** `lying` が 18/24 → **15/24** に悪化した。
  悪化の正体は `staged_only`(正解 `precommit`)で、
  **3 回とも「(none of these)」を conf 0.50 で選んだ** —— 正解はロスターに有る。

つまり逃げ道を選択肢に混ぜると、**「難しい」と「該当なし」が同じ出口を共有してしまう**。
別の問いにすれば、難しさは `pick` の confidence に、
該当なしは `applicable` に分かれて出る。

### ゲートの代償

noul ゲートは無料ではない。答えのあるシナリオで正解を捨てる:

| arm | raw | ゲート後 | 捨てた正解 | p(applicable) の平均 |
| --- | --- | --- | --- | --- |
| `names` | 81/90 | 75/90 | **6** | 0.741 |
| `names_escape` | 81/90 | 77/90 | 4 | 0.744 |
| **`descriptions`** | 90/90 | **90/90** | **0** | **0.953** |
| `commands` | 90/90 | 87/90 | 3 | 0.899 |

**ロスターの説明が良いとゲートは無料になる。** 名前だけだと
`applicable` が 0.741 まで下がって、答えのあるものまで「該当なし」に落ちる。
説明文を足すと 0.953 まで上がり、**捨てる正解が 0 件になる**。
ゲートを入れる前提なら、ロスターに 1 行ずつ説明を書く価値は accuracy だけでなく
**ゲートの副作用を消すことにもある**。

36 シナリオ全部(108 判定)を 1 つの数字にすると:

| arm | raw | ゲート後 |
| --- | --- | --- |
| `names` | 81/108 75.0% | 93/108 86.1% |
| `names_escape` | 97/108 89.8% | 95/108 88.0% |
| **`descriptions`** | 90/108 83.3% | **108/108 100.0%** |
| `commands` | 90/108 83.3% | 105/108 97.2% |

**説明文 + noul ゲートで全問正解。**
`names_escape` はゲートを足すと**むしろ下がる**(89.8% → 88.0%)ので、
逃げ道は二重にかけない。

## 4. スケール — 14 → 133 タスクで 100% → 85.6%

`names` arm、同じシナリオ、ロスターだけ大きくする
(core では正解タスクが存在しないシナリオがあるので、**到達可能なものだけ**で測る):

| タスク数 | top-1(到達可能) | | 該当なし(ゲート) | mean confidence |
| --- | --- | --- | --- | --- |
| 14(core) | 30/30 | **100.0%** | 18/18 | 0.830 |
| 53(medium) | 81/90 | 90.0% | 18/18 | 0.913 |
| 133(large) | 77/90 | 85.6% | 18/18 | 0.883 |

**緩やかに劣化する(100% → 85.6%)が、崩壊はしない。**
133 択でも 1 リクエスト・0.18 秒で、confidence もほとんど動かない(0.83〜0.91)。
**逃げ道の検出はロスターの大きさに影響されない**(全サイズで 18/18)。

注意: core が 100% なのはロスターが小さいからだけではなく、
**紛らわしいタスクがそもそも存在しない**から(`test:unit` も `check` も `verify` も
medium 以降にしかない)。劣化の原因は選択肢の数と
**名前の近いタスクが増えること**の両方で、ここでは分離できていない。

## 5. リポジトリの文脈は要らなかった

state に載せた文脈(`cwd`・monorepo の構成・`changed_files`・
直前のコマンドと終了コード)を全部外して測り直した(`--no-context`):

| arm | 文脈あり | 文脈なし |
| --- | --- | --- |
| `names` | 81/90(direct 36/36・decoy 27/30・lying 18/24) | **81/90(内訳も同一)** |
| `descriptions` | 90/90 | **90/90** |

**1 件も動かなかった。** confidence がわずかに上がる(0.913 → 0.922)だけで、
外したシナリオも同じ 3 件。

[01](01-shell-risk.md#2-同じコマンドでも文脈で判断が変わる)・
[05](05-browser-chaos.md#2-効いたのは質問ではなく-state-だった) では
**state の設計が最大のレバー**だったので、これは逆向きの結果になる。
理由はおそらく**ゴール文が意図を明示しているから** ——
「staged のファイルだけ lint したい」と書いてあれば、
`changed_files` を見る必要がない。

つまり **文脈が効くのはゴールが曖昧なとき**で、そこは本実験では測っていない(§6)。
実測としては、**タスク選択では文脈のトークンを払う価値がなかった**。

## 6. 正直な限界

- **正解ラベルはこちらが付けた。** [16](16-eslint-oracle.md) は ESLint が
  ラベルを出すので主観が入らなかったが、ここは違う。緩和のために
  「正解はコマンドが実際にやること」という規則を先に決め、
  ロスターの `command` を書いてからシナリオを書いたが、
  **ロスターもシナリオも同じ人間が書いている**ことは残る。
- **ロスターは合成。** 実在の monorepo に似せてあるが本物ではない。
  特に**嘘をつく名前 6 個はこちらが仕込んだ**もので、
  実リポジトリでの嘘の頻度は測っていない。`lying` がシナリオの 8/30 を占めるのは
  **実際の分布より確実に多い**ので、90.0% は悲観側に寄っている。
- **ゴール文が丁寧すぎる。** どのシナリオも 1 文で意図を明示している。
  実際のエージェントが持つのは「テスト通して」「CI 直して」のような曖昧な指示で、
  §5 の結論(文脈は要らない)はそこでは反転するはず。
- **1 タスクしか選べない。** 実際には「`db:migrate` してから `db:seed`」のような
  複数タスクの連鎖が要る場面がある。`db:reset` を正解にしたシナリオはそれを
  1 タスクに畳んで回避しているだけで、**連鎖の必要性の判断は測っていない**。
- **255 の上限には触っていない。** large は 133 で、上限の半分強。
  クライアント側は 255 超で例外を投げる(`experiments/shared/jev.ts`)ので
  API には届かないが、**200〜255 付近の劣化は未測定**。
- **実行していない。** 選んだタスクを走らせて成功したかではなく、
  「こちらが正解と決めたタスクと一致するか」を測っている。
- **`escape` 6 件は全部「タスクランナーの外の仕事」**(依存追加・リネーム・PR)。
  「ロスターに似たタスクはあるが微妙に違う」という難しい該当なしは
  `rollback_prod` の 1 件だけで、逃げ道の 18/18 はやや楽な設定で出た数字。

## 7. この実験で確定したこと

1. **名前だけで選べる。** 53 タスクから 90.0%、133 タスクでも 85.6%。
   1 リクエスト 0.18 秒・$0.00007(§2・§4)。
2. **名前が自分を説明しているタスクは完璧**(`direct` 36/36)。
   **落ちるのは名前が嘘をつくところだけ**で、[16](16-eslint-oracle.md) の予測どおり(§2)。
3. **1 行の説明を足すと 100%。** 実際のコマンドを見せても同じ 100% なので、
   **散文で情報が尽きている**([16](16-eslint-oracle.md) の
   「逃げ道は言語化さえすれば渡せる」の別ドメインでの再現)(§2)。
4. **逃げ道は選択肢ではなく別の noul にする。** noul ゲートは 18/18、
   選択肢に混ぜると 16/18 で、さらに**答えのある難問をそこへ逃がす**
   (`lying` 18/24 → 15/24)(§3)。
5. **ゲートの代償はロスターの説明で消える。** 名前だけだとゲートが正解を 6 件捨てるが、
   説明文があると 0 件(§3)。
6. **説明文 + noul ゲート = 108/108。** 該当なしを含む全 36 シナリオで全問正解(§3)。
7. **confidence が誤りの種類を分ける。** 名前から原理的に読めない `strict_types` は
   0.99 で誤答し、単に迷っている `pre_push_gate` は 0.36。
   **後者だけがゲートで拾える**(§2)。
8. **リポジトリの文脈は 1 件も動かさなかった。** ゴール文が意図を明示している限り、
   `changed_files` や直前の終了コードは払い損(§5)。

## 8. 次に試すこと

> **追記: 最初の 2 つは [23](23-task-filter.md) で検証した。**
> ゴール文を渡さず diff だけを state にすると **§5 は反転する** ——
> ブランチ名と題名まで外すと、パスだけでは無害な変更の判別が
> **0.482(コイン投げ)**に落ち、hunk を渡す arm だけが 0.183 で残る
> ([23 §4](23-task-filter.md#4-文脈は効いた--17-との違いは意図が書かれているかどうか))。
> 連鎖のほうは**二段構えが要らなかった**: `just` の依存グラフを外に置いて
> **ゴールだけ採点し、前提は閉包に足させる**と、順序も前提も判断の外に出る
> ([23 §1](23-task-filter.md#1-しくみ))。§6 の「1 タスクしか選べない」もそこで消えている。

- **曖昧なゴールで測り直す。** 「テスト通して」「CI 直して」だけを state に入れ、
  文脈(`changed_files`・直前の失敗ログ)を足したときの差を測る。
  §5 が反転するはずで、反転すれば
  「**文脈は意図が曖昧なときだけ効く**」という一般則になる。
- **複数タスクの連鎖。** 「1 つで足りるか」を noul で聞き、
  足りないなら順序付きで 2 つ選ばせる二段構え([06 の H](06-ideas.md))。
- **実在のロスターで。** 手元の `package.json` / `Makefile` / `moon` の
  タスク一覧をそのまま読み、人手ラベルの代わりに
  **「エージェントが実際に選んで実行し、終了コード 0 だったか」**を正解にする。
  §6 の「実行していない」と「ラベルが主観」を同時に潰せる。
- **エージェントの一手目として実装する。** [06 の C](06-ideas.md) の
  permission hook と同じ形で、`npm run <?>` の補完に挿す。
  0.18 秒なので体感に乗らない。
