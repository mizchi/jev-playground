[43](43-finish.md) は guard を端から端まで測り、
**配線可能な 4 つのうち 3 つを未実施のまま残しました**([TODO §1.1](../TODO.md))。
これがその 3 つです。

そして答えの形は、入る前に想像していた形ではありませんでした:

| コンポーネント | 配線 | 判断したか | 端から端まで何が出たか |
| --- | --- | --- | --- |

## 0. アームを書く前に、そのアームが何も測らないと分かった

書こうとしていたのはこれです ——
`run.ts` に `router` アームを足し、32 タスク走らせ、固定モデルのアームと比べる。
**1 時間のエージェント時間を使って、全行が同じモデルの表が出るところでした。**

理由は [32](32-repair.md) と [36](36-router-e2e.md) の修理タスクの作り方です:

```ts
export const REPAIR_PROMPT =
  "The tests under test/ are failing. Fix the source under src/ so that all tests pass. " +
  "Do not modify any test file.";
```

**53 タスクが共有する 1 本の文字列です。**
リクエストについて聞くルータは、**同一の質問を 53 回聞かれる**ので、
返せる答えは 1 つしかありません。

だから `src/probe.ts` を先に書きました ——
**エージェントを走らせずに、1 タスクにつき 3 判断**。
58 タスクで 174 コール、中央値 184 ms、数セント、数分。
掃き掃除は数時間です。
[24 §2](24-adhoc-rules.md) が主張する順番で、**私が何度も学び直している順番**です。

probe が答えたこと:

| 問い | 答え |
| --- | --- |
| model router: タスクごとに tier は変わるか | **リクエストだけなら 58/58 が sonnet の 1 段** |
| 何を見せれば変わるか | 実際のテスト失敗を足すと 8/58 が haiku に |
| orchestration gate: `Task` を通すか | **58/58 で通さない**(平均 0.15、cutoff 0.50) |
| skill router: 300 件から何か読むか | 58 タスクで 31 件ロード、**実体は 3 種類** |

## 1. Model router

### 1.2 答えがどこから来ているのか —— 出荷された `minConfidence` が自分の tier 判断を上書きする

**これが probe で探していなかったのに出てきたものです。** 58 タスク、エージェント抜き:

| | n | / 58 |
| --- | --- | --- |
| **tier score が haiku と言った**(0.5 未満) | 22 | 38% |
| ...で、haiku になった | 8 | 14% |
| ...**`minConfidence` が sonnet に留めた** | **14** | **24%** |
| confidence が出荷値 `minConfidence: 0.5` を下回る | **39** | **67%** |

tier score は 0.17..1.09(中央値 0.59)、confidence は 0.21..0.76(**中央値 0.44**)。

**confidence の分布が丸ごと床の下に在ります。**

`minConfidence: 0.5` は「確信の低い判断で**梯子を下げるな**」という規則で
([21 §7](21-confidence.md))、意図は「時々出る不確かな答えを止める」ことです。
ところがこのコーパスでは**中央値 0.44・最大 0.76** ——
つまり規則は例外の受け皿ではなく、**67% に効いていて、
効く方向は常に高い方**です。

[25](25-thresholds.md) の主題そのもので、
[37](37-hermes.md) が `escalateAt: 0.7` について見つけたのと**同じ形**が隣のフィールドに在りました。

### 1.3 同じリクエストを 53 回 —— このプログラムで一番きついドロー測定が、無料で手に入った

53 の修理タスクが 1 本のプロンプトを共有しているので、
`onPrompt` の列は**同一リクエストに対する 53 ドロー**です。
つまり**この質問自身の再現性の測定**で、追加コストはゼロです:

| | |
| --- | --- |
| 同一リクエスト 53 回の score | **1.01..1.04、sd 0.006** |

**この質問についてルータはほぼ決定的です。**
[25](25-thresholds.md) がドローの分散を主題にしているので、
「小さい差はドローだ」と言い逃れできない土台がここで初めて手に入りました。

そして実際のテスト出力を足したときの**対になった差**:

| | |
| --- | --- |
| tier が変わったタスク | 8 / 58 |
| tier score が**下がった**タスク | **57 / 58** |
| 対になった下がり幅 | 平均 **0.46**、sd 0.21(0..2 の梯子上) |
| 上のドロー sd との比 | **82 倍** |
| ドロー sd の 2 倍を超えたタスク | 57 / 58 |

**実際の失敗を見せると、仕事が小さく見えます。**
ここに書くと思っていたことの逆でした ——
「テストが落ちている、src を直せ」という指示のほうが、
**具体的な 1 本の assertion より開いて読める**わけです。

そしてこれは**安い方向**です。テストを先に走らせるホストは
`node --test` 1 回で安い答えを手に入れ、
**外したときに戻れるのは安い段のほう**です。

## 3. Orchestration gate —— 配線されていて、一度も発言しない

`Task` を `--allowedTools` に入れたので**エージェントは委譲できます**。
gated アームには出荷の `jev-orchestrator` が `PreToolUse` の `Task` matcher で載っています。

境界コーパス 5 件 × 2 アーム × 2 反復 = **20 run**:

| アーム | 完遂 | tests intact | 中央値 tool call |
| --- | --- | --- | --- |
| `subagent`(`Task` 許可、gate なし) | 10/10 | 10/10 | 12 |
| `orchestrated`(`Task` 許可、gate あり) | 10/10 | 10/10 | 10 |

### 3.1 seam に通信が流れなかった

| | |
| --- | --- |
| `Task` 呼び出し | **0** |
| tool call 総数 | 227(Bash 135・Read 80・Edit 12) |
| gate が相談された回数 | **0** |

**ツールを持っていて、一度も使いませんでした。**
だから上の表の差(中央値 12 対 10)は**gate のコストではありません** ——
gate は発言していないので、これは 10 run 対 10 run のドローの幅です。

### 3.2 では何が確立したのか、そして何によって

コーパスがこの拒否を引き出せないので、**wire で確認しました**:

| 主張 | 何で |
| --- | --- |
| hook が gate に届き、split 拒否が spawn を deny する。**gate 自身の理由付きで** | `test.ts`、合成 `Task` イベント |
| driver が死んだら fail open し、行に**「許可した」ではなくそう書かれる** | `test.ts` |
| このコーパスでは gate は**全 spawn を拒否する** | `records/probe.json`: 出荷 cutoff 0.50 を超えたもの 0/58、平均 0.15 |
| エージェントが**そもそも spawn を求めない** | この掃き掃除 |

**そして gate が拒否するのは正しい答えです。**
1 ファイルのバグ修正に subagent は要りません。
コンポーネントがコーパスに同意し、エージェントが両方に同意し、
**全員が一致した測定に情報は入っていません**。

[43 §3](43-finish.md) が guard で踏んだのと同じ失敗で、より悪いです ——
guard は 978 コマンド中 12 件では**発言した**。ここは分母がゼロです。

## 4. 100% は計器の数字でした

新しいアームが全部 100% で返ってきました。**そこで結果ではなく計器を見ました。**

両方のプロンプトの末尾はこれです:

> ... **Do not modify any test file.**

そして `passed` の定義はこれでした:

```ts
export function testsPass(dir: string): boolean {
  const out = spawnSync("node", ["--test"], { cwd: dir, encoding: "utf8", timeout: 120_000 });
  return out.status === 0;
}
```

**assertion を書き換えたエージェントも、これで 0 を返します。**
[43](43-finish.md) の 186 run はこの穴の上で採られました。

直し方は `Run.testsIntact` —— エージェントが走る**前に** `test/` を撮り、後で比べる。
`passed` は終了コードのままにして [43](43-finish.md) の行との比較可能性を保ち、
**2 つを合わせるのはレポート側**でやります。

そして**コードを読むテストではなく、走らせるテスト**で確認しました:

```
ok   a passing run is checked against the instruction it was given
ok   the grader actually catches a neutered test file
```

2 つ目が実際にやること —— 本物のタスクを取り、テストファイルを
`test("ok", () => {})` に置き換え、**`node --test` が PASS になることを確認し**、
スナップショット比較が捕まえることを確認する。

**穴が在ったことより、見つけた理由のほうが残す価値があります。**
100% は嬉しい数字で、嬉しい数字が出たときに計器を疑うのは習慣が要ります。
このプログラムで繰り返し効いている規律 ——
**入ってきたときの予想を裏書きする測定を疑う** —— の、
一番安い形がこれでした。

ledger も直しました: Edit/Write の `file_path` を記録するので、
`testsIntact` が「触った」と言ったとき **どの呼び出しがやったか**が分かります。

## 5. この 3 つの数字が何でないか

- **`--out` が無かったら記録が壊れていました。** 3 つの掃き掃除を並列に走らせるので、
  read-then-write の `save()` が 1 ファイルを共有すると行が消えます。
- **compactor は相変わらず配線不可です。** `PreCompact` は中断か要約指示の書き換えだけで、
  `jev-compact` は要約せず削除します([39](39-compact-ranking.md))。
  **4 つのうち 4 つが配線され測られ、5 つ目はホストについての事実です。**
- **束ねた 4 つではありません。** [37 §6](37-hermes.md) が「束ねるのは無料ではない」と測っているので、
  ここの数字は 4 つ同時には持ち越せません。
- **fence と ledger は全アームに在ります。** どちらも tool call ごとに node 起動 1 回を払うので、
  **完全に素のエージェントはここに 1 つも居ません**。
