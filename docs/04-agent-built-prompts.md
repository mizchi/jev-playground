# 04. コーディングエージェントに質問を組ませる

Jev に渡す質問を人間ではなくエージェントに設計させ、動的に判定パイプラインを組み立てる。
評価には [01](01-shell-risk.md) のシェルコマンド判定を使う。
**正解ラベル付きコーパス 24 件**と**手書きのベースライン 23/24** が既にあるので、
「エージェントの設計は人間の設計に届くか」を数字で言える。

再現:

```bash
cd experiments/agent-questions && npm install
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --condition blind   --repeat 3
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --condition briefed --repeat 3
```

エージェントは `claude -p --model claude-sonnet-5`。2 条件で比較する:

- **blind** — 課題と API リファレンス(3 プリミティブの仕様)だけを渡す
- **briefed** — 加えて [docs/README.md の「効いたパターン」](README.md#効いたパターン要約)を渡す

エージェントは**質問と読み取り方の両方**を JSON で出す。ただし読み取り方は
宣言的に書かせる(どの質問から読むか + score の閾値 or choice の対応表)。
コードを生成させて eval はしない。

---

## 1. 結果: 書かせたままでは当たらない。ばらつきが巨大

| 条件 | 3 回の正解数 | 平均 | 出てきた形 |
| --- | --- | --- | --- |
| blind | 18, **23**, 19 | 20.0 | score/1問, score/1問, **choice**/2問 |
| briefed | 17, **10**, 22 | 16.3 | 全て score(6〜9 問) |
| 手書き([01](01-shell-risk.md)) | **23** | — | score/9問 |

**同じプロンプトで 10/24 から 23/24 まで振れる。** 1 回試して良い数字が出たら
それは運で、悪い数字が出てもそれも運。**エージェントに書かせるなら評価が必須**という、
当たり前だが実測すると重い結論。

**briefed は平均を改善しなかった**(むしろ下がった)。ただし n=3 でばらつきが大きいので、
「悪化させた」とは言えない。**「効いたパターンを渡すだけでは当たるようにならない」**が
言える範囲。

## 2. 原因は設計ではなく閾値だった

briefed の 3 サンプルについて、**質問はそのまま・閾値だけをラベル付きデータに
合わせ直す**とこうなる(2-fold: 半分で閾値を決めて残り半分で測る):

| サンプル | 書かせたまま | 閾値を合わせ直す(held out) | エージェントが選んだ閾値 |
| --- | --- | --- | --- |
| briefed #1 | 17/24 | **22/24** | block ≥ 3.5, confirm ≥ 1.5 |
| briefed #2 | **10/24** | **22/24** | block ≥ 3.0, confirm ≥ 1.0 |
| briefed #3 | 22/24 | 21/24 | block ≥ 3.5, confirm ≥ 1.5 |

**質問は良い。閾値が壊れている。** 10/24 だった #2 も、閾値を差し替えるだけで 22/24 になる。

理由は明快で、**エージェントは自分が書いた rubric が実際にどんな値を出すかを見ていない**。
5 段階(0〜4)の rubric を書いて「block は 3.5 以上」と決めても、
実際の期待値がほとんど 2 前後に集まっていれば、全部が `confirm` 以下に落ちる。
[01 の 3 節](01-shell-risk.md#3-順序のある結論は-score-で聞く)で手書き側が使った
`1.5 / 0.5` という閾値は、**スコア分布を見てから決めた**ものだった。

> **分業はこう切るのが正しい。**
> **質問の設計 → エージェント。閾値の決定 → ラベル付きデータ。**
> 閾値を合わせ直すと、正解数が上がるだけでなく**ばらつきが消える**
> (書かせたまま 10〜22 → 合わせ直して 21〜22)。これが実務上は一番おいしい。

注意点として、**24 件のうち 12 件で閾値を決めるのは少なすぎる**場面もある。
briefed #3 は書かせたまま 22 が合わせ直して 21 に下がっており、
標本が小さいと過学習側に振れる。数十件は欲しい。

## 3. blind でも `score` に自力でたどり着くことがある

blind の 3 サンプルのうち 2 つは、助言なしで**順序のある結論に `score` を選んだ**
(18/24 と 23/24)。残り 1 つは `choice` を選び、
[01 が予測したとおりの壊れ方](01-shell-risk.md#3-順序のある結論は-score-で聞く)をした。

`choice` を選んだサンプルの別の回では **14/24 で、10 件の誤りが全て「甘い側」**だった。
`rm -rf /`・`dd if=/dev/zero of=/dev/sda`・`mkfs.ext4` などが揃って `confirm` に落ちる。
3 択の `choice` は隣接レベルに分散して最上位が立ちにくい、という 01 の観察が
**別のエージェントの設計で再現した**。

つまり「順序があるなら score」は、**エージェントが半分くらいは自力で当てるが、
外したときの壊れ方が大きい**種類の知識だった。だから助言する価値はあるが、
助言だけでは足りない(2 節)。

## 4. エージェントが書いたものの中身

briefed が繰り返し出してきた形は、実は [01](01-shell-risk.md) の手書きとほぼ同じ構成だった:

- `risk_level` を `score`(順序あり)にして、これだけで判定する
- 破壊性・影響範囲・データ送出・安全機構の回避・曖昧さを `noul` で**監査用に**添える。
  判定はさせない

自分で書いたメモ(抜粋):

> risk_level is a single monotonic score ... read via thresholds per the findings on
> ordered outcomes; the four noul questions are supporting/auditable signals ... that
> inform but don't directly gate the verdict, since **combining them via a hand-written
> rule would just move the bug surface**.

最後の一節は [01 の 4 節](01-shell-risk.md#4-分解は万能ではない)の結論そのままで、
渡した助言を理解して使ってはいる。**理解と校正は別の能力**だった、という話。

## 5. 正直な限界

- **各条件 3 サンプル。** 平均の差(20.0 vs 16.3)はこのばらつきでは有意と言えない。
  言えるのは「ばらつきが巨大」と「閾値の合わせ直しが効く」の 2 点。
- 課題が 1 つ(シェルコマンド判定)だけ。他の課題で同じ分業が効くかは未検証。
- 閾値の合わせ直しは 2-fold の 12 件フィット。実運用なら数十〜数百件欲しい。
- エージェントは `claude -p` の 1 ショット。ツールも反復も与えていないので、
  **「生成 → 評価 → 閾値調整 → 再生成」のループを回させれば当然もっと良くなる**はず。
  そのループを回すのに要る材料(ラベル付きコーパスと評価関数)は、
  この実験でそのまま揃っている。

## 6. この実験で確定したパターン

1. **エージェントに質問を書かせるなら評価を必ず付ける**(1 節)。
   同じプロンプトで 10/24 〜 23/24 に振れる。
2. **質問はエージェント、閾値はデータ**(2 節)。
   閾値を合わせ直すと平均が上がり、ばらつきが 10〜22 → 21〜22 に収束する。
3. **助言を渡しても校正はされない**(2 節)。「順序があるなら score」は伝わるが、
   「その score のどこで切るか」は分布を見ないと決まらない。
4. **`score` の選択は半分は自力で当たる**(3 節)。ただし外したときは大きく壊れる。

## 7. 次に試すこと

- **生成 → 評価 → 閾値フィット → 再生成のループ。** 材料は揃っている
  (`src/run.ts` の評価関数をそのままエージェントに握らせる)。
  何周で手書きの 23/24 を超えるか。
- 閾値フィットを標準の部品にする。`lib` 側に「score の期待値 + ラベルから閾値を引く」
  ヘルパを置けば、[01](01-shell-risk.md) も [02](02-moba.md) も同じ形で校正できる。
- エージェントに**コーパスも書かせる**条件。評価用データまで自作させると、
  自分の設計に都合の良いコーパスになるかどうか。
