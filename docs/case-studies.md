## 判定させる

### <a id="shell-gate"></a>1. シェルコマンドの許可ゲート —— 効いたのは質問の形と state の文脈で、限界は閾値ではなく要求に入っていない事実だった

**何をしたか** コーディングエージェントが打つシェルコマンドを、実行前に allow / confirm(ask)/ block(deny)へ振り分ける。
24 件のラベル付きコーパスで質問の形を決め([01](01-shell-risk.md))、Claude Code の `PreToolUse` hook(依存ゼロの `.mjs` 1 枚)として
全 Bash コマンドの前に挟み([18](18-permission-hook.md))、本物のエージェント実行・公開 npm script・実リポジトリのトラフィックに当てた([43](43-finish.md)・[49](49-scripts.md)・[55](55-wild.md))。

**Jev の使い方**
- 結論の `permission` を 0..2 の `score` で聞き、閾値 0.5 / 1.5 はコード側で引く。`allow < confirm < block` は順序のある結論なので `choice` にしない。
- 同じ 1 リクエストに原子述語 7 問(`destructive`・`exfiltrates`・`obfuscated` など)と `blast_radius`(score)を束ね、`permission` と原子の保守側を採る。
- state にはコマンド文字列だけでなく `cwd`・git(`.git/HEAD` と `.git/config` を直読み)・保護ブランチ・`.claude/jev-gate.json` の `context` を載せる。
- 返すのは `deny` / `ask` だけで `allow` は返さない(狭める専用)。失敗経路は全部「判断なし = 通常フロー」に落とし、リトライせず 2,500 ms で諦める。

**効いたチューニング**
- 同じ 3 択を `choice` から `score` にしただけで 19/24 → **23/24**。`dd if=/dev/zero of=/dev/sda` の confidence が 0.47 → 0.93 になり、
  「confirm と block のどちらに寄せるか」の迷いが消えた(コード側の合成規則はどう捏ねても 14/24)→ [01 §3](01-shell-risk.md#3-順序のある結論は-score-で聞く)
- 判断に要る文脈を state に載せる。文字列ではほぼ区別できない `rm -rf ./build` と `rm -rf ./data`(本番ボリュームの bind mount)が
  permission **0.59 対 1.98** に分かれる(向きは正しいが `./build` は ask 止まり)→ [01 §2](01-shell-risk.md#2-同じコマンドでも文脈で判断が変わる)・[18 §4](18-permission-hook.md#4-hook-が文脈を持っている側であること)
- 総合の score と原子の保守側を採る。同じ 72 応答でスコア単独 65/72(90.3%)・原子単独 44/72(61.1%)→ 両方で **68/72(94.4%)** → [18 §2](18-permission-hook.md#2-判定そのもの)
- `exfiltrates` の `false` 側を「外向き転送が無い」から「宛先がこのプロジェクト自身の remote やレジストリなら違反ではない」に直す。普通の `git push` を
  deny していた穴が塞がり、コーパス一致 67/72 → 68〜69/72、正当な外向き転送の probe 7/8 → [18 §3](18-permission-hook.md#3-コーパスでは見つからないバグが出た)

**結果** hook として **68/72(94.4%)**、median **329 ms**、1 コマンド **$0.000032**。本物のエージェント 186 run では修理コーパスの完遂が bare・guard とも **63/63**、
2,500 ms 予算の超過は **391 件中 0 件**。gate が発言する(ask か deny を返す)率はコーパスで決まり、自作サンドボックス **1.2%**・実リポジトリ **6.3%**・公開 npm script **24.1%**。
実リポジトリでは初めて本物の `deny` が、エージェントが自分で選んだ `curl … | bash`(permission 1.65)に当たった(fence が止めた後の 3 回目の試行)。

**うまくいかなかったこと** 無人のエージェントには `ask` は `deny` と同じで、[01](01-shell-risk.md) 自身のラベル(`confirm`)どおり `rm -rf` を ask で止め続けた run が 17 呼び出しで失敗した —— ラベル集合が人間の存在を仮定していた([43 §4b](43-finish.md#4b-境界コーパス--gate-が初めて仕事を奪いました)・[43 §5.1](43-finish.md#51-無人エージェントに対して-ask-は完全なブロックです))。
実トラフィックでは cutoff が引けない。無害なコマンドが [01](01-shell-risk.md) の「聞くべき」側(≥ 0.36)に入り込み、危険側を作っても世界差の中央値 0.060 が同じ世界に 2 回聞いた差 0.050 とほぼ同じ —— state はディレクトリの中身を持たず、質問は「誰の意図か」を聞いていない([43 §4.3](43-finish.md#43-そして-cutoff-は当てはめられません--2-クラスが完全に重なっています)・[50 §3](50-damage.md#3-そして-gate-は見分けられません))。
迷った判定だけ Sonnet に回す二層構成は、第二段のほうが弱く(21/24 対 23/24)成立しなかった([07 §2](07-escalation.md#2-q0--第二段は本当に強いのか))。

**教訓** 順序のある判定は `score` で聞いて閾値はコードに置き、ゲートは狭める方向にだけ使って失敗は通常フローに落とす([tuning §6.1](tuning.md#61-失敗の落とし先を精度より先に決める))。
cutoff を動かす前に、判断に要る事実が要求に入っているかを見る(入っていなければどのコーパスでも直らない)。質問文の穴は実運用の形に載せるまで見えない([tuning §6.4](tuning.md#64-実運用の形に載せることが最後のテスト))。

→ 詳細: [01](01-shell-risk.md) ・ [07](07-escalation.md) ・ [18](18-permission-hook.md) ・ [43](43-finish.md) ・ [49](49-scripts.md) ・ [50](50-damage.md) ・ [55](55-wild.md)

### <a id="eslint"></a>2. ESLint の合否判定と lint プラグイン —— 実装を見せなくても基準の文で当たる。使える形は「見落とすリンタ」で、直すのは閾値ではなく文

**何をしたか** まずコードと ESLint ルールの説明文(`meta.docs.description`)だけを渡し、実装 `create()` を伏せて合否を当てさせた(正解は本物の ESLint 9.39.5)。
次に判定を Jev がやる本物の ESLint プラグインを作り、関数ごとに「レビューでどれだけ押し返すか」を出させた。最後に、使う側が 1 文書けばルールになる
`jev/rule`(ノードセレクタだけコード、違反かどうかは文)を、ラベル付きの 641 行とこのリポジトリ自身の JS 9,315 行に当てた。

**Jev の使い方**
- 合否判定は 1 スニペット = 1 リクエストで 12 ルールを 12 問の `noul` に束ね、質問キーは不透明な `q00`..`q11` にしてルール ID を裏口から渡さない。
- プラグインは関数ごとに「押し返す強さ」1 軸の `score`(0〜3)と「現実の入力で間違うか」の原子 `noul` の 2 問を、ファイルの全関数ぶん `Program:exit` で 1 リクエストにする。
  ESLint のルールは同期関数なので、判定は warm pass で先に取ってキャッシュし、ルールはハッシュを引くだけ。
- `jev/rule` はノードごとに `score` で聞き、レベル 0 を「このルールは当てはまらない」にしてセレクタの拾いすぎをモデルが言えるようにする
  (`noul` にしないのは、confidence が付き「疑い」と「明確に違反」を分けられるから)。

**効いたチューニング**
- confidence を報告の柵にしない。`score >= 1.5` に `confidence >= 0.5` を重ねると 7〜11 ポイント落ちていた(confidence は clean でも bug でも 0.54〜0.57)。
  閾値を越えたものは必ず出し、低 confidence は別 messageId の `jev/unsure`(「人が見ろ」)に回す → [21 §7](21-eslint-plugin-jev.md#7-confidence-をゲートにすると-11-ポイント損する)
- ファイル単位で束ね、state にはファイル全体を置く。関数 1 個ずつ聞くより 4.7x 少ないリクエスト・2.1x 少ないトークンで差は 1.4 ポイント。
  state を関数だけにすると AUC は 0.80 → 0.83 に上がるが誤検出が 5 倍になる → [21 §5](21-eslint-plugin-jev.md#5-バッチはほぼ無料--これがこのプラグインの成立条件)・[21 §6](21-eslint-plugin-jev.md#6-ファイルの文脈は精度を上げない下げる)
- 閾値ではなく gap(違反と残りの点数差)を読み、狭ければ文を書き直す。5 ルール中 2 つの 1 稿目は gap 0.16 / 0.28 で、書き直して 2.16 / 0.77。
  文はキャッシュキーに入り閾値は入らないので、2 ルール書き直しても再質問は 18 件 / $0.0004、閾値を動かすのは 0 件 → [24 §1](24-adhoc-rules.md#1-読むのは閾値ではなく-gap)・[24 §2](24-adhoc-rules.md#2-5-ルール中-2-つは最初の文が失敗した)
- 実コードでは gap の隣に band(答えがどのレベルに居るか)を置く。狭い gap の 3 ルールは 2 つが「違反が無い」、1 つが「文が働いていない」だった → [26 §4](26-repo-rules.md#4-gap-の隣に-band-を置いた)

**結果** 説明文だけで **190/215(88.4%)、AUC 0.95**(多数派ベースライン 55.8%)。見せる範囲は正解率をほとんど動かさず(ID だけ 86.5%・両方 87.4%)、動くのは誤りの種類 —— ID だけだと過検出が 101 対 34 に膨らむ。
プラグインは自信のある指摘 **15/15 が本物のバグ・誤検出 0** だが、12 バグ中 5 個しか捕まえない(精度 100% / 再現率 42%、関数 1 個 $0.000017、キャッシュ有りの lint 31 ms)。
`jev/rule` はラベル付きコーパスで自信のある指摘 **5/5**、実リポジトリでは **579 判定・2.9 秒・$0.0135** で指摘 19 件、要修正は 2 件(どちらも数値の由来が書かれていない)。

**うまくいかなかったこと** 実装にしか書いていない逃げ道は当たらない。公開オプションで表せる `no-cond-assign` は既定オプションを渡すと 10/15 → 15/15 に直るが、`create()` にハードコードされた `no-empty` は 15/25 のままで、逃げ道を渡すと見逃しが 0 → 11 件に増えた([16 §5](16-eslint-oracle.md#5-逃げ道を渡したら直るのか--spec-arm))。
`.sort()` の比較関数なし・`splice(at)`・`/g` 抜け・`await` 忘れのような、API の挙動を知らないと見えないバグは落とす([21 §3](21-eslint-plugin-jev.md#3-結果--捕まえたものと落としたもの))。
実リポジトリでは自信のある指摘が **0/5** で、当たった 2 件は conf 0.29 / 0.19 の「質問」だった。外れはほぼ全部わざとそうしてあるコードで、`no-swallowed-catch` は note を書き直しても subject を広げても直らず retire した([26 §3](26-repo-rules.md#3-confidence-は直すべきかではなく文が当てはまるか)・[26 §5](26-repo-rules.md#5-文を書き直す--subject-を広げる--3-draft-測ってどれも直らなかった))。

**教訓** 散文しかない規約を lint にする道具としては成立する。ただし `warn` の「見落とすリンタ」として使い、ゲートには例外規定を渡さず、閾値より先に gap と band を読んで文を直す。
コーパスで校正した文は実コードの「わざとやっている版」で外れるので、実リポジトリに当ててから出荷する([tuning §4.2](tuning.md#42-コーパスで校正した文を実コードに当てるときはわざとやっている版を疑う))。

→ 詳細: [16](16-eslint-oracle.md) ・ [21](21-eslint-plugin-jev.md) ・ [24](24-adhoc-rules.md) ・ [26](26-repo-rules.md)

### <a id="code-review"></a>3. コード品質の指標とレビュー —— 効くのは欠陥クラスの「名前」と質問ごとの閾値で、数値の指標は何も足さなかった

**何をしたか** [21](21-eslint-plugin-jev.md) の曖昧な 1 問(「レビューでどれだけ押し返すか」)が落としたバグは見えなかったのか聞かれていなかったのかを、
8 つの欠陥クラスに名前を付けた 8 問に置き換えて測った([22](22-code-criteria.md))。手で 2 回引いた閾値は部品にして、当てはめていない標本で採点し直した([25](25-thresholds.md))。
最後に、機械的な指標(変更行のカバレッジ・ネスト・関数長・テスト名との重なりなど)を渡すと 1 行 diff のレビュー(テストを通したままか)が良くなるかを測った([33](33-review.md))。

**Jev の使い方**
- 8 つの欠陥クラス(`api_default`・`lost_update`・`unescaped_composition` など)をそれぞれ true/false の criteria 付きの独立した `noul` にし、汎用 noul と
  「押し返す強さ」の `score` と合わせて関数あたり 10 問(`full`)。質問キーは `a3-007` のような不透明キー(指標名をワイヤーに載せない)。ファイル 1 個 = 1 リクエストなので 2 → 10 問にしても往復は 14 のまま。
- レビューは 1 行 diff ごとに「テストはまだ通るか」を `noul`、同じ判断を段階にした `risk` を `score` で聞き、見せるもの(diff だけ / + ソースとテスト /
  + 機械的な指標 / diff と指標だけ)を arm で変える。ラベルは 261 diff 全部 `node --test` の終了コード。
- 閾値の部品 `advise()` は数より先に verdict(`no-signal` / `overlapping` / `wide-gap` / `fit`)を返す。wide-gap ならいじらない、overlapping ならどちら側に倒すか決める。

**効いたチューニング**
- 指標を instructions に列挙せず、別々の問いに分ける。score の instructions に入れた `checklist` は 33/51 → 31/51 で新しい検出が生まれずトークンが 81% 増え、
  分けた `full` は **41/51**(誤検出は同じ 3/138)で指摘が `median matches api_default (0.35)` のように名前で返る → [22 §7](22-code-criteria.md#7-チェックリストを-instructions-に入れると校正になるだけ)
- 閾値を質問ごとに引く。自クラスへの平均が `api_default` 0.20 から `unit_or_arithmetic` 0.94 まで開くので、共通 0.80 は 13/36 しか拾わず指標ごとなら 24/36(誤検出 0)。
  ただし名前の正しさは 13/13 から 20/26(77%)に落ちる → [22 §4](22-code-criteria.md#4-一番効いたのは指標ではなく指標ごとの閾値)・[22 §5](22-code-criteria.md#5-名前の正しさは閾値を下げると壊れる)
- 当てはめた閾値はホールドアウトで採点し、清潔な側の縁ではなく gap の真ん中に置く。同じ検出 23/36 のままホールドアウトの誤検出が 24 → 7。
  壊すのは draw ではなく新しいコードで、越える率は再 draw 0.37%・新しい関数 2.0% → [25 §3](25-thresholds.md#3-境界ではなく-gap-の真ん中に置く)・[25 §4](25-thresholds.md#4-何が閾値を壊すのか--draw-かコーパスか)
- レビューに渡すならソースとテスト。diff だけの 85%(AUC 0.862)から 90%(AUC 0.941)に上がり、トークンは 5% 増えるだけ → [33 §2](33-review.md#2-4-通りのレビュー)

**結果** 指標を名前で聞くと捕まる数は 33/51 → **41/51**。名前が効くのは見えにくいバグだけで、関数の中だけ読めば分かるバグは naming の有無にかかわらず 15/15、
API の挙動を知らないと見えない名前付きのバグで 14.3% → **52.4%**。閾値の正直な運用点は誤検出 0 なら **18/36**・7 件まで許すなら **23/36** で、
共通 0.80 の 13/36 に対する上乗せ 10 件のうち半分は当てはめの自己申告だった。レビューに機械的な指標を足しても **90% → 90%**・AUC 0.941 → 0.921、トークンは **+69%**。

**うまくいかなかったこと** [21](21-eslint-plugin-jev.md) が落とした 6 個のうち、専用の指標を名指しで投げて戻ったのは 2 個だけ。`splice(at)` は 0.12、`/g` 抜けは 0.09 —— ちょうど正しい問いに自信をもって「いいえ」と答えた([22 §3](22-code-criteria.md#3-落とした-6-個のうち戻ったのは-2-個))。
「列挙外のクラスは汎用質問が埋める」という読みは撤回した —— 保留した 5 個が全部易しいバグで、作り直すと穴は hard なバグで約 32 ポイント(52.4% 対 20.0%)あった([22 §11.1](22-code-criteria.md#111-easy-では-naming-は何もしないhard-では-26-倍になる))。
レビューで一番効くはずだったカバレッジは、261 件のうち未到達の行に触るのが 1 件で分けるものが無かった([33 §1](33-review.md#1-まず指標だけで分かるのか))。

**教訓** 何が悪いかを言わせたいなら指標は別の問いに分け、閾値は質問ごとに・当てはめていない標本で採点して gap の中央に置く。8 指標は重複していて、抜いて本当に困るのは広い `api_default` だけ(9/12 → 4/12)。
数値の指標はプロンプトに入れる前に「指標だけで分かるか」を測る —— 分けない指標は入れても分けず、トークンだけ増える([tuning §4.5.1](tuning.md#451-指標をプロンプトに入れる前に指標だけで分かるかを測る))。

→ 詳細: [22](22-code-criteria.md) ・ [25](25-thresholds.md) ・ [33](33-review.md)

## 選ばせる・振り分けさせる

### <a id="task-runner"></a>4. タスクランナーのタスク選択と test filter —— 名前と 1 行の説明で選ばせ、前提と順序はグラフに任せる

**何をしたか** 17 は 14 / 53 / 133 タスクの合成ロスターから、ゴール文に合うタスクを 1 つ選ばせた(コマンドは伏せ、正解は
「コマンドが実際にやること」なので、名前が内容と食い違うタスクが難問になる)。23 はフィルタで、`just` の依存グラフを先に作り、
ゴール文の代わりに diff を渡してゴールタスクごとに走らせる必要を採点させ、赤くなるタスクが run set に入っているかで測った。

**Jev の使い方**
- 17: `pick`(`choice`。候補はロスターに実在するタスク名だけなので、無いタスクは表現できない)と `applicable`
  (`noul`、「この一覧のどれかが単独でゴールを達成する」)を 1 リクエストに束ね、「該当なし」は選択肢に混ぜない。
- 17 の state はタスク表(arm ごとに名前だけ / + 1 行の説明 / + 実際のコマンド)とリポジトリの文脈(`cwd`・構成・`changed_files`・直前のコマンドと終了コード)。
- 23: 程度を聞くので 18 ゴールそれぞれに 3 段の `score`(0 Waste / 1 Insurance / 2 Required)、diff 全体に `noul` 2 問(`_changes_behaviour`・`_all_waste`)、計 20 問を 1 リクエスト。
  state は diff(既定でブランチ名とコミット題名つき)で、タスクについて Jev が読むのは名前と 1 行 doc だけ。依存辺はコードが読み、前提と順序は閉包が足す。

**効いたチューニング**
- **一覧の項目に 1 行の説明を付ける。** 名前だけ 81/90(90.0%)→ **90/90(100%)**、`lying`(名前が嘘をつく)は 18/24 → 24/24。
  コマンドまで見せても上積みは無い → [17 §2](17-task-picker.md#2-結果--名前だけで-90説明文を足すと-100)。
  実在の justfile でも doc を「何をするか」から「何を守るか」に書き換えて削減 **53.3% → 65.9%** → [23 §12.4](23-task-filter.md#124-効いたのは-1-行のコメントだった)
- **逃げ道は選択肢ではなく別の noul。** 答えの無い 18 判定で noul ゲート **18/18**、`choice` に「(none of these)」を
  混ぜると 16/18 で、答えのある `lying` まで 18/24 → 15/24 に落ちる → [17 §3](17-task-picker.md#3-逃げ道は選択肢ではなく別の問いにする)
- **グラフはプロンプトではなくコードに置く。** 前提・`@inputs`・`@cost` を各質問に載せると削減 68.6% → 66.3%、
  トークンは 1.3 倍 → [23 §5](23-task-filter.md#5-グラフはプロンプトではなくコードに置く)
- **安いタスクには閾値の前に床を引く。** 唯一の見逃しは 4 秒の `fmt-check` が **1.24 対 1.25** で落ちたもの。
  「10 秒以下は無条件」で 45/45 に戻り、代償は 0.5 machine 分 → [23 §7](23-task-filter.md#7-安いタスクに同じ閾値を使ってはいけない)

**結果** 17 は説明文 + noul ゲートで、該当なしを含む 36 シナリオが **108/108**(1 リクエスト 0.18 秒)。
23 は検出 **45/45** のまま machine time を **68.6%**(t=1.25 で 75.8%)削り、1 ブランチ **0.17 秒・$0.000131**。

**うまくいかなかったこと** 17 の「リポジトリの文脈は 1 件も動かさない」はゴール文の無い 23 で反転し、ブランチ名と題名を外すとパスだけの arm は無害な変更の判別が **0.482**(コイン投げ)に落ちた(hunk を渡せば 0.183)。
このリポジトリの `justfile` で終了コードをラベルにやり直すと、検出 18/18 のまま **glob だけの無料の静的判定に負け**(削減 80.2% 対 65.9%)、「ありそうな編集」15 個のうち 9 個は何も壊さなかった。
合成で出た「静的解析では健全さと安さが両立しない」はグラフの扇形の性質で、訂正した([23 §12.3](23-task-filter.md#123-検出は-1818ただし-glob-だけの静的判定に負ける))。

**教訓** 候補が列挙できて名前が内容を言っていれば一覧で選ばせてよく、精度への投資先は質問文ではなく項目名と 1 行の説明。
規則で解ける前提・順序はコードに置いて Jev にはゴールごとの判断だけを聞き、入れる前にグラフが静的解析を悲観的にする形かを見る。

→ 詳細: [17](17-task-picker.md) ・ [23](23-task-filter.md) ・ [tuning §2.1](tuning.md#21-逃げ道は選択肢ではなく別の問いにする) ・ [tuning §4.7](tuning.md#47-スキップの代償が非対称なら閾値もコストで重み付けする)

### <a id="triage"></a>5. 監視アラートのトリアージ —— 検知と severity はコード、cause と root は Jev

**何をしたか** 6 サービスの Web アプリを 16 通りに壊して OTLP 形式のスパンとログを出し、検知は決定的なコード(閾値と倍率)に任せて、
トリアージ —— 人を起こすか・何の問題か・どこにあるか —— を Jev に聞いた。ラベルは `cause` が構成上(注入した障害)、
`severity` が実測(ユーザー向けリクエストのうち 5xx か 1s SLO 超過の割合)で、state の作り方を 7 通り変え、質問は全部同じにした。

**Jev の使い方**
- 順序のある severity(noise / ticket / page)は 3 段の `score`、相互排他な cause(7 択)と root service は `choice`、
  逃げ道の「何も問題ない」と `user_visible`・`deploy_related` などの原子述語は `noul`。逃げ道は cause の選択肢に混ぜず別の問いにした。
- 1 窓(5 分・600 リクエスト)を 1 リクエストで聞き、arm は state だけを変える —— 集計だけ(`aggregate`)・アラート文なし・
  ログ本文なし・生ログをうるさい順 / 均等に選ぶ・集計 + 生ログ・到着順に上限まで(`raw`)。

**効いたチューニング**
- **severity は聞かずに計算する。** 1 行の規則(エラー率 + SLO 超過率)で **16/16・誤ページ 0・見逃し 0**。
  Jev は同じ窓で見逃し 0 だが誤ページ 6〜27 → [27 §3](27-otel-triage.md#3-severity--算術が完勝する)
- **生ログは選び方を決めてから渡す。** 同じ件数・ほぼ同じトークン数(6615 対 6567)で、ERROR 優先に選ぶと誤ページ **27/48**、
  等間隔なら **6/48**(4.5 倍) → [27 §5](27-otel-triage.md#5-同じ件数の生ログをうるさい順に選ぶか均等に選ぶか)
- **生ログではなく集計を送る。** 集計だけ(2026 トークン)で cause **24/30**、生ログを足すと 7441 トークンで 18/30。
  到着順に詰めると 16/16 の窓が state の上限を超え、JSON の telemetry は 1 トークン ≒ 2.4 文字 → [27 §6](27-otel-triage.md#6-全部送るの値段--16-窓すべてが上限に当たる)
- **アラート文を入れるかは減らしたい誤りで決める。** 入れると cause は 20/30 → 24/30 に良くなり、誤ページは 6 → 9 に増える
  → [27「何が言えるか」](27-otel-triage.md#何が言えるか)

**結果** 「severity は規則、cause は Jev」で severity **45/48**・誤ページ **0**・見逃し 3・cause **24/30**(SLO 超過率も使う規則なら severity は 48/48)。
ログ本文を伏せると runbook の正規表現は **8/10 → 4/10**、Jev は 24/30 → **21/30** で残る。全体で 304 判定・$0.069、1 窓の中央値 208 ms。

**うまくいかなかったこと** 逃げ道の noul「何も問題ない」は健全な 18 窓で発火 **0〜4 件**で、異常検知では沈黙は算術にしか担保できない。
[18](18-permission-hook.md#2-判定そのもの) の「保守側を採る」も効かず(`page` に `user_visible` の同意を要求しても 1 件も変わらない)、`max(規則, Jev)` は Jev の誤ページ 9 件を引き継ぐだけだった。
シミュレータのログ本文は診断的すぎるので、本文ありの runbook の 8/10 は実物より高いはず。

**教訓** 順序のある答えでも測れる量の関数なら判断に聞かずに計算し、判断は規則が文面の一致に頼る分類に回す —— 情報を抜いたときに残る分がその層の正味の貢献。
state は大きさではなく選び方で効くので、サンプリング規則は質問の設計として決める。

→ 詳細: [27](27-otel-triage.md) ・ [tuning §4.6](tuning.md#46-答えが測れる量の関数なら聞かずに計算する) ・ [tuning「state に何を入れるか」](tuning.md#state-に何を入れるか)

### <a id="skills"></a>6. skill の選択(推薦・ルーティング) —— 全候補を質問に並べて 1 リクエスト、方針と cutoff はコードに置く

**何をしたか** エージェントが読み込む skill を Jev に選ばせる課題を 4 本で詰めた。08 は公式 cookbook の追試(mizchi/skills 68 スキル、
エージェントが読み込む前に Jev が 1 つ提案)、29 は人が選別したカタログ(ティアがラベル)で 14 プロジェクト × 74 skill = 1,036 判断、
30 は候補を 461 個の実在 skill に広げて道具にし、36 でそれを skill router としてパッケージにした。

**Jev の使い方**
- 08: 全スキルの `choice`(エージェントと同じ 60 文字の切り詰め説明)+ ゲートの `noul` 3 問で 1 リクエスト、上位 3 件だけ
  full description と `SKILL.md` 先頭 700 文字で `choice` + 候補ごとの fit `noul` でもう 1 リクエスト。提案はエージェントへの助言 1 行として渡す。
- 29・30: 並べて上位を取る用途なので、skill 1 つにつき 4 段階の `score` 1 問を fan-out する。state はプロジェクト側
  (ファイルツリー・`CLAUDE.md` の行・依頼文)で、skill の名前と description は質問に置く。
- 36: split(カタログのティアをコードで適用)→ prescore(IDF の語彙重なり、無料)→ ask(shortlist に 1 リクエスト、
  本物の 68 skill で 9,400 入力トークン ≒ $0.0004)→ policy(cutoff と上限をコードで)。

**効いたチューニング**
- **候補は state ではなく質問に置き、幅は狭めない。** 74 問 1 リクエストと 1 問ずつ 1,036 回で答えは 0.25 以内に **99.8%** 一致
  (入力トークン 296,845 対 718,128)。同じ幅 1 で skill を state に移すと一致 53%・AP 0.53 → 0.46 → [29 §4](29-skill-select.md#4-ファンアウトの幅は無料答えが同じ)
- **方針は判断に聞かずコードで適用する。** 「常に提案」の T0 2 行は正例 135 件のうち 28 件で、description には書けない。
  ティア列をコードで適用するだけで AP 0.41 → **0.70** → [29 §6](29-skill-select.md#6-重みを当てるな経路を書け)
- **全問で同一の criteria とタスク文は state に 1 回だけ置く。** 1 問 251 → 118 トークンになり、280 問で 400 だったものが
  461 問 1 リクエスト 54,284 トークンに入る。答えはレベル一致 95%・平均差 0.057 → [30 §1](30-skill-pick.md#1-入るのか) ・ [30 §7](30-skill-pick.md#7-criteria-の文字列の値段)
- **「どこでも高い」を引く。** skill ごとに他 13 プロジェクトでの平均を引くと、461 件全部で AP 0.19 → **0.29**・P@12 0.19 → 0.23。
  前段の絞り込みとは独立に効く → [30 §6](30-skill-pick.md#6-どこでも高いものを引く)

**結果** 08 は wrong load **13.2% → 5.9%**(cookbook の 2.3x に対し 2.2x、ゲートを直して 4.4%)。30 の終点 `overlap@60 + terse + prior` は
**1 リクエスト・$0.0003/プロジェクト・P@12 0.30**(無作為に 60 件残す対照 0.08 の 3.75 倍)。出荷している router の cutoff 2.5 / cap 3 は格子の最良で precision **0.844**。

**うまくいかなかったこと** 08 の cookbook ゲート(noul 3 問の平均)はこのロスターでは純損失で、提案の wrong はゲート無し 1.5% に対しゲートありで 10.3% —— 平均が信号を持つ `needs_procedure` を薄め、3 問が「スキル = 手順書」という定義を埋め込んでいた。
29 では共通の閾値が無く(AUC 0.668)、単体で当てはめた閾値(youden の 1.39)は cap 3 と組み合わせると recall 0.252 のまま precision を 0.844 → 0.750 に下げた。
30 で前段の k を増やして recall を 63% → 100% にすると、curate されていない実在 skill が正しく高く付いて P@12 は 0.25 → 0.19 に下がった。

**教訓** 候補を並べて選ぶ用途は「全候補に同じ問いを 1 リクエストで」が素直に効き、判断に任せるのは description から読める適合だけ。
「常に入れる」「頼まれたら」のような方針と cutoff・上限はコードに置き、閾値は後ろの cap ごと当てはめる。

→ 詳細: [08](08-skill-suggestion.md) ・ [29](29-skill-select.md) ・ [30](30-skill-pick.md) ・ [36](36-routers.md)(同じ回の model router は、この corpus では元が取れなかった) ・ [tuning §3.1](tuning.md#31-判断の対象は-state-ではなく質問に置く) ・ [tuning §4.4.1](tuning.md#441-どこでも高いを引く--判断に対する-idf)

### <a id="bilingual"></a>7. 英語と日本語の一致チェック —— 数値と識別子は diff、文の意味は判断

**何をしたか** このリポジトリの実物の対訳(`eslint-plugin-jev` の `README.md` / `README.ja.md`、1,244 行)を見出しの順で 24 セクションに整列させ、
400 文字以上の 20 対で「同じことを言っているか」を判定させた。実物の 20 対を `equivalent`(faithful という仮定)、日本語側への決定的な
文字列編集 8 種を `diverged` とし、うち言い換えと箇条書きの段落化の 2 種は翻訳者がやって良いこととして `equivalent` にした。

**Jev の使い方**
- セクション対 1 つにつき 8 問(`score` 1 + `choice` 1 + `noul` 6)を 1 リクエスト。どれだけ違うかは順序があるので `score`、
  違いの種類は `choice`、`omits`・`adds`・`numbers_agree` のような原子述語は `noul` で、1 リクエストで「どこがどう違うか」まで返る。
- state はセクション対だけ。先に規則(測定値・識別子・長さ比の diff)を書き、判定は規則と判断の和で出す。

**効いたチューニング**
- **層を分ける。** 規則の diff だけで 26/30・誤検出 0 で、落ちるのは否定の反転・claim の追加・hedge の強化という「文の意味」だけ。
  判断はそのうち否定(2.69)と追加(1.96)を埋め、合わせて 8 クラス中 6 → [28 §2](28-bilingual.md#2-判断は何を足すか)
- **数値の diff は「測定値」に限る。** 生の桁 diff は "one request" 対「1 リクエスト」の類で faithful な 20 対のうち **14 対**を誤検出し、
  綴られた数の正規化でも残る。単位・小数・%・3 桁以上に限って誤検出 0 → [28 §1](28-bilingual.md#1-先に-diff-を書く)
- **文書全体を state に入れない。** 足すと omission が 1.84 → **0.57**、terminology が 2.12 → **1.20**、トークンは 12 倍。
  消えた文も入れ替えた識別子も文書のどこかに実在してしまう → [28 §4](28-bilingual.md#4-文書全体を渡すと悪くなるそして機構が見える)

**結果** セクション対だけの arm で **84/90・誤検出 0**、実物の翻訳 20 対には **0/60** 発火(平均 0.11)。1 対 2,101 トークン・181 ms・**$0.00009**。

**うまくいかなかったこと** hedge の強化(「ことがあります」→「ことが必ず起きます」)は **0.43** で見逃し、本当の盲点として残った。
変異のラベルも 1 つ間違えていて、`claim_strength` の 1 稿目(「ほとんど関係ありません」→「すべて関係ありません」)は見逃しに数えたが、日本語ではどちらも「関係ない」でモデルが正しかった([28 §3](28-bilingual.md#3-変異はラベルで1-つ間違えた))。
対訳は片方から片方を訳したもので変異も日本語側だけなので、実務の drift(原文が更新されて翻訳が取り残される)は測っていない。

**教訓** 言語をまたぐ比較で規則が扱えるのは表記が一致するもの(数値・識別子)だけで、判断には否定や追加のような文の意味を聞く。
「この範囲に無い」を判定するときに範囲を広げると、質問が変わる。

→ 詳細: [28](28-bilingual.md) ・ [tuning「state に何を入れるか」](tuning.md#state-に何を入れるか)

## 行動させる・遊ばせる

### <a id="browser"></a>8. ブラウザを操作させる —— 効いたのは質問文ではなく、state に渡す事実と action space の形だった

**何をしたか** 付属のチェックアウト SPA(注文完了まで 8 手連続の正解が要り、各画面に 14〜17 個のコントロールと進捗を巻き戻す罠 2 つ)を、Jev に 1 手 1 リクエストで操作させた。
chaosbringer の重み付きランダムな次操作選択の置き換えから始め、透明な overlay・URL に出ない分岐・6 択のドロップダウン・空にしないと通らない割引欄を足しながら、何を渡すと着くかを測った。同じハーネスで 1 文からのテスト生成と、性能改善の指名もやった。

**Jev の使い方**
- 次の手は `choice`。criteria はその画面で操作できる候補そのもの(列挙できて順序が無い)。05 は同じリクエストに `noul` 2 問(行き止まりか・進捗を巻き戻す手か)を足した。
- 61 からは `operation` の `choice`(いまは `CLICK` / `TYPE_TEXT` / `CLEAR` / `SELECT` / `DONE`)と操作別の target head(`CLICK` はクリックできる要素、`SELECT` は `index:option` の対)を 1 リクエストで聞き、選ばれた操作の head だけ読む。
- state には goal・URL・候補に加え、画面の表示テキスト・フォームの現在値・Playwright のエラー本文・`last_action_error` と無効果の連続数を入れた。
- 周辺の判断: テスト生成は前後差分からコードが出した候補ごとに、それが操作の結果かを `noul` で、性能改善はどのステップを先に直すかを `choice` で聞いた。

**効いたチューニング**
- **state に判断材料を入れ、関連ありと印付けする**: 質問は一字も変えず state だけを 4 回作り直し、画面の表示テキストとフォームの現在値を入れた 4 版目で初めて深度 **5**・注文完了 **3/3**(1 版目は `Continue to payment` を 7 回連打して深度 3)。未実行の関数名は state の配列に素で置くと **1/12**、ゴール文に置くか指示を書くと **9/12** → [05 §2](05-browser-chaos.md#2-効いたのは質問ではなく-state-だった) [58 §4.5](58-coverage-guidance.md#45-追記-残りの-2-マスを埋めたら5-の説明は間違っていた)
- **action space の表現力を上げる**: target を要素ではなく実行単位(`index:option`)にして操作別に聞くと、6 択で要素だけの `flat` **0/2**・記憶付き `flat-memo` 15.0 手に対し `fanout` **2/2**・10.0 手。判断は 2 往復の `sequential` と全実行で同一で、リクエストは半分・モデル壁時計 **−53%**。「空にする」を `CLEAR` として持たないと **0/2**、持つと **2/2** → [61 §3](61-speculative-fanout.md#3-six-options-the-flat-shape-stops-arriving) [61 §4](61-speculative-fanout.md#4-the-speculation-is-free) [62 §6.7](62-browser-accuracy.md#67-clear--4-つの転用候補で唯一そのまま採用できたもの)
- **決定的に測れることはコードで測って候補に付ける**: `elementFromPoint` 1 回で、無駄手 13 件中 **12 件**(透明な overlay に飲まれたクリック)を当てた。消しても伝えても精度は同値で、消す側の差はトークン 4% → [57 §5](57-confidence-fallback.md#5-効いたのはモデルに聞かないほうだった) [62 §4](62-browser-accuracy.md#4-docs57-の解釈を-1-つ訂正する)
- **注記の散文を 1 行直す**: 「転送中はメインスレッドが空いている」を「ユーザーは壁時計を待ち切る」に替えると、指名どおり直して測り直した節約が **188ms → 1,664ms** → [60](60-perf-automation.md#結論先に)

**結果** 重み付きランダムが **0/3** だった 8 手深い注文完了に、Jev は **3/3** で着いた(到達状態数はランダムの 8.3/14 が Jev の 7.0/14 より多く、置き換えではなく併用が正しい)。
手法を重ねたフルスタックから型付き action space かジオメトリの片方を抜いても 2/2 で着き、両方抜いた `none` だけ **0/2** —— 足し算ではなく崖。
生成テストは事後条件を足すと捕まえるバグが **1 → 2** で、5 回独立に生成して 5/5 同じ差。

**うまくいかなかったこと** confidence の閾値フォールバックは無駄手 13 件中 **1 件**しか拾わず(12 件は 0.99 以上)、失敗を state に戻して初めて 0.91 → 0.45 と減衰した。
候補や質問を削って安くする 3 機構 —— ゴール語彙での候補検索(recall@20 が **1/10**、何もせず先頭 20 件なら 10/10)・action キャッシュ(注文を記録しないアプリでも 10/10 再生して `ordered: no`)・視野絞り + `SCROLL`(効いていた盤面で 2/2 → 0/2)—— はどれも精度を買わず却下した。
05・57 の「伝えるより消すほうが効く」と 58 の「望ましさはゴールに置かないと勝てない」は、置いていなかったアームを足すと否定された。

**教訓** 行動させるときは、質問文や閾値より先に action space(値を乗せた target・足りない操作)と state(判断材料・失敗の履歴)を設計する。精度を買うのは表現力を上げる機構で、候補や質問を削る機構が買えるのはトークンだけ。

### <a id="games"></a>9. ゲームを遊ばせる(チェス・NetHack・三目並べ) —— 合法手から選ばせれば反則は消えるが、前に進むかは渡した事実しだい

**何をしたか** Jev と Claude Sonnet 5 に同じ局面・同じ合法手リストを渡してチェスを 2 局対戦させ、本物の NetHack(`nethack-console` を tmux で駆動)を 1 手 1 リクエストで遊ばせ、完全に解ける小さなゲーム 5 種(nim・三目並べ・目標だけ反転した三目並べ・4×4 のコネクト 3・どの手も結果を変えない `drift`)を自己対戦させた。
強さに加えて、画面を読めるか(記録した 244 画面について盤から正解を計算できる 12 問)と、confidence が局面の難しさを測っているか(solver が聞かずに計算した criticality との照合)を測った。

**Jev の使い方**
- 手は `choice` で、criteria はその場の合法手そのもの。チェスは chess.js の合法手(最大 218 手なので 255 択に収まる)、NetHack は 80×24 の画面からコードで読み出した 11〜12 個の行動。列挙できるので、集合の外は表現できない。
- 局面の優劣は順序のある評価なので `score`(`standing`、5 段階)で、手と同じリクエストに入れた。NetHack の知覚は真偽 11 問を `noul`、敵の数を `score` にして 1 画面 1 リクエスト。
- 行動の criteria の説明文に、コードが安く計算できる事実を添えた。チェスは「何を取るか」「チェックか」「直後に何を失うか」、NetHack は「その先のマスが何で描かれているか」。

**効いたチューニング**
- **合法手を criteria にする**: チェスは 37 手で反則 **0**(Sonnet は合法手リストを渡されても 2 回リストの外を答えた)。NetHack でも、ルールエンジンではなく絵から作る毎手変わる集合で、1,200 リクエスト中 **0 件** → [03 §2](03-chess.md#2-一番の発見-反則手が表現できないことの価値) [34 §2.1](34-roguelike.md#21-反則は-1200-リクエストで-0-件)
- **隣のマスを言葉で書き添える**: 地図は同じだけ渡して方向名だけにした `jevbare` は却下率 **31%**(600 手中 151 手が `>` に張り付く)、その先のマスが何かを添えた `jev` は **3%** → [34 §2.3](34-roguelike.md#23-注釈を外すと却下率が-10-倍になりconfidence-が逆を向く)
- **記憶を渡す、ただし矛盾させない**: 「そのマスに何回立ったか」を添えると、壁には必ず「まだ立ったことがない」と付くので記憶が壁を推薦し、1 マスに 200 回却下され続けた。壁に回数を出さないガードを入れると、訪問回数だけで地図化 **+12**(却下 20% → 6%)、「歩いていないマスの方を選べ」の 1 文と合わせて **+86**(`jev` 比、6 ゲームずつ) → [40 §k](40-homework.md#k-jevcount-にもガードを入れる--記憶は単独で効く矛盾が無ければ)

**結果** チェスは両サイドで Jev の勝ち(白番 1-0・駒得 +22、黒番は 34 手で詰み)で、1 手 **0.3 s**(Sonnet は 2 局で 13.7 s と 24.1 s)、1 局 $0.001。
NetHack の画面はステータス行が 100% 読めるのに、地図は「`<` は `@` より下の行か」**96%** 対「右の列か」**74%**、「隣に敵が居るか」は真のとき 49%。
5 種のゲームで `doubt`(1 − confidence の平均)は solver の criticality と同じ順に並んだ(Spearman **0.900**、結果の変わらない `drift` が最下位)。

**うまくいかなかったこと** `jev` は却下率が探索ボットより低い(3% 対 4%)のに地図化はランダム並み(48 対 40、探索ボットは 193)で、これは大部分が、探索ボットにだけ訪問済み集合と目標を渡していた私の交絡だった。
confidence は手の正しさと別のものを見る —— 目標反転の三目並べで着手は 81% 正しいのに `doubt` は普通の三目並べの criticality を **+0.813** で追い、画面を読めない `jevbare` では「ゲームがその行動を受け付けたか」への AUC が **0.282** と逆を向き、どの手も結果を変えない `drift` でも `doubt` は 0.418 で「どうでもいい」とは言わない。
チェスは計 2 局で、Sonnet は思考もツールも無い 1 回の問い合わせ(測ったのは強さではなくインターフェースの形)。35 の `swing` の順位は、隣接 4 組のうち両方の尺度で分離したのが 0 組で、確立されていない。

**教訓** 手が列挙できるゲームは `choice` の形にそのまま合い、反則は表現できなくなる。前に進ませるのは渡した事実(隣のマス・矛盾しない記憶)で、confidence は難しさの順位付けには使えても、「どうでもいい手」や「正しい手」の検出には使えない。

### <a id="spatial"></a>10. 空間を読ませる(盤面・矩形の符号化) —— 読める軸は渡した形で決まり、残る難しさは比べる 2 つがどれだけ近いか

**何をしたか** 34 の NetHack で同じ盤の同じ `<` について「`@` より下の行か」は 96%、「右の列か」は 74% だった非対称を、同じ 244 画面・同じ質問文のまま幾何の符号化だけ 7 通りに変えて測り直し、真偽を構成で厳密に半々にした描いた部屋 144 でも確かめた(64)。
続いて `@` の居ない矩形 2 つの重なり(240 組)と、スライスに積んだ 3 次元(128 ブロック)で、関係の種類・答えの細かさ・入れ子の深さを分けた(65)。

**Jev の使い方**
- 空間の真偽は 1 問 1 `noul`(「`<` は `@` より右の列か」「2 つは 1 マスでも共有しているか」)、量(敵の数・距離・共有マス数)は `score`。64 は質問文を 34 からそのまま import し、64・65 とも質問は全腕で同一で、変えたのは state の幾何の形だけ。
- 形は 7 通り: 絵(34 の state そのもの)・絵 + 列ルーラー・`{x, y, glyph}` の JSON 表・床を抜いた表・1 文字 1 文のコード(`screen.put(x, y, "-")`)・連続 1 つ 1 文(`screen.span`)・`@` 相対。65 では矩形を `{x, y, width, height}` と端の列・行でも渡した(`@` 相対とこの 2 つは答えを含むので、天井として読む)。
- 対照帯として、符号化で 1 バイトも変わらないステータス行を state に残した。

**効いたチューニング**
- **読みたい軸を state の構造にする**: 本物の画面で列は絵の **74%** から座標表で **100%**(床を抜いた表は 63 件の不一致中 **63 勝**、p<1e-4)。列番号のルーラーを見せるだけでは 2 コーパスで −4.2pp と +4.2pp で、符号すら一致しない → [64 §2.2](64-spatial.md#same-structure) [64 §1.3](64-spatial.md#the-ruler)
- **座標は JSON ではなくコードで、連続はまとめる**: 描いた部屋で JSON とコードの payload はほぼ同寸(+0.8%)なのに、入力トークンは 9,211 対 **4,840**。連続 1 つ 1 文なら ASCII の 1.3 倍で列 **96%**、数え上げも要るなら 1 マス 1 文のコード(列 94%・AUC 0.964、絵は 0.934) → [64 §2.4](64-spatial.md#code-not-json)
- **`@` 中心の関係は窓を切ってから聞く**: 21×80 を `@` の周り 3×3 に切るだけで「隣に敵が居るか」が 61% → **79%**、`@` からのオフセットも渡すと **95%**。本物の画面では、絶対座標にしても直らない → [64 §3](64-spatial.md#the-crop)
- **物が図形なら図形で、境界のケースは端を渡す**: 絵は接しているだけの 2 つを「重なっている」と言い過ぎ(`touch` 40%)、`{x, y, width, height}` は接触を直す代わりに 1 列だけの重なりを落とす(95% → 48%)。端の列と行で渡すと余白 4 種すべて **100%** で、値段は絵と同じ(975 対 961 トークン) → [65 §1.3](65-shapes.md#13-図形を渡すと間違いの向きが反転します) [65 §1.6](65-shapes.md#16-図形は一番安くて一番正確でした)

**結果** 描いた部屋では行が 7 符号化すべてで 100%、本物の画面の列は絵の 74% → 座標表 100% —— 非対称は判断の限界ではなく state の設計だった(高さ 11 行のまま幅だけ広げると、ASCII の列軸だけが 90% → 73% に落ち、行は 100% のまま)。
3 次元の絵では外側の添字 **98%**・内側の添字 **88%**・文字位置 **54%**(偶然)と入れ子の深さに沿って並び、層と行の数を入れ替えても 1 ポイントも動かない。座標にすると ×1.1〜1.2 の値段で x が 97〜98%。
列差を制御すると列差 1 で **56〜69%**・列差 8 で **97〜100%** で、観測者(p = 0.17)も大きさ(p = 0.21)も区別できなかった。

**うまくいかなかったこと** 64 の最初の版の「列軸を直すと数え上げが壊れる。タダ飯はない」は撤回した —— 床を抜いて件数を 3 分の 1 にしても AUC 0.736 で落ち、同じ座標をコードで書くと 0.964 で、壊していたのは量でも座標でもなく JSON という直列化の形だった(JSON の何が悪いかは未分離)。
65 §1.4 の「`@` を外したら易しくなった」「矩形は大きいから易しい」という読み(95% 対 74〜83%)も根拠の半分が外れた —— 64 の部屋に 1 列隣の標的が 3.6 倍多かったことの反映で、残ったのは向き(精度の問題)だけ。
「AUC が高いのに 0.5 で外すのは校正のずれ」という読みは、あとで当てはめた閾値を当てはめていない fold で採点して確かめた —— 距離の帯は 29% → **65%**、切り出した `in_room` は −7.0pp → **+12.3pp** で当たり、重なり判定の `sparse` は 60% → 79% で**半分**(1 マスの境界は残る)([64 §4](64-spatial.md#held-out))。全腕 100% に張り付いた対照帯が漏れを検出できるかは、まだ確かめていない([TODO §1.19](../TODO.md#119-対照帯が天井に張り付いている))。

**教訓** 2 次元・3 次元のものは、聞きたい関係が乗る軸を state の構造(座標・図形の端)にして渡し、自己中心の関係は窓を切るか関係そのものを渡す。「読めない」と書く前に、符号化を 1 つ変えて測るのが安い。

→ 詳細: [64](64-spatial.md) ・ [65](65-shapes.md) ・ [65 §3](65-shapes.md#observer-size-gap) ・ [34 §1](34-roguelike.md#1-画面は読めるのか) ・ [TODO §5.2](../TODO.md#52-64-の符号化にタダ飯はないは撤回した) ・ [TODO §5.3](../TODO.md#53-65-14-の根拠の半分が外れた) ・ [tuning §3.3](tuning.md#33-2-次元のものを渡すときはstate-の形が読める軸を決めている)

### <a id="moba"></a>11. MOBA —— チームの判断は 1 リクエストで下せる。ただし勝つことと正しいことは別の測定だった

**何をしたか** ヘッドレスの MOBA(3v3、のちに 5v5)で、チーム全員の次の手を Jev に決めさせた。
3v3 は勝敗しか測れなかったので、5v5 では**ルールが決定的なことを使い、答えをシミュレータ自身に出させる**
採点ベンチマーク(52 シナリオ・170 問)を作った。コードとレポートは
[jev-playground-moba](https://github.com/mizchi/jev-playground-moba) に移してある。

**Jev の使い方**
- **チームの視界 = 1 state、判断が要る champion の数 = 質問の数。** 全員の行動を 1 リクエストで決める(fan-out)。
- 行動は `choice` で、**選択肢はその tick の合法手だけ**。「何 hop 先か」「タワーがあるか」「見えているか」は
  コードが criteria の説明文に書き添える。
- 採点では、同じ state について `noul`(この集団戦は勝てるか)と `choice`(いま殴るか)を**同じリクエストで**聞き、
  正解率と一緒に**2 問の整合性**も読む。

**効いたチューニング**
- **criteria を合法手にする** —— 不正な手は 3v3 の **489 判断**、5v5 の **1751 判断**とも **0 件**
  → [02 §5](https://github.com/mizchi/jev-playground-moba/blob/main/docs/02-moba.md#5-この実験で確定したパターン)
  [56 §3](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#3-スループット-3v3-より良くなった)
- **全員を 1 リクエストに入れる** —— 5v5 で 1 リクエスト **4.86 体分**、キャラ 1 体あたり **53 ms**(3v3 の 76 ms より速い)
  → [56 §3](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#3-スループット-3v3-より良くなった)
- **視界の霧はプロセスの境界で強制する** —— referee と player を別プロセスにすると、相手の観測がワイヤーに乗らない。
  scripted 同士の **3/3 引き分け**が、Jev 同士では **6/6 決着**
  → [10](https://github.com/mizchi/jev-playground-moba/blob/main/docs/10-jev-vs-jev.md#1-構成--視界の霧を配線で強制する)

**結果** 試合は両サイドから両方の bot に **12-0**。同じモデル・同じ observation を採点すると **0.55**、
手書きの床は **0.57** で、ほぼ同じだった。16 クラスのうち「一番良い定型答え(ゴム印)より明確に上」は **5 つ**
→ [56 §4](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#4-採点できるベンチマーク)
[56 §6](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#6-それでも試合には勝つ)。

**うまくいかなかったこと**
- 「16 局面のうち 13 で『勝てない』と答えた直後に『殴れ』と答える」は、数えると `false` 14/16 と `fight_now` 15/16 から
  **14 + 15 − 16 = 13** が強制されていた —— **2 つのゴム印の言い換え**で、対の証拠ではなかった。
- 2 択を 3 択に割ると、「勝てない」と言って殴った 41 局面のうち **30(73%)**が中央の「勝てないが殴る価値がある」を選んだ。
  ところが同じ 3 択を説明文 4 通りで聞き直すと、その割合は **56% から 100%** まで動いた —— **割合は私の文言の関数**だった。
- 12-0 の中身は `farm` が **1652 手(94%)**・`structure` が **0 手**で、巧さではなくミニオンの規則の結果だった。
  3v3 の「弱い編成 + Jev が強い編成 + scripted に 5-1」も、基準を強い bot にすると **0-6** に反転した
  → [12 §8](https://github.com/mizchi/jev-playground-moba/blob/main/docs/12-comeback.md#8-追記--強い-bot-を基準にすると取り返し幅は縮む)。
- 霧の読みは **A 側 0.25 対 B 側 0.008** で、confidence は両側 **0.28** —— 外していることに気づいていない
  → [56 §5](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#5-戦場の霧-初めて採点した-自信を持って外す)。
  そして環境の側にバグが **9 つ**在り、全部テストか対称性の検査で見つかった(観察では見えない)
  → [56 §8](https://github.com/mizchi/jev-playground-moba/blob/main/docs/56-moba5.md#8-環境を測ったら環境にバグが-9-つ在った)。

**教訓**
- **勝率は判断の質の測定ではない。** 決定的なルールが在るなら答えはシミュレータに出させ、
  正解率は床やランダムではなく**一番良い定型答え**に対して読む。
- **fan-out は矛盾の検出器にもなる**が、共起を読む前に**周辺度数が何を強制しているか**を確かめる。
  説明を書く前に**環境のバグを疑う** —— mirror 戦を毎 tick 検査するテストが、プレイからしか到達できないバグを掘り出した。

## エージェントに組み込む

### <a id="agent-parts"></a>12. エージェントの部品にする(オーケストレーション判断・修復ループ・コンテキスト圧縮・router) —— 判断を 1 か所に閉じれば部品になる。他モデルと比べて一貫したのは速さだけ

**何をしたか** orchestration gate(31)、model router と skill router(36)、削除だけする compaction(37・39)に guard を足した 5 つを
1 本の pi 拡張に束ね(37)、台本のモデルで実物の pi に挿し(38)、別に植えたバグを直す修復ループ(32)も組んだ。
Jev に決めさせたのは「通すか」「分けるか・どの形か」「どの段・どの skill か」「どのエントリを消してよいか」「どの候補編集が直すか」だけで、
文字列を返さないのでパッチも要約も書かせていない。最後に 5 つを haiku / sonnet と同じコーパスで比べた(41・42)。

**Jev の使い方**
- 段は順序なので `score`([36 §2.1](36-routers.md#21-梯子は-score-で聞くchoice-ではない) は `choice` 14/24 対 `score` **23/24** に従った)、トポロジー 8 択と修復候補は
  相互排他なので `choice` 1 問(`probabilities` がそのまま全候補の順序)、compaction は各エントリのダイジェスト(頭と尾)に「使い切ったか」の `score`。
- 「2 人以上でやるべきか」は 4 条件に分解して組み立てても 30/38 対 30/38 で同点なので `noul` 1 問で聞き、逃げ道(topology を選ばず「1 人でやる」、
  「要求が曖昧か」、「まだ何も消せない」、「直る候補がそもそも入っているか」)も選択肢に混ぜず別の `noul` にした —— `choice` の確率は和が 1 なので
  全滅でも誰かが高くなり、confidence は強制された選択を AUC **0.601** でしか見分けない。
- 同じ turn の request を読む model router・skill router・orchestrator は 1 リクエスト(約 **1,300** input tokens)に束ね、tool call ごとに
  2,500 ms 予算で動く guard は束ねない。tool_call と結果の対応は品質ではなく妥当性の問題なので、判断に渡さずコードに置いた。

**効いたチューニング**
- **framing と閾値を組にする** —— 第 2 ワーカーのコストを先に述べると **22/38**(誤り 16 件が全部「分けない」側)、消すと **30/38**。この 21 ポイントの
  大部分は閾値で、framing ごとに引くと素の一致の差は **20 → 8 ポイント**。出荷は **0.5 / 0.73** → [31 §8](31-orchestration.md#8-追記--閾値を-framing-ごとに当てはめる追加リクエスト-0)
- **相互排他な候補は `choice` 1 問で並べる** —— テスト実行が生成順 3.00・無作為 7.69 回に対し **1.00** 回(**16/16** 一発)、1 タスク **1,554** トークンで
  候補ごとの `score`(3,254)の半分以下 → [32 §5](32-repair.md#5-1-つの-choice-で全部の順序が出る)
- **逃げ道の閾値を答えの塊の外へ** —— `underspecified` は 8 turn 中 6 つが **0.606〜0.729** に固まり、ハードコードの 0.70 がその真ん中で、束ね方で
  変わった decision 3 件のうち 2 件がこれの跨ぎ。`escalateAt` を設定にし hermes は **0.85** → [37 §7](37-hermes.md#7-副産物--逃げ道の閾値が答えの塊の真ん中にあった)
- **同じ答えを「残す割合」ではなく「順位」として使う** —— リクエストもコストも同じで削除 **100/100/100/96%** 対 抽出的要約 **100/78/78/67%**。要約は予算を
  全エントリに配るので、判断が使い切ったと言ったものにも配ってしまう → [39 §7.1](39-compact-ranking.md#71-削除が勝つただし-docs-の言った理由ではない)

**結果** 修復ループは `choice` 1 問で **16/16** を 1 回のテスト実行で緑にし(`--verify` で本物のプロセスに当て直しても同じ)、5 部品は実物の pi
(モデルは台本)で **5/5** が配線で確認できた。haiku / sonnet と比べて一貫しているのは速度だけで、5 部品すべてで **26〜103 倍** ——
品質で jev が明確に勝っている列は無い(guard で sonnet と同点、他は分離しないかコーパスが測れない)→ [42 §4'](42-versus-rest.md#4-まとめ-5-コンポーネントを本物のモデルと並べた結果)

**うまくいかなかったこと** model router はこのコーパスでは元が取れない —— 53 題材中 52 が haiku で足り、penalty 100 の当てはめ値 **1.81** は
ホールドアウトで **3.54** と「常に haiku」の 2.89 より悪い([36 §5.4](36-routers.md#54-コストの梯子--当てはめは何もしないに負ける))。束ねるのは無料ではなく 7 問すべてが再試行のばらつきより
聞き方の違いで大きく動き(比 1.71〜7.32、[37 §6](37-hermes.md#6-1-リクエストturn--これだけ測る価値があった))、pi の中ではバグ 4 件がどれも拡張のログの側では正しく見えていた([38 付録](38-agent.md#付録-何が実際に動くの証拠になるか))。
compaction の「判断 96〜100% 対 11〜78%」は大半が自分の弱いベースラインで、無料の `overlap`(ゴールとの語の重なり)が 67〜100% を取り、
残る差は予算が厳しいときだけ([39 §5](39-compact-ranking.md#5-判断は何を分けていたのか--そして無料ベースラインを書き直した))。

**教訓** Jev は文字列を返さない([fit §0](fit.md#0-そもそも向いている問題か))ので、生成はコードに任せて判断を「並べる・選ぶ・述語に答える」の 1 か所に閉じると部品になる。
売れるのは「判断が賢い」ではなく「判断が間に合う」で、効くのは答えの形と閾値の置き場所 —— 閾値は framing ごと・答えの塊の外に置き、
「常に安い方」と比べてホールドアウトで採点する([tuning §4.4](tuning.md#44-当てはめるなら境界ではなく-gap-の真ん中に置くそしてホールドアウトで採点する))。

### <a id="real-agents"></a>13. 本物のエージェントの中で端から端まで測る —— レイテンシ予算には収まったが、完遂では差が出なかった。学んだのは主に計器のことだった

**何をしたか** `claude -p` を本物のツールを持つ本物のエージェントとして走らせ、jev を Claude Code の seam(`PreToolUse` とその `Task` matcher、
起動時の `--model` と `.claude/skills/`、要約指示を渡す `PreCompact`)に挿して、判定は `node --test` の終了コードで採った(43・44)。
Jev に決めさせたのは tool call ごとの許可、モデルの段、読み込む skill、subagent に分けるか、要約器の前にどのコマンドの出力を逐語で残すか(45〜48)。
コーパスは自分が書いた修理・境界タスクから、公開パッケージの合成 `scripts`(53)、実リポジトリで著者自身が書いた `- [ ]` 項目(55・63)へ広げた。

**Jev の使い方**
- guard は出荷 hook のまま —— 許可の段階は順序なので `permission` を `score`、`outside_project`・`obfuscated` などの原子述語は
  `noul`、9 問を 1 リクエストで聞いて保守側を取る。
- model router は段の `score` と confidence の床(`minConfidence: 0.5`)。修理タスクは 53 件が 1 本のプロンプトを共有するので、state がリクエストだけだと
  58/58 が sonnet の 1 段になることをアームの前に probe(1 タスク 3 判断)で確かめた。orchestration gate は「分けるか」の `noul` と 8 択 topology の
  `choice`、skill router は実在 300 件から上限 3 —— どれも出荷の設定のまま。
- 要約器の前段は、transcript が出力を既にコマンドでグループ化しているので約 10 個のラベル付きコマンド群への `choice` 1 問にし、
  state にはラベルだけを入れて出力は入れない。

**効いたチューニング**
- **`--unattended-ask block`** —— 無人のホストは `ask` を自分の文面(「A hook requires confirmation to run the Bash command」)で拒否するだけなので、
  理由と「人間が居ない」を付けた `deny` で返す。境界 run 135 件を束ねて **22 介入・17 run・16/17 完遂**、唯一の失敗は既定の `ask` の下(小さい分母の null)→ [44 §4.4](44-components.md#44---unattended-ask-block--todo-12-のアーム)
- **天井では尺度を替える** —— Bash が在るとエージェントは緑まで回すので(同じ hard コーパスが Bash 無しで 31/32、有りで 32/32)完遂は 3 アームとも **32/32** で
  不一致 0 組。対になった tool call なら高い段が中央値 **−2.0**・32 件中 28〜29 件で少なく **p < 0.001** → [44 §1.1](44-components.md#11-高い段は仕事を多く終えたか--いいえただし少ないターンで終えた) ・ [54 §1](54-ceiling.md#1-同じコーパスがテストランナー有りと無しで記録に入っています)
- **問いの形を替える** —— 「どのエントリが答えを持つか」を 56 件のエントリの順位として読むと jev 14/40 対 無料 15/40(p = 1.000)、約 10 個の
  コマンド群への `choice` にすると **7/8 対 3/8** —— この掃討で初めて jev が無料に明確に勝った列 → [47 §3](47-stages.md#3-段-2-を測る--順位付けより良い形の問いだから)
- **段を足さずに外す** —— 群の数値行(119〜1,630 文字)を全部逐語で渡してどれが答えかは決めないと、答えの在る群なら oracle と同点(**5/5**)、
  jev が選んだ群で端から端まで **1/4 → 3/4** → [48 §2](48-keep.md#2-結果--oracle-と同点どれが答えかを教えられずに)

**結果** guard に与えた 2,500 ms 予算に対し、出荷配線(コマンドごとの node 起動込み)で 391 コマンド中央値 **371 ms**・超過 **0**、掃き直し・実リポジトリ・
広げた roster でも超過 0([43 §2](43-finish.md#2-18-1-の-2500-ms-予算に40-本ぶん遅れて数字が付いた))。修理コーパスでは完遂を 1 件も奪わない(**63/63 対 63/63**)が、そこでは一度も発言しない。
「全部に回せる」は本物のエージェントの中では品質の主張にならなかった —— 他モデル比較で一貫したのは速度(5 部品すべてで **26〜103 倍**、[42 §4'](42-versus-rest.md#4-まとめ-5-コンポーネントを本物のモデルと並べた結果))だけで、端から端までは 3 部品とも完遂が天井で分離しない。

**うまくいかなかったこと** 「gate が初めて仕事を奪った」1 件(境界 **14/15**)は掃き直しで **15/15** になって再現せず、率ではなく存在証明にとどまった
([44 §4.2](44-components.md#42-そして掃き直しは-43-の追試になりました))。初めて本物に当たった `deny`(`curl … | bash`、permission **1.65**)は 3 回目の試行で 1 回目は自分の fence が止めており、
広げた roster では同じ意図を 2 コマンドに割ると **0.94** で出荷の `deny` 閾値 1.5 の下をくぐった([63 §3.2](63-widen.md#32-同じ意図が-2-コマンドに割れると165--094-に落ちます))。orchestration gate は
`Task` 呼び出し 0 件で一度も相談されず、著者が並列で出荷した 52 件では topology が **52/52** で `sequential`(自分の 38 シナリオでは 22/22、[53 §2](53-fanout.md#2-そして-topology-がcutoff-に依存しない鋭い所見です))。

**教訓** 本物のホストでの売りは「安くて速いから、迷ったら聞いておける」で、「賢い」ではない。端から端までの測定が一番多く教えたのは jev ではなく
自分の計器で、100% が出たら計器を見る(`passed` はテストを書き換えたエージェントも通す定義だった)、判断を聞き直すハーネスが世界を正しく渡しているか確かめる、
正しさのラベルが無ければ閾値は値段で語る、率は母集団と一緒に書く(同じ gate の発言率が 1.2%・6.3%・11.8%・24.1%)→ [計器の規律](summary.md#計器の規律)

## 事例を横に並べて見えること

1. **一番効いたのは答えの形と候補の集合で、質問文の言い回しではなかった。**
   シェルのゲートは `choice` → `score` の一手で 19/24 → **23/24**。
   合法手を選択肢にすると、MOBA の 489 判断と 1751 判断、チェスの 37 手、NetHack の 1,200 リクエストのどれでも反則は **0**。
   一覧から選ぶ課題では、名前に 1 行の説明を足すだけで **90.0% → 100%**
   → [tuning §1](tuning.md#1-答えの形を決めるここが一番効く) [§2](tuning.md#2-質問を書く)
2. **規則で解ける部分をコードに出した事例ほど、Jev に聞くことがはっきりした。**
   - タスクの filter は前提と順序を依存グラフの閉包に任せた。
   - 監視のトリアージは severity を 1 行の規則にした(**16/16・誤ページ 0**)。
   - 英日の一致チェックは数値と識別子を diff に任せた(**26/30・誤検出 0**)。

   Jev に残したのは、規則で書けない判断だけだった
   → [tuning §4.6](tuning.md#46-答えが測れる量の関数なら聞かずに計算する)
3. **state の中身と形が、質問文より効いた。**
   - ブラウザ操作は質問を一字も変えず、state を 4 回作り直して注文完了 **3/3**。
   - 空間は同じ質問のまま符号化だけ変えて、列の判定が **74% → 100%**。
   - NetHack は隣のマスを書き添えるだけで、却下率が **31% → 3%**。

   ただし足せば良くなるとは限らない。英日の比較に文書全体を足すと omission が 1.84 → **0.57** に下がり、
   監視に生ログを足すと cause が 24/30 → **18/30** に下がった
   → [tuning §3](tuning.md#3-1-リクエストに詰めるほぼ考えなくてよい) [「state に何を入れるか」](tuning.md#state-に何を入れるか)
4. **閾値と confidence は、事例ごとに引き直しになった。**
   - 閾値は質問ごとに引く(**13/36 → 24/36**)。framing ごとにも引く(差が **20 → 8 ポイント**)。
   - 答えが 0.606〜0.729 に固まっていたところへ閾値 0.70 を置いていて、答えの塊の真ん中だった。閾値は塊の外に置く。
   - confidence をゲートにすると損をする(**62.5% 対 73.7%**)。「どうでもいい手」の検出にも使えない(結果の変わらない局面でも `1 - confidence` が **0.418**)

   → [tuning §4](tuning.md#4-閾値を決めるここが一番手間)
5. **本物の場所に載せると、精度とは別のものが効いた。**
   - hook では、失敗をどこに落とすかと 2,500 ms の予算が先に決まった。
   - lint では、拡張点が同期であることが設計を決めた。
   - 無人のエージェントには、`ask` が `deny` と同じ意味だった。

   そして品質で他のモデルに明確には勝たず、選ぶ理由は速さ(**26〜103 倍**)と値段だった
   → [tuning §6](tuning.md#6-運用に載せる) [when-to-use.md](when-to-use.md#速さと値段が変えること)
6. **一番多く学んだのは、Jev ではなく自分の計器についてだった。**
   - MOBA の「13/16 が矛盾」は、周辺度数の言い換えだった。
   - 3 択で中央を選んだ 73% は、私の書いた説明文の関数だった。
   - 12-0 の勝ちは、ミニオンの規則の結果だった。
   - compaction の大差は、大半が自分で書いた弱いベースラインのせいだった。
   - 「gate が初めて仕事を奪った」1 件は、掃き直すと再現しなかった。

   → [tuning §7](tuning.md#7-測り続ける) [summary の計器の規律](summary.md#計器の規律)
