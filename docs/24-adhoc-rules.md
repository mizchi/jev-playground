# 24. まだ存在しないルールを自然言語で書く — セレクタだけコードで

**[21](21-eslint-plugin-jev.md) と [22](22-code-criteria.md) は「何を聞くか」を
こちらが決めていた。** 21 は曖昧な 1 問、22 は 8 つの名前付き指標。どちらも
プラグインに埋め込まれた固定の質問セットで、使う側が足せるものではない。

ここで測るのは逆の形。**使う側が ESLint の設定に 1 文書けば、それがルールになる。
コードで書くのはノードセレクタだけ。**

```js
"jev/rule": ["warn", { rules: [{
  id: "fetch-timeout",
  selector: "CallExpression[callee.name='fetch']",
  rule: "fetch は必ずタイムアウト (AbortSignal.timeout など) を渡すこと",
  note: "リトライラッパの内側で既に設定されている場合は違反ではない",
}] }],
```

```
 12:3  warning  fetch-timeout: fetch は必ずタイムアウトを渡すこと
                (violation, 2.74/3 confidence 0.74; reports at 2.00)   jev/rule
```

チームの規約が lint ルールにならない理由はいつも同じで、
**セレクタは 10 秒で書けて述語は 1 週間かかる**から。
`CallExpression[callee.name='fetch']` は自明だが、「ただしリトライラッパの内側で
既にタイムアウトが設定されている場合を除く」を AST で書くのは別の仕事になる。

再現:

```bash
cd experiments/eslint-plugin-jev && npm install
npm test                                     # 105 件、API 不要
npm run rules                                # 記録した判定から下の表を再計算、API 不要
TYPESAFEAI_API_KEY=... npm run warm:rules    # 49 ノードを 12 リクエスト、$0.0011
TYPESAFEAI_API_KEY=... npm run lint          # eslint が両ルールの判定を読む
```

---

## 結論(先に)

**成立する。そして読むべき数字は閾値ではなく gap(違反と残りの点数差)だった。**

コーパス([22](22-code-criteria.md) の 15 ファイル / 641 行)に 5 ルールを書いて、
**49 ノードを 12 リクエスト・$0.0011** で判定:

| | |
| --- | --- |
| セレクタが当てたノード | 49 |
| 文で絞ったあとの指摘 | **7** |
| ラベル付きのバグ/smell の上 | 6 |
| **自信のある指摘の正解** | **5 / 5** |
| 自信のない指摘の正解 | 1 / 2 |

自信のある 5 件は全部ラベル付きのバグの上に落ちた —— lost update、埋め込みクエリ、
比較関数のない `.sort()`、文字列経由の丸め、握り潰した書き込み失敗。
外した 1 件は**意図的に catch している** `readJsonOrDefault` で、
**confidence 0.31** だったので「指摘」ではなく「質問」として出た。
これが `unsureBelow` の存在理由([07](07-escalation.md)・[21](21-eslint-plugin-jev.md) と同じ結論)。

## 1. 読むのは閾値ではなく gap

```
rule                        cutoff  matches  reported  widest gap  cutoff in gap
no-string-built-query         2.50       20         2        1.82  yes
atomic-read-modify-write      2.00        7         1        1.79  yes
explicit-sort-comparator      2.00        4         1        1.90  yes
no-stringly-arithmetic        2.00       14         1        2.16  yes
no-swallowed-catch            1.50        4         2        0.77  yes
```

`npm run rules` が出すこの表が作業ループの中心で、**gap を読む**。

- **gap が広ければ閾値はどこに置いても同じ答えになる。**
  4 ルールは gap 1.79〜2.16 で、既定の 2.0 はその真ん中に落ちている。
  この状態の「閾値チューニング」は**やることが無い**のが正しい。
- **gap が狭いのは閾値の問題ではなく文の問題。** 校正でどうにかなる範囲の外にある。
  [22](22-code-criteria.md) の「指標ごとに閾値を引く」は、
  **指標の文がまず discriminating である**ことを前提にしていた。ここはその前提の話。

これは [22](22-code-criteria.md#4-一番効いたのは指標ではなく指標ごとの閾値) の
「検出の問題ではなく校正の問題」と**対**になる。
22 は答えが分かれているのに共通閾値で潰していた(校正の問題)。
ここで狭い gap が出るのは答えが**そもそも分かれていない**(質問の問題)。
**同じ「閾値を動かす」という操作で、直る場合と直らない場合がある。**

## 2. 5 ルール中 2 つは最初の文が失敗した

| ルール | 1 稿目の gap | 何が悪かったか | 2 稿目の gap |
| --- | --- | --- | --- |
| `no-magic-rounding` → `no-stringly-arithmetic` | **0.16** | `*100 / 100` で丸める話を聞いたが、コーパスにそんなコードは無い | **2.16** |
| `no-swallowed-catch` | **0.28** | 「呼び出し元が失敗を知る必要があるか」= 判断の一番難しい部分を聞いた | **0.77** |

**`no-magic-rounding` の 0.53 は、間違った質問への正しい答えだった。**
コーパスの該当バグは `amount.toFixed(2)` の結果を `fixed * 1` で数値に戻す型強制で、
`*100 / 100` はしていない。セレクタ(`BinaryExpression[*|/]`)は当てていたのに、
文が別のものを聞いていた。**モデルは正しく「違反ではない」と答えていた。**
実際にあるものを聞く文に書き直したら 0.16 → **2.16** になり、
その 1 関数だけを指摘するようになった。

**`no-swallowed-catch` は逃げ道を文の中に書いてしまった。**
1 稿目の note は「呼び出し元が失敗を知る必要がない場合は違反ではない」で、
これは catch 節を見ても決められない。結果 4 件全部が 1.03〜1.58 の真ん中に来た。
**catch 節自体が何をしているか**だけを聞く形に書き直して 0.28 → 0.77。
[practice](practice.md#21-逃げ道は選択肢ではなく別の問いにする) の
「逃げ道は別の問いにする」が、ここでは
**「判断できない条件を文に混ぜない」**として現れた。

そして書き直したあと、レポートが `no-swallowed-catch` について
**「閾値が gap の外にある」**と言った。2.0 は 2.31 と 1.94(0.37 差)を割っていて、
答えの構造的な切れ目は 1.94 と 1.17 の間(0.77)にあった。
上位 2 件はどちらも本物の握り潰しだったので**レポートが正しい**。
`at: 1.5` に下げて 2 件拾うようになった。

## 3. 書き直しは安い —— 文がキーに入っているから

ルール文(と note)は**キャッシュキーの一部**なので、1 文直すと
そのルールの判定だけが無効になる。

```
49 unique, 31 already cached, 18 to ask     # 2 ルール書き直し後
5 request(s), 9838 input tokens, $0.00041
```

**閾値はキーに入っていない。** `at` を変えても再質問は 0 件で、
`reportAt` も `unsureBelow` も同じ。
[19](19-jevlang.md#4-record--replay--確率的な言語に必須の道具) の record / replay が
そのまま効いている —— **判定を記録して、決定は毎回計算し直す。**

| 操作 | 再質問 | コスト |
| --- | --- | --- |
| 文を書き直す | そのルールだけ | 18 件 / $0.0004 |
| 閾値を動かす | **0 件** | $0 |
| ノードのコードを直す | そのノードだけ | 1 件 |

## 4. セレクタはわざと広く書くのが正しい

49 → 7。**セレクタは判断がゼロの側なので、判断をさせない。**

score のスケールにレベル 0 =「このルールはこのコードには当てはまらない」を
置いたのはそのため。セレクタが余計なものを拾ったことを**モデルが言える**ようにしてある。

| 0 | 1 | 2 | 3 |
| --- | --- | --- | --- |
| ルールが当てはまらない | 満たしている | 破っている疑い | 明確に違反 |

`reportAt` の既定 2.0 は**当てはめた数字ではなくレベル境界**。
レベル 1 は「コードがルールを満たしている」なので、
ここを報告するのは調整で消せる誤検出ではなく**ルールの逆走**。

`noul` ではなく `score` を選んだ理由は 2 つで、どちらも [00](00-api-notes.md) と
[07](07-escalation.md) の結果:

- **noul には confidence が付かない。** 自信のない判定を捨てるか出すかの
  選択肢が無くなる(21 で confidence をゲートにすると 7〜11 ポイント損すると分かっている)。
- **ルールは二値ではない。** 「疑い」と「明確に違反」を別のメッセージにできる。

## 5. セレクタは静かに失敗する(これは直せない)

**2 つの失敗モードがあって、性質が全く違う。**

| | いつ分かるか | 閾値で直るか |
| --- | --- | --- |
| 文が間違っている | レポートの gap に出る | 直らない(文を書き直す) |
| **セレクタが当たっていない** | **出ない** | **直らない** |

コーパスのバグ `compareTokens`(空トークン 2 つが一致して認証が通る)は
落とした。これは握り潰しの一種だが **catch が無い**ので `CatchClause` に
当たらず、**どの閾値でも質問されない。レポートにも現れない。**

これが「セレクタだけコードで書く」の代金。
[22](22-code-criteria.md) の「列挙の穴」は
**指標を増やせば埋まる可能性がある**穴だったが、
こちらの穴は**セレクタを読むしかない**。
広く書くのが正解なのは、これが理由でもある。

## 6. 256 は自分で決めた上限で、効いているのはファイル単位

1 リクエストに最大 256 件詰めるようにしたが、実コードでは**先にファイル単位の
まとまりが効く**。49 ノードが 12 リクエストになったのはファイルが 12 個だったからで、
256 には届いていない。

実際の上限は [00](00-api-notes.md#token-ceilings) のトークン 2 枠
(リクエスト 64Ki / state 32Ki)で、そちらは下で守っている。
score 質問は 4 段の説明を毎回繰り返すので、**256 件だけで約 50K トークン**になる。
256 は「1 リクエストが失敗したときに巻き戻る量の上限」として意味がある。

## 7. テストで塞いだ fail-safe の穴

**ESLint がパースできないセレクタは、トラバース中に throw して lint 全体を落としていた。**
`create()` が返ったあとにセレクタが解釈されるので、ルールの中からは捕まえられない。

[18](18-permission-hook.md) と [21](21-eslint-plugin-jev.md) で決めた
「判定層は必ず沈黙に倒す」の唯一の例外になっていたので、
**セレクタを事前に検証**(捨てる `Linter` に同じ visitor を組ませる / メモ化)して、
不正なものは落として `ruleConfig` として報告する形にした。周りのルールは動き続ける。

**ただし設定不備は沈黙させない。** 設定が落とされて発火しないルールは、
**何も見つからなかったルールと見分けが付かない**。
これは「失敗したら沈黙」の例外で、沈黙すると嘘になる側。

## 何が言えるか

- **述語を自然言語にすると、書かれなかったルールが書ける。**
  セレクタは既存の ESLint 資産そのままで、判断だけ外に出す。
- **読む数字は gap。** 広ければ閾値は考えなくてよく、
  狭ければ閾値ではなく文を直す。**同じ操作が直す場合と直さない場合がある**のが要点。
- **書き直しループが安い**(文だけがキー、閾値はキーでない)ので、
  「1 発で正しい文を書く」必要が無い。5 つ書いて 2 つ直した。
- **セレクタは静かに失敗する。** ここだけは測れないので、広く書いて文で絞る。

**限界** 5 ルール・49 ノード・ラベル付き 641 行での結果で、
**5/5 は 5 件であって率ではない**。~~実リポジトリでは走らせていない。~~

> **追記: 走らせた → [26](26-repo-rules.md)。** このリポジトリ自身の JS **9,315 行**に
> 8 文(うち 3 文はここの文を逐語で)当てて **579 判定・2.9 秒・$0.0135**。
> 結論が 2 つ反転しました:
>
> - **自信のある指摘が外れる。** ここでは自信のある 5 件が 5/5 正解でしたが、
>   実コードでは **0/5** で、当たった 2 件はどちらも conf 0.29 / 0.19 の「質問」でした。
>   理由は **confidence が「文が literal に当てはまるか」の確信**で、
>   形が自明な違反は**意図的であることが多い**から。
> - **狭い gap は「文を書き直せ」ではないこともある。** 実コードでは
>   「違反が 1 件も無い」が普通の状態で、gap は狭くなります。
>   区別するには**答えがどのレベルに居るか**(band)が要るので、
>   `rules-report` に 4 列足しました([26 §4](26-repo-rules.md#4-gap-の隣に-band-を置いた))。
>
> そして §5 の「セレクタは広く書くのが正しい」は実コードで裏付き
> (`TemplateLiteral` 422 件のうち **398 件が level 0**・誤検出 0)、
> **§2 の「判断できない条件を文に書かない」は note の例外にも当てはまる**
> ことが分かりました(「これはテストのプローブである」は catch 節から見えない)。
