## 3. 一番学んだのは自分の計器について

### 3.1 「カウントだけ直すと悪化する」と書いた項目で、カウントだけ直した

[§4.1](../TODO.md) の本文にこう書いてありました:

> **カウントだけ 44 に直すと中身と食い違って悪化します。**

そして最初の編集で見出しを「**44 本**」にしました。
**44 は最大番号で、本数ではありません**(13〜15 が欠番なので当時 42 本)。

さらに訂正を書きかけて**間違った訂正を出す手前で止まりました** ——
「前の版の 36 本も最大番号だった」と書こうとして `git ls-tree` で数えたら、
**当時ちょうど 36 ファイル**でした。**壊したのはこちらの更新だけ**です。

→ **数えられるものを数えずに、近くにある数字で代用した。**
本文には「この見出しの数字は毎回 `ls [0-9][0-9]-*.md | wc -l` で取ること」と書き足しました。

### 3.2 綺麗な 8/8 を基準率に当てた

[45 §1.3](45-floor.md): `minConfidence` が効いた **8 件全部**で安い段の方が高くついた ——
「床が狙って効いている」と読めます。

**確認したら、安い段はコーパスの 88% で高くつきます。**
だから**任意の 8 件でも 8/8 は約 34% 起きます**。→ **選別の証拠になりません。**

[44 §1.2c](44-components.md) は同じ罠に 2 回はまっていて
(先に「床が高すぎて無駄払い」、次に「床がターンを買っている」)、
**効いた防御は毎回「説明」ではなく「帰無の計算」**でした。

### 3.3 部品を書く前に、設計の天井を測れる

[45 §2](45-floor.md) の `oracle` アームは**正解の文字列そのものを渡します**。
[§1.5](../TODO.md) 自身が「ほぼ同語反復」と書いていたのが要点で、
**分類器は正解を渡されるのには勝てない**ので、これは上限です:

| 起きたこと | 意味 |
| --- | --- |
| 上限が下限を超えない | **設計が否定される。部品を書かずに** |
| 上限が天井に届く | **設計は成立。残る未測定は精度だけ** |

**届きました**(9/9・捏造 0)。そして[§1.6](../TODO.md) で精度を測ろうとしたら ——

### 3.4 問いそのものが否定できることが在る。ラベルを作る前に

[46 §1](46-relevance.md): コーパスを見たら、9 事実のうち

- **3 件は数字を 1 文字も含まない**(`registerFlag("jev-advise"` は測定値ではなく**問いの答え**)
- **4 件はコマンドが計算した量ではなくコマンドが表示したソース**

だから「数字を含むか」の完璧な分類器の上限は **6/9** で、
**何も指示を送らないアームが既に 6/9**。

→ **完璧に答えても何もしないのに勝てない問い**だった、と**リクエスト 0 件**で分かりました。
[24 §2](24-adhoc-rules.md) の「高い掃きの前に安いプローブ」がこの掃討で 3 回効きましたが、
**アームではなく問いを否定したのは初めて**です。

そして**上限アームが効いた理由を、上限アームの説明で済ませてはいけませんでした** ——
`oracle` が勝っていたのは測定値を見抜いたからではなく、
**ゴールが訊いている値**を渡したからです。**別の述語**でした。

### 3.5 2 つの列が同じなら、片方が入力を失っている

[46 §2.0](46-relevance.md): 無料の baseline 2 本(`overlap` と `largest`)の行が**バイト単位で同一**に。
候補集合に制限**してから**ランク付けしたので、
その集合が **pin されたゴールのターンを除外している**ぶん
`overlap` はゴールを見つけられず、**自分の契約どおり `largest` にフォールバック**していました。

**ただし「同じになった」が全部バグでもありません** ——
入れた検査が次に `stale == oldest` で止まり、**そちらは本物の性質**でした
(どのコマンドも直前に宣言され二度と参照されないコーパスなので)。
**[39](39-compact-ranking.md) 自身の表が 4 予算のうち 2 つでバイト単位で同一の行を出していて、そう書いていません。**
検査は「**全 transcript で同一**」のときだけ止めるようにしました。

### 3.6 失敗し得ないテストは、通り得ないテストと同じくらい悪い

[44 §5.1](44-components.md) は「**通り得ない wire check は、失敗し得ない wire check より悪い**」でした。
この掃討で裏も出ました:

  フォールバックが発火せず、**バグを戻してもテストが通った**

→ 追加したテストは**全部、壊して落ちることを確認してあります**
(再生を出荷値以外の床にする / 単調性を反転する / 符号検定の期待値を 0.125 にする /

### 3.7 null は、問いの形の診断かもしれない

[46](46-relevance.md) は「どのエントリが答えを持つか」を
**56 件の不透明なエントリの順位付け**で聞いて、**無料の語数と p = 1.000** ——
**分離なし**でした。

ところが transcript は**自分の出力をコマンドで既にグループ化している**ので、
同じことを **10 個ほどのラベル付き候補に対する `choice`** で聞くと **jev 7/8 対 無料 3/8**
([47 §3](47-stages.md))—— **この掃討で初めて jev が無料に明確に勝った列**です。

**[46](46-relevance.md) の null は、コンポーネントが弱いことの証拠ではなく問いの形の問題でした。**

設計の指針ではなく **null 結果の診断**として効いた形です。

### 3.8 段の点数は掛け算にならない

[47 §3.2](47-stages.md): 段 2 が 3/4、段 3 が 2/4 で、**合成すると 1/4**。
2 件が**段 2 を通って段 3 で同じ行に落ちる**ので、
掛け算(3/4 × 2/4 = 0.375)でも足し引きでも出ません ——
**同じ行で落ちる失敗は 1 件分しか引けません。**
**合成した数だけが呼び出し側の体験する数です。**

### 3.9 「見つける」で設計する前に、「落とさない」で足りるか問う

[48](48-keep.md): 比較型のゴールの前段を **3 段**(検出 / 絞り込み / 集約)で作って
**端から端まで 1/4**。集約を**足すのではなく外して**、
選んだ群の**数値行を全部**渡すようにしたら **上限アームと同点(5/5)** ——
**どれが答えかを教えられずに**。**端から端まで 3/4。**

**そして後継の問い(引数の範囲で切る)が消えました** ——
あれは**段 3 が 1 行を選ばなければならなかったから問題だった**のです。

**ただし一般則にしてはいけません。**
外せたのは**この問いが「落とさない」で足りた**からで、
要約に 1 行だけ書きたい問いでは集約が必要なままです。

### 3.10 点数が上がっても、失敗が沈黙になる設計は悪い性質を足している

`keepnums` は前段が数値行の無い群を選ぶと**走れません** ——

**「1/4 が 3/4 になった」より悪い性質**で、運用で見つけにくいからです。
**点数の隣に失敗の形を書くこと。**

### 3.11 自分が書いたコーパスは、部品を実際より静かに見せる —— 20 倍

**部品が静かに見えていたのは、部品の性質ではなくコーパスの性質でした。**

### 3.14 「どちらが大きいか」は、大きさより先に消える

この 1 行は **2 回間違えました**:

| 草稿 | 書いたこと | 実際 |
| --- | --- | --- |
| 1 | 2 世界は**同一の点数**になる | **違う** —— 19 ペア中 2 ペアが完全一致 |
| 2 | ドローを並べた上で「**世界の方が大きい**」 | **同じコードを 2 回走らせたら反転**(0.060 対 0.050 と 0.050 対 0.080) |

完全に同じに戻ったのに、順序だけが消えました。**

→ **レポート生成側に「報告しない」を実装する。**
今は差の大きさだけを出し、**どちらが大きいかは n が足りないと言います**。

### 3.15 レポート生成器に測定値をリテラルで書くな

`"1 of 19 pairs matched exactly"` と `"19 commands"` を**文字列に焼き込んでいました** ——

**2 回目のスイープで 2/19 になったので、生成器は嘘を印刷するところでした。**

→ **レポートの中の数はすべて記録から導く。例外は無い。**

### 3.16 キー無しで走るレシピが、記録を消してはいけない

`--worlds` は API キー不要なので `score` が全部 null で、
**その null を `damage.json` に上書きしていました** ——
つまり[このレポート自身が公開している再現手順](50-damage.md)を踏むと、
**レポートの元になった点数が消え、`npm test` も落ちる**ところでした。

**このプログラムの規律は「記録はキー無しで再生できる」**でした。
**その規律を、再生手順そのものが壊していました。**

→ **書き込み先は「キーが在るか」で分ける。** 今は記録の隣に書きます。

### 3.17 帰無結果の値は、間違っていても正しく見える

同じ比較の p 値を **2 か所で違う値**で印刷していました:

| 節 | 計算 | p |
| --- | --- | --- |
| [50 §3](50-damage.md) | `signTest(down, up)` = `signTest(7, 10)` | **0.629** |
| [50 §4](50-damage.md) | `signTest(n - up, up)` = `signTest(9, 10)` | **1.000** |

**同点 2 件が負けに畳まれ**、不一致ペアが 17 から 19 に増えていました。
**符号検定は不一致ペアの上で走るもので、同点は「負け」ではありません。**

**そして出力を見ても分かりません** —— **1.000 は帰無結果がちょうど取る値**だからです。
[46](46-relevance.md) が本物の p = 1.000 を報告しているので、**見慣れた数字**でもありました。
記録から両方を手で計算し直して見つけました。

→ **統計量は 1 か所で計算する。そして「予想どおりの値」こそ手で検算する。**
