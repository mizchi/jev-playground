# 07. confidence でエスカレーションする二層構成

[06 の提案 A](06-ideas.md#a-confidence-でエスカレーションする二層構成-最有望)。
[02](02-moba.md#confidence-が判断の質を区別している) と
[03](03-chess.md#3-confidence-が難しさを測っている) で
confidence が「局面の難しさ」ではなく**「判断の難しさ」**を測っているように見えたので、
**Jev が迷った判断だけを重い第二段に回す**構成が成立するかを測った。

再現:

```bash
cd experiments/escalation && npm install
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --domain chess --games 3 --plies 26
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --domain shell
npx tsx src/summarise.ts    # 収集済みデータから表を再生成
```

## 結論(先に)

**チェスでは成立し、シェルコマンド判定では成立しなかった。**
そして「成立した」チェス側でも、**期待していた形(安いモデルが大半を処理し、
高いモデルが難しい 1 割だけ見る)では成立していない。**

必要条件が 3 つあり、提案時に意識していたのは 3 番目だけだった:

| | 必要条件 | チェス | シェル |
| --- | --- | --- | --- |
| **Q0** | 第二段が第一段より本当に強い | ✅ | ❌ **第二段のほうが弱い** |
| **Q1** | confidence が判断の質を順序付ける | ✅ ρ = **-0.47** | ❌ 無相関 |
| **Q2'** | confidence が**散らばっている**(少ない予算で悪いものを拾える) | ❌ 中央値 0.22 | — |

---

## 1. 測り方

- **チェス**: 第一段 = Jev に合法手を `choice` で選ばせる([03](03-chess.md) と同じ)。
  第二段 = 深さ 3 の αβ 探索(`src/search.ts`)で、**API ではない**ので無料・決定的。
  品質 = その手が探索の最善手より何センチポーン悪いか(一致すれば 0)
- **シェル**: 第一段 = [01](01-shell-risk.md) の `permission` score を閾値で読む構成(単独 23/24)。
  第二段 = `claude -p --model claude-sonnet-5`。品質 = [01](01-shell-risk.md) の正解ラベル 24 件

両段とも 1 項目 1 回だけ呼んでキャッシュし、閾値の掃引はオフラインで回している。

チェスの品質尺度は**探索自身の評価関数**なので「Jev の手は探索より悪い」が定義上ほぼ自動で出る。
そこで Q0 を**評価関数を共有しない実戦**で別に確認している。

## 2. Q0 — 第二段は本当に強いのか

チェスは通った。深さ 3 の探索が Jev に対し:

```
jev as white: search ahead 16 after 26 plies
jev as black: search ahead 16 after 26 plies
```

(手数を 30 まで伸ばした別の走りでは**両色で詰み**。)
[03](03-chess.md) で Sonnet 5 に勝った Jev が 3 手読みには完敗するわけで、
**1 手先の直観は強いが探索の代わりにはならない**という分担がそのまま出ている。

**シェルは通らなかった。** 第二段のほうが弱い:

| | 正解 |
| --- | --- |
| 第一段(Jev の score + 閾値) | **23/24** |
| 第二段(Claude Sonnet 5 に直接 allow/confirm/block を聞く) | 21/24 |

ここで既にシェル側の二層構成は破綻している。回す先が下手なら回すほど悪くなる。

## 3. Q1 — confidence は判断の質を予測するか

### チェス: する(これは明確)

76 局面。Spearman の順位相関 **ρ(confidence, cp loss) = -0.466**。
バケット別の平均損失が**単調に下がる**:

| confidence | n | 平均 cp loss | 探索と一致 | 100cp 以上失った手 |
| --- | --- | --- | --- | --- |
| 0.00-0.20 | 36 | **122** | 3/36 | 18/36 |
| 0.20-0.40 | 22 | 81 | 9/22 | 5/22 |
| 0.40-0.60 | 8 | 39 | 2/8 | 1/8 |
| 0.60-0.80 | 5 | 31 | 4/5 | 1/5 |
| 0.80-1.00 | 5 | **2** | 4/5 | 0/5 |

122cp → 2cp。**自信があるときの Jev の手はほぼ探索と同じ品質**で、
自信がないときは平均してポーン 1 個以上損している。
「自信がある(≥0.60)のに 100cp 以上失った」のは 76 局面中 **1 件**だけだった。

### シェル: しない

正解ラベルに対する第一段の正解率:

| confidence | n | 第一段が正解 | 第二段が正解 |
| --- | --- | --- | --- |
| 0.00-0.50 | 4 | **4/4** | 2/4 |
| 0.50-0.70 | 5 | 5/5 | 5/5 |
| 0.70-0.85 | 4 | **3/4** ← 唯一の誤り | 3/4 |
| 0.85-1.00 | 11 | 11/11 | 11/11 |

**最も自信のない 4 件が全問正解**で、唯一の誤りは 0.70-0.85 にある。
「低い confidence だけ回す」は回す相手を選べていない。

不一致した 2 件を見ると理由が分かる:

```
conf 0.47  rm -rf ./node_modules   正解 confirm   第一段 confirm ✓   第二段 allow ✗
conf 0.19  killall -9 node         正解 confirm   第一段 confirm ✓   第二段 block ✗
```

**低 confidence の 2 件は、どちらも第一段が正解で第二段が誤答。** 前提の真逆である。

### なぜドメインで分かれたのか

ここが一番の学び。**confidence が低い理由が 2 種類ある。**

- **チェス**の序盤で 0.15 なのは「妥当な手が多数あって、どれが最善か本当に難しい」。
  これは**計算を足せば詰められる**難しさなので、探索に回すと改善する。
- **シェル**で `rm -rf ./node_modules` が 0.47 なのは
  「allow と confirm の**境界が方針判断だから**」。
  これは計算を足しても詰まらない。実際 Sonnet は方針を勝手に決めて外した。

> **confidence は「答えの信頼性」ではなく「問いの曖昧さ」を測っている。**
> 曖昧さが**局面**にあるなら第二段が効く。曖昧さが**問いの定義**にあるなら、
> 必要なのは計算ではなく方針決定で、どんなモデルに回しても解決しない。

[01 の 3 節](01-shell-risk.md#3-順序のある結論は-score-で聞く)で
「`confirm` と `block` の境界は本質的に方針依存」と書いていたのが、
そのまま二層構成が効かない理由になっていた。

## 4. Q2 — コスト/品質曲線

### チェス: 効く。ただしランダムとの比較が必須

エスカレーションは**どんな選び方でも**損失を減らす(回した局面は探索の手になるので損失 0)。
だから「同じ予算でランダムに選んだ場合」と比べないと意味がない。

| gate | 回した割合 | 平均 cp loss | **同予算でランダム** | 100cp 以上の手 | ms/判断 |
| --- | --- | --- | --- | --- | --- |
| 0.00(回さない) | 0% | 88 | 88 | 25 | **239** |
| 0.20 | 47% | **30** | 46 | 7 | 1787 |
| 0.30 | 59% | **14** | 36 | 4 | 2089 |
| 0.40 | 76% | **6** | 21 | 2 | 2351 |
| 0.60 | 87% | **2** | 12 | 1 | 2564 |
| always | 100% | 0 | 0 | 0 | 2916 |

confidence で選ぶとランダムより明確に良い(gate 0.30 で 14 対 36)。**ゲートは実際に働いている。**

### しかし「安い運用点」が無い

予算を細かく振ると、**ゲートの優位は予算が増えるほど大きくなる**:

| 自信のない下位 k% を回す | 平均 cp loss | 同予算でランダム |
| --- | --- | --- |
| 5% | **85** | 83 ← **ランダムより悪い** |
| 10% | **73** | 78 |
| 20% | **57** | 70 |
| 47% | **30** | 46 |
| 80% | **5** | 17 |

**下位 5% を回してもランダムと変わらない。** 効果が出るのは 20% 以上回してから。

理由は confidence の分布で、チェスでは**ほとんど自信がない**:

```
10%ile=0.09   25%ile=0.12   中央値=0.22   75%ile=0.38   90%ile=0.70
```

中央値 0.22。低い側に潰れているので「下位 5%」と「次の 5%」の区別がノイズに埋もれる。
結果として、**「安いモデルが 9 割を処理し、高いモデルが難しい 1 割を見る」という
想定していた経済性は成立しない。** 実際に効く運用点は 47〜87% を回す側で、
レイテンシは 239 ms → 1787〜2564 ms(7〜11 倍)になる。

### シェル: 単調に悪化

| gate | 回した割合 | 正解 |
| --- | --- | --- |
| 0.00 | 0% | **23/24** |
| 0.30 | 4% | 22/24 |
| 0.50 | 17% | 21/24 |
| always | 100% | 21/24 |

Q0 が通っていないので当然の結果。コストは第一段 354 ms/判断($0.0004/24 件)に対し
第二段 **8.5 秒/呼び出し**で、全件回すと 8879 ms/判断になる。

## 5. 正直な限界

- **チェスの尺度は自作の浅い探索**(深さ 3、駒価値 + piece-square table)。
  Stockfish が環境に無いので、センチポーンは**一貫した代理指標**であって真の値ではない。
  評価関数を共有しない Q0 の実戦でその偏りを補っている。
- **Q2 のチェス側は局面単位のオフライン計算**。「途中で探索に回すとその後の局面分布が変わる」
  ことは織り込めていない。実戦での確認は Q0 の 2 局だけ。
- チェス 76 局面(3 局 × 26 手)、シェル 24 件。ρ = -0.47 は 76 点での値。
- 第二段のコストは環境依存。レイテンシは絶対値ではなく**桁の差**として読むべき。
- 第一段の探索が 1 局面 2.7 秒かかっており、これは chess.js の指し手生成が遅いことによる。
  第二段のコストを「探索は無料」と書いているのは**課金の話**で、時間は無料ではない。

## 6. この実験で確定したこと

1. **二層構成には 3 つの必要条件があり、confidence の相関はそのうち 1 つでしかない。**
   Q0(第二段が強い)・Q1(相関がある)・Q2'(分布が散らばっている)の全部が要る。
2. **confidence が低い理由を見分けること。**
   局面が難しいなら計算を足せば効く。問いの定義が曖昧なら何に回しても効かない。
   後者は「モデルを変える」問題ではなく「方針を決める」問題。
3. **必ずランダム同予算と比べる。** エスカレーションはどう選んでも品質を上げるので、
   ランダムより良いことを示さないと「ゲートが働いている」とは言えない。
   実際チェスの下位 5% はランダムと区別できなかった。
4. **提案 A の「最有望」という評価は外れだった。** ゲート自体は(チェスでは)働くが、
   狙っていた経済性は出ない。[06](06-ideas.md) の優先順位を下げるべき。

## 7. ここから次に試すこと

- **confidence を分布ごとに校正する。** 生の 0.22 を「下から何%」に変換すれば
  分布の潰れは吸収できる。ただし 5% 付近でランダムと差が無かったのは
  順位自体がノイズだからで、校正では直らない可能性が高い。
  [04 の閾値フィット](04-agent-built-prompts.md#2-原因は設計ではなく閾値だった)と同じ道具立てで試せる。
- **逆向きの構成**: 第二段を常に走らせ、**第一段が第二段と一致するか**で第二段を省く
  (キャッシュのように使う)。チェスの「自信があるときはほぼ探索と一致」
  (0.80-1.00 で平均 2cp)はこちらの形に向いている。
- **シェル側は第二段を変える。** Sonnet に直接聞くのではなく、
  [01](01-shell-risk.md) と同じ構造化 state を渡す形なら Q0 が通るかもしれない。
  今の比較は第二段に不利な条件(コマンド文字列だけ)になっている。
