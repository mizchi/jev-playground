# 12. コードと「ルールの説明文」だけ渡して、ESLint の合否を当てさせる

Jev に渡すのは **(1) 入力コード** と **(2) ESLint ルールの評価基準** だけ。
**ルールの実装(`create()`)は一切見せない**。それで合格・不合格を当てられるかを測った。

正解ラベルは本物の ESLint 9.39.5 が出す。「このコードは違反のはず」というこちらの
意見は一切入らない。制御しているのは**ルールのどこまでを見せるか**だけ。

再現:

```bash
cd experiments/eslint-oracle && npm install
npx tsx src/truth.ts                                   # ESLint の正解ラベルだけ(API 不要)
TYPESAFEAI_API_KEY=... npx tsx src/run.ts --repeat 5    # 4 arm × 5 回 = 860 リクエスト、$0.058
```

---

## 結論(先に)

**当てられる。説明文だけで 190/215(88.4%)、AUC 0.95**(多数派ベースライン 55.8%)。
素直な違反と素直な合格はほぼ取りこぼさない(それぞれ 55/60・60/60)。

そして**どこまで見せるかは正解率をほとんど動かさなかった**。
ID だけ 86.5% / 説明文だけ 88.4% / 両方 87.4% / + 既定オプション 87.4% —
1 回あたり 43 問中 37〜38 問正解で全 arm が並ぶ。動くのは**正解率ではなく、
何を間違えるか**だった。

外すものには構造がある。5 回とも外したペアは全部
**「説明文は禁止と言っているが、実装だけが例外を認めている」**ケースだった。
そこで **ESLint が metadata として公開している既定オプションだけを追加で渡す arm**
を足したら、この解釈がそのまま確認できた:

- 逃げ道が**公開オプションで表現できる** `no-cond-assign`(`except-parens`)は
  **10/15 → 15/15** で完全に直る。
- 逃げ道が **`create()` にハードコードされている** `no-empty`(コメント許容・
  関数本体の除外)は **15/25 のまま動かない**。
- ただし副作用がある。逃げ道を教えると**逃げ道を探しに行く**ので、
  見逃しが 0 件 → 11 件に増え、`while (true)` の免除を `do/while (true)` にまで
  広げて p 0.16〜0.19 の**自信のある誤答**を出す。

> **説明文は仕様ではない。逃げ道が仕様で、それは実装にしかない。**
> そして逃げ道を渡せば直るのは、**逃げ道が言語化できる場合だけ**。

## 1. しくみ — 何を隠して何を渡すか

1 スニペット = 1 リクエスト。コードを state に 1 回だけ載せ、**12 ルールを 12 問の
noul として束ねる**([00](00-api-notes.md#speculative-fan-out) の fan-out。
質問を増やすコストは質問文のトークンだけ)。

渡すもの(`src/arms.ts`)を 4 通り用意して比べた:

| arm | ルールについて渡すもの |
| --- | --- |
| `name` | ルール ID だけ(`"eqeqeq"`)— **ESLint を暗記しているだけなのかの対照** |
| `desc` | 説明文だけ(`"Require the use of \`===\` and \`!==\`"`)— **本題** |
| `both` | ID + 説明文 — 実運用のゲートが送る形 |
| `spec` | ID + 説明文 + **公開されている既定オプション** — §5 の検証用 |

**説明文はこちらで書いていない。** ESLint 自身の `meta.docs.description` を
実行時に読み出している(`src/rules.ts`)。`spec` arm が足す既定オプションも
同じく `meta.defaultOptions` と JSON schema から機械的に取っている。
どちらもこちらのヒントが混ざらないし、「インストールされた ESLint がそう言っている」
という再現可能な根拠になる。

隠しているものが本当に漏れていないかは、**主張ではなくコードで**担保した:

- 送信ペイロードに、読み込んだ 12 個の `create()` 本体の **48 文字窓が 1 つでも
  出現したら例外**(`assertNoImplementationLeak`)。
- こちらが付けた「この near-miss はここが罠」という `note` / `kind` / スニペット ID も
  同じ検査で禁止。
- 質問のキーは全 arm で **`q00`..`q11` の不透明キー**。質問名を `eqeqeq` にすると、
  説明文だけの arm に ID が裏口から渡ってしまう。
- state も全 arm で同一。ファイル名は `sample.js` 固定
  (`eqeqeq_null_idiom.js` ではルール名も罠の種類も漏れる)。

### コーパス

43 スニペット × 12 ルール = 516 ペア。スニペットは 3 種類に分けて作った:

- `violation` (12) — 素直に違反する
- `clean` (12) — 素直に合格する
- `nearmiss` (19) — **デフォルトオプションか実装の例外規定が合否を決める**もの。
  説明文だけではどちらに転ぶか読めない。ここが本題。

near-miss はどちらに転ぶか**先に ESLint に聞いて確定させた**(`npx tsx src/truth.ts`)。
19 スニペットの想定はすべて実測と一致した。例:

```
pass  constcond_while_true      while (true) は checkLoops の carve-out で許される
FAIL  constcond_do_while_true   同じ無限ループを do/while で書くと報告される
pass  unused_arg_before_used    args:"after-used" なので未使用の第 1 引数は報告されない
FAIL  unused_caught_error       caughtErrors は ESLint 9 で "all" に変わったので報告される
pass  empty_function_body       空ブロックだが関数本体は no-empty-function の担当
FAIL  empty_catch               空 catch は allowEmptyCatch が false なので報告される
FAIL  eqeqeq_null_idiom         == null は "smart" なら許されるが、デフォルトは "always"
```

正解ラベルの偏り: **targeted ペア(スニペット × 自分のルール)は 19 違反 / 24 合格**で
ほぼ均衡。一方 **全マトリクス 516 ペアは 3.7% しか違反がない**ので、
「全部合格」と答えるだけで 96.3% 取れる。だから以下は targeted を主に読み、
全マトリクスは**精度ではなく過検出の数**で読む。

## 2. 結果

targeted ペア、閾値 0.5、5 回プール(215 判定):

| arm | 正解 | | balanced | AUC | 1 回ごとの内訳(43 問) |
| --- | --- | --- | --- | --- | --- |
| `name`(ID だけ) | 186/215 | 86.5% | 87.9% | 0.98 | 37 37 37 38 37 |
| **`desc`(説明文だけ)** | **190/215** | **88.4%** | 89.0% | 0.95 | 38 38 38 38 38 |
| `both` | 188/215 | 87.4% | 88.8% | 0.97 | 38 38 38 37 37 |
| `spec`(+ 既定オプション) | 188/215 | 87.4% | 87.5% | 0.94 | 37 37 38 38 38 |

多数派ベースラインは 55.8%。ケースの種類別に割ると、どこで効いてどこで落ちるかが出る:

| ケース | `name` | `desc` | `both` | `spec` |
| --- | --- | --- | --- | --- |
| `violation`(素直な違反 60 判定) | **60/60** | 55/60 | **60/60** | 54/60 |
| `clean`(素直な合格 60 判定) | 55/60 | **60/60** | 58/60 | **60/60** |
| `nearmiss`(実装が決める 95 判定) | 71/95 | 75/95 | 70/95 | 74/95 |

**素直なケースはほぼ解けている。取りこぼしは全部 near-miss に集まる。**
ファイル単位の合否(どれか 1 ルールでも閾値を超えたら不合格)も同水準:
`name` 80.0% / `desc` 87.9% / `both` 85.6% / `spec` 82.8%。

## 3. 「どこまで見せるか」は正解率を動かさない。動くのは過検出

arm 間の差は 1 回あたり ±1 問で、**正解率では区別がつかない**
(3 回走らせた別の run では `name` 114・`desc` 114・`both` 112 と順位すら入れ替わる)。
ここを「説明文のほうが優れている」と読んではいけない。

はっきり差が出るのは**全マトリクスの過検出**で、こちらは 3 回の run すべてで再現した:

| arm | 過検出 | 見逃し | precision | recall |
| --- | --- | --- | --- | --- |
| `name` | **101** | **0** | 48.5% | 100.0% |
| `desc` | 34 | 5 | 72.6% | 94.7% |
| `both` | 46 | **0** | 67.4% | 100.0% |
| `spec` | 41 | 11 | 67.2% | 88.4% |

**ID だけ渡すと過検出が 2〜3 倍に膨らむ**(101 対 34〜46)。
つまり Jev は「ESLint の `eqeqeq` の挙動」を暗記から引いているのではなく、
**渡した評価基準を読んで判断している**。ID だけだと問いが曖昧になり、
「何か問題があるはず」の方向に倒れる。

`prefer-const` が分かりやすい。ID だけの arm は **10/20**、説明文を渡すと **20/20**:

```
preferconst_reassigned   let value = start; value += 1; return value;
  name arm: p 0.62 0.63 0.66 0.61 0.62 → 5 回とも不合格と判定(ESLint は合格)
  desc arm: 5 回とも正解
```

ID だけだと「`prefer-const` というルールがあるなら `let` は怪しい」に流れる。
「宣言後に再代入されない変数に const を要求する」という**基準を渡すと、
再代入されていることを見て正しく合格にする**。

## 4. 外すのは全部「実装にしか書いていない逃げ道」

`both` arm で **5 回とも**外したのはこの 5 ペアで、性質が完全に揃っている:

| スニペット | ルール | Jev | ESLint | 実装にしかない例外 |
| --- | --- | --- | --- | --- |
| `empty_block_with_comment` | `no-empty` | 0.78〜0.80 | pass | ブロック内のコメントを意図とみなして黙る |
| `fallthrough_comment` | `no-fallthrough` | 0.67〜0.73 | pass | `// falls through` が報告を抑止(`commentPattern`) |
| `constcond_while_true` | `no-constant-condition` | 0.75〜0.80 | pass | `checkLoops: "allExceptWhileTrue"` がこの綴りだけ免除 |
| `condassign_parens` | `no-cond-assign` | 0.73〜0.75 | pass | 既定 `except-parens`。括弧が「意図的」の合図 |
| `empty_function_body` | `no-empty` | 0.54〜0.61 | pass | 空ブロックだが関数本体は `no-empty-function` の担当 |

全部が **「説明文は禁止と言い、実装だけが例外を認めている」** 形。
`no-cond-assign` は `name`・`desc`・`both` すべて **10/15** で、
ID を渡しても説明文を渡しても改善しない。

**これは Jev がルールを読み間違えたのではない。** `while (true)` は
「条件式に定数式」そのもので、説明文に忠実なら違反と答えるのが正しい。
`constcond_while_true` が合格で `constcond_do_while_true` が不合格なのは、
**同じ無限ループのうち片方の綴りだけを実装が免除しているから**で、
この区別は説明文に存在しない情報である。

## 5. 逃げ道を渡したら直るのか — `spec` arm

§4 は解釈でしかないので、検証用の arm を足した。
`meta.defaultOptions` と JSON schema の選択肢語彙 —— **ESLint が metadata として
公開しているもの**で、依然として実装ではない —— を追加で渡す。
こちらが書いた文章ではないので、失敗を知ってからヒントを書き足したことにはならない。

予測は分岐する。**逃げ道がオプションとして表現できるルールなら直り、
`create()` にハードコードされているルールなら直らない**はず:

| ルール | 逃げ道の正体 | `name` | `desc` | `both` | `spec` |
| --- | --- | --- | --- | --- | --- |
| `no-cond-assign` | `except-parens` — **公開された既定値** | 10/15 | 10/15 | 10/15 | **15/15** |
| `no-constant-condition` | `checkLoops` — 公開された既定値 | 15/20 | 20/20 | 15/20 | 15/20 ※ |
| `no-empty` | コメント許容・関数本体の除外 — **`create()` 内** | 20/25 | 15/25 | 15/25 | 15/25 |
| `no-fallthrough` | `commentPattern` の既定正規表現 — **`create()` 内** | 16/20 | 15/20 | 15/20 | 15/20 |

**そのとおりになった。**

- `no-cond-assign` は **10/15 → 15/15**。`condassign_parens` は `spec` arm の
  誤答リストから完全に消える。**逃げ道を言語化すれば直る。**
- `no-empty` は **15/25 のまま**。`empty_block_with_comment`(p 0.87〜0.90)と
  `empty_function_body`(p 0.65〜0.70)は 5 回とも外し続ける。
  これらの例外は `defaultOptions` に無い —— `create()` の中にしかないので、
  metadata をいくら渡しても届かない。
- `no-fallthrough` も **15/20 のまま**。schema には `commentPattern` という
  名前だけがあって、既定の正規表現は無いので届かない。

※ `no-constant-condition` は数字が動かないが、**外す先が入れ替わった**。
これが一番面白い失敗:

```
both arm: constcond_while_true     p 0.75〜0.80 → 不合格と判定(ESLint は合格)  ← 免除を知らない
spec arm: constcond_do_while_true  p 0.16〜0.19 → 合格と判定(ESLint は不合格)  ← 免除を広げすぎ
```

`checkLoops: "allExceptWhileTrue"` を渡すと `while (true)` は正しく合格にするが、
その免除を **`do/while (true)` にまで一般化**して、しかも p 0.16〜0.19 という
**自信のある誤答**を出す。[00](00-api-notes.md#closed-world) の
「範囲外入力が conf 0.96 で誤ルーティングされる」と同じ形が、
オプションの一般化でも起きている。

そして `spec` arm には全体的な代償がある:

```
見逃し(全マトリクス)   both 0 件 → spec 11 件     recall 100.0% → 88.4%
素直な違反              both 60/60 → spec 54/60
no-unused-vars          both 20/20 → spec 18/20   (実際に未使用の変数を見逃す)
違反ペアの平均 p        both 0.846 → spec 0.780
```

**逃げ道を教えると逃げ道を探しに行く。**
`unused_local`(本物の違反)を p 0.50〜0.59 で迷い、
`unused_arg_before_used` を p 0.31〜0.44 で「引数の例外だろう」と流す。
例外規定を渡すことは無料ではない。

## 6. 誤りの向きと、ゲートとしての性質

targeted 判定の誤りを向きで分けると:

| arm | 過検出(Jev 不合格・ESLint 合格) | 見逃し(Jev 合格・ESLint 不合格) |
| --- | --- | --- |
| `name` | 29 | **0** |
| `desc` | 20 | 5 |
| **`both`** | 27 | **0** |
| `spec` | 16 | 11 |

`name` と `both` は targeted 215 判定・全マトリクス 2580 判定を通して**見逃し 0**。
ゲートとしては都合のよい性質で、**実際の違反を通してしまうより、
合格を疑って人に回すほうに倒れる**。[09](09-guardrails.md) の
「境界帯は人間へ」という運用に素直に乗る。
`spec` はこの性質を失う。過検出を 27 → 16 に減らす代わりに**見逃しを 0 → 11 に増やす**
だけで、精度の合計はほぼ動かない(188/215)。**交換しているのは正解率ではなく誤りの向き**で、
ゲートとしては悪いほうに交換している。**ゲートに使うなら例外規定は渡さないほうがよい。**

## 7. 説明文が曖昧なときは逆に振れる

`no-self-compare` は逆で、**ID を渡したほうが強い**
(`name` 20/20・`both` 20/20 に対し、`desc` 15/20・`spec` 15/20):

```
selfcompare_nan   return x !== x;      ← 古典的な NaN チェック
  desc arm: p 0.33 0.38 0.36 0.25 0.29 → 5 回とも合格と判定(ESLint は不合格)
```

説明文は "Disallow comparisons where both sides are exactly the same" だけ。
これだけ渡すと `x !== x` は「意図的な NaN 判定であって、
*両辺が同じ比較* という間違いではない」と読まれる。ID を足すと直る。

つまり **ID と説明文は補い合っている**:

- 説明文が**厳密すぎる**とき(逃げ道が書かれていない)→ 過検出。ID では直らない(§4)。
- 説明文が**曖昧**なとき → 誤読。ID が効く(ここ)。

どの arm も 37〜38/43 で並ぶのはこのためで、**arm を選ぶことより、
ルールごとにどちらの失敗モードに当たるかのほうが支配的**。

## 8. 安定性とコスト

near-miss の判定は 0.50〜0.59 に落ちるものが多く、
[09](09-guardrails.md#3-cookbook-の-15-ケースの再現) で「閾値の境界に乗った決定を
そのまま採る」を落とし穴として挙げている。そこで各 arm を 5 回走らせた:

| arm | 5 回で判定が一致 | 反転 | p のばらつき(平均) |
| --- | --- | --- | --- |
| `name` | 42/43 | 1 | 0.034 |
| `desc` | **43/43** | **0** | 0.038 |
| `both` | 42/43 | 1 | 0.042 |
| `spec` | 41/43 | 2 | 0.039 |

**ばらつきはコイン投げではない。**§4・§5 の誤答は 5 回とも同じ側に外していて、
系統的な不一致である。一方 `name` arm の `fallthrough_comment`
(4/5 で誤り、p 0.51 0.54 0.53 0.45 0.58)のような境界ペアは実在するので、
**0.5 ちょうどで切った 1 回の結果を信じてはいけない**という教訓は残る。

コスト: **860 リクエスト / 1,372,290 入力トークン / $0.0576 / 1 リクエスト 0.33 秒**
(並列度 4、37 件はレート制限でリトライ。直列・非輻輳時は 0.18 秒)。
**1 ファイルを 12 ルールに対して判定して $0.00007。**
リポジトリ全体に回しても数十セントで収まる([06 の E](06-ideas.md) と同じ経済性)。

## 9. 正直な限界

- **ESLint を予測しても実用価値はない。** ESLint はタダで正確なので、
  この実験は ESLint を**測定器として**使っているだけ(正解ラベルが自動で手に入る)。
  実用になるのは**実装が存在しないルール** —— 社内規約、`CLAUDE.md` の約束事、
  レビュー観点のような「散文しかないルール」で、そこは本実験では測っていない。
  §4・§5 はむしろ**「散文だけのルールには逃げ道が書かれていないので過検出する」**
  と予測している。
- **12 問を 1 リクエストに束ねているので、「この 12 ルールが世界のすべて」という
  事前情報が漏れている。** 実リポジトリではルールは数百あり、
  [00](00-api-notes.md#closed-world) の閉じた世界の問題がそのまま乗る。
- **コーパスは 43 件で、こちらが書いた。** しかも targeted ペアの 19/43 を
  意図的に near-miss で埋めているので、**88.4% は普通のコードに対しては悲観的**
  (素直なケースなら 60/60 + 60/60)で、**もっと敵対的なコーパスに対しては楽観的**。
  実コードの分布ではない。
- **1 ファイルにつき違反ルールが最大 1 つ**(全マトリクスの違反 19 件はすべて
  targeted ペア)。複数ルールが同時に当たるファイルでの干渉は測っていない。
- **`spec` arm の既定オプションは機械的に取ったが、選び方はこちらの裁量**
  (`meta.defaultOptions` + schema の語彙)。`meta.docs.url` の本文まで渡せば
  結果は変わるはずで、「metadata をどこまで渡すか」の連続的な軸は測っていない。
- **JavaScript の、しかも数行のスニペットだけ。** TypeScript の型情報が要るルール
  (`@typescript-eslint/no-floating-promises` など)は入っていない。
  長いファイルでの劣化も未測定。
- **閾値 0.5 は校正していない。** sweep では `name` arm が 0.55 で 92.1% まで伸びる。
  [04](04-agent-built-prompts.md#2-原因は設計ではなく閾値だった) の
  「閾値はデータで決める」がここでも効くはずだが、43 件で閾値を合わせるのは
  過学習なのでやっていない。

## 10. この実験で確定したこと

1. **実装を伏せて評価基準だけ渡しても合否は当たる。** 説明文だけで 88.4%・AUC 0.95。
   素直な違反と素直な合格は 55/60・60/60(§2)。
2. **どこまで見せるかは正解率をほとんど動かさない**(全 arm 37〜38/43)。
   動くのは**誤りの種類と過検出の量**で、ID だけ渡すと過検出が 2〜3 倍になる(§3)。
3. **効いているのはルール名の暗記ではなく、渡した基準の読解。**
   `prefer-const` は ID だけなら 10/20、説明文を渡せば 20/20(§3)。
4. **当てられないのは「実装にしか書いていない逃げ道」。**
   5 回とも外した 5 ペアは全部、説明文が禁止して実装が例外を認めている形(§4)。
5. **それは解釈ではなく実証できた。** 逃げ道が**公開オプション**なら渡せば直る
   (`no-cond-assign` 10/15 → 15/15)。**`create()` にハードコード**なら
   metadata では届かない(`no-empty` 15/25 のまま)(§5)。
6. **例外規定を渡すのは無料ではない。** 見逃しが 0 → 11 件に増え、
   `while (true)` の免除を `do/while (true)` に一般化して p 0.18 の自信ある誤答を出す。
   **ゲートに使うなら例外規定は渡さないほうがよい**(§5・§6)。
7. **誤りは片側に寄る。** `name`・`both` は 2580 判定で見逃し 0(§6)。
8. **判定は安定していて、外し方も系統的。** `desc` arm は 43/43 で 5 回一致(§8)。

## 11. 次に試すこと

- **実装が無いルールでやる。** `CLAUDE.md` や社内規約の 1 行を評価基準にして、
  人間がラベルを付けた diff に対して測る。§9 のとおり**本命はこちら**で、
  ESLint はその前段の校正にすぎない。§5 から予測が立つ:
  **散文ルールは例外規定が書かれていないので過検出し、
  例外を書き足すと今度は見逃す。**この山の頂点を探すのが次の測定。
- **`meta.docs.url` の本文まで渡す arm。** §5 で届かなかった
  `no-empty` のコメント許容・`no-fallthrough` の `// falls through` は、
  **公式ドキュメントの散文には書いてある**。metadata では届かず散文では届くなら、
  「実装の逃げ道は言語化さえすれば渡せる」が確定する(§9 の未測定軸)。
- **ルール数を増やして閉じた世界を壊す。** 12 → 100 ルールにして、
  1 リクエストに noul を並べる形が破綻する点を探す。
- **過検出を人間に回す二層構成。** §6 の向きが安定なら、
  Jev が不合格と言ったものだけ本物のリンタか人間に回す運用が成立する。
  [07](07-escalation.md) の必要条件 3 つに当てはめて測る価値がある。
