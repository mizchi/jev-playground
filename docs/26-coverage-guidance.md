# 26. カバレッジ誘導: 同じ事実を、どこに置くかで 3/12 と 11/12 に分かれる

[25](25-confidence-fallback.md) は「決定的に判定できることは、モデルに伝えるのでは
なく選択肢から消す」で終わった。ではカバレッジも候補に添えればいいのか——
**添えても効かなかった。ゴール文に入れたら効いた。**送った文字列は同一である。

> [!NOTE]
> 引用した原則のうち「**伝えるのではなく消す**」の部分は後に
> [30 §4](30-browser-accuracy.md#4-docs25-の解釈を-1-つ訂正する) で否定されている
> (伝えるだけで同値、消す側の差はトークンのみ)。
> 本稿が使っているのは残った半分 ——「決定的に判定できることはコードで測って候補に付ける」
> —— で、そこから「**ではカバレッジも**」と進む筋は変わらない。
> むしろ本稿の結論(置き場所で 3/12 と 11/12 に分かれる)は、
> **「候補に付ける」が万能ではない**ことを示す側である。

再現:

```bash
cd experiments/browser-chaos
npm install
npx tsx src/check-coverage.ts                      # 計測の健全性(API 不要)
npx tsx src/check-code-map.ts                      # 名前の突き合わせ(API 不要)
TYPESAFEAI_API_KEY=... npx tsx src/run-coverage.ts --steps 24 --seeds 3
```

## 結論先に

| 腕 | 未実行の関数名を | 分岐 /12 | 到達状態 /14 | 無駄手 | トークン |
| --- | --- | --- | --- | --- | --- |
| blind | 渡さない | 3 | 10.3 | 10.0 | — |
| listed | state の配列に入れる(全部) | 3 | 13.7 | 3.0 | +8.2% |
| **listed-camel** | **state の配列に入れる(in-goal と同一の名前)** | **3** | **14.0** | 2.3 | +6.6% |
| mapped | 該当する**候補に注釈**する | 6 | 11.0 | 7.0 | +2.7% |
| **in-goal** | **ゴール文に埋める** | **11** | 13.3 | 2.0 | +4.5% |

`listed-camel` と `in-goal` は**同じ名前の同じ集合を送っている**。
違うのは `code_not_yet_executed` というフィールドに置いたか、
ゴールの文の中に置いたかだけ。**3/12 と 11/12。**

2 つの効果は別物で、分離できる。

- **配列に入れるだけで「幅」が出る。** 到達状態 10.3 → 14.0(全状態、全 seed)、
  無駄手 10.0 → 2.3。未実行集合の大半はルート関数なので、実質「まだ行っていない
  画面のリスト」として読める。
- **「振る舞い」を動かすのはゴールに入れたときだけ。** 分岐 3/12 → 11/12、
  しかも幅(13.3)と無駄手(2.0)を落とさない。

理由は 25 との対比で言える。

> **「効かない」という事実は候補に置く。「やる価値がある」という事実はゴールに置く。**
> 25 のジオメトリは**選択肢を消した**——「これは動くのか」への答えだった。
> 26 のカバレッジは「まだ誰も通っていない」で、これは*現在のゴールに対して*
> それを選ぶ理由にならない。**推薦はゴールと competing するので、
> ゴールそのものを書き換えないと勝てない。**

## 1. 盤面: URL では見えない分岐を 4 つ

`?branches=1` でデコイ 4 つを本物にした。どれも**名前付き関数**で、内部状態と
status 行を変えるが**ハッシュは動かさない**。

```js
function applyPromoCode()        { extra.promo = true; render(); }
function compareSelected()       { extra.compared = true; render(); }
function subscribeToNewsletter() { extra.newsletter = !extra.newsletter; render(); }
function addGiftWrap()           { extra.wrapped = true; render(); }
```

つまり **URL で測る novelty には原理的に見えない**。chaosbringer の crawler も
05 の picker も novelty は URL で測っている。V8 のカバレッジには見える。
デフォルト off なので 05 の数値はそのまま再現する。

## 2. 計測側で 3 回転んだ(どれも「もっともらしい出力」を出す)

この実験のコストの大半は、モデルではなく**自分の計測**だった。3 つとも
「壊れていることが出力から分からない」種類のバグで、記録しておく価値がある。

### 2.1 未カバー集合は一瞬しか完全ではない

`Profiler.takePreciseCoverage` の 0 件側をそのまま読めばいい、と思っていた。
V8 は関数を遅延コンパイルし、**誰も呼ばない関数のメタデータを捨てる**ので、
0 件エントリは時間とともに消える。実測: ロード直後の 1 発目は inline script の
関数を 15 個すべて挙げ(うち 11 個が未カバー)、ハッシュ遷移 2 回と
Playwright のクリック 1 回のあとは、同じ script について**カバー済みだけを挙げ、
未カバーを 1 つも挙げない**。古くなるのではなく**言及されなくなる**ので、
「もう全部カバーした」と見分けがつかない。

対策: **インベントリはロード直後に 1 回取り、`uncovered = inventory − everCovered`
で出す。**

### 2.2 `takePreciseCoverage` はカウンタを毎回リセットする

`everCovered` を union で持つのは保険ではなく必須だった。`render` の呼び出し回数を
take ごとに数えると **1 → 2 → 1**。累積なら 1 → 3 → 4 になる。何も起きていない
状態で 2 回続けて take すると、**1 回目は script を報告し 2 回目は報告しない。**

`@mizchi/playwright-v8-coverage` の README は逆を書いている
(「Counters accumulate across `take()` calls — diff against a previous snapshot
to get per-action deltas」)。これに従って 1 発の take を全体像として読むと間違える。
**chaosbringer 自身は無事**で、各 take を run 全体の `globalCoverage` に union して
そこに対して novelty を採点しているので、区間読みでも同じ答えになる。

### 2.3 セレクタが 1 つも当たっていなかった(これが一番痛い)

最初の 3 腕は全部 0/4 で、「ヒントが効かない」と結論しかけた。実際には
**分岐ボタンが押せていなかった**。候補のセレクタを
`tag + ":nth-of-type(" + n + ")"`(n は文書全体の可視要素カウンタ)で作っていて、
`:nth-of-type` は**同じ親の同じ型の兄弟の中で数える**ので意味が合わない。
nav の `<a>` 10 個は偶然正しく当たり、`#view` の中の `<button>` は**何にも当たらない**。

そして**何にも当たらない locator は見えない**。`.first()` がタイムアウトし、
その手は「画面が変わらなかった」として記録され、
**本当に何もしないコントロールと区別がつかない。**
id を持たないデコイは全部これで、4 分岐のうち 3 つがデコイだった。

対策: プローブが毎ステップ `data-probe-idx` を**刻んで**、それで引く。
`check-overlay.ts` に「17 個の候補セレクタが全部ちょうど 1 要素に解決する」
「デコイのクリックがタイムアウトしない」を入れた。

> これは 05 §3 と同じ形の失敗だ。あそこは「効果判定の取りこぼしが正解を封じる」で、
> ここは「解決しないセレクタが、押せないボタンを『効かないボタン』に化かす」。
> **効果の信号が壊れているとき、実験は失敗ではなく"きれいな結果"を返してくる。**

## 3. 名前で code と control を結ぶ

`mapped` 腕は、未カバーの関数名を**その名前に見えるコントロール**に注釈する。

```
button "Apply promo code"   [never executed: applyPromoCode()]
```

突き合わせは `applyPromoCode → ["apply","promo","code"]` を分解して、
ラベルの語集合に**全部含まれるか**を見る。**2 語以上を要求する**のは調整ではない:
未カバー集合の大半はハンドラではなく、ルートはキー(`#/danger`)、ヘルパは
`save` / `go` / `update` なので、1 語では偶然当たる——`#/danger` が
`link "Account" -> #/danger` に、`save` が `button "Save cart for later"` に。
**識別子とラベルの 1 語一致は、一方が他方を呼ぶ証拠ではない。**
どこでも発火する注釈は何も運ばない。

この fixture でこれが成り立つのはハンドラがボタン名で命名されているからで、
一般には**実行時 attribution**(クリック → カバレッジ差分 → どのコントロールが
どの関数を通したか)になる。chaosbringer の `targetNovelty` がやっているのは
それだ。どちらでも要点は同じで、**join は計算するものであってモデルに推論させる
ものではない**——`listed` 腕はそれを任せた場合に何が起きるかである。

## 4. 結果

24 手 × 3 seed。分岐は 4 つ、3 seed で 12 回のチャンス。

| 腕 | 分岐 /12 | 踏んだ分岐 | 到達状態 /14 | 無駄手 | 注釈発火 | トークン |
| --- | --- | --- | --- | --- | --- | --- |
| blind | 3 (1,1,1) | newsletter | 10.3 (10,10,11) | 10.0 | — | — |
| listed | 3 (1,1,1) | promo | 13.7 (14,13,14) | 3.0 | 0 | +8.2% |
| listed-camel | 3 (1,1,1) | promo | **14.0 (14,14,14)** | 2.3 | 0 | +6.6% |
| mapped | 6 (2,2,2) | compare, newsletter | 11.0 (11,11,11) | 7.0 | 40 | +2.7% |
| **in-goal** | **11 (4,4,3)** | **4 つ全部** | 13.3 (14,14,12) | 2.0 | 0 | +4.5% |

360 コール / 477,134 入力トークン / **$0.020**。

`mapped` の 6/12 は blind の 3/12 より上だが、幅(11.0)と無駄手(7.0)を
犠牲にしている。注釈が「目の前のボタンを押す」方向に引っぱるが、
**行っていない画面のことは何も言わない**ので、ローカルに粘って幅を失う。

`in-goal` は 2 回まわして両方 11/12、seed ごとの内訳も (4,4,3) で同じだった。

## 5. なぜ場所で決まるのか

25 の注釈と 26 の注釈は、モデルに対する**主張の種類**が違う。

| | 25: `covered by <div#tip-backdrop>` | 26: `never executed: applyPromoCode()` |
| --- | --- | --- |
| 何の話か | **実行可能性** | **望ましさ** |
| ゴールとの関係 | 無関係。ゴールが何でも押せない | ゴールと**競合する**。買い物の役には立たない |
| コードで何ができるか | **選択肢を消せる**(25 の probe-prune) | 消せない。踏ませたいのだから |

だから「望ましさ」は候補の横に置いても負ける。ゴールが「注文を完了しろ」なら、
「この関数はまだ実行されていない」は**関係のない情報**として正しく無視される。
**ゴールを書き換えれば、それは無視すべき雑音ではなく仕事になる。**

`listed-camel` が効かないのも同じ理由で説明できる。state の
`code_not_yet_executed` は「事実」の置き場であって「指示」の置き場ではない。
それでも幅が出るのは、未カバー集合が**ルート名で埋まっている**ため——
「まだ行っていない画面」はゴール(探索)と競合しないので、事実のままでも動く。

## 6. わかったこと

1. **同じ事実でも、置き場所で効果が変わる。** 名前の集合を state の配列から
   ゴール文に移すだけで分岐 3/12 → 11/12(§4)。
2. **実行可能性はコード側で消す、望ましさはゴールに書く。** 25 の原則の適用条件が
   これで分かった(§5)。
3. **未カバー集合を state に入れるだけでも「幅」には効く。** 到達状態 10.3 → 14.0、
   無駄手 10.0 → 2.3。中身がルート名だから(§4, §5)。
4. **`takePreciseCoverage` は 1 発では全体像にならない。** 未カバーは消え、
   カウンタは毎 take リセットされる。インベントリ 1 回 + covered の union で持つ
   (§2.1, §2.2)。
5. **識別子とラベルの 1 語一致は join の証拠ではない。** 2 語以上を要求する
   (§3)。
6. **効果の信号が壊れると、実験は失敗せず"結果"を返す。** 解決しないセレクタが
   「効かないボタン」を捏造していた(§2.3)。

## 7. 次に試すこと

- 実行時 attribution でこの join を作る(名前に依存しない形)。chaosbringer の
  `targetNovelty` はもう持っているので、それをゴール文に流し込むだけでいい。
- ゴール文が長くなると何手目で効かなくなるか。いまは未カバーが 4 件で、
  これが 40 件になったときに「全部やれ」は指示として機能しない。
- `@mizchi/playwright-v8-coverage` の README の `take()` の説明(§2.2)。
  公開パッケージなので、同じ道を通る人がいる。
